# مراجعة سريعة: قواعد البيانات من الأول للآخر

دليل مختصر، سؤال وجواب، من الأسهل للأصعب. كل سؤال بيبني على اللي قبله.

---

## القسم الأول: الأساسيات (مراجعة سريعة)

**Q1 — الجدول (Table) ايه، والصف (Row) والعمود (Column)؟**
الجدول زي شيت إكسل: كل عمود ليه اسم ونوع بيانات ثابت (نص، رقم، تاريخ...)، وكل صف ده سجل واحد كامل (مثلاً عميل واحد بكل بياناته). قاعدة البيانات عادةً بتحتوي عشرات أو مئات الجداول، كل واحد بيمثل كيان مختلف (customers، orders، products).
```sql
CREATE TABLE customers (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100)
);
```

**Q2 — Primary Key ايه؟**
عمود (أو أكتر) بيحدد كل صف بشكل فريد، مفيش صفين ليهم نفس القيمة، ومينفعش يبقى فاضي (NULL). غالباً `id` تلقائي الترقيم (Auto Increment). بيستخدمه أي جدول تاني عايز "يشاور" على الصف ده.

**Q3 — Foreign Key ايه؟**
عمود في جدول بيشاور على Primary Key في جدول تاني، عشان يربط بينهم. مثلاً `orders.customer_id` بيشاور على `customers.id`. قاعدة البيانات بتمنعك تحط قيمة مش موجودة أصلاً (زي `customer_id = 999` وده العميل مش موجود)، وده بيحافظ على تكامل البيانات (Referential Integrity).
```sql
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    customer_id INTEGER REFERENCES customers(id),
    total NUMERIC
);
```

**Q4 — أنواع العلاقات بين الجداول؟**
- **One-to-Many**: عميل واحد ليه طلبات كتير — الأشهر والأكتر استخداماً.
- **Many-to-Many**: طالب ممكن ياخد كورسات كتير، وكورس فيه طلاب كتير — محتاج جدول وسيط (Junction Table) فيه عمودين، كل واحد Foreign Key لجدول.
- **One-to-One**: نادرة، كل صف في جدول ليه صف واحد بس مقابله في جدول تاني (زي user وuser_settings).

**Q5 — Normalization ليه؟**
تقسيم البيانات لجداول منفصلة عشان تتجنب تكرارها. لو اسم العميل مكرر في كل طلب ليه، وعدّلت اسمه، لازم تعدّله في كل مكان — الحل تخزنه مرة واحدة في جدول `customers` وتربطه بـ Foreign Key. الميزة: تحديث واحد بس، والحفاظ على الاتساق. العيب: محتاج JOIN عشان تجيب البيانات كاملة تاني.

## القسم الثاني: SQL الأساسي

**Q6 — أساسيات SELECT؟**
```sql
SELECT name, email
FROM customers
WHERE city = 'Cairo'
ORDER BY name
LIMIT 10;
```
`WHERE` بتفلتر الصفوف، `ORDER BY` بترتبها، `LIMIT` بتحدد عدد النتايج. ترتيب التنفيذ الفعلي في قاعدة البيانات: FROM، WHERE، ثم SELECT، ثم ORDER BY.

**Q7 — JOIN بيعمل ايه، والفرق بين أنواعه؟**
بيربط جدولين في استعلام واحد بناءً على شرط تطابق. `INNER JOIN` بيرجع بس الصفوف اللي عندها تطابق في الجدولين الاتنين. `LEFT JOIN` بيرجع كل صفوف الجدول الشمال، حتى لو مفيش تطابق في اليمين (يرجع NULL بدل الأعمدة الناقصة) — مفيد لو عايز مثلاً "كل العملاء حتى اللي معندهمش طلبات".
```sql
SELECT orders.id, customers.name
FROM orders
LEFT JOIN customers ON customers.id = orders.customer_id;
```

**Q8 — GROUP BY ودوال التجميع؟**
`GROUP BY` بتجمع الصفوف المتشابهة في مجموعة واحدة، وبتستخدمها مع دوال زي `COUNT`, `SUM`, `AVG`, `MAX` عشان تحسب رقم لكل مجموعة. لو عايز تفلتر على نتيجة التجميع نفسها (مش الصفوف الأصلية)، تستخدم `HAVING` مش `WHERE`.
```sql
SELECT customer_id, COUNT(*) AS order_count, SUM(total) AS total_spent
FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 5;
```

**Q9 — Subquery ولا JOIN؟**
Subquery استعلام جوه استعلام تاني. أحياناً بيبقى أسهل في القراءة (خصوصاً مع `IN` أو `EXISTS`)، بس JOIN غالباً أسرع في الأداء لأن محرك قاعدة البيانات بيقدر يحسّنه أكتر ويستخدم الفهارس بكفاءة أعلى. القاعدة العملية: جرب JOIN الأول، ولو الاستعلام بقى معقد جداً وصعب القراءة، فكر في Subquery أو CTE (`WITH ... AS`).

**Q10 — الفهرس (Index) بيعمل ايه بالظبط؟**
بدل ما قاعدة البيانات تدور على القيمة صف صف في كل الجدول (Full Table Scan)، الفهرس بيديها طريق مباشر للصفوف المطلوبة، زي فهرس الكتاب. بيسرّع القراءة بشكل كبير جداً على الجداول الكبيرة، لكن بيبطّئ شوية كل عملية كتابة (INSERT/UPDATE/DELETE) لأنه لازم يتحدّث هو كمان — فمش لازم تفهرس كل عمود عشوائياً (هنرجع للنقطة دي بتفصيل أكتر في القسم الرابع).
```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
```

## القسم الثالث: Transactions، ACID، وBASE (بالتفصيل)

**Q11 — Transaction ايه؟**
مجموعة عمليات (INSERT/UPDATE/DELETE) بتتنفذ كوحدة واحدة: إما كلها تنجح (Commit)، أو كلها ترجع لورا (Rollback) لو حصل خطأ في أي خطوة. مثال كلاسيكي: تحويل فلوس بين حسابين، لازم الخصم من الأول والإضافة للتاني يحصلوا مع بعض أو محدش منهم — لو السيرفر وقع بعد الخصم مباشرة وقبل الإضافة، الـ Transaction كلها بترجع لورا وكأن حاجة ما حصلتش.
```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- لو أي خطأ حصل قبل COMMIT، تعمل ROLLBACK وكل حاجة ترجع زي ما كانت
```

**Q12 — ACID يعني ايه، بمثال لكل حرف؟**
- **Atomicity (الذرية)**: كل العملية أو ولا حاجة. مثال: التحويل البنكي فوق، مفيش سيناريو "اتخصم من حساب واتضاف للتاني" فقط.
- **Consistency (الاتساق)**: البيانات تفضل ضمن القواعد المتفق عليها (Constraints زي Foreign Keys أو `CHECK (balance >= 0)`) قبل وبعد الـ Transaction. لو محاولة تخلي الرصيد سالب، قاعدة البيانات ترفض العملية كلها.
- **Isolation (العزل)**: Transactions شغالة في نفس الوقت مش المفروض تتأثر ببعض، وكأن كل واحدة شغالة لوحدها بالكامل. مثال: اتنين بيحولوا فلوس من نفس الحساب في نفس اللحظة، لازم النتيجة تبقى صحيحة كأنهم اتنفذوا واحد ورا التاني.
- **Durability (الديمومة)**: بعد الـ Commit، البيانات محفوظة فعلاً على الديسك حتى لو السيرفر وقع بعدها بثانية واحدة — مش هتلاقيها اختفت.

**Q13 — مستويات العزل (Isolation Levels) وإيه المشاكل اللي بتحلها؟**
لما Transactions كتير شغالة في نفس الوقت، ممكن تحصل مشاكل (Anomalies) لو مفيش عزل كافي:
- **Dirty Read**: تقرا بيانات من Transaction تانية لسه ماعملتش Commit، ولو عملت Rollback بعدها تبقى قريت بيانات ملهاش وجود.
- **Non-Repeatable Read**: تقرا نفس الصف مرتين جوه نفس الـ Transaction، وتلاقي القيمة اتغيرت في النص لأن Transaction تانية عدّلته وعملت Commit بينهم.
- **Phantom Read**: تنفذ نفس الاستعلام مرتين (زي `WHERE amount > 100`)، والمرة التانية بيظهر صف جديد كان مش موجود قبل كده، لأن Transaction تانية أضافت صف جديد يطابق الشرط بينهم.

قواعد البيانات بتحل المشاكل دي بمستويات عزل متدرجة:
| المستوى | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| Read Uncommitted | ممكن تحصل | ممكن تحصل | ممكن تحصل |
| Read Committed (الافتراضي غالباً) | ممنوعة | ممكن تحصل | ممكن تحصل |
| Repeatable Read | ممنوعة | ممنوعة | ممكن تحصل (في بعض القواعد ممنوعة كمان) |
| Serializable | ممنوعة | ممنوعة | ممنوعة |

كل ما رفعت مستوى العزل، زودت الأمان لكن قلّلت الأداء (لأن قاعدة البيانات محتاجة تحجز أقفال أكتر أو تعمل فحوصات أكتر).
```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT * FROM accounts WHERE id = 1;
-- أعلى مستوى أمان، لكن أبطأ وممكن يرفض Transactions تتصادم مع بعض
COMMIT;
```

**Q14 — Deadlock ايه، وإزاي بيحصل عملياً؟**
لما Transaction A مستنية قفل (Lock) ممسكه Transaction B، وB في نفس الوقت مستنية قفل ممسكه A — الاتنين واقفين لبعض للأبد. مثال شائع: A بتعدّل الصف 1 وبعدين عايزة تعدّل الصف 2، وB بتعدّل الصف 2 وبعدين عايزة تعدّل الصف 1، في نفس التوقيت تقريباً. قاعدة البيانات بتكتشف الموقف ده تلقائياً، وبتلغي (Rollback) واحدة منهم عشوائياً أو حسب أولوية معينة، عشان الحركة تكمل والتانية تقدر تنجح — التطبيق لازم يكون مستعد يعيد محاولة الـ Transaction اللي اتلغت.

**Q15 — Optimistic vs Pessimistic Locking؟**
**Pessimistic**: تحجز قفل من الأول قبل ما تعدّل، مناسب لو الاصطدام بين المستخدمين متوقع كتير (زي حجز آخر تذكرة في حفلة).
```sql
BEGIN;
SELECT * FROM tickets WHERE id = 1 FOR UPDATE; -- بيحجز قفل على الصف
UPDATE tickets SET status = 'sold' WHERE id = 1;
COMMIT;
```
**Optimistic**: تفترض إن الاصطدام نادر، تعدّل من غير قفل، وتتحقق وقت الـ Save إن حد تاني معدلش نفس الصف في نفس اللحظة عن طريق عمود `version`.
```sql
UPDATE tickets SET status = 'sold', version = version + 1
WHERE id = 1 AND version = 3; -- لو حد تاني عدّل قبلك، الشرط ده هيفشل ومحدش صفوف هتتحدث
```
الأول أأمن بس بيقلل التوازي (Concurrency)، التاني أسرع في الحالة العادية بس محتاج التطبيق يتعامل مع فشل التحقق ويعيد المحاولة.

**Q16 — إيه هو BASE، وليه أنظمة NoSQL كتير بتتبناه بدل ACID؟**
BASE اختصار لـ **Basically Available, Soft state, Eventually consistent** — فلسفة تصميم بديلة لـ ACID، ظهرت مع أنظمة NoSQL الموزعة عشان تحل مشكلة عملية: الالتزام بضمانات ACID الكاملة (خصوصاً Isolation وConsistency الفورية) عبر مئات السيرفرات الموزعة جغرافياً بيكلف أداء وتوافر كبير جداً.
- **Basically Available**: النظام بيرد على كل طلب دايماً (حتى لو جزء منه واقع أو فيه مشكلة شبكة)، بدل ما يرفض الطلب لحد ما يتأكد من الاتساق الكامل.
- **Soft State**: حالة البيانات ممكن تتغير مع الوقت حتى من غير Input جديد من المستخدم، لأن النظام بيكون لسه بيوصل لحالة اتساق نهائية بين النسخ المختلفة.
- **Eventually Consistent**: لو مفيش تحديثات جديدة، كل النسخ هتوصل في النهاية لنفس القيمة — لكن مش فوراً، ممكن تاخد أجزاء من الثانية أو أكتر حسب الظروف.
مثال عملي: لما تعمل لايك على بوست في منصة تواصل اجتماعي، العداد ممكن يفضل يوريك رقم قديم شوية لثواني معدودة لبعض المستخدمين في مناطق جغرافية مختلفة، قبل ما كل السيرفرات تتزامن على الرقم الصح — وده مقبول تماماً في السياق ده.

**Q17 — مقارنة مباشرة: ACID ولا BASE، إمتى تختار كل واحد؟**
| المعيار | ACID | BASE |
|---|---|---|
| الأولوية | الاتساق الفوري (Consistency) | التوافر المستمر (Availability) |
| شكل الضمان | قراءة تديك دايماً أحدث نسخة مؤكدة | قراءة ممكن تديك نسخة قديمة شوية مؤقتاً |
| الأداء تحت التوسع الضخم | بيتأثر بالضغط لو النظام موزع جغرافياً بشكل كبير | مصمم يتحمل توسع ضخم من غير ما يبطأ |
| أمثلة | PostgreSQL، MySQL، أي نظام بنكي | Cassandra، DynamoDB، أنظمة العدادات الاجتماعية |
| الاستخدام المثالي | فلوس، مخزون، أي بيانات غلط فيها مكلف جداً | فيدّات، عدادات، بيانات تحليلية بتتحمل تأخير بسيط |

القاعدة العملية: لو غلط في البيانات ممكن يسبب خسارة مالية أو قانونية مباشرة (رصيد بنكي، فاتورة)، ACID أنسب بكتير. لو البيانات بطبيعتها بتتحمل تأخير بسيط في الاتساق مقابل توافر أعلى وسرعة توسع (فيدّ أخبار، عداد مشاهدات)، BASE مقبول واستراتيجي.

## القسم الرابع: الأداء والفهرسة (بالتفصيل)

**Q18 — B-Tree Index بيشتغل إزاي؟**
النوع الافتراضي للفهرسة في أغلب قواعد البيانات، شجرة متوازنة (Balanced Tree) بترتب القيم بحيث البحث ياخد خطوات قليلة جداً (لوغاريتمية، O(log n)) بدل ما يعدي على كل صف في الجدول. بيدعم البحث بالمساواة (`=`) وبالمدى (`BETWEEN`, `>`, `<`) بكفاءة عالية، لأن القيم مرتبطة ببعض بترتيب متسلسل جوه الشجرة.

**Q19 — Composite Index وLeftmost Prefix؟**
فهرس على أكتر من عمود مع بعض، بيتبني بترتيب هرمي زي دليل تليفونات مرتب بالاسم الأول وجواه بالاسم التاني. لو الفهرس على `(customer_id, status)`، بيفيدك في استعلام على `customer_id` لوحده أو الاتنين مع بعض، لكن **مش** على `status` لوحده — ترتيب الأعمدة وقت إنشاء الفهرس مهم جداً وبيتحدد حسب أنماط الاستعلام الأكتر شيوعاً.
```sql
CREATE INDEX idx_orders_cust_status ON orders (customer_id, status);
```

**Q20 — Covering Index؟**
فهرس بيحتوي كل الأعمدة اللي الاستعلام محتاجها (سواء في WHERE أو في SELECT نفسه)، فقاعدة البيانات مش محتاجة ترجع للجدول الأصلي على الديسك خالص، دي بتسمى Index-Only Scan — أسرع بكتير من الفهرس العادي اللي بيحتاج "رحلتين" (واحدة للفهرس وواحدة للجدول).
```sql
CREATE INDEX idx_covering ON orders (customer_id, status, total_amount);
-- الاستعلام اللي بيجيب customer_id, status, total_amount بس هيتغطى بالكامل من الفهرس
```

**Q21 — فيه أنواع فهارس تانية غير B-Tree؟**
- **Hash Index**: مناسب بس للمساواة (`=`)، أسرع شوية من B-Tree في الحالة دي بس مبيدعمش المدى (`>`, `BETWEEN`) خالص.
- **GIN (Generalized Inverted Index)**: مناسب للبحث جوه بيانات معقدة زي مصفوفات، JSON، أو Full-Text Search — بيفهرس كل عنصر جوه القيمة مش القيمة كوحدة واحدة.
- **GiST**: مناسب للبيانات الجغرافية (Geospatial) والبحث بالتقارب المكاني.
القاعدة العملية: B-Tree هو الافتراضي المناسب لـ 90% من الحالات، والأنواع التانية بتستخدم لما يكون عندك احتياج محدد (بحث نصي، بيانات جغرافية، JSON معقد).

**Q22 — Partial Index وUnique Index؟**
**Partial Index**: فهرس بيغطي جزء بس من الجدول بناءً على شرط، مفيد لو أغلب استعلاماتك بتفلتر على قيمة معينة بس (زي الطلبات النشطة فقط)، وده بيخلي الفهرس أصغر حجماً وأسرع.
```sql
CREATE INDEX idx_active_orders ON orders (customer_id) WHERE status = 'active';
```
**Unique Index**: بيضمن إن مفيش قيمتين متكررتين في العمود (زي الإيميل)، وبيعمل فهرسة في نفس الوقت — أغلب قواعد البيانات بتنشئه تلقائياً على أي عمود عليه Constraint اسمه `UNIQUE`.

**Q23 — إمتى ميستحقش تعمل فهرس على عمود؟**
لو العمود قليل التنوع جداً (Low Cardinality) زي عمود `is_active` بس قيمتين (true/false)، الفهرس مش هيفيد كتير لأن قاعدة البيانات هتضطر تقرا نسبة كبيرة من الجدول برضو. لو الجدول نفسه صغير (كام مية صف)، Full Table Scan أصلاً سريع ومفيش داعي لتكلفة فهرس إضافي. وكل فهرس بيبطّئ كل INSERT/UPDATE/DELETE على الجدول لأنه لازم يتحدّث، فالقاعدة: افهرس بس الأعمدة اللي فعلاً بتستخدم في WHERE أو JOIN أو ORDER BY بشكل متكرر وعلى جداول كبيرة.

**Q24 — إزاي أعرف إن استعلام بطيء ليه؟**
`EXPLAIN` بيوريك خطة التنفيذ المتوقعة من غير تنفيذ فعلي، و`EXPLAIN ANALYZE` بينفذ الاستعلام فعلياً ويوريك الوقت الحقيقي لكل خطوة. أهم حاجة تدور عليها في النتيجة: كلمة `Seq Scan` على جدول كبير (يعني مفيش فهرس بيتستخدم)، وقارن بين "rows estimated" و"rows actual" — فرق كبير بينهم معناه إحصائيات الجدول قديمة ومحتاجة تحديث.
```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 4821;
-- Index Scan using idx_orders_customer_id (actual time=0.02..0.03 rows=11)  -- كويس
-- Seq Scan on orders (actual time=1450..3820 rows=11)                       -- مشكلة
```

**Q25 — مشكلة N+1 وحلها؟**
استعلام واحد بيرجع N نتيجة، وبعدين استعلام منفصل لكل نتيجة من الـ N دول (شائعة جداً مع ORMs، لما تكتب `order.customer.name` جوه Loop من غير ما تلاحظ إنه بيطلق استعلام SQL منفصل كل مرة). الحلول الرئيسية:
- **JOIN واحد** في SQL بدل اللف.
- **Eager Loading** جوه الـ ORM (`select_related` في Django، `.includes` في Rails)، بيحول العملية لاستعلام أو اتنين بس مهما كان عدد الصفوف.
- **Batching / DataLoader Pattern**: بدل ما تجيب كل عميل لوحده، تجمع كل الـ IDs المطلوبة الأول، وتعمل استعلام واحد بـ `WHERE id IN (...)` يجيبهم كلهم مرة واحدة.
```python
# WRONG
for order in orders:
    print(order.customer.name)  # N استعلام إضافي

# CORRECT
orders = Order.objects.select_related('customer').all()  # استعلام واحد بس
```

## القسم الخامس: التوسع (Scaling)

**Q26 — Vertical Scaling ليه محدود؟**
تكبير قوة نفس السيرفر (رامات أكبر، معالج أسرع، ديسك أسرع). سهل التنفيذ ومش محتاج تغيير في الكود، بس ليه سقف فيزيائي (مفيش سيرفر بقوة لا نهائية) وسقف مالي (التكلفة بتزيد بشكل أسي مش خطي)، وكمان بيفضل السيرفر ده نقطة فشل واحدة — لو وقع، كل حاجة تقف.

**Q27 — Read Replica ايه؟**
نسخ كاملة من قاعدة البيانات الأساسية (Primary)، بتتحدث تلقائياً كل ما يحصل تغيير على الـ Primary. الكتابة كلها بتروح للـ Primary بس، والقراءة بتتوزع على الـ Replicas عشان تخفف الحمل عنه. مناسب جداً لما القراءة أكتر بكتير من الكتابة (الحالة الشائعة في أغلب التطبيقات)، وبيدّي كمان مرونة أعلى لو Replica وقعت.

**Q28 — Replication Lag ايه، وليه بيسبب مشاكل؟**
الفرق الزمني بين لحظة الكتابة على الـ Primary ولحظة وصول نفس التغيير للـ Replica. لو قريت من Replica على طول بعد كتابة (في نفس الطلب)، ممكن تلاقي بيانات قديمة لجزء من الثانية، لأن النظام بيتحول من Strong Consistency لـ Eventual Consistency (نفس فكرة BASE اللي اتكلمنا عنها فوق). الحل للحالات الحرجة: اقرا من الـ Primary مباشرة بعد الكتابة، مش من Replica.

**Q29 — Horizontal Scaling وSharding؟**
لما الكتابة نفسها تكبر أكتر من طاقة أي سيرفر واحد (مهما كبّرته رأسياً)، بتقسم البيانات نفسها (مش تكررها زي الـ Replicas) على عدة سيرفرات (Shards)، كل واحد يحمل جزء بس. كل صف بيروح لـ Shard معين بناءً على Shard Key (عمود زي customer_id)، إما بمدى قيم (Range-Based) أو بدالة Hash (Hash-Based) عشان توزيع أكتر توازناً. اختيار الـ Shard Key الغلط صعب التراجع عنه لاحقاً لأنه بيعني إعادة توزيع كل البيانات.

**Q30 — مشكلة الاستعلامات عبر أكتر من Shard؟**
JOIN عادي مش متاح مباشرة عبر Shards مختلفة، لأن كل Shard فعلياً سيرفر منفصل تماماً مالوش رؤية على بيانات Shard تاني. الحلول: Scatter-Gather (تبعت نفس الاستعلام لكل الـ Shards وتجمع النتايج في الذاكرة)، أو الأهم: اختيار Shard Key بحيث البيانات المرتبطة (عميل وطلباته مثلاً) تعيش على نفس الـ Shard دايماً، عشان تتجنب الحاجة لاستعلام عبر أكتر من سيرفر من الأساس.

## القسم السادس: NoSQL وMongoDB

**Q31 — ليه NoSQL ظهرت؟**
حل لمشكلتين أساسيتين: شكل البيانات بيتغير باستمرار وسريع (Schema صارم بقى معطل، لأن `ALTER TABLE` على جدول فيه مليارات الصفوف بطيء ومكلف)، والحاجة لتوسع أفقي ضخم مبني من الأول مش كحل أخير. مش بديل مطلق لـ SQL، ده اختيار هندسي بيضحي بحاجات (زي Schema الصارم أو ضمانات ACID الكاملة، ويتبنى بدالها فلسفة BASE) عشان يكسب مرونة وتوسع.

**Q32 — أنواع NoSQL الأساسية، وإمتى تختار كل واحد؟**
- **Document Stores** (MongoDB): بيانات متداخلة مرنة الشكل، مناسبة لبروفايلات ومحتوى متغير.
- **Key-Value** (Redis): مفتاح وقيمة بس، سرعة قصوى، مناسب لـ Caching والجلسات.
- **Column-Family** (Cassandra): كتابة ضخمة جداً، مناسب لسجلات الأحداث والبيانات المتراكمة بسرعة.
- **Graph** (Neo4j): علاقات معقدة ومتشابكة، مناسب لشبكات التواصل وأنظمة التوصيات.

**Q33 — Document وCollection في MongoDB؟**
Document زي صف بس بصيغة JSON مرنة (BSON)، والـ Collection زي جدول بس من غير ما تفرض إن كل Document فيها يبقى بنفس الشكل بالظبط — Document واحد ممكن يكون فيه حقول مختلفة تماماً عن Document تاني في نفس الـ Collection.
```javascript
db.products.insertOne({ name: "Laptop", specs: { ram: "16GB", storage: "512GB" } });
db.products.insertOne({ name: "Mouse", colors: ["black", "white"] }); // شكل مختلف تماماً، ومقبول
```

**Q34 — Embedding ولا Referencing؟**
**Embed** البيانات جوه نفس الـ Document لو صغيرة الحجم وبتتقرا مع بعض دايماً (زي عنوان الشحن جوه الطلب). اعمل **Reference** (معرف بيشاور لـ Document منفصل في Collection تانية) لو البيانات بتنمو بلا حدود (زي تعليقات على بوست ممكن توصل آلاف) أو بتتغير بمعدل مختلف تماماً عن الطرف التاني. القاعدة العملية: "البيانات اللي بتتقرا مع بعض، خزنها مع بعض".

**Q35 — نظرية CAP؟**
أي نظام قاعدة بيانات موزع، وقت انقسام الشبكة (Network Partition) بين السيرفرات، لازم يختار بين **Consistency** (كل قراءة تديك أحدث نسخة مضمونة، فلسفة ACID) و**Availability** (كل طلب يرد حتى لو ببيانات مش أحدث، فلسفة BASE). Partition Tolerance ضرورة حتمية في أي نظام موزع حقيقي، فالاختيار الحقيقي دايماً بين CP وAP حسب طبيعة النظام — نظام بنكي غالباً CP، عداد لايكات غالباً AP.

## القسم السابع: القرار — SQL ولا NoSQL؟ (الأصعب، ميكس)

**Q36 — الأسئلة اللي بتوجه القرار؟**
1. شكل البيانات مستقر ولا بيتغير باستمرار؟ (مستقر → SQL)
2. العلاقات معقدة ومتشابكة ولا بسيطة ومحدودة؟ (معقدة → SQL)
3. محتاج ضمانات ACID قوية عبر كيانات متعددة، ولا BASE مقبولة؟ (ACID لازم → SQL)
4. الحجم أو الحمل المتوقع فعلاً محتاج توسع أفقي ضخم من اليوم الأول؟ (أيوه → NoSQL)
القرار بيتاخد لكل جزء أو موديول في النظام لوحده، مش قرار واحد شامل لكل المشروع.

**Q37 — Polyglot Persistence؟**
الأنظمة الكبيرة الحقيقية بتستخدم أكتر من نوع قاعدة بيانات مع بعض، كل واحدة في المكان اللي بتتفوق فيه: PostgreSQL للمعاملات والدفع (ACID)، Elasticsearch للبحث النصي، Redis للكاش والجلسات (BASE مقبولة في الاتنين دول). التحدي مش اختيار الأدوات، التحدي هو **مزامنة البيانات** بينهم صح، وإلا هتلاقي بيانات متضاربة بين الأنظمة.

**Q38 — علامات إن الاختيار كان غلط، وإزاي تصلحه؟**
علامة على SQL غلط: Migrations متكررة كتير وأعمدة فاضية (NULL) كتير في الجدول. علامة على NoSQL غلط: كود تكامل بيانات معقد بتكتبه يدوي في التطبيق، واحتياج متكرر لضمانات ACID عبر مستندات متعددة كانت مفروض تبقى Transaction واحدة. الحل مش هجرة كاملة دفعة واحدة (خطر جداً)، لكن هجرة جزئية تدريجية للجزء المتضرر بس، مع فترة تشغيل متوازي (Dual Write) للتأكد من صحة البيانات قبل ما تكمل الانتقال بالكامل.

---

**الخلاصة في سطرين**: ابدأ بـ SQL وضمانات ACID كخيار افتراضي آمن، وفهرس صح قبل ما تكبّر السيرفر، وجرّب Read Replicas قبل Sharding. انتقل لـ NoSQL وفلسفة BASE أو استخدم أكتر من أداة مع بعض (Polyglot Persistence) بس لما يكون فيه سبب واضح ومحدد من الأسئلة الأربعة في Q36، مش بناءً على الموضة.
