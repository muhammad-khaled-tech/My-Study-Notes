# مراجعة شاملة: قواعد البيانات من الأول للآخر

دليل مراجعة متوسط الطول، سؤال وجواب، من الأسهل للأصعب. كل سؤال بيبني على اللي قبله، وفيه شرح كافي تفهم منه "ليه" مش بس "إيه".

---

## القسم الأول: الأساسيات

**Q1 — الجدول (Table)، الصف (Row)، والعمود (Column) إيه بالظبط؟**
الجدول زي شيت إكسل منظم: كل عمود ليه اسم ونوع بيانات ثابت (نص، رقم، تاريخ، Boolean...)، وكل صف ده سجل واحد كامل (مثلاً عميل واحد بكل بياناته). قاعدة البيانات عادةً بتحتوي عشرات أو مئات الجداول، كل واحد بيمثل كيان مختلف (customers، orders، products)، ومترابطين مع بعض بعلاقات هنشرحها بعد شوية.
```sql
CREATE TABLE customers (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE,
    created_at TIMESTAMP DEFAULT NOW()
);
```

**Q2 — إيه أهم الـ Constraints (القيود) اللي بتحط على الأعمدة؟**
القيود دي بتمنع بيانات غلط من الأصل تدخل الجدول:
- `NOT NULL`: العمود ده لازم تتحط له قيمة، مينفعش يفضل فاضي.
- `UNIQUE`: القيمة لازم تكون فريدة، مفيش تكرار (زي الإيميل).
- `DEFAULT`: لو ماتحطش قيمة، يتحط قيمة افتراضية معينة تلقائياً.
- `CHECK`: شرط منطقي لازم يتحقق (زي `CHECK (age >= 18)`).
الفايدة الكبيرة: قاعدة البيانات نفسها بترفض البيانات الغلط، مش هتعتمد بس على كود التطبيق إنه يتأكد من كل حاجة.

**Q3 — Primary Key إيه، وليه لازم كل جدول يكون ليه واحد؟**
عمود (أو أكتر) بيحدد كل صف بشكل فريد، مفيش صفين ليهم نفس القيمة، ومينفعش يبقى فاضي. غالباً `id` تلقائي الترقيم (Auto Increment/Serial). أهميته إنه بيدّي كل صف "هوية" ثابتة تقدر تشاور بيها عليه من أي جدول تاني، وبيستخدمه Foreign Key وبيستخدمه الفهرس الأساسي للجدول (Clustered Index في أغلب القواعد).

**Q4 — Foreign Key إيه، وإزاي بتحافظ على تكامل البيانات؟**
عمود في جدول بيشاور على Primary Key في جدول تاني، عشان يربط بينهم. مثلاً `orders.customer_id` بيشاور على `customers.id`. قاعدة البيانات بتمنعك تحط قيمة مش موجودة أصلاً (زي `customer_id = 999` وده العميل مش موجود)، ودي اللي بتسمى Referential Integrity. كمان تقدر تحدد إيه اللي يحصل لو العميل الأصلي اتمسح، عن طريق `ON DELETE`.
```sql
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    customer_id INTEGER REFERENCES customers(id) ON DELETE CASCADE,
    total NUMERIC(10,2)
);
-- ON DELETE CASCADE: لو العميل اتمسح، كل طلباته تتمسح تلقائياً معاه
-- ON DELETE SET NULL: العمود customer_id يبقى NULL بدل ما يمنع الحذف
-- ON DELETE RESTRICT (الافتراضي غالباً): يمنع مسح العميل طالما ليه طلبات مرتبطة بيه
```

**Q5 — أنواع العلاقات بين الجداول؟**
- **One-to-Many**: عميل واحد ليه طلبات كتير — الأشهر والأكتر استخداماً في أي نظام.
- **Many-to-Many**: طالب ممكن ياخد كورسات كتير، وكورس فيه طلاب كتير — محتاج جدول وسيط (Junction Table أو Pivot Table) فيه عمودين، كل واحد Foreign Key لجدول من الاتنين.
- **One-to-One**: نادرة نسبياً، كل صف في جدول ليه صف واحد بس مقابله في جدول تاني (زي `users` وجدول منفصل `user_settings`)، بتستخدم غالباً لفصل بيانات كبيرة أو نادرة الاستخدام عن الجدول الأساسي.
```sql
-- جدول وسيط لعلاقة Many-to-Many
CREATE TABLE enrollments (
    student_id INTEGER REFERENCES students(id),
    course_id INTEGER REFERENCES courses(id),
    PRIMARY KEY (student_id, course_id)  -- Composite Primary Key
);
```

**Q6 — Composite Key إيه؟**
Primary Key مكون من أكتر من عمود مع بعض بدل عمود واحد، زي المثال فوق (`student_id` و`course_id` مع بعض). الفكرة إن التركيبة (Combination) بتاعتهم لازم تكون فريدة، حتى لو كل عمود لوحده متكرر (نفس الطالب مسجل في كذا كورس، ونفس الكورس فيه كذا طالب، لكن نفس الطالب في نفس الكورس مرة واحدة بس).

**Q7 — Normalization ليه، وإيه أشهر مستوياتها؟**
تقسيم البيانات لجداول منفصلة عشان تتجنب تكرارها. لو اسم العميل مكرر في كل طلب ليه، وعدّلت اسمه، لازم تعدّله في كل مكان — الحل تخزنه مرة واحدة في جدول `customers` وتربطه بـ Foreign Key. أشهر المستويات (Normal Forms): **1NF** (كل خانة فيها قيمة واحدة بس، مش قايمة قيم)، **2NF** (كل عمود غير أساسي معتمد على المفتاح الأساسي كامل، مش جزء منه)، **3NF** (مفيش عمود معتمد على عمود تاني غير المفتاح الأساسي). الميزة: تحديث واحد بس ومفيش تضارب بيانات. العيب: محتاج JOINs كتير عشان تجيب البيانات كاملة تاني، وده أحياناً بيأثر على الأداء.

**Q8 — Denormalization إيه، وإمتى تعمله عمداً؟**
عكس الـ Normalization: بتكرر بعض البيانات عمداً في أكتر من جدول، عشان تقلل عدد الـ JOINs المطلوبة وقت القراءة، على حساب مساحة تخزين إضافية وتعقيد في التحديث (لازم تحدّث كل النسخ المكررة مع بعض). بتعمله لما يكون عندك قراءة كتيرة جداً وكتابة قليلة نسبياً لنفس البيانات، ومستعد تضحي بشوية تكرار عشان سرعة قراءة أعلى.

## القسم الثاني: SQL بالتفصيل

**Q9 — أساسيات SELECT وترتيب التنفيذ الفعلي؟**
```sql
SELECT name, email
FROM customers
WHERE city = 'Cairo'
ORDER BY name
LIMIT 10;
```
`WHERE` بتفلتر الصفوف قبل التجميع، `ORDER BY` بترتبها، `LIMIT` بتحدد عدد النتايج المرجعة. مهم تعرف: قاعدة البيانات بتنفذ الاستعلام بترتيب مختلف عن اللي بتكتبه بيه — الترتيب الفعلي: `FROM` (تحديد الجدول) → `WHERE` (فلترة) → `GROUP BY` → `HAVING` → `SELECT` (اختيار الأعمدة) → `ORDER BY` → `LIMIT`. ده بيفسر ليه مينفعش تستخدم اسم مستعار (Alias) من الـ SELECT جوه الـ WHERE في بعض القواعد.

**Q10 — JOIN بيعمل إيه، وإيه الفرق بين أنواعه؟**
بيربط جدولين في استعلام واحد بناءً على شرط تطابق. `INNER JOIN` بيرجع بس الصفوف اللي عندها تطابق في الجدولين الاتنين. `LEFT JOIN` بيرجع كل صفوف الجدول الشمال، حتى لو مفيش تطابق في اليمين (يرجع NULL بدل الأعمدة الناقصة). `RIGHT JOIN` عكسه بالظبط. `FULL OUTER JOIN` بيرجع كل الصفوف من الجدولين، سواء فيه تطابق ولا لأ.
```sql
-- كل العملاء حتى اللي معندهمش طلبات (NULL في أعمدة orders)
SELECT customers.name, orders.id
FROM customers
LEFT JOIN orders ON customers.id = orders.customer_id;
```

**Q11 — GROUP BY ودوال التجميع بالتفصيل؟**
`GROUP BY` بتجمع الصفوف المتشابهة في مجموعة واحدة، وبتستخدمها مع دوال زي `COUNT`, `SUM`, `AVG`, `MAX`, `MIN` عشان تحسب رقم لكل مجموعة. لو عايز تفلتر على نتيجة التجميع نفسها (مش الصفوف الأصلية قبل التجميع)، تستخدم `HAVING` مش `WHERE` — لأن `WHERE` بتتنفذ قبل التجميع، و`HAVING` بتتنفذ بعده.
```sql
SELECT customer_id, COUNT(*) AS order_count, SUM(total) AS total_spent
FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 5
ORDER BY total_spent DESC;
```

**Q12 — Subquery ولا JOIN، وإيه الفرق بين IN وEXISTS؟**
Subquery استعلام جوه استعلام تاني. أحياناً بيبقى أسهل في القراءة (خصوصاً مع `IN` أو `EXISTS`)، بس JOIN غالباً أسرع في الأداء لأن محرك قاعدة البيانات بيقدر يحسّنه أكتر ويستخدم الفهارس بكفاءة أعلى. `EXISTS` عادةً أسرع من `IN` على جداول كبيرة، لأنه بيوقف البحث أول ما يلاقي تطابق واحد بس، بينما `IN` بيجمع كل النتايج الأول.
```sql
-- بيستخدم EXISTS، بيوقف أول ما يلاقي طلب واحد
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

**Q13 — UNION وDISTINCT بيعملوا إيه؟**
`UNION` بيدمج نتيجة استعلامين في نتيجة واحدة (لازم نفس عدد ونوع الأعمدة)، وبيشيل التكرارات تلقائياً (لو عايز تسيب التكرارات استخدم `UNION ALL` وهو أسرع). `DISTINCT` بيشيل الصفوف المكررة تماماً من نتيجة استعلام واحد.
```sql
SELECT city FROM customers
UNION
SELECT city FROM suppliers;   -- يدمج المدينتين ويشيل التكرار

SELECT DISTINCT city FROM customers;  -- مدن العملاء بدون تكرار
```

**Q14 — View إيه، وليه تستخدمه؟**
استعلام محفوظ بيتصرف وكأنه جدول، بس مش بيخزن بيانات فعلياً — كل مرة تستعلم منه، الاستعلام الأصلي بيتنفذ من جديد. مفيد لو عندك استعلام معقد بتستخدمه كتير (JOINs كتير مع بعض)، بدل ما تكرره في كل مكان، تعمله View مرة واحدة وتستعلم منه زي أي جدول عادي.
```sql
CREATE VIEW customer_orders_summary AS
SELECT customer_id, COUNT(*) AS order_count, SUM(total) AS total_spent
FROM orders
GROUP BY customer_id;

SELECT * FROM customer_orders_summary WHERE total_spent > 1000;
```

**Q15 — Stored Procedure وFunction إيه بشكل مختصر؟**
كود SQL (وأحياناً منطق برمجي أكتر تعقيداً) بيتخزن جوه قاعدة البيانات نفسها، وتقدر تناديه بدل ما تكتب نفس الاستعلامات كتير من التطبيق. الميزة: منطق مركزي في مكان واحد، وأداء أسرع أحياناً لأنه أقرب للبيانات. العيب: منطق العمل (Business Logic) بيتوزع بين التطبيق وقاعدة البيانات، وده بيصعّب الصيانة والاختبار لو استخدمته بكثرة زيادة.

**Q16 — إمتى أفهرس Foreign Key؟**
تقريباً دايماً. لو عندك `orders.customer_id` كـ Foreign Key، ومعندكش فهرس عليه، أي JOIN أو فلترة بيه هتعمل Full Table Scan. أغلب قواعد البيانات (زي PostgreSQL) **مبتفهرسش** الـ Foreign Key تلقائياً (بعكس الـ Primary Key اللي بيتفهرس تلقائياً)، فلازم تعمل ده يدوياً.
```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
```

## القسم الثالث: Transactions، ACID، وBASE

**Q17 — Transaction إيه؟**
مجموعة عمليات (INSERT/UPDATE/DELETE) بتتنفذ كوحدة واحدة: إما كلها تنجح (Commit)، أو كلها ترجع لورا (Rollback) لو حصل خطأ في أي خطوة. مثال كلاسيكي: تحويل فلوس بين حسابين، لازم الخصم من الأول والإضافة للتاني يحصلوا مع بعض أو محدش منهم — لو السيرفر وقع بعد الخصم مباشرة وقبل الإضافة، الـ Transaction كلها بترجع لورا وكأن حاجة ما حصلتش.
```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- لو أي خطأ حصل قبل COMMIT، تعمل ROLLBACK وكل حاجة ترجع زي ما كانت
```

**Q18 — ACID يعني إيه، بمثال لكل حرف؟**
- **Atomicity (الذرية)**: كل العملية أو ولا حاجة. مثال: التحويل البنكي فوق، مفيش سيناريو "اتخصم من حساب واتضاف للتاني" فقط.
- **Consistency (الاتساق)**: البيانات تفضل ضمن القواعد المتفق عليها (Constraints زي Foreign Keys أو `CHECK (balance >= 0)`) قبل وبعد الـ Transaction. لو محاولة تخلي الرصيد سالب، قاعدة البيانات ترفض العملية كلها.
- **Isolation (العزل)**: Transactions شغالة في نفس الوقت مش المفروض تتأثر ببعض، وكأن كل واحدة شغالة لوحدها بالكامل.
- **Durability (الديمومة)**: بعد الـ Commit، البيانات محفوظة فعلاً على الديسك حتى لو السيرفر وقع بعدها بثانية واحدة.

**Q19 — مستويات العزل (Isolation Levels) وإيه المشاكل اللي بتحلها؟**
لما Transactions كتير شغالة في نفس الوقت، ممكن تحصل مشاكل (Anomalies) لو مفيش عزل كافي:
- **Dirty Read**: تقرا بيانات من Transaction تانية لسه ماعملتش Commit، ولو عملت Rollback بعدها تبقى قريت بيانات ملهاش وجود.
- **Non-Repeatable Read**: تقرا نفس الصف مرتين جوه نفس الـ Transaction، وتلاقي القيمة اتغيرت في النص لأن Transaction تانية عدّلته وعملت Commit بينهم.
- **Phantom Read**: تنفذ نفس الاستعلام مرتين، والمرة التانية بيظهر صف جديد كان مش موجود قبل كده، لأن Transaction تانية أضافت صف جديد يطابق الشرط بينهم.

| المستوى | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| Read Uncommitted | ممكن تحصل | ممكن تحصل | ممكن تحصل |
| Read Committed (الافتراضي غالباً) | ممنوعة | ممكن تحصل | ممكن تحصل |
| Repeatable Read | ممنوعة | ممنوعة | ممكن تحصل (بعض القواعد بتمنعها كمان) |
| Serializable | ممنوعة | ممنوعة | ممنوعة |

كل ما رفعت مستوى العزل، زودت الأمان لكن قلّلت الأداء (لأن قاعدة البيانات محتاجة تحجز أقفال أكتر أو تعمل فحوصات أكتر).

**Q20 — Deadlock إيه، وإزاي بيحصل عملياً؟**
لما Transaction A مستنية قفل (Lock) ممسكه Transaction B، وB في نفس الوقت مستنية قفل ممسكه A — الاتنين واقفين لبعض للأبد. مثال شائع: A بتعدّل الصف 1 وبعدين عايزة تعدّل الصف 2، وB بتعدّل الصف 2 وبعدين عايزة تعدّل الصف 1، في نفس التوقيت تقريباً. قاعدة البيانات بتكتشف الموقف ده تلقائياً، وبتلغي (Rollback) واحدة منهم عشوائياً أو حسب أولوية معينة، عشان الحركة تكمل والتانية تقدر تنجح — التطبيق لازم يكون مستعد يعيد محاولة الـ Transaction اللي اتلغت.

**Q21 — Optimistic vs Pessimistic Locking؟**
**Pessimistic**: تحجز قفل من الأول قبل ما تعدّل، مناسب لو الاصطدام بين المستخدمين متوقع كتير (زي حجز آخر تذكرة في حفلة).
```sql
BEGIN;
SELECT * FROM tickets WHERE id = 1 FOR UPDATE; -- بيحجز قفل على الصف
UPDATE tickets SET status = 'sold' WHERE id = 1;
COMMIT;
```
**Optimistic**: تفترض إن الاصطدام نادر، تعدّل من غير قفل، وتتحقق وقت الـ Save إن حد تاني معدلش نفس الصف في نفس اللحظة عن طريق عمود `version`.
```sql
UPDATE tickets SET status = 'sold', version = version + 1
WHERE id = 1 AND version = 3; -- لو حد تاني عدّل قبلك، الشرط ده هيفشل
```

**Q22 — إيه هو BASE، وليه أنظمة NoSQL كتير بتتبناه بدل ACID؟**
BASE اختصار لـ **Basically Available, Soft state, Eventually consistent** — فلسفة تصميم بديلة لـ ACID، ظهرت مع أنظمة NoSQL الموزعة عشان تحل مشكلة عملية: الالتزام بضمانات ACID الكاملة عبر مئات السيرفرات الموزعة جغرافياً بيكلف أداء وتوافر كبير جداً.
- **Basically Available**: النظام بيرد على كل طلب دايماً (حتى لو جزء منه واقع)، بدل ما يرفض الطلب لحد ما يتأكد من الاتساق الكامل.
- **Soft State**: حالة البيانات ممكن تتغير مع الوقت حتى من غير Input جديد، لأن النظام لسه بيوصل لحالة اتساق نهائية بين النسخ.
- **Eventually Consistent**: لو مفيش تحديثات جديدة، كل النسخ هتوصل في النهاية لنفس القيمة — لكن مش فوراً.
مثال: عداد لايكات على بوست ممكن يوريك رقم قديم شوية لثواني لبعض المستخدمين، قبل ما كل السيرفرات تتزامن — ومقبول تماماً في السياق ده.

**Q23 — مقارنة مباشرة: ACID ولا BASE؟**
| المعيار | ACID | BASE |
|---|---|---|
| الأولوية | الاتساق الفوري | التوافر المستمر |
| شكل الضمان | قراءة تديك دايماً أحدث نسخة مؤكدة | قراءة ممكن تديك نسخة قديمة شوية مؤقتاً |
| الأداء تحت التوسع الضخم | بيتأثر بالضغط لو النظام موزع جغرافياً بشكل كبير | مصمم يتحمل توسع ضخم من غير ما يبطأ |
| أمثلة | PostgreSQL، MySQL، أي نظام بنكي | Cassandra، DynamoDB، أنظمة العدادات الاجتماعية |
| الاستخدام المثالي | فلوس، مخزون، أي بيانات غلط فيها مكلف جداً | فيدّات، عدادات، بيانات تحليلية بتتحمل تأخير بسيط |

القاعدة العملية: لو غلط في البيانات ممكن يسبب خسارة مالية أو قانونية مباشرة، ACID أنسب. لو البيانات بطبيعتها بتتحمل تأخير بسيط في الاتساق مقابل توافر أعلى وسرعة توسع، BASE مقبول واستراتيجي.

## القسم الرابع: الأداء والفهرسة

**Q24 — B-Tree Index بيشتغل إزاي؟**
النوع الافتراضي للفهرسة في أغلب قواعد البيانات، شجرة متوازنة (Balanced Tree) بترتب القيم بحيث البحث ياخد خطوات قليلة جداً (لوغاريتمية، O(log n)) بدل ما يعدي على كل صف في الجدول (Full Table Scan). بيدعم البحث بالمساواة (`=`) وبالمدى (`BETWEEN`, `>`, `<`) بكفاءة عالية.
```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
```

**Q25 — Composite Index وLeftmost Prefix؟**
فهرس على أكتر من عمود مع بعض، بيتبني بترتيب هرمي زي دليل تليفونات مرتب بالاسم الأول وجواه بالاسم التاني. لو الفهرس على `(customer_id, status)`، بيفيدك في استعلام على `customer_id` لوحده أو الاتنين مع بعض، لكن **مش** على `status` لوحده — ترتيب الأعمدة وقت إنشاء الفهرس مهم جداً وبيتحدد حسب أنماط الاستعلام الأكتر شيوعاً.
```sql
CREATE INDEX idx_orders_cust_status ON orders (customer_id, status);
```

**Q26 — Covering Index؟**
فهرس بيحتوي كل الأعمدة اللي الاستعلام محتاجها (سواء في WHERE أو في SELECT نفسه)، فقاعدة البيانات مش محتاجة ترجع للجدول الأصلي على الديسك خالص، دي بتسمى Index-Only Scan — أسرع بكتير من الفهرس العادي اللي بيحتاج "رحلتين".
```sql
CREATE INDEX idx_covering ON orders (customer_id, status, total_amount);
```

**Q27 — فيه أنواع فهارس تانية غير B-Tree؟**
- **Hash Index**: مناسب بس للمساواة (`=`)، مبيدعمش المدى خالص.
- **GIN**: مناسب للبحث جوه بيانات معقدة زي مصفوفات، JSON، أو Full-Text Search.
- **GiST**: مناسب للبيانات الجغرافية (Geospatial) والبحث بالتقارب المكاني.
B-Tree هو الافتراضي المناسب لـ 90% من الحالات.

**Q28 — Partial Index وUnique Index؟**
**Partial Index**: فهرس بيغطي جزء بس من الجدول بناءً على شرط، مفيد لو أغلب استعلاماتك بتفلتر على قيمة معينة بس، وده بيخلي الفهرس أصغر حجماً وأسرع.
```sql
CREATE INDEX idx_active_orders ON orders (customer_id) WHERE status = 'active';
```
**Unique Index**: بيضمن إن مفيش قيمتين متكررتين في العمود، وبيعمل فهرسة في نفس الوقت.

**Q29 — إمتى ميستحقش تعمل فهرس على عمود؟**
لو العمود قليل التنوع جداً (Low Cardinality) زي `is_active` بس قيمتين، الفهرس مش هيفيد كتير. لو الجدول نفسه صغير، Full Table Scan أصلاً سريع. وكل فهرس بيبطّئ كل INSERT/UPDATE/DELETE لأنه لازم يتحدّث، فالقاعدة: افهرس بس الأعمدة اللي فعلاً بتستخدم في WHERE أو JOIN أو ORDER BY بشكل متكرر على جداول كبيرة.

**Q30 — إزاي أعرف إن استعلام بطيء ليه؟**
`EXPLAIN` بيوريك خطة التنفيذ المتوقعة، و`EXPLAIN ANALYZE` بينفذ الاستعلام فعلياً ويوريك الوقت الحقيقي. أهم حاجة تدور عليها: كلمة `Seq Scan` على جدول كبير، وقارن بين "rows estimated" و"rows actual" — فرق كبير بينهم معناه إحصائيات الجدول قديمة.
```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 4821;
```

**Q31 — مشكلة N+1 وحلها؟**
استعلام واحد بيرجع N نتيجة، وبعدين استعلام منفصل لكل نتيجة (شائعة جداً مع ORMs). الحلول: **JOIN واحد**، أو **Eager Loading** جوه الـ ORM (`select_related`)، أو **Batching**: تجمع كل الـ IDs الأول، وتعمل استعلام واحد بـ `WHERE id IN (...)`.
```python
orders = Order.objects.select_related('customer').all()  # استعلام واحد بس
```

## القسم الخامس: التوسع (Scaling)

**Q32 — Connection Pooling إيه، وليه أول حاجة تفكر فيها قبل أي توسع تاني؟**
فتح اتصال جديد بقاعدة البيانات لكل طلب مكلف (وقت واستهلاك موارد)، خصوصاً لو التطبيق بيستقبل آلاف الطلبات في الثانية. Connection Pool بيحتفظ بمجموعة اتصالات مفتوحة ومُعاد استخدامها، بدل ما يفتح ويقفل اتصال جديد كل مرة. أدوات زي PgBouncer بتعمل ده كطبقة منفصلة، وده غالباً أرخص وأسهل حل قبل ما تفكر في أي توسع أكبر.

**Q33 — Vertical Scaling ليه محدود؟**
تكبير قوة نفس السيرفر (رامات أكبر، معالج أسرع). سهل التنفيذ ومش محتاج تغيير في الكود، بس ليه سقف فيزيائي ومالي (التكلفة بتزيد بشكل أسي)، وبيفضل السيرفر ده نقطة فشل واحدة — لو وقع، كل حاجة تقف.

**Q34 — Read Replica إيه؟**
نسخ كاملة من قاعدة البيانات الأساسية (Primary)، بتتحدث تلقائياً كل ما يحصل تغيير على الـ Primary. الكتابة كلها بتروح للـ Primary بس، والقراءة بتتوزع على الـ Replicas عشان تخفف الحمل عنه. مناسب جداً لما القراءة أكتر بكتير من الكتابة.

**Q35 — Replication Lag إيه، وليه بيسبب مشاكل؟**
الفرق الزمني بين لحظة الكتابة على الـ Primary ولحظة وصول نفس التغيير للـ Replica. لو قريت من Replica على طول بعد كتابة، ممكن تلاقي بيانات قديمة لجزء من الثانية (نفس فكرة BASE اللي اتكلمنا عنها). الحل للحالات الحرجة: اقرا من الـ Primary مباشرة بعد الكتابة، مش من Replica.

**Q36 — Caching Layer (زي Redis) كأداة توسع؟**
قبل ما تفكر في تعقيد Sharding، طبقة كاش (زي Redis) قدام قاعدة البيانات بتقدر تمتص جزء كبير من الحمل — بتخزن نتايج استعلامات متكررة في الذاكرة، فمعظم الطلبات مبتوصلش أصلاً لقاعدة البيانات. المشكلة الأساسية: لازم استراتيجية واضحة لإبطال الكاش (Cache Invalidation) لما البيانات الأصلية تتغير، وإلا هتقدّم بيانات قديمة للمستخدمين.

**Q37 — Horizontal Scaling وSharding؟**
لما الكتابة نفسها تكبر أكتر من طاقة أي سيرفر واحد، بتقسم البيانات نفسها (مش تكررها) على عدة سيرفرات (Shards). كل صف بيروح لـ Shard معين بناءً على Shard Key، إما بمدى قيم (Range-Based) أو بدالة Hash (Hash-Based). اختيار الـ Shard Key الغلط صعب التراجع عنه لاحقاً لأنه بيعني إعادة توزيع كل البيانات.

**Q38 — مشكلة الاستعلامات عبر أكتر من Shard؟**
JOIN عادي مش متاح مباشرة عبر Shards مختلفة، لأن كل Shard سيرفر منفصل تماماً. الحلول: Scatter-Gather (تبعت نفس الاستعلام لكل الـ Shards وتجمع النتايج)، أو الأهم: اختيار Shard Key بحيث البيانات المرتبطة تعيش على نفس الـ Shard دايماً.

## القسم السادس: NoSQL وMongoDB

**Q39 — ليه NoSQL ظهرت؟**
حل لمشكلتين أساسيتين: شكل البيانات بيتغير باستمرار (Schema صارم بقى معطل، لأن `ALTER TABLE` على جدول فيه مليارات الصفوف بطيء ومكلف)، والحاجة لتوسع أفقي ضخم مبني من الأول. مش بديل مطلق لـ SQL، ده اختيار هندسي بيضحي بحاجات (زي ضمانات ACID الكاملة، ويتبنى بدالها BASE) عشان يكسب مرونة وتوسع.

**Q40 — أنواع NoSQL الأساسية، وإمتى تختار كل واحد؟**
- **Document Stores** (MongoDB): بيانات متداخلة مرنة الشكل.
- **Key-Value** (Redis): مفتاح وقيمة بس، سرعة قصوى، مناسب لـ Caching.
- **Column-Family** (Cassandra): كتابة ضخمة جداً.
- **Graph** (Neo4j): علاقات معقدة ومتشابكة.

**Q41 — Document وCollection في MongoDB؟**
Document زي صف بس بصيغة JSON مرنة (BSON)، والـ Collection زي جدول بس من غير ما تفرض إن كل Document فيها يبقى بنفس الشكل بالظبط.
```javascript
db.products.insertOne({ name: "Laptop", specs: { ram: "16GB", storage: "512GB" } });
db.products.insertOne({ name: "Mouse", colors: ["black", "white"] }); // شكل مختلف تماماً، ومقبول
```

**Q42 — Embedding ولا Referencing؟**
**Embed** البيانات جوه نفس الـ Document لو صغيرة وبتتقرا مع بعض دايماً. اعمل **Reference** لو البيانات بتنمو بلا حدود أو بتتغير بمعدل مختلف تماماً. القاعدة العملية: "البيانات اللي بتتقرا مع بعض، خزنها مع بعض".

**Q43 — Aggregation Pipeline في MongoDB؟**
بدل الـ SQL بجملة `GROUP BY`/`JOIN`، MongoDB عندها سلسلة مراحل (Stages)، كل مرحلة بتاخد نتيجة اللي قبلها. أشهر المراحل: `$match` (زي WHERE)، `$group` (زي GROUP BY)، `$sort`، و`$lookup` (المكافئ التقريبي لـ JOIN، بس أبطأ من JOIN في نظام علائقي محسّن).
```javascript
db.orders.aggregate([
  { $match: { status: "delivered" } },
  { $group: { _id: "$customer_id", total: { $sum: "$amount" } } },
  { $sort: { total: -1 } }
]);
```

**Q44 — نظرية CAP؟**
أي نظام قاعدة بيانات موزع، وقت انقسام الشبكة، لازم يختار بين **Consistency** (فلسفة ACID) و**Availability** (فلسفة BASE). Partition Tolerance ضرورة حتمية، فالاختيار الحقيقي دايماً بين CP وAP — نظام بنكي غالباً CP، عداد لايكات غالباً AP.

**Q45 — الفروق العملية اللي تأثر على قرارات يومية بين SQL وMongoDB؟**
Schema صارم مقابل مرن، JOINs محسّنة مقابل Embedding مفضّل، Transactions ناضجة من زمان مقابل دعم حديث نسبياً، وSharding مدمج من الأساس في MongoDB مقابل أدوات إضافية غالباً مطلوبة في SQL.

## القسم السابع: القرار العملي — SQL ولا NoSQL؟

**Q46 — الأسئلة اللي بتوجه القرار؟**
1. شكل البيانات مستقر ولا بيتغير باستمرار؟ (مستقر → SQL)
2. العلاقات معقدة ومتشابكة ولا بسيطة ومحدودة؟ (معقدة → SQL)
3. محتاج ضمانات ACID قوية عبر كيانات متعددة، ولا BASE مقبولة؟ (ACID لازم → SQL)
4. الحجم أو الحمل المتوقع فعلاً محتاج توسع أفقي ضخم من اليوم الأول؟ (أيوه → NoSQL)
القرار بيتاخد لكل جزء أو موديول في النظام لوحده، مش قرار واحد شامل لكل المشروع.

**Q47 — Polyglot Persistence؟**
الأنظمة الكبيرة الحقيقية بتستخدم أكتر من نوع قاعدة بيانات مع بعض: PostgreSQL للمعاملات (ACID)، Elasticsearch للبحث النصي، Redis للكاش (BASE مقبولة). التحدي هو **مزامنة البيانات** بينهم صح، وإلا هتلاقي بيانات متضاربة.

**Q48 — علامات إن الاختيار كان غلط، وإزاي تصلحه؟**
علامة على SQL غلط: Migrations متكررة وأعمدة فاضية كتير. علامة على NoSQL غلط: كود تكامل بيانات معقد يدوي واحتياج متكرر لضمانات ACID. الحل: هجرة جزئية تدريجية للجزء المتضرر بس، مع فترة تشغيل متوازي (Dual Write) للتأكد قبل الانتقال الكامل.

**Q49 — مثال واقعي متكامل يجمع كل اللي اتقال؟**
منصة تجارة إلكترونية: PostgreSQL للطلبات والمدفوعات (علاقات معقدة، ACID لازم). Redis Cache قدام صفحة المنتجات الأكتر زيارة (تقليل الحمل قبل أي توسع تاني). Read Replicas لصفحات القراءة الكتيرة زي "طلباتي". Elasticsearch للبحث عن المنتجات (مليون منتج، بحث نصي معقد). كل قرار اتاخد بناءً على طبيعة الجزء ده تحديداً، مش قرار واحد شامل.

**Q50 — الخلاصة العملية النهائية؟**
ابدأ بـ SQL وضمانات ACID كخيار افتراضي آمن. حسّن الاستعلامات وفهرس صح قبل أي حاجة تانية. جرّب Caching ثم Read Replicas قبل التفكير في Sharding. انتقل لـ NoSQL وفلسفة BASE، أو استخدم أكتر من أداة مع بعض (Polyglot Persistence)، بس لما يكون فيه سبب واضح ومحدد من الأسئلة الأربعة في Q46 — مش بناءً على الموضة.
