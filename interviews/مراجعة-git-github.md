# مراجعة سريعة: Git وGitHub من الأول للآخر

دليل مختصر، سؤال وجواب، من الأسهل للأصعب. كل سؤال بيبني على اللي قبله.

---

## القسم الأول: أساسيات Git المحلي

**Q1 — Git ايه أصلاً، والفرق بينه وبين GitHub؟**
Git برنامج بيتابع تاريخ التغييرات في ملفاتك (Version Control System)، بيشتغل على جهازك محلياً حتى من غير إنترنت. GitHub منصة أونلاين بتستضيف المشاريع اللي بتستخدم Git، وبتضيف عليها حاجات زي الـ Pull Requests والـ Issues والتعاون بين فريق. يعني Git هو الأداة، وGitHub هو المكان اللي بترفع عليه شغلك وتتعاون فيه مع ناس تانية.

**Q2 — إزاي أبدأ Git في مشروع جديد؟**
```bash
git init          # يبدأ مستودع Git جديد جوه المجلد الحالي
git status         # يوريك حالة الملفات دلوقتي (معدلة، جديدة، إلخ)
```
`git init` بيعمل مجلد مخفي اسمه `.git` جوه المشروع، وده اللي بيخزن كل تاريخ التغييرات.

**Q3 — إزاي أحفظ تغييراتي (Commit)؟**
Git بيشتغل بمرحلتين: الأول تضيف الملفات لمنطقة مؤقتة اسمها **Staging Area** (`git add`)، وبعدين تعمل **Commit** يحفظ لقطة (Snapshot) دائمة من الملفات دي في التاريخ.
```bash
git add file.txt        # يضيف ملف واحد للـ Staging Area
git add .                # يضيف كل الملفات المتغيرة
git commit -m "Add login feature"   # يحفظ لقطة دائمة برسالة توضيحية
```

**Q4 — ليه فيه مرحلة Staging منفصلة عن Commit؟**
عشان تقدر تختار بالظبط أي تغييرات تدخل جوه الـ Commit، حتى لو عندك ملفات كتير اتعدلت. مثلاً لو عدّلت حاجتين مختلفتين تماماً (إصلاح باج وميزة جديدة)، تقدر تعمل `git add` للملفات بتاعة الباج بس، وتعمل Commit منفصل ليه، وبعدين Commit تاني للميزة — كده تاريخك بيفضل منظم ومفهوم.

**Q5 — إزاي أشوف تاريخ التغييرات؟**
```bash
git log                 # يوريك كل الـ Commits بالتفصيل
git log --oneline        # نسخة مختصرة، سطر واحد لكل Commit
git diff                 # يوريك الفرق بين الملفات الحالية وآخر Commit
```

**Q6 — ملف .gitignore بيعمل ايه؟**
بيقول لـ Git "متتبعش الملفات أو المجلدات دي خالص"، زي مجلد `node_modules`، ملفات بيئة العمل (`.env`)، أو ملفات مؤقتة بيولدها المحرر. بيمنع رفع ملفات كبيرة أو حساسة بالغلط للمستودع.
```
node_modules/
.env
*.log
```

## القسم الثاني: Branching (التفرع)

**Q7 — Branch ايه، وليه مهم؟**
Branch خط تطوير منفصل، بيسمحلك تشتغل على ميزة جديدة أو إصلاح من غير ما تأثر على الكود الرئيسي (غالباً اسمه `main` أو `master`). لو الميزة فشلت أو محتاجة وقت أطول، الكود الأساسي فاضل سليم وشغال.
```bash
git branch feature-login       # يعمل Branch جديد بس مش بيروحله
git checkout feature-login     # يروح للـ Branch ده
git checkout -b feature-login  # الاتنين مع بعض في أمر واحد
```

**Q8 — إزاي أدمج Branch في التاني (Merge)؟**
بعد ما تخلص شغلك في Branch، بتدمجه في الـ Branch الرئيسي.
```bash
git checkout main            # ارجع للـ Branch الرئيسي الأول
git merge feature-login       # ادمج التغييرات من feature-login جواه
```
لو مفيش تعارض بين التغييرات، Git بيدمجهم تلقائياً. لو فيه تعارض، هتحتاج تحله يدوياً (هنتكلم عنه بالتفصيل قريب).

**Q9 — Fast-Forward Merge ايه، والفرق عن Merge العادي؟**
لو الـ Branch الرئيسي متغيرش خالص من وقت ما عملت Branch جديد، Git بيقدر "يقدّم" مؤشر الـ Branch الرئيسي لآخر Commit في الـ Branch التاني من غير ما يعمل Commit دمج جديد — ده اسمه Fast-Forward. لو الاتنين اتغيروا بشكل منفصل، Git بيعمل Commit دمج جديد (Merge Commit) بيربط التاريخين مع بعض.

**Q10 — إزاي أشوف كل الـ Branches الموجودة؟**
```bash
git branch          # يوريك كل الـ Branches المحلية
git branch -a        # يوريك المحلية والبعيدة (Remote) مع بعض
git branch -d feature-login   # يمسح Branch بعد ما تخلص منه (لو اندمج بالفعل)
```

**Q11 — نظام تسمية Branches الشائع؟**
عادةً بتتسمى حسب الغرض منها: `feature/login-page`، `bugfix/header-crash`، `hotfix/payment-error`. التسمية الواضحة دي بتخلي أي حد في الفريق يفهم غرض الـ Branch من اسمه بس، وبتسهل التنظيم لو عندك عشرات الـ Branches شغالة في نفس الوقت.

## القسم الثالث: Remote وGitHub

**Q12 — Remote Repository ايه؟**
نسخة من المستودع مخزنة على سيرفر بعيد (زي GitHub)، عشان تقدر تشارك شغلك مع فريقك أو تعمل Backup بره جهازك. الاسم الافتراضي للـ Remote غالباً `origin`.
```bash
git remote add origin https://github.com/username/repo.git
git remote -v    # يوريك روابط الـ Remotes المرتبطة بالمشروع
```

**Q13 — الفرق بين Clone وInit؟**
`git clone` بتنزّل نسخة كاملة من مستودع موجود بالفعل على GitHub (بكل تاريخه)، مناسب لما تنضم لمشروع موجود. `git init` بتبدأ مستودع جديد من الصفر على جهازك.
```bash
git clone https://github.com/username/repo.git
```

**Q14 — Push وPull بيعملوا ايه؟**
```bash
git push origin main     # يرفع الـ Commits المحلية عندك لـ GitHub
git pull origin main      # يجيب آخر تحديثات من GitHub ويدمجها عندك محلياً
```
`git pull` فعلياً بتساوي `git fetch` (تجيب التحديثات بس من غير دمج) + `git merge` (تدمجها في شغلك الحالي) في أمر واحد.

**Q15 — إيه الفرق بين Fetch وPull؟**
`git fetch` بتجيب آخر التغييرات من الـ Remote، لكن مبتدمجهاش في شغلك الحالي — بتقدر تراجعها الأول قبل ما تقرر تدمجها. `git pull` بتعمل الحاجتين مع بعض تلقائياً. الأفضل لو عايز تتأكد من التغييرات قبل الدمج، استخدم `fetch` وبعدين `merge` يدوي.
```bash
git fetch origin
git log origin/main       # شوف التغييرات الجديدة قبل ما تدمجها
git merge origin/main
```

**Q16 — Fork ايه، والفرق بينه وبين Clone؟**
Fork بينشئ نسخة كاملة من مستودع حد تاني على حسابك أنت على GitHub، عشان تعدّل فيها بحرية من غير ما تأثر على المستودع الأصلي. Clone بعد كده بتنزّل النسخة دي (أو أي مستودع) لجهازك. الاستخدام الشائع: Fork مستودع مفتوح المصدر، عدّل فيه، وابعت Pull Request للمشروع الأصلي.

## القسم الرابع: التراجع والإصلاح

**Q17 — عايز أرجع تعديل عملته قبل ما أعمل Commit، أعمل ايه؟**
```bash
git checkout -- file.txt     # يرجع الملف لآخر حالة محفوظة، ويلغي التعديلات الغير محفوظة
git restore file.txt          # نفس الفكرة، أمر أحدث وأوضح في الاسم
```

**Q18 — عايز أشيل ملف من Staging Area بعد ما عملتله git add؟**
```bash
git restore --staged file.txt   # يشيل الملف من الـ Staging، بس التعديلات فيه تفضل موجودة
```

**Q19 — الفرق بين git reset وgit revert؟**
`git reset` بيرجع تاريخ الـ Branch لـ Commit سابق، وكأن الـ Commits اللي بعده اختفت خالص (خطير لو الشغل ده اتشارك مع فريق). `git revert` بيعمل Commit جديد بيلغي تأثير Commit قديم، من غير ما يمسح تاريخ الـ Commits — أأمن بكتير في مشاريع الفريق لأنه مش بيغيّر التاريخ اللي حد تاني ممكن يكون شايفه بالفعل.
```bash
git reset --hard HEAD~1     # يمسح آخر Commit تماماً (خطير، تفقد التعديلات)
git revert HEAD              # يعمل Commit جديد يلغي آخر Commit، والتاريخ فاضل كامل
```

**Q20 — الفرق بين reset --soft وreset --mixed وreset --hard؟**
- `--soft`: بيرجع مؤشر الـ Branch بس، والتعديلات بتفضل في الـ Staging Area (زي إنك عملت Commit وعايز تلغيه بس تحتفظ بالتعديلات جاهزة).
- `--mixed` (الافتراضي): بيرجع مؤشر الـ Branch ويشيل من الـ Staging، لكن التعديلات لسه موجودة في ملفاتك.
- `--hard`: بيمسح كل حاجة تماماً، التعديلات بتضيع نهائياً — استخدمه بحذر شديد.

**Q21 — عايز أحفظ تعديلاتي مؤقتاً من غير Commit، عشان أروح Branch تاني؟**
```bash
git stash                # يحفظ التعديلات الغير محفوظة جانباً مؤقتاً
git checkout other-branch
# ... تشتغل على حاجة تانية ...
git checkout original-branch
git stash pop             # يرجع التعديلات المحفوظة تاني
```
مفيد جداً لو محتاج تبدّل Branch بسرعة وعندك شغل نص خلصان مش عايز تعمله Commit لسه.

**Q22 — إزاي أعرف مين عدّل سطر معين في ملف، وإمتى؟**
```bash
git blame file.txt    # يوريك آخر Commit عدّل كل سطر في الملف، ومين عمله
git log -p file.txt    # يوريك تاريخ كل التعديلات على ملف معين بالتفصيل
```

## القسم الخامس: Merge vs Rebase وحل التعارضات

**Q23 — Conflict (تعارض) بيحصل إمتى، وإزاي أحله؟**
بيحصل لما Branchين عدّلوا نفس السطر في نفس الملف بشكل مختلف، وGit مش عارف يختار مين الصح. Git بيوقف الدمج ويعلّم مكان التعارض في الملف نفسه.
```
<<<<<<< HEAD
كود من الـ Branch الحالي
=======
كود من الـ Branch التاني
>>>>>>> feature-login
```
لازم تفتح الملف، تختار أو تدمج الكود الصح يدوياً، تمسح العلامات دي، وبعدين:
```bash
git add file.txt
git commit         # يكمل عملية الدمج بعد حل التعارض
```

**Q24 — Rebase ايه، والفرق بينه وبين Merge؟**
Merge بيدمج الـ Branchين ويعمل Commit دمج جديد بيربط التاريخين. Rebase بياخد الـ Commits بتاعتك ويعيد "تشغيلها" فوق آخر نسخة من الـ Branch الرئيسي، وكأنك بدأت الشغل من الأساس على النسخة الجديدة — النتيجة تاريخ خطي نضيف من غير Merge Commits زيادة.
```bash
git checkout feature-login
git rebase main       # يعيد بناء Commits الـ feature فوق آخر نسخة من main
```

**Q25 — إمتى أستخدم Rebase وإمتى Merge؟**
استخدم **Rebase** على Branch شغال عليه لوحدك ولسه ماتشاركش مع حد، عشان تخلي تاريخك نضيف قبل ما تدمجه في الـ main. استخدم **Merge** لو الـ Branch متشارك مع فريق أو اتنشر بالفعل، لأن Rebase بيغيّر تاريخ الـ Commits (بيديها معرفات جديدة)، ولو حد تاني شغال على نفس الـ Branch، Rebase هيسبب له مشاكل كبيرة ودمج معقد.

**Q26 — Squash ايه، وليه بيستخدموه في Pull Requests؟**
Squash بيدمج كذا Commit صغير في Commit واحد بس، غالباً وقت دمج Pull Request. مفيد لو عملت 15 Commit صغير أثناء تطوير ميزة (زي "fix typo"، "try again"، "actually fix it")، وعايز تاريخ الـ main يفضل نضيف بـ Commit واحد واضح بس يمثل الميزة كاملة.
```bash
git merge --squash feature-login
git commit -m "Add login feature"   # كل الـ Commits الصغيرة اتلخصت في واحد بس
```

## القسم السادس: GitHub Workflow

**Q27 — Pull Request (PR) ايه؟**
طلب رسمي على GitHub إنك عايز تدمج تغييرات من Branch (أو Fork) في Branch تاني (غالباً main). بيسمح لباقي الفريق يراجعوا الكود (Code Review)، يعلّقوا عليه، ويطلبوا تعديلات قبل ما يتم الدمج فعلياً — ده أساس التعاون في GitHub.

**Q28 — إزاي شكل الـ Workflow العملي لفتح PR؟**
```bash
git checkout -b feature/add-search
# ... تعمل تعديلاتك وCommits ...
git push origin feature/add-search
```
بعدها تفتح GitHub، وتعمل Pull Request من الـ Branch ده لـ main، وتكتب وصف واضح للتغيير، وتستنى مراجعة زملائك قبل الدمج.

**Q29 — Code Review في PR بيتم إزاي؟**
المراجع بيقدر يعلّق على أسطر معينة في الكود، يقترح تعديلات، أو يوافق (Approve) على الـ PR. لو فيه طلب تعديلات، بتعمل Commits جديدة على نفس الـ Branch، وGitHub بيحدّث الـ PR تلقائياً من غير ما تفتح واحد جديد. لما المراجعة تخلص والفريق موافق، الـ PR بيتدمج (Merge أو Squash).

**Q30 — Issues في GitHub بتستخدم لإيه؟**
تتبع المهام، الأخطاء (Bugs)، والاقتراحات في المشروع. كل Issue بتوصف مشكلة أو طلب ميزة، وممكن تتربط بـ Labels (زي `bug`, `enhancement`)، تتحدد لحد معين، وتترتبط بـ Pull Request بيحلها.
```
Closes #42
```
كتابة السطر ده في وصف الـ PR بيخلي GitHub يقفل الـ Issue رقم 42 تلقائياً لما الـ PR يتدمج.

**Q31 — GitHub Actions ايه بشكل مختصر؟**
أداة أتمتة مدمجة في GitHub، بتخليك تشغّل أوامر تلقائياً عند حدث معين (زي كل ما حد يعمل Push أو يفتح PR) — زي تشغيل الاختبارات (Tests) تلقائياً، أو نشر المشروع (Deployment) تلقائياً بعد كل دمج ناجح في main.
```yaml
# .github/workflows/test.yml
name: Run Tests
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm test
```

## القسم السابع: مواضيع متقدمة

**Q32 — Cherry-pick ايه؟**
بتاخد Commit واحد بس من Branch معين، وتطبقه على Branch تاني، من غير ما تدمج كل تاريخ الـ Branch الأول. مفيد لو عملت إصلاح مهم في Branch، ومحتاج نفس الإصلاح ده بس في Branch تاني (زي إصلاح عاجل محتاج ينزل في نسخة إنتاج قديمة كمان).
```bash
git cherry-pick abc1234    # يطبق الـ Commit ده بس على الـ Branch الحالي
```

**Q33 — Git Bisect بيعمل ايه؟**
أداة بتساعدك تلاقي أنهي Commit بالظبط سبب مشكلة معينة (Bug)، عن طريق البحث الثنائي (Binary Search) بين Commit قديم كان شغال كويس وCommit حديث فيه المشكلة. Git بيوريك Commits في النص، وأنت تقوله "كويس" أو "فيه المشكلة"، لحد ما يوصل بالظبط للـ Commit المسبب.
```bash
git bisect start
git bisect bad              # الـ Commit الحالي فيه المشكلة
git bisect good v1.0        # الإصدار ده كان شغال كويس
# Git هيقولك تجرب Commits في النص، ورد عليه good/bad لحد ما يلاقي المسبب
```

**Q34 — Tags بتستخدم لإيه؟**
علامة على Commit معين، غالباً بتستخدم لتحديد إصدارات رسمية (زي `v1.0.0`، `v2.1.3`). بخلاف الـ Branch، الـ Tag ثابت ومبيتحركش مع Commits جديدة.
```bash
git tag v1.0.0             # يعلّم آخر Commit كإصدار v1.0.0
git push origin v1.0.0      # يرفع الـ Tag لـ GitHub
```

**Q35 — Git Hooks ايه؟**
سكريبتات بتتشغل تلقائياً عند حدث معين في Git (زي قبل ما تعمل Commit، أو بعد ما تعمل Push)، بتتخزن في مجلد `.git/hooks`. استخدام شائع: تشغيل فحص تلقائي على الكود (Linting) قبل ما يتم أي Commit، عشان تمنع كود فيه أخطاء واضحة من الوصول للتاريخ من الأساس.

**Q36 — Submodules ايه، ومتى تستخدمها؟**
طريقة تضيف بيها مستودع Git كامل جوه مستودع تاني، كأنه مكتبة منفصلة بتاريخها الخاص. مفيد لو عندك مكون مشترك بين أكتر من مشروع ومحتاج تتبع نسخة معينة منه بالظبط. الاستخدام معقد نسبياً وبيسبب مشاكل لو الفريق مش متعود عليه، فبيتستخدم بس لما فعلاً محتاج فصل واضح بين مستودعين مستقلين.

## القسم الثامن: القرار العملي — إيه الـ Workflow المناسب لفريقي؟

**Q37 — إيه أشهر أنماط الـ Branching Workflows؟**
| النمط | الفكرة | مناسب لـ |
|---|---|---|
| **GitHub Flow** | Branch واحد رئيسي (main)، كل ميزة في Branch منفصل، PR، دمج مباشر | فرق صغيرة، نشر مستمر (Continuous Deployment) |
| **Git Flow** | Branches ثابتة زي `develop`, `release`, `hotfix` جنب main | مشاريع بإصدارات رسمية دورية (زي تطبيقات موبايل) |
| **Trunk-Based Development** | الكل بيدمج في main بشكل متكرر جداً (يومياً)، Branches قصيرة العمر جداً | فرق كبيرة، اختبارات تلقائية قوية جداً |

**Q38 — إمتى أختار Git Flow بدل GitHub Flow البسيط؟**
لو مشروعك محتاج تدير كذا إصدار (Version) في نفس الوقت (زي تطبيق موبايل لسه فيه ناس شغالة على v2 وناس تانية بتصلح باجات في v1 القديمة)، Git Flow بيدّيك هيكل واضح لده بـ Branches مخصصة (`release/2.0`, `hotfix/1.5.2`). لو مشروعك بينشر باستمرار (Web App بتتحدث كذا مرة في اليوم)، الهيكل ده زيادة تعقيد مش لازم، وGitHub Flow البسيط (main + feature branches) هيكفي.

**Q39 — أهم القواعد العملية اللي تحافظ على تاريخ Git نضيف في أي فريق؟**
- اكتب رسائل Commit واضحة وقصيرة بتشرح "ليه" مش بس "ايه" (`Fix null pointer in login validation` أحسن من `fix bug`).
- خلّي كل Commit يمثل تغيير منطقي واحد، مش خليط من كذا حاجة مش مرتبطة.
- استخدم Branches قصيرة العمر، وادمجها بسرعة بعد المراجعة بدل ما تسيبها شهور مفتوحة (بتكبر فرصة التعارضات).
- متعملش Force Push (`git push --force`) على Branch متشارك مع فريق، إلا لو الكل متأكد ومتفق.

**الخلاصة في سطرين**: Git بيتابع تاريخ التغييرات محلياً بـ add/commit، وGitHub بيضيف طبقة التعاون فوقه بـ Push/Pull وPull Requests. ابدأ بـ GitHub Flow البسيط (main + feature branches + PR) لحد ما يبقى عندك سبب واضح تحتاج معاه Git Flow أو Trunk-Based، واستخدم Rebase على شغلك الشخصي بس، وMerge على أي حاجة متشاركة مع الفريق.
