## Q1 — إيه هي قاعدة البيانات (Database) أصلاً، وإيه الفرق بين نظام إدارة قواعد البيانات (DBMS) ونظام إدارة قواعد البيانات العلائقية (RDBMS)؟

### أصل الحكاية
تخيل إنك بتبني النسخة الأولى من تطبيق طلب الأكل زي "طلبات" (Talabat). في الأول خالص، معندكش مستخدمين كتير، فممكن تفكر تقول: "أنا هخزن بيانات العملاء والمطاعم والطلبات في ملفات نصية (Text Files) أو ملفات إكسل (Excel) على السيرفر". الموضوع هيمشي معاك أول يومين، بس بمجرد ما التطبيق يبدأ يشتغل ويجيلك آلاف المستخدمين في نفس اللحظة، الدنيا هتنهار.
تخيل عميلين بيطلبوا أوردر في نفس اللحظة، والسيرفر بيحاول يكتب في نفس ملف النص. هنا هيحصل تداخل والبيانات هتتمسح أو تبوظ، ودي مشكلة الوصول المتزامن (Concurrent Access). كمان لو السيرفر فصل فجأة والملف بيتكتب، البيانات هتضيع. 
هنا بيجي دور قاعدة البيانات (Database) وهي ببساطة حاوية منظمة لتخزين البيانات. وعشان نعرف نتعامل مع الحاوية دي بكفاءة وأمان، بنحتاج برنامج وسيط يسمى نظام إدارة قواعد البيانات (Database Management System - DBMS). الـ DBMS ده هو اللي بيتحكم في مين يقرأ ومين يكتب، وبيضمن إن البيانات تفضل سليمة.
أما لو قررنا ننظم البيانات دي في شكل جداول (Tables) بينها علاقات منطقية، بنستخدم نوع خاص من الـ DBMS اسمه نظام إدارة قواعد البيانات العلاقاتي (Relational Database Management System - RDBMS) زي ماي إس كيو إل (MySQL) أو بوستجرس (PostgreSQL).

الكود اللي جاي بيوضح إزاي بننشئ جدول للعملاء وجدول للطلبات وبنربطهم ببعض داخل نظام RDBMS عشان نضمن تنظيم البيانات.

```sql
-- Creating the Customers table to store user details
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL
);

-- Creating the Orders table and referencing the Customers table
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,
    order_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    amount DECIMAL(10, 2),
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
```

#### مثال 1: كتابة بيانات الأوردرات وقت الـ Scale
لو عندنا ملف نصي عادي وحصل ضغط طلبات (1000 طلب في الثانية)، الملف هيحصله قفل (Lock) من أول عملية كتابة، وباقي العمليات هتفشل أو تنتظر كتير. الـ RDBMS بيحل ده عن طريق إدارة الطابور وقفل الصفوف (Row-level locking) عشان العمليات تمشي بالتوازي بأمان.

#### مثال 2: ضياع البيانات بسبب انقطاع الكهرباء
لو السيرفر فصل أثناء تعديل ملف إكسل، الملف كله ممكن يبوظ (Corrupted). في نظام الـ RDBMS، فيه سجل للعمليات (Transaction Log) بيضمن إنه حتى لو السيرفر فصل، أول ما يرجع يشتغل هيصلح نفسه ويرجع البيانات للحالة السليمة.

### الفايدة الانترفيوية
What is the difference between a Database, DBMS, and RDBMS? Explain with a real-world scenario.
**الإجابة المثالية:**
قاعدة البيانات (Database) هي مجرد مكان بنخزن فيه البيانات بشكل منظم. نظام إدارة قواعد البيانات (DBMS) هو البرنامج أو البرنامج الوسيط اللي بيتحكم في إدارة وتأمين وقراءة وكتابة البيانات دي. أما الـ RDBMS فهو نوع متطور من الـ DBMS بيعتمد على النموذج العلاقاتي (Relational Model)، واللي يتم تنظيم البيانات في جداول مرتبطة ببعضها بواسطة علاقات منطقية مثل المفاتيح الأساسية والخارجية (Primary and Foreign Keys). في الأنظمة الواقعية مثل تطبيقات التجارة الإلكترونية، استخدام الـ RDBMS يضمن عدم تداخل البيانات عند محاولة آلاف المستخدمين شراء منتجات في نفس الوقت، ويمنع تلف البيانات في حالة حدوث عطل مفاجئ في النظام بفضل الالتزام بخصائص الـ ACID.

## Q2 — يعني إيه النموذج العلاقاتي (Relational Model) بالظبط؟ وإزاي بيقسم البيانات لجداول وصفوف وأعمدة؟

### أصل الحكاية
لما فكروا يعملوا نظام يخزن بيانات الشركات الكبيرة، قالوا لازم نلاقي طريقة يفهمها العقل البشري وتكون سهلة في الحسابات الرياضية. طلع عالم اسمه "إدجار كود" (Edgar F. Codd) بفكرة النموذج العلاقاتي (Relational Model) سنة 1970. الفكرة قايمة على إننا نمثل البيانات في شكل ثنائي الأبعاد: جداول (Tables) - وبتتسمى رياضياً العلاقات (Relations).
في نظام زي "فيسبوك" أو "إنستجرام"، لو فكرنا نخزن بيانات المنشورات (Posts)، النموذج العلاقاتي بيقولنا نقسم المنشور لعناصر أساسية:
1. الجدول (Table/Relation): بيمثل الكيان ككل، وليكن جدول المنشورات `posts`.
2. الصف (Row/Tuple/Record): بيمثل منشور واحد محدد لعميل محدد.
3. العمود (Column/Attribute): بيمثل خاصية معينة للمنشور، زي تاريخ النشر، نص المنشور، أو معرف الكاتب.
4. النطاق (Domain): وهو نوع البيانات المسموح بيها في العمود ده، يعني مثلاً عمود تاريخ النشر لازم يقبل تاريخ ووقت بس، مش نصوص عشوائية.

الـ RDBMS بيجبرنا نمشي على الهيكل ده عشان نضمن إن البيانات متناسقة، ومفيش صف فيه أعمدة زيادة عن صف تاني في نفس الجدول.

الكود التالي بيوضح تصميم جدول المنشورات وفقاً للنموذج العلاقاتي، واللي نحدد الأعمدة وأنواع بياناتها بكل دقة.

```sql
-- Creating the Posts table representing the Post entity in a social media app
CREATE TABLE posts (
    post_id INT PRIMARY KEY,
    author_id INT NOT NULL,
    post_content TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    likes_count INT DEFAULT 0
);
```

#### مثال 1: هيكلة المنشور في قاعدة البيانات
لو يوزر نزل بوست جديد، السيرفر هينشئ صف (Row) جديد في جدول الـ `posts` وكل خاصية للبوست هتنزل تحت العمود (Column) المناسب ليها. ده بيسهل استرجاع البوستات بناءً على أي خاصية (مثلاً: هات البوستات اللي ليها أكتر من 100 لايك).

#### مثال 2: محاولة إدخال نص في عمود الأرقام
لو حاولنا ندخل كلمة "كتير" في عمود `likes_count` اللي نوعه رقم (INT)، الـ Database هترفض العملية فوراً وتطلع خطأ. ده بيحافظ على نظافة البيانات وبيمنع المشاكل البرمجية في الـ Application layer.

### الفايدة الانترفيوية
Explain the core components of the Relational Model and how it structures data.
**الإجابة المثالية:**
النموذج العلاقاتي (Relational Model) هو نموذج لتنظيم البيانات وتخزينها على شكل جداول ثنائية الأبعاد تسمى رياضياً العلاقات (Relations). يتكون الجدول من صفوف (Rows/Tuples) تمثل السجلات الفردية، وأعمدة (Columns/Attributes) تمثل الخصائص المميزة للكيان. يتم التحكم في جودة البيانات من خلال تحديد نوع البيانات (Data Type) أو النطاق (Domain) لكل عمود، وفرض قيود (Constraints) مثل عدم قبول قيم فارغة (Not Null). النموذج ده بيسهل عمليات البحث والتعديل ويضمن سلامة البيانات من خلال منع تخزين بيانات غير مطابقة للهيكل المحدد مسبقاً.

## Q3 — إيه الفرق الجوهري بين الـ SQL والـ NoSQL بشكل عام؟ (تمهيد سريع)

### أصل الحكاية
تخيل إنك بتبني تطبيق تواصل اجتماعي كبير زي "تويتر" (Twitter). في البداية، فكرت تستخدم MySQL (نظام SQL) عشان تخزن التويتات واليوزرات والعلاقات بينهم (مين عامل فولو لمين). الموضوع شغال تمام. لكن مع الوقت، لما بقا عندك ملايين التويتات بتنزل في الدقيقة، وكل مستخدم بيعمل Feed خاص بيه بيجمع تويتات الناس اللي بيتابعهم، الـ Joins الكتيرة بين الجداول بدأت تخلي النظام بطيء جداً، وتكلفة السيرفرات بقت فلكية.
هنا ظهرت الحاجة لنوع جديد من قواعد البيانات بيتعامل مع البيانات بشكل مختلف، وسموه NoSQL (Not Only SQL). 
الفرق الجوهري هو:
1. قواعد بيانات SQL: بتعتمد على جداول وعلاقات صارمة ومحددة مسبقاً (Schema-on-write). لازم تحدد الهيكل قبل ما تخزن أي حاجة. وممتازة جداً لما تكون البيانات مترابطة ومحتاج تضمن سلامتها 100% (زي المعاملات المالية).
2. قواعد بيانات NoSQL: مرنة جداً ومش بتجبرك على هيكل محدد (Schema-on-read). ممكن تخزن البيانات في شكل وثائق (Documents) زي JSON، أو Key-Value، أو Graphs. وممتازة للـ Scale الأفقي وللبيانات الضخمة اللي بتتغير بسرعة.

الجدول التالي بيوضح مقارنة سريعة بين الاتنين:

| وجه المقارنة | SQL | NoSQL |
| :--- | :--- | :--- |
| **الهيكل (Schema)** | ثابت وصارم (Structured) | مرن ومتغير (Unstructured/Semi-structured) |
| **العلاقات (Relationships)** | قوية جداً باستخدام الـ Joins | ضعيفة أو غير موجودة (يفضل عدم ربط الجداول) |
| **الـ Scaling** | رأسي (Vertical) - بنكبر السيرفر نفسه | أفقي (Horizontal) - بنضيف سيرفرات رخيصة جنب بعض |
| **أشهر مثال** | PostgreSQL, MySQL | MongoDB, Redis, Cassandra |

```sql
-- SQL requires predefined columns. You cannot insert a row with an extra column dynamically.
INSERT INTO customers (customer_id, customer_name, email) 
VALUES (1, 'Mohamed Khaled', 'mohamed@inboxsales.com');
```

#### مثال 1: إضافة حقل جديد لبيانات المستخدم
في الـ SQL، لو قررت تضيف حقل "رقم التليفون الثاني" للمستخدمين، لازم تعمل عملية تعديل للجدول (Alter Table) وهي عملية مكلفة وقد تعطل السيرفر لو الجدول فيه ملايين الصفوف. في NoSQL (زي MongoDB)، ممكن ببساطة تحفظ وثيقة مستخدم جديد فيها الحقل ده، بدون ما تأثر على المستخدمين القدام.

#### مثال 2: حساب رصيد الحساب البنكي وقت الـ Scale
في البنوك، الـ Consistency هي أهم شيء. لازم عملية تحويل الفلوس من حساب لحساب تسمع في نفس اللحظة في الحسابين، وده اللي بتتقنه قواعد بيانات SQL بفضل دعمها الكامل للـ ACID Transactions. قواعد NoSQL قد تضحي ببعض التناسق اللحظي في مقابل السرعة والـ Scale.

### الفايدة الانترفيوية
What are the key differences between SQL and NoSQL databases, and when would you choose one over the other?
**الإجابة المثالية:**
الفرق الجوهري يكمن في مرونة الهيكل (Schema) وطريقة التوسع (Scaling). قواعد بيانات SQL تعتمد على هيكل صارم وعلاقات واضحة بين الجداول، وتتوسع رأسياً (Vertical Scaling) عن طريق زيادة موارد السيرفر نفسه، وهي الخيار الأفضل للأنظمة اللي بتتطلب معاملات مالية دقيقة وتناسق فوري للبيانات (Strict Consistency). بينما قواعد NoSQL تتميز بمرونة عالية واللي لا تشترط هيكلاً ثابتاً، وتتوسع أفقياً (Horizontal Scaling) بسهولة عبر إضافة سيرفرات متعددة، مما يجعلها مثالية للبيانات الضخمة ذات الهيكل المتغير مثل المنشورات، سجلات الأحداث (Logs)، وأنظمة الكاش.

## Q4 — إيه هو المفتاح الأساسي (Primary Key) وإيه هي شروطه الصارمة؟

### أصل الحكاية
تخيل إنك شغال في مصلحة الأحوال المدنية وبتصمم قاعدة بيانات للمواطنين. لو جيت تعرف المواطن باسمه، هتكتشف إن فيه آلاف المواطنين اسمهم "محمد أحمد محمد". ولو عرفتهم بالاسم وتاريخ الميلاد، برضه هتلاقي تطابق. لو حصل تطابق، وجينا نعدل بيانات مواطن (مثلاً نغير حالته الاجتماعية)، النظام ممكن يعدل بيانات شخص تاني بالخطأ!
عشان كده، النموذج العلاقاتي فرض وجود مفهوم المفتاح الأساسي (Primary Key). المفتاح الأساسي هو عمود (أو مجموعة أعمدة) بيحدد الصف بشكل فريد ومستحيل يتكرر داخل الجدول.
شروط المفتاح الأساسي صارمة جداً:
1. الفرادة (Uniqueness): القيمة الموجودة في عمود المفتاح الأساسي للصف ده مستحيل تتكرر في أي صف تاني في نفس الجدول.
2. عدم قبول الفراغ (Not Null): مستحيل تسيب خانة المفتاح الأساسي فاضية (NULL). لأن الفراغ معناه إن الكيان ملوش هوية، وده يهدد سلامة البيانات.

في الأنظمة الواقعية، بنستخدم غالباً معرفات رقمية تلقائية الزيادة (Auto-incremented IDs) أو معرفات فريدة عالمياً (Universally Unique Identifiers - UUID).

الكود اللي جاي بيوريك إزاي بنعرف المفتاح الأساسي في جدول المستخدمين وإزاي الـ Database بتمنع أي تكرار أو قيم فارغة.

```sql
-- Creating users table with primary key
CREATE TABLE users (
    user_id INT PRIMARY KEY AUTO_INCREMENT, -- Generates unique IDs automatically
    username VARCHAR(50) NOT NULL
);

-- Inserting a user (ID will be 1 automatically)
INSERT INTO users (username) VALUES ('ahmed');

-- This explicit insert will fail because ID 1 already exists (Uniqueness violation)
-- INSERT INTO users (user_id, username) VALUES (1, 'ali'); -- Error!
```

#### مثال 1: نظام حجز تذاكر قطارات
لو المفتاح الأساسي لكرسي القطار مش فريد، ممكن النظام يبيع نفس التذكرة لشخصين مختلفين (Double Booking). تحديد رقم التذكرة أو رقم الكرسي كمفتاح أساسي يمنع الـ RDBMS من قبول حجزين بنفس الرقم تماماً.

#### مثال 2: استخدام الـ UUID وقت الـ Scale
في الأنظمة الموزعة (Distributed Systems) اللي فيها سيرفرات كتير بتكتب في قواعد بيانات مختلفة في نفس الوقت، لو استخدمنا أرقام متتالية (1, 2, 3...) هيحصل تصادم بين السيرفرات. الحل هنا هو استخدام UUID كمفتاح أساسي، وهو عبارة عن سلسلة نصية طويلة فريدة جداً بيتم توليدها عشوائياً بدون الحاجة للتنسيق بين السيرفرات.

### الفايدة الانترفيوية
What is a Primary Key, what are its constraints, and why is it essential in database design?
**الإجابة المثالية:**
المفتاح الأساسي (Primary Key) هو حقل أو مجموعة حقول تحدد كل سجل (Row) في الجدول بشكل فريد وغير قابل للتكرار. شروطه الأساسية هي الفرادة (Uniqueness) التامة، وألا يحتوي على قيم فارغة (Not Null). هو حجر الأساس لسلامة البيانات (Entity Integrity) لأنه يمنع تكرار السجلات ويسمح بالوصول السريع والدقيق لأي صف، كما أنه يستخدم كمرجع للجداول الأخرى لإنشاء العلاقات عبر المفاتيح الخارجية (Foreign Keys).

## Q5 — إيه الفرق الجوهري بين المفتاح الأساسي (Primary Key) والمفتاح الفريد (Unique Key)؟

### أصل الحكاية
تخيل إنك بتصمم جدول للمستخدمين في موقع تجارة إلكترونية زي "أمازون". الطبيعي إن كل مستخدم ليه معرف فريد (User ID) وده هو المفتاح الأساسي (Primary Key) اللي بنربط بيه أوردراته وعناوينه.
لكن، الموقع بيطلب من المستخدم يسجل بالإيميل بتاعه، والإيميل ده برضه مينفعش يتكرر في النظام (مفيش اتنين يوزرز بنفس الإيميل). هنا ممكن تسأل: "طب ما نخلي الإيميل هو الـ Primary Key؟"
الرد العملي: الإيميل عبارة عن نص طويل، وممكن اليوزر يحتاج يغيره في المستقبل. المفتاح الأساسي يفضل إنه يكون ثابت وميتغيرش أبداً وسريع في البحث (زي الرقم الرقمي).
عشان كده بنسيب الـ User ID كمفتاح أساسي، وبنعمل قيد فريد (Unique Constraint/Key) على عمود الإيميل.
الفرق بين الاتنين جوهري:
1. المفتاح الأساسي: مسموح بواحد بس في الجدول، ولا يقبل قيم فارغة (NULL) نهائياً.
2. المفتاح الفريد: ممكن تعمل منه كذا واحد في الجدول (على الإيميل، رقم التليفون، الرقم القومي)، وبيقبل قيم فارغة (NULL) في أغلب قواعد البيانات (لأن الفراغ لا يعتبر تكراراً للمعلومة).

الجدول التالي بيوضح الفروق الأساسية:

| وجه المقارنة | المفتاح الأساسي (Primary Key) | المفتاح الفريد (Unique Key) |
| :--- | :--- | :--- |
| **العدد في الجدول** | واحد فقط | متعدد (ممكن أكتر من عمود) |
| **قبول الـ NULL** | لا يقبل نهائياً | يقبل (في معظم الأنظمة) |
| **توليد الفهرس تلقائياً** | ينشئ Clustered Index | ينشئ Non-Clustered Index |

```sql
-- Creating users table showcasing Primary Key vs Unique Key
CREATE TABLE ecom_users (
    user_id INT PRIMARY KEY AUTO_INCREMENT, -- Primary Key (Only 1 allowed)
    email VARCHAR(100) UNIQUE,              -- Unique Key (Multiple allowed)
    phone VARCHAR(20) UNIQUE                -- Another Unique Key
);
```

#### مثال 1: تسجيل مستخدم بدون رقم تليفون
لو مستخدم سجل في الموقع وحط إيميله وساب خانة التليفون فاضية (NULL)، العملية هتنجح. ولو مستخدم تاني سجل وساب التليفون فاضي برضه هتنجح، لأن الـ RDBMS بيعتمد إن الـ NULL مش قيمة متكررة في الـ Unique Key. لكن لو حاولنا نسيب الـ `user_id` فاضي، العملية هتفشل فوراً.

#### مثال 2: أداء البحث (Search Performance)
الـ Primary Key بيترتب الجدول بناءً عليه في الذاكرة (Clustered Index)، فالبحث بيه بيكون فائق السرعة. أما الـ Unique Key فبيتعمل له فهرس خارجي (Non-Clustered Index) عشان يمنع التكرار ويسرع البحث برضه بس بخطوة إضافية مقارنة بالمفتاح الأساسي.

### الفايدة الانترفيوية
What is the difference between a Primary Key and a Unique Key?
**الإجابة المثالية:**
الجدول يمكن أن يحتوي على مفتاح أساسي (Primary Key) واحد فقط، بينما يمكن أن يحتوي على عدة مفاتيح فريدة (Unique Keys). المفتاح الأساسي لا يقبل قيم فارغة (NULL) مطلقاً ويقوم بترتيب البيانات في الجدول فيزيائياً (Clustered Index). في المقابل، المفتاح الفريد يقبل قيم فارغة (NULL) - واللي لا تمثل القيمة الفارغة تكراراً في معظم محركات قواعد البيانات - ويتم فهرستها باستخدام (Non-Clustered Index). نستخدم المفتاح الأساسي كهوية ثابتة للسجل، والمفاتيح الفريدة لفرض شروط الأعمال (Business Rules) على حقول أخرى مثل البريد الإلكتروني أو رقم الهاتف.

## Q6 — إيه هو المفتاح الخارجي (Foreign Key) وإزاي بيربط بين الجداول ويضمن سلامة العلاقات؟

### أصل الحكاية
تخيل إنك بتدير نظام بنكي زي "البنك الأهلي". عندك جدول للحسابات البنكية (Accounts) وجدول للمعاملات (Transactions) اللي بتحصل على الحسابات دي (سحب، إيداع).
لو العميل رقم 5 عمل عملية سحب، المفروض نكتب في جدول المعاملات إن العملية دي تخص الحساب رقم 5.
لكن ماذا لو كتبنا بالخطأ إن العملية تخص الحساب رقم 999 والحساب ده أصلاً مش موجود في البنك؟ هنا البيانات هتبوظ وهيبقا عندنا معاملة "يتيمة" ملهاش صاحب.
عشان نمنع الكارثة دي، بنستخدم المفتاح الخارجي (Foreign Key). المفتاح الخارجي هو عمود في جدول (جدول المعاملات) بيشاور على المفتاح الأساسي في جدول تاني (جدول الحسابات).
الـ RDBMS بيراقب الجدولين دول بدقة، وبيضمن ما يسمى بـ "السلامة المرجعية" (Referential Integrity):
- مستحيل تضيف معاملة لحساب مش موجود.
- مستحيل تمسح حساب بنكي ولسه متسجل عليه معاملات في الجدول التاني (إلا لو حددت إيه اللي يحصل للبيانات المرتبطة بيه).

الكود اللي جاي بيوضح إزاي بنربط جدول المعاملات بجدول الحسابات البنكية وبنحدد سلوك التعديل والمسح.

```sql
-- Creating the Accounts table
CREATE TABLE bank_accounts (
    account_number INT PRIMARY KEY,
    owner_name VARCHAR(100) NOT NULL
);

-- Creating the Transactions table linked to Accounts via Foreign Key
CREATE TABLE account_transactions (
    transaction_id INT PRIMARY KEY,
    account_number INT,
    amount DECIMAL(12, 2),
    FOREIGN KEY (account_number) REFERENCES bank_accounts(account_number)
    ON DELETE RESTRICT -- Prevents deleting account if transactions exist
);
```

#### مثال 1: تجنب مسح عميل له طلبات نشطة
لو عميل دخل مسح الأكونت بتاعه من على موقع تسوق، وكان ليه أوردرات تحت الشحن. لو مسحنا العميل، الأوردرات هتبقا ملهاش صاحب. الـ Foreign Key هيمنع مسح العميل ده (Restrict) لحد ما أوردراته تتقفل أو تتمسح الأول، أو ممكن نخليه يمسح الأوردرات تلقائياً (Cascade) لو دي رغبتنا.

#### مثال 2: المعاملات المعلقة وقت الـ Scale
في الأنظمة الكبيرة جداً اللي فيها ملايين المعاملات في الثانية، التحقق من الـ Foreign Key في كل عملية كتابة ممكن يسبب بطء (Overhead) لأن الـ Database لازم تروح تتأكد إن المفتاح الأساسي موجود في الجدول التاني. في الحالات دي، بعض المهندسين بيفضلوا يمسحوا قيد الـ Foreign Key من الـ Database ويعملوا التحقق ده برمجياً في الـ Application layer لزيادة سرعة الكتابة، ودي مقايضة (Trade-off) شهيرة بين الأمان والأداء.

### الفايدة الانترفيوية
What is a Foreign Key, and how does it maintain Referential Integrity?
**الإجابة المثالية:**
المفتاح الخارجي (Foreign Key) هو حقل أو مجموعة حقول في جدول تشير إلى المفتاح الأساسي في جدول آخر. وظيفته الأساسية هي الحفاظ على السلامة المرجعية (Referential Integrity)، بحيث يضمن عدم إدخال بيانات غير صالحة أو يتيمة في الجدول التابع. كما يتحكم في سلوك البيانات المرتبطة عند المسح أو التعديل من خلال قواعد مثل `ON DELETE CASCADE` (مسح البيانات التابعة تلقائياً) أو `ON DELETE RESTRICT` (منع المسح في حال وجود سجلات مرتبطة).

## Q7 — إيه هو المفتاح المركب (Composite Key) وإمتى بنحتاج نستخدمه؟

### أصل الحكاية
تخيل إنك بتصمم نظام حجز مقاعد لسينما أو مسرح. المقعد بيتحدد بحاجتين: رقم الصف ورقم الكرسي جوه الصف ده (مثلاً الصف A الكرسي 5).
لو عملنا جدول لحجز التذاكر واستخدمنا رقم الصف لوحده كمفتاح أساسي، مش هنعرف نحجز غير كرسي واحد في كل صف! ولو استخدمنا رقم الكرسي لوحده، مش هنعرف نحجز الكرسي رقم 5 غير في صف واحد بس في السينما كلها!
هنا العمود الواحد مينفعش يكون مفتاح أساسي لوحده. الحل هو دمج العمودين مع بعض (رقم الصف + رقم الكرسي) عشان يشكلوا مع بعض مفتاح أساسي واحد لا يتكرر. ده بنسميه المفتاح المركب (Composite Key).
المفتاح المركب هو مفتاح أساسي بيتكون من عمودين أو أكتر مع بعض، ولازم التركيبة دي مع بعضها تكون فريدة في كل صف.

الكود اللي جاي بيوريك إزاي بنصمم جدول حجوزات كراسي السينما بمفتاح مركب بيجمع بين الصف والكرسي.

```sql
-- Creating ticket sales table using a Composite Key
CREATE TABLE cinema_seats (
    row_letter CHAR(1) NOT NULL,
    seat_number INT NOT NULL,
    is_reserved BOOLEAN DEFAULT FALSE,
    PRIMARY KEY (row_letter, seat_number) -- Combining two columns as the Primary Key
);

-- Reserve seat A-5
INSERT INTO cinema_seats (row_letter, seat_number, is_reserved) VALUES ('A', 5, TRUE);

-- This will fail because seat A-5 is already inserted (Composite Key violation)
-- INSERT INTO cinema_seats (row_letter, seat_number, is_reserved) VALUES ('A', 5, TRUE);
```

#### مثال 1: جدول الصلاحيات للمستخدمين
لو بتعمل جدول بيربط المستخدمين بالأدوار بتاعتهم (Roles) في النظام (مثلاً المستخدم رقم 3 عنده صلاحية "أدمن"). المفتاح الأساسي للجدول ده هيكون (User ID + Role ID) مع بعض. ده بيضمن إن المستخدم مياخدش نفس الدور مرتين في قاعدة البيانات ويسجل صفوف مكررة بلا داعي.

#### مثال 2: المفتاح البديل (Surrogate Key) كبديل للمركب
في الأنظمة المعقدة، استخدام المفاتيح المركبة بيصعب عمليات الربط (Joins) لأنك في كل جدول تاني هتحتاج تشيل العمودين مع بعض كمفتاح خارجي. لتسهيل ده وقت الـ Scale، بنلجأ لعمل مفتاح بديل (Surrogate Key) وهو رقم عشوائي أو متتالي (ID) كـ Primary Key للجدول، وبنعمل قيد فريد (Unique Constraint) على العمودين التانيين عشان نحافظ على منطق العمل وسهولة الربط في نفس الوقت.

### الفايدة الانترفيوية
What is a Composite Key, and when is it appropriate to use one over a Surrogate Key?
**الإجابة المثالية:**
المفتاح المركب (Composite Key) هو مفتاح أساسي يتكون من عمودين أو أكثر مجتمعين لتحديد السجل بشكل فريد. نستخدمه عندما تعتمد هوية الكيان بطبيعتها على أكثر من خاصية مثل (رقم الصف ورقم الكرسي في السينما). ومع ذلك، في الأنظمة الكبيرة، يفضل غالباً استبداله بمفتاح بديل (Surrogate Key) وهو معرف أحادي مصطنع (مثل Auto-increment ID أو UUID) لتسهيل عمليات الربط (Joins) وتقليل مساحة التخزين في الجداول التابعة، مع فرض قيد فريد (Unique Constraint) على الأعمدة الأصلية لضمان عدم التكرار.

## Q8 — إيه هو تصنيف المفاتيح الشامل: المفتاح المرشح (Candidate Key)، المفتاح الفائق (Super Key)، والمفتاح البديل (Alternate Key)؟

### أصل الحكاية
تخيل إنك بتصمم جدول للموظفين في شركة تقنية كبيرة. الموظف عنده بيانات كتير فريدة:
- الرقم التلقائي للشركة (Employee ID)
- البريد الإلكتروني المهني (Work Email)
- الرقم القومي (National ID)
- رقم جواز السفر (Passport Number)

لو قعدنا نتأمل البيانات دي، هنلاقي إن أي واحد منهم ينفع لوحده يكون مفتاح أساسي للجدول لأنه مستحيل يتكرر وبيحدد الموظف بدقة.
عشان نفهم المصطلحات دي، خلينا نقسمهم كالتالي:
1. المفتاح الفائق (Super Key): أي عمود أو مجموعة أعمدة بتحدد الصف بشكل فريد. يعني (Employee ID) لوحده Super Key. و (Employee ID + Name) مع بعض برضه Super Key (لأن وجود الـ ID بيضمن الفرادة حتى لو الاسم مكرر).
2. المفتاح المرشح (Candidate Key): هو أصغر Super Key ممكن (Minimal Super Key). يعني مفيش فيه أي حشو. (Employee ID) لوحده مرشح، لكن (Employee ID + Name) مش مرشح لأنه فيه حشو (Name) وممكن نحدده بدقة بدونه.
3. المفتاح الأساسي (Primary Key): هو المفتاح المرشح اللي المهندس اختاره فعلياً عشان يمثل الجدول ويربط بيه باقي الجداول.
4. المفتاح البديل (Alternate Key): هي المفاتيح المرشحة اللي متمش اختيارها كمفتاح أساسي (زي الرقم القومي أو البريد الإلكتروني).

الكود اللي جاي بيورينا جدول الموظفين وتوضيح للـ Constraints اللي بنستخدمها لتمثيل المفاهيم دي.

```sql
-- Creating employees table showing candidates and alternates
CREATE TABLE employees (
    emp_id INT PRIMARY KEY,              -- Chosen Primary Key (Candidate Key)
    national_id VARCHAR(20) UNIQUE NOT NULL, -- Alternate Key (Candidate Key)
    work_email VARCHAR(100) UNIQUE NOT NULL, -- Alternate Key (Candidate Key)
    emp_name VARCHAR(100) NOT NULL
);
```

#### مثال 1: تحديد الـ Super Keys للجدول
في الجدول ده، المجموعات دي كلها تعتبر Super Keys:
- `(emp_id)`
- `(emp_id, emp_name)`
- `(national_id, work_email)`
أي استعلام بيستخدم المجموعات دي هيضمن إنه يرجع صف واحد بالظبط (أو لا شيء) بسبب وجود المعرفات الفريدة.

#### مثال 2: اختيار المفتاح المناسب للربط
لو اخترنا الرقم القومي كمفتاح أساسي، وجينا نربطه بجدول الرواتب، هنضطر نخزن الرقم القومي (نص طويل) في جدول الرواتب. الأفضل نستخدم `emp_id` (رقم قصير) كمفتاح أساسي، ونعلم الرقم القومي كـ Alternate Key عن طريق الـ `UNIQUE` constraint لتوفير مساحة التخزين وسرعة المعالجة.

### الفايدة الانترفيوية
Differentiate between Super Key, Candidate Key, Primary Key, and Alternate Key.
**الإجابة المثالية:**
المفتاح الفائق (Super Key) هو أي مجموعة من الأعمدة جوه الجدول اللي بتقدر تحديد السجل بشكل فريد. المفتاح المرشح (Candidate Key) هو حالة خاصة من الـ Super Key ولكن بشرط أن يكون بالحد الأدنى من الأعمدة (Minimal) دون أي حقول زائدة. المفتاح الأساسي (Primary Key) هو المفتاح المرشح اللي بيختاره مصمم قاعدة البيانات ليكون المعرف الرئيسي للجدول. أما المفاتيح البديلة (Alternate Keys) فهي باقي المفاتيح المرشحة اللي ما اتاختارتش كمفتاح أساسي ولكنها تظل فريدة وتعرف السجل بدقة.

## Q9 — إيه هي أنواع العلاقات بين الجداول (One-to-One, One-to-Many, Many-to-Many) وإزاي بنصمم كل واحدة عملياً؟

### أصل الحكاية
تخيل إنك بتبني نظام متكامل لإدارة عيادة طبية. البيانات مش هتقعد في جدول واحد، لازم تتقسم وعشان تتقسم لازم نفهم العلاقات بين الكيانات دي.
العلاقات بتنقسم لتلات أنواع أساسية:
1. علاقة واحد لواحد (One-to-One): كل سجل في الجدول (أ) بيرتبط بسجل واحد بس في الجدول (ب). زي المريض (Patient) وتاريخه الطبي التفصيلي (Medical History). المريض ليه سجل طبي واحد، والسجل الطبي يخص مريض واحد. بنصممها بوضع المفتاح الأساسي للمريض كمفتاح خارجي وفريد (Unique Foreign Key) في جدول السجل الطبي.
2. علاقة واحد لمتعدد (One-to-Many): السجل في الجدول (أ) يرتبط بأكثر من سجل في الجدول (ب)، ولكن السجل في (ب) يرتبط بسجل واحد فقط في (أ). زي الطبيب (Doctor) والمرضى (Patients) اللي بيتابعهم. الطبيب بيعالج كذا مريض، بس المريض بيتابع مع طبيب واحد في التخصص ده. بنصممها بوضع المفتاح الخارجي في جدول الـ "Many" (جدول المرضى يشير لطبيبهم).
3. علاقة متعدد لمتعدد (Many-to-Many): السجل في (أ) يرتبط بأكثر من سجل في (ب)، والعكس صحيح. زي المرضى (Patients) والأدوية (Medicines). المريض بياخد كذا دوا، والدوا بياخده كذا مريض. دي مستحيل تتربط بشكل مباشر في الجداول، ولازم نكسرها لجدول وسيط (Junction/Bridge Table) زي ما هنشوف بالتفصيل في السؤال اللي جاي.

الكود اللي جاي بيوريك تصميم علاقة One-to-One وعلاقة One-to-Many.

```sql
-- Doctor table (One side of One-to-Many)
CREATE TABLE doctors (
    doctor_id INT PRIMARY KEY,
    doctor_name VARCHAR(100) NOT NULL
);

-- Patient table (Many side of One-to-Many, and One side of One-to-One)
CREATE TABLE patients (
    patient_id INT PRIMARY KEY,
    patient_name VARCHAR(100) NOT NULL,
    assigned_doctor_id INT,
    FOREIGN KEY (assigned_doctor_id) REFERENCES doctors(doctor_id) -- One-to-Many
);

-- Medical History table (One-to-One with Patients)
CREATE TABLE medical_histories (
    history_id INT PRIMARY KEY,
    patient_id INT UNIQUE, -- UNIQUE guarantees One-to-One relationship
    blood_group VARCHAR(5),
    FOREIGN KEY (patient_id) REFERENCES patients(patient_id)
);
```

#### مثال 1: علاقة الـ One-to-One للملفات الكبيرة
في الأنظمة الضخمة، لو عندنا جدول للمستخدمين فيه حقول بنقرأها كتير (الاسم، الإيميل) وحقول تانية كبيرة الحجم ونادر لما بنحتاجها (الصورة الشخصية الثنائية، الوثائق الممسوحة ضوئياً). بنفصل الحقول الكبيرة دي في جدول منفصل بعلاقة One-to-One عشان نحسن سرعة القراءة لجدول المستخدمين الأساسي.

#### مثال 2: العلاقات وتأثيرها على الحذف (Cascade Delete)
في علاقة الـ One-to-Many (مثل طبيب ومرضى)، لو الطبيب ساب المستشفى وتم حذفه من قاعدة البيانات، لازم نقرر هنعمل إيه في المرضى بتوعه. هل هنحذفهم برضه؟ (Cascade) - ده غلط طبعاً! الحل المناسب هنا هو ضبط المفتاح الخارجي ليكون `ON DELETE SET NULL` عشان المريض يفضل موجود ويتم تعيين طبيب تاني ليه لاحقاً.

### الفايدة الانترفيوية
What are the three main types of database relationships, and how do you implement them in SQL?
**الإجابة المثالية:**
أنواع العلاقات الثلاثة هي: One-to-One ويتم تصميمها بوضع المفتاح الأساسي للجدول الأول كمفتاح خارجي في الجدول الثاني مع قيد فريد `UNIQUE`. علاقة One-to-Many ويتم تصميمها بوضع المفتاح الأساسي للجدول الأب (One) كمفتاح خارجي في الجدول التابع (Many) بدون قيد فريد. وعلاقة Many-to-Many ويتم تصميمها باستخدام جدول وسيط (Junction Table) يحتوي على مفتاحين خارجيين يشيران إلى الجدولين الأصليين، وغالباً ما يشكلان معاً مفتاحاً مركباً (Composite Key).

## Q10 — إزاي بنصمم علاقة متعدد لمتعدد (Many-to-Many) فعلياً باستخدام جدول وسيط (Junction/Bridge Table)؟

### أصل الحكاية
تخيل إنك بتصمم قاعدة بيانات لتطبيق زي "سبوتيفاي" (Spotify). عندك جدول للأغاني (Songs) وجدول لقوائم التشغيل (Playlists).
قائمة التشغيل الواحدة ممكن تحتوى على أغاني كتيرة جداً. والأغنية الواحدة ممكن تكون موجودة في قوائم تشغيل كتيرة عند مستخدمين مختلفين.
لو حاولت تحط عمود `song_id` جوه جدول الـ `playlists` مش هتعرف تحط غير أغنية واحدة بس لكل قائمة (أو تضطر تعمل حشو وتخزنهم كـ نص مفصول بفواصل وده بيكسر قواعد الـ Normalization). ولو حاولت تحط `playlist_id` جوه جدول الـ `songs` هتقابلك نفس المشكلة.
الحل العبقري في قواعد البيانات العلاقاتية هو إنشاء جدول تالت في النص بنسميه الجدول الوسيط (Junction/Bridge/Association Table).
الجدول ده وظيفته الوحيدة يربط الاتنين ببعض. كل صف فيه بيمثل عملية ربط واحدة (رقم قائمة التشغيل + رقم الأغنية). وممكن كمان نحط فيه بيانات تانية تخص العلاقة نفسها، زي تاريخ إضافة الأغنية للقائمة.

الكود اللي جاي بيوضح إزاي بنبني جدول وسيط يربط الأغاني بقوائم التشغيل بكفاءة عالية.

```sql
-- Songs table
CREATE TABLE songs (
    song_id INT PRIMARY KEY,
    title VARCHAR(100) NOT NULL,
    duration_seconds INT
);

-- Playlists table
CREATE TABLE playlists (
    playlist_id INT PRIMARY KEY,
    playlist_name VARCHAR(100) NOT NULL
);

-- Junction table to resolve Many-to-Many relationship
CREATE TABLE playlist_songs (
    playlist_id INT,
    song_id INT,
    added_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (playlist_id, song_id), -- Composite Key prevents duplicates
    FOREIGN KEY (playlist_id) REFERENCES playlists(playlist_id) ON DELETE CASCADE,
    FOREIGN KEY (song_id) REFERENCES songs(song_id) ON DELETE CASCADE
);
```

#### مثال 1: منع تكرار نفس الأغنية في نفس القائمة
بفضل استخدام المفتاح المركب `PRIMARY KEY (playlist_id, song_id)` في الجدول الوسيط، لو حاول السيرفر يضيف نفس الأغنية لنفس القائمة مرتين بالخطأ، الـ Database هترفض العملية فوراً وتحمي القائمة من التكرار.

#### مثال 2: الاستعلام عن الأغاني داخل قائمة تشغيل (Query Performance)
وقت الـ Scale، جدول الـ `playlist_songs` ده ممكن يوصل لمليار صف بسهولة. عشان نجيب كل الأغاني اللي في قائمة تشغيل معينة بسرعة، الـ Database بتعتمد على الفهرس التلقائي للمفتاح المركب. يفضل وضع الـ `playlist_id` هو الأول في تعريف المفتاح المركب لأننا بنبحث بيه دايماً لعرض محتويات القائمة للمستخدم.

### الفايدة الانترفيوية
How do you implement a Many-to-Many relationship in a relational database, and what constraints should be applied to the junction table?
**الإجابة المثالية:**
لتصميم علاقة Many-to-Many، نقوم بإنشاء جدول وسيط (Junction Table) يكسر العلاقة لعلاقتين من نوع One-to-Many. يحتوي الجدول ده على مفتاحين خارجيين (Foreign Keys) يشيران للجداول الأصلية. لضمان سلامة البيانات ومنع التكرار، ندمج المفتاحين الخارجيين في مفتاح مركب واحد (Composite Primary Key). كما نطبق قيد `ON DELETE CASCADE` على المفاتيح الخارجية للتأكد من أنه إذا تم مسح أغنية أو قائمة تشغيل، يتم مسح سجلات الربط الخاصة بها تلقائياً لمنع وجود بيانات يتيمة في النظام.

## Q11 — إيه هي تصنيفات أوامر SQL؟ (DDL، DML، DQL، DCL، TCL) وإيه الفرق بينهم؟

### أصل الحكاية
تخيل إنك شغال كمهندس في نظام متكامل لتطبيق تجارة إلكترونية (E-Commerce Platform) زي أمازون أو جوميا. عشان تدير قاعدة البيانات للسيستم ده، مش هتعمل كل حاجة بنفس الأمر. كل مهمة بتحتاج نوع معين من أوامر SQL:
1. **أوامر تعريف البيانات (DDL - Data Definition Language)**: دي بتستخدمها عشان تبني البنية التحتية للنظام، زي إنشاء جدول للعملاء `customers` أو جدول للمنتجات `products` باستخدام أمر `CREATE TABLE` أو تعديل هيكل الجدول بـ `ALTER TABLE`.
2. **أوامر معالجة البيانات (DML - Data Manipulation Language)**: بمجرد ما البنية التحتية تبوظ أو تجهز، بنحتاج نتحكم في الداتا نفسها. لما بائع يضيف منتج جديد، بنستخدم `INSERT` لتخزين تفاصيل المنتج. لما يعدل السعر بنستخدم `UPDATE`. ولما يقرر يشيل منتج بنستخدم `DELETE`.
3. **أوامر الاستعلام عن البيانات (DQL - Data Query Language)**: دي بتتمثل في أمر `SELECT` وهو الأكثر استخداماً في حياتك اليومية. لما العميل يدخل التطبيق ويعمل بحث عن "ساعة ذكية"، التطبيق بيبعت استعلام DQL عشان يجيب المنتجات المناسبة ويعرضها ليه.
4. **أوامر التحكم في البيانات (DCL - Data Control Language)**: دي تخص الصلاحيات والأمان. مش أي موظف خدمة عملاء في الشركة ينفع يشوف بيانات الكروت الائتمانية للمستخدمين أو يمسح جداول. هنا بنستخدم أوامر زي `GRANT` لإعطاء صلاحيات و`REVOKE` لسحبها.
5. **أوامر التحكم في المعاملات (TCL - Transaction Control Language)**: دي الأوامر اللي بتضمن سلامة العمليات المعقدة اللي لازم تتم كلها أو تترفض كلها (Transactions). لما العميل يشتري منتج، لازم رصيده يقل في جدول المحفظة، وفي نفس الوقت كمية المنتج تقل في جدول المخزن. لو عملية الدفع فشلت في النص، بنعمل `ROLLBACK` عشان نلغي كل التعديلات ونرجع لحالتنا الأصلية، ولو نجحت بنعمل `COMMIT` لحفظ التعديلات نهائياً على الهارد ديسك.

الكود اللي جاي بيوضح أمثلة عملية لكل نوع من التصنيفات دي في سياق جدول الطلبات `orders`.

```sql
-- 1. DDL: Creating a table to define the structure of orders
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    user_id INT NOT NULL,
    total_amount DECIMAL(10, 2) NOT NULL
);

-- 2. DML: Inserting a new order record into the table
INSERT INTO orders (order_id, user_id, total_amount) 
VALUES (1, 101, 1500.00);

-- 3. DQL: Querying the database to fetch completed orders for a user
SELECT * FROM orders 
WHERE user_id = 101;

-- 4. TCL: Simulating transaction control for safety
-- COMMIT; -- Saves changes permanently
-- ROLLBACK; -- Reverts changes in case of failure
```

#### مثال 1: إضافة ميزة المحفظة الرقمية (Digital Wallet) للعملاء
لما بنقرر نضيف ميزة المحفظة الرقمية، بنستخدم الـ DDL لإنشاء جدول المحفظة `CREATE TABLE wallets`. بعد كده بنستخدم الـ DML لإدخال رصيد ترحيبي للعميل بـ `INSERT INTO wallets`. ولما العميل يعرض شاشته عشان يشوف رصيده بنستخدم الـ DQL بـ `SELECT balance`. وأخيراً، لما العميل يسحب فلوس، بنستخدم الـ TCL عشان نضمن إن عملية الخصم وعملية تسجيل السحب تموا مع بعض بأمان تام.

#### مثال 2: إدارة الصلاحيات في بيئة الإنتاج (Production Security)
في الشركات الكبيرة، المطورين (Developers) مش مسموح لهم ينفذوا أوامر DDL أو DCL مباشرة على الـ Production Database لتجنب أي كوارث أو مسح جداول بالخطأ. الـ Database Administrator (DBA) بيستخدم الـ DCL لتحديد صلاحياتهم بـ `GRANT SELECT, INSERT, UPDATE` فقط، ويمنع أي أوامر تانية لضمان أمان النظام واستقراره.

### الفايدة الانترفيوية
Explain the different categories of SQL commands (DDL, DML, DQL, DCL, TCL) with a brief example of each.
**الإجابة المثالية:**
تتكون لغة SQL من خمسة تصنيفات رئيسية مقسمة حسب الوظيفة:
1. **DDL (Data Definition Language)**: مسؤولة عن تحديد وتعديل بنية الهيكل الخاص بقواعد البيانات مثل `CREATE` لبناء الجداول، و`ALTER` لتعديلها، و`DROP` لحذفها.
2. **DML (Data Manipulation Language)**: مسؤولة عن التلاعب بالبيانات وتعديلها داخل الجداول وتشمل `INSERT` و`UPDATE` و`DELETE`.
3. **DQL (Data Query Language)**: وتتمثل في أمر `SELECT` المخصص للاستعلام وجلب البيانات للمستخدمين.
4. **DCL (Data Control Language)**: تهتم بالأمان والصلاحيات وتشمل أمر `GRANT` لمنح الصلاحيات و`REVOKE` لسحبها.
5. **TCL (Transaction Control Language)**: تتحكم في إدارة الـ Transactions لضمان تكامل البيانات مثل `COMMIT` لتأكيد حفظ العمليات و`ROLLBACK` للتراجع عنها في حال حدوث أي خطأ.

## Q12 — إيه الفرق بين CREATE TABLE و ALTER TABLE و DROP TABLE و TRUNCATE TABLE؟

### أصل الحكاية
تخيل إنك بتبني تطبيق ترفيهي لبث الأفلام والمسلسلات زي Netflix. في البداية، بتحتاج تبني البنية التحتية عشان تسجل المستخدمين. دي مهمة أوامر الـ DDL اللي بتتعامل مع الـ Structure (الهيكل) مش البيانات نفسها:
- `CREATE TABLE`: هو الأمر اللي بيبني الجدول من الصفر وبيحدد الأعمدة ونوع كل عمود والقيود المفروضة عليه (زي الـ Primary Key والـ Unique).
- `ALTER TABLE`: ده بيستخدم لما السيستم يكون شغال فعلياً وتكتشف إنك محتاج تعدل في الهيكل بدون ما تخسر الداتا الحالية. مثلاً، Netflix قررت تضيف ميزة "رمز الأمان للملف الشخصي (Profile PIN)". هنا مش هتمسح الجدول وتبنيه، بل هتستخدم `ALTER TABLE` لإضافة عمود جديد.
- `TRUNCATE TABLE`: ده بيستخدم لما تحب تفضي الجدول تماماً من البيانات بس تحافظ على الهيكل والـ Structure بتاعه زي ما هو. كأنك بتمسح الكلام المكتوب على السبورة بس بتسيب السبورة نفسها معلقة على الحيطة جاهزة للكتابة من جديد.
- `DROP TABLE`: ده بقى الأمر المدمر. بيمسح البيانات وهيكل الجدول بالكامل من الهارد ديسك ومن الـ System Catalog. كأنك فككت السبورة نفسها ورميتها في الزبالة.

الكود اللي جاي بيوريك إزاي تستخدم الأوامر دي لتغيير هيكل مستخدمين Netflix.

```sql
-- Creating the netflix_users table
CREATE TABLE netflix_users (
    user_id INT PRIMARY KEY,
    email VARCHAR(100) UNIQUE NOT NULL,
    plan_type VARCHAR(20) DEFAULT 'Basic'
);

-- Adding a new column for profile pin using ALTER
ALTER TABLE netflix_users 
ADD COLUMN profile_pin VARCHAR(4);

-- Clearing all records quickly using TRUNCATE (structure remains)
TRUNCATE TABLE netflix_users;

-- Completely destroying the table and its structure using DROP
DROP TABLE netflix_users;
```

#### مثال 1: تعديل الجداول الكبيرة في الإنتاج (Live Alteration)
في قواعد البيانات الضخمة اللي فيها ملايين الصفوف، تشغيل أمر `ALTER TABLE` لإضافة عمود بقيمة افتراضية (Default Value) ممكن يكون كابوس حقيقي. الداتابيز ممكن تضطر تقفل الجدول كله (Table Lock) عشان تملأ العمود الجديد بالقيمة الافتراضية لكل مستخدم، وده هيخلي الأبليكيشن يقف تماماً (Downtime). عشان كده المهندسين بيفضلوا يضيفوا العمود كـ Nullable الأول بدون قيمة افتراضية، أو بيستخدموا أدوات خارجية بتعمل الـ Migration في الخلفية بدون حجب القراءة والكتابة.

#### مثال 2: تنظيف البيانات بعد الـ Integration Tests
لما بنكون بنشغل اختبارات آلية (Automated Tests) للسيستم، بنحتاج نملأ الجداول ببيانات تجريبية ونختبرها، وبعد ما نخلص التيست بنحتاج ننظف الجداول عشان تستقبل التيست اللي بعده. في الحالة دي، استخدام `TRUNCATE` بيكون أسرع بآلاف المرات من استخدام `DELETE` لأنه بيفضي الصفحات التخزينية مباشرة من غير ما يعدي على الصفوف صف صف.

### الفايدة الانترفيوية
What is the difference between CREATE, ALTER, DROP, and TRUNCATE in SQL DDL?
**الإجابة المثالية:**
الأوامر دي بتتعامل مع بنية الجدول (Schema Structure):
- `CREATE` يُستخدم لإنشاء جدول جديد بتحديد أسمائه وأنواع بياناته والـ Constraints المفروضة عليه.
- `ALTER` يُستخدم لتعديل هيكل جدول موجود بالفعل، مثل إضافة أعمدة جديدة، أو مسح أعمدة، أو تغيير نوع البيانات، أو تعديل القيود دون فقدان البيانات الحالية.
- `TRUNCATE` يُفرغ الجدول تماماً من محتواه من البيانات ولكنه يحتفظ ببنيته وهيكله كما هو للاستخدام المستقبلي، وهو أسرع بكثير من الحذف العادي لأنه يمسح مؤشرات البيانات مباشرة.
- `DROP` يقوم بحذف الجدول بأكمله (البيانات والهيكل والقيود والمؤشرات المرتبطة به) من نظام الملفات تماماً.

## Q13 — إيه الفرق بين DROP و TRUNCATE و DELETE؟ (سؤال المليون دولار)

### أصل الحكاية
لو سألت أي مهندس قواعد بيانات عن أشهر سؤال بيتكرر في الإنترفيوهات، هيقولك فوراً: "إيه الفرق بين DROP و TRUNCATE و DELETE؟". مع إن التلاتة وظيفتهم إزالة البيانات، إلا إن طريقتهم وتأثيرهم على النظام مختلفين تماماً:
1. **أمر `DELETE` (DML)**: ده زي الممحاة الدقيقة. بتسمحلك تمسح صفوف معينة بناءً على شرط `WHERE` (مثلاً: امسح الطلبات الملغية بس). العملية دي بتسجل كل صف بيتمسح في الـ Transaction Logs (Row-level logging) عشان كده هي عملية بطيئة في الجداول الكبيرة، لكن ميزتها إنك تقدر تعمل لها `ROLLBACK` وتراجع عنها لو كنت جوة Transaction. كمان `DELETE` مش بتصفر عداد الـ Auto-Increment (لو مسحت آخر صف رقمه 10، الصف الجديد هياخد رقم 11).
2. **أمر `TRUNCATE` (DDL)**: ده زي القنبلة الموجهة. بيمسح كل الصفوف اللي في الجدول دفعة واحدة. مش بيقبل شرط `WHERE` ومينفعش تمسح بيه جزء من البيانات. السرعة بتاعته خرافية لأنه مش بيمسح صف صف، هو بيروح يلغي تخصيص صفحات التخزين (Data Pages Deallocation) للجدول في الهارد ديسك. وبيرجع يصفر عداد الـ Auto-Increment للبداية. في أغلب قواعد البيانات (زي MySQL)، الـ `TRUNCATE` بتعمل Auto-Commit تلقائي، يعني مقدرش أعمل لها `ROLLBACK` وأرجع البيانات لو راحت.
3. **أمر `DROP` (DDL)**: ده بقى البلدوزر. بيمسح البيانات وهيكل الجدول بالكامل. كأن الجدول مكنش موجود أصلاً في النظام. لو جربت تعمل استعلام على الجدول بعد الـ `DROP` هيطلعلك خطأ "Table does not exist". ولا يمكن التراجع عنها بأي شكل.

الجدول اللي جاي بيلخص الفروق الجوهرية دي:

| وجه المقارنة | DELETE | TRUNCATE | DROP |
| :--- | :--- | :--- | :--- |
| **التصنيف** | DML (Data Manipulation) | DDL (Data Definition) | DDL (Data Definition) |
| **شرط WHERE** | مدعوم (تحديد صفوف معينة) | غير مدعوم (يمسح كل شيء) | غير مدعوم |
| **السرعة** | بطيء (يمسح صفاً صفاً) | سريع جداً (يلغي حجز الصفحات) | سريع جداً (يمسح الهيكل والبيانات) |
| **التراجع (Rollback)** | مدعوم | غير مدعوم (في أغلب الأنظمة) | غير مدعوم نهائياً |
| **الـ Auto-Increment** | لا يعاد تعيينه (يستمر في العد) | يعاد تعيينه للصفر | يُحذف العداد والجدول كله |
| **المساحة التخزينية** | لا يحرر المساحة فوراً للسيستم | يحرر المساحة المخصصة فوراً | يحرر كل المساحة ويحذف الجدول |

```sql
-- DELETE: Deletes specific rows, generates rollback logs, slow
DELETE FROM user_activity_logs 
WHERE log_date < '2025-01-01';

-- TRUNCATE: Deletes all rows, resets identity counter, fast
TRUNCATE TABLE user_activity_logs;

-- DROP: Destroys both rows and table definition permanently
DROP TABLE user_activity_logs;
```

#### مثال 1: تنظيف جدول الـ Session Tokens المتضخم
تخيل عندك جدول بيخزن الـ Web Session Tokens المؤقتة ووصل حجمه لـ 80 مليون صف، والـ Disk عندك قرب يتملي ومحتاج تفضيه فوراً. لو كتبت `DELETE FROM sessions;` السيرفر ممكن يقع أو يهنج بسبب محاولة تسجيل 80 مليون عملية حذف في الـ Transaction Logs (WAL)، وممكن الـ Transaction Log نفسه يملأ الهارد ديسك ويوقف السيستم. الحل الاحترافي السريع والآمن هنا هو: `TRUNCATE TABLE sessions;` لأنه هيفضي المساحة في أقل من ثانية وبدون تحميل على المعالج.

#### مثال 2: استرجاع البيانات المحذوفة بالخطأ
تخيل لو شغال على سيستم البنك وعملت تعديل أو مسحت بالخطأ بيانات عملاء بـ `DELETE`. لو إنت لسه مقفلتش الـ Transaction، تقدر فوراً تكتب `ROLLBACK;` وكل البيانات هترجع مكانها كأن شيئاً لم يكن. لكن لو استخدمت `TRUNCATE` بالخطأ، العملية دي بتعمل Auto-Commit والبيانات بتتمسح نهائياً، والحل الوحيد وقتها هيكون استرجاع آخر نسخة احتياطية (Backup) للبنك، ودي عملية معقدة ومكلفة جداً.

### الفايدة الانترفيوية
What is the difference between DELETE, TRUNCATE, and DROP in SQL?
**الإجابة المثالية:**
الفرق يكمن في طريقة الحذف وتسجيل العمليات وتأثيرها على البنية التحتية:
1. **DELETE** هي أمر DML، تقوم بحذف صفوف محددة باستخدام شرط `WHERE`، وهي عملية بطيئة لأنها تسجل عمليات الحذف صفاً بصف في الـ Transaction Logs (Row-level Logging)، مما يسمح بالتراجع عنها (Rollback)، ولا تعيد تعيين عداد الـ Auto-Increment.
2. **TRUNCATE** هي أمر DDL، تقوم بحذف جميع البيانات من الجدول دفعة واحدة عن طريق إلغاء تخصيص صفحات التخزين (Data Pages)، وهي سريعة جداً ولا تقبل شرط `WHERE` ولا تسجل الحذف صفاً بصف، وتعيد تعيين عداد الـ Auto-Increment، وغالباً لا يمكن التراجع عنها.
3. **DROP** هي أمر DDL، تقوم بحذف الجدول بالكامل (البيانات والـ Structure والـ Indexes المرتبطة به) من قاعدة البيانات نهائياً، ولا يمكن التراجع عنها.

## Q14 — إيه هي أوامر الـ DML (INSERT, UPDATE, DELETE) وإزاي بتتعامل مع الـ Constraints؟

### أصل الحكاية
تخيل إنك بتبني نظام لتطبيق طلب وتوصيل رحلات (Ride-Hailing App) زي Uber أو Careem. في النظام ده، البيانات بتتحرك وتتغير في كل ثانية مع كل رحلة جديدة بيطلبها مستخدم أو بيقبلها كابتن. دي وظيفة أوامر الـ DML:
1. **إدخال البيانات (`INSERT`)**: أول ما العميل يفتح الأبليكيشن ويطلب رحلة، التطبيق بينفذ أمر `INSERT INTO trips` عشان يضيف سجل جديد للرحلة بحالة 'REQUESTED' مع تحديد العميل والموقع وسعر الرحلة المقدر.
2. **تعديل البيانات (`UPDATE`)**: لما كابتن يقبل الرحلة، السيرفر بينفذ أمر `UPDATE trips SET driver_id = X, status = 'ACCEPTED' WHERE trip_id = Y` عشان يحدث بيانات الرحلة المحددة دي فقط.
3. **حذف البيانات (`DELETE`)**: لو العميل قرر يلغي الرحلة قبل ما الكابتن يتحرك، السيستم ممكن يمسح السجل بـ `DELETE FROM trips WHERE trip_id = Y` (أو يعمل لها Soft Delete كما سنشرح).

لكن الـ Database مش بتسيب أوامر الـ DML تعدل براحتها؛ هي دايماً بتراقب الـ Constraints (القيود) اللي حددناها في الـ DDL عشان تحمي جودة وسلامة البيانات (Data Integrity):
- لو جيت تعمل `INSERT` لرحلة وما حددتش الـ `passenger_id` والعمود ده عليه قيد `NOT NULL`، الداتابيز هترفض الطلب فوراً.
- لو جيت تعمل `UPDATE` لحالة الرحلة وتخليها 'COMPLETED' والرحلة لسه مفيهاش كابتن (`driver_id IS NULL`)، وكان عندك قيد فحص `CHECK` بيمنع ده، العملية هتفشل.
- لو جيت تعمل `DELETE` لكابتن من جدول الكباتن `drivers` وهو عنده رحلات مسجلة باسمه في جدول الرحلات، الداتابيز هترفض الحذف فوراً لحماية جدول الرحلات من وجود معرفات يتيمة (إلا لو كنت ضابط القيد على `ON DELETE CASCADE`).

```sql
-- INSERT: Creating a new trip record
INSERT INTO trips (trip_id, passenger_id, status, fare) 
VALUES (7845, 9021, 'REQUESTED', 150.00);

-- UPDATE: Assigning a driver and changing status when accepted
UPDATE trips 
SET driver_id = 4410, status = 'ACCEPTED' 
WHERE trip_id = 7845;

-- DELETE: Removing a trip record, only if it doesn't violate Foreign Key rules
DELETE FROM trips 
WHERE trip_id = 7845;
```

#### مثال 1: حماية البيانات باستخدام الـ Soft Delete بدل الـ Hard Delete
في التطبيقات الحقيقية زي Uber، تقريباً مفيش بيانات بتتمسح فعلياً من قواعد البيانات باستخدام أمر `DELETE` العادي (Hard Delete) لأن مسح البيانات بيفقد الشركة القدرة على تحليل سلوك المستخدمين وعمل التقارير المالية. البديل هو الـ "Soft Delete"، واللي بنضيف عمود للجدول اسمه `is_deleted` (نوعه Boolean) أو `deleted_at` (نوعه Timestamp). ولما العميل يلغي حسابه أو رحلته، بنعمل `UPDATE` للحقل ده ونخليه `TRUE` أو نسجل الوقت الحالي، وجميع استعلامات الـ `SELECT` بعد كده بتستثني الصفوف دي بـ `WHERE is_deleted = FALSE`.

#### مثال 2: خطورة نسيان شرط الـ WHERE في التعديل والحذف
تخيل مهندس مبتدئ عايز يعدل سعر رحلة معينة عشان العميل اشتكى، فكتب الكود ده:
`UPDATE trips SET fare = 20.00;` ونسي يكتب `WHERE trip_id = 7845;`. الكارثة هنا إن قاعدة البيانات هتنفذ الأمر على الجدول كله! وهتخلي سعر كل الرحلات التاريخية والحالية في الداتابيز 20 جنيه. نفس الكارثة هتحصل لو نفذ `DELETE FROM trips;` بدون شرط، هيمسح كل الرحلات. عشان كده أغلب قواعد البيانات وأدوات الـ Client بيكون فيها حماية مفعلة تمنع تشغيل الـ UPDATE/DELETE بدون WHERE بشكل افتراضي (Safe Updates mode).

### الفايدة الانترفيوية
Explain DML operations and how they interact with schema constraints in relational databases.
**الإجابة المثالية:**
تُستخدم أوامر DML (INSERT, UPDATE, DELETE) لإضافة وتعديل وحذف البيانات الفعلية المخزنة داخل الجداول. أثناء تنفيذ الأوامر دي، يقوم محرك قاعدة البيانات بالتحقق الصارم من قيود الجدول (Schema Constraints) للتأكد من عدم تلف تكامل البيانات (Data Integrity). فمثلاً، يفشل أمر `INSERT` إذا انتهك قيد المفتاح الأساسي الفريد (Unique Constraint)، ويفشل أمر `UPDATE` إذا حاول إدخال قيمة تنتهك قيد التحقق (CHECK Constraint)، ويفشل أمر `DELETE` إذا حاول مسح سجل ترتبط به سجلات أخرى في جداول فرعية عن طريق مفتاح خارجي (Foreign Key Constraint) مفروض عليه قاعدة `RESTRICT`.

## Q15 — إيه هو الترتيب الفعلي لتنفيذ استعلام الـ SQL؟ (SQL Execution Order) وليه ده بيفرق معاك؟

### أصل الحكاية
تخيل إنك بتكتب استعلام SQL عشان تجيب أعلى 5 عملاء عملوا طلبات شراء بقيمة تزيد عن 1000 جنيه، وترتبهم من الأكبر للأصغر. الكود هيتكتب كده بالترتيب اللي إحنا متعودين عليه:
```sql
SELECT customer_id, SUM(order_amount) AS total_spent
FROM orders
WHERE status = 'Completed'
GROUP BY customer_id
HAVING SUM(order_amount) > 1000
ORDER BY total_spent DESC
LIMIT 5;
```
إحنا كبشر بنقرأ الاستعلام ده من فوق لتحت: بنشوف الـ `SELECT` الأول، بعدين الـ `FROM` والـ `WHERE` وهكذا.
لكن بالنسبة للـ Database Engine (محرك قاعدة البيانات)، الترتيب ده مختلف تماماً! المحرك مش بيبدأ بالـ `SELECT`؛ هو بيبدأ بتجميع الداتا وتصفيتها الأول قبل ما يقرر هيعرض إيه.
الترتيب الفعلي لتنفيذ الاستعلام تحت الغطاء بيكون كالتالي:

1. **`FROM` & `JOINs`**: أول حاجة الداتابيز بتعملها هي تحديد الجداول اللي هتقرأ منها، وتدمجهم لو فيه Joins. (عايزين نقرأ من جدول `orders`).
2. **`WHERE`**: بعد تحديد الجدول، بنفلتر الصفوف الفردية عشان نقلل حجم الداتا اللي هنتعامل معاها. (هنا هنستبعد كل الأوردرات الملغية ونخلي الـ Completed بس).
3. **`GROUP BY`**: بنجمع الصفوف المتبقية في مجموعات بناءً على العمود المحدد. (هنقسم الأوردرات لـ buckets كل bucket يخص `customer_id` معين).
4. **`HAVING`**: بنفلتر المجموعات اللي نتجت بعد الـ Grouping. (هنستبعد أي عميل مجموع أوردراته أقل من 1000 جنيه).
5. **`SELECT`**: أخيراً! هنا الداتابيز بتحدد إيه الأعمدة اللي هتظهر وتطبق العمليات الحسابية والـ Aliases (الأسماء المستعارة زي `total_spent`).
6. **`DISTINCT`**: لو فيه طلب لمنع التكرار، بيتم تصفية الصفوف المكررة في الخطوة دي.
7. **`ORDER BY`**: بيتم فرز وترتيب الناتج النهائي بناءً على الأعمدة المحددة. (هنرتب العملاء تنازلياً حسب الـ `total_spent`).
8. **`LIMIT` / `OFFSET`**: في النهاية خالص، بيتم قص الناتج وعرض العدد المطلوب فقط وإهمال الباقي. (هناخد أول 5 عملاء بس).

فهم الترتيب ده بيفرق معاك جداً وأنت بتكتب كود، لأنه بيحميك من أخطاء بناء الاستعلامات وبيخليك تفهم ليه الداتابيز بترفض بعض الشروط.

```sql
-- Demonstrating the logical flow and why aliases can be used in ORDER BY but not WHERE
-- 1. FROM orders
-- 2. WHERE status = 'Completed'
-- 3. GROUP BY customer_id
-- 4. HAVING SUM(order_amount) > 1000
-- 5. SELECT customer_id, SUM(order_amount) AS total_spent
-- 6. ORDER BY total_spent DESC
-- 7. LIMIT 5
SELECT customer_id, SUM(order_amount) AS total_spent
FROM orders
WHERE status = 'Completed'
GROUP BY customer_id
HAVING SUM(order_amount) > 1000
ORDER BY total_spent DESC
LIMIT 5;
```

#### مثال 1: الخطأ الشهير في استخدام الـ Alias داخل شرط الـ WHERE
تخيل لو كتبت الاستعلام ده:
`SELECT customer_id, SUM(order_amount) AS total FROM orders WHERE total > 1000;`
الـ Database فوراً هتطلعلك Error وتقولك: `Unknown column 'total' in where clause`. السبب بقى واضح دلوقتي: الـ `WHERE` بتتنفذ في الخطوة رقم 2، بينما الـ `SELECT` (اللي بتعرف الاسم المستعار `total`) بتتنفذ في الخطوة رقم 5! الداتابيز لسه متعرفش يعني إيه `total` وقت تشغيل الـ `WHERE`. عشان تحل ده، لازم تستخدم الـ `HAVING` لأنها بتتنفذ بعد ما الـ Aggregation يتحسب.

#### مثال 2: استخدام الـ Alias في الـ ORDER BY
على العكس تماماً، لو كتبت:
`SELECT customer_id, SUM(order_amount) AS total FROM orders GROUP BY customer_id ORDER BY total DESC;`
الاستعلام ده هيشتغل 100% بدون أي مشاكل. السبب هو إن الـ `ORDER BY` بتتنفذ في الخطوة رقم 7، يعني بعد ما الـ `SELECT` (الخطوة 5) اتنفذت وعرفّت الاسم المستعار `total` وحسبت قيمته.

### الفايدة الانترفيوية
What is the logical order of query execution in SQL, and how does it affect the usage of column aliases?
**الإجابة المثالية:**
الترتيب المنطقي لتنفيذ استعلام SQL هو:
`FROM` ➔ `ON/JOIN` ➔ `WHERE` ➔ `GROUP BY` ➔ `HAVING` ➔ `SELECT` ➔ `DISTINCT` ➔ `ORDER BY` ➔ `LIMIT/OFFSET`.
الترتيب ده بيأثر بشكل مباشر على استخدام الأسماء المستعارة (Aliases)؛ واللي لا يمكننا استخدام Alias تم تعريفه في بند الـ `SELECT` داخل بند الـ `WHERE` لأن بند الـ `WHERE` يتم تقييمه وتنفيذه قبل مرحلة الـ `SELECT` بعدة خطوات. في المقابل، يمكننا استخدام الـ Alias داخل بند الـ `ORDER BY` لأن عملية الفرز والترتيب تتم في مرحلة متأخرة بعد اكتمال مرحلة الـ `SELECT` وتحديد قيم الأعمدة والأسماء المستعارة.

## Q16 — إيه الفرق الجوهري بين WHERE و HAVING؟ وإمتى بتتدخل كل واحدة؟

### أصل الحكاية
تخيل إنك شغال في نظام تقارير المبيعات لمتجر إلكتروني. المدير طلب منك تقرير يوضح "إجمالي المبيعات لكل منتج، بس للمنتجات اللي سعرها فوق 100 جنيه، وعايز فقط المنتجات اللي حققت إجمالي مبيعات أكتر من 5000 جنيه في الآخر".
عشان تعمل الاستعلام ده، هتحتاج تستخدم الـ `WHERE` والـ `HAVING` مع بعض في نفس الاستعلام. ليه؟ لأن كل واحدة منهم بتعمل فلترة على مستوى مختلف تماماً:
- **`WHERE` (فلترة على مستوى الصف الفردي - Row-Level Filter)**: دي بتشتغل قبل التجميع (Before Aggregation). بتعدي على صفوف الجدول صف صف وتفحص شرط السعر: "هل سعر المنتج ده في الفاتورة دي أكبر من 100 جنيه؟". الصفوف اللي بتوافق الشرط بتدخل معانا للخطوة اللي بعدها، والصفوف التانية بتستبعد تماماً. الـ `WHERE` متعرفش تتعامل مع الدوال التجميعية زي `SUM` أو `AVG` لأنها بتبص على صف واحد في المرة، مش مجموعة صفوف.
- **`HAVING` (فلترة على مستوى المجموعات - Group-Level Filter)**: دي بتشتغل بعد التجميع (After Aggregation / Group By). بعد ما جمعنا مبيعات كل منتج وحسبنا المجموع (`SUM`) لكل مجموعة، الـ `HAVING` بتيجي تفحص المجموع النهائي للمجموعة كلها: "هل إجمالي مبيعات المنتج ده بكل فواتيره عدى الـ 5000 جنيه؟". المجموعات اللي بتوافق الشرط بتظهر في النتيجة النهائية، والباقي بيتحذف.

الكود اللي جاي بيوضح إزاي بنستخدمهم مع بعض لحل طلب المدير.

```sql
-- Combining WHERE (filters rows first) and HAVING (filters groups later)
SELECT 
    product_id, 
    SUM(quantity * unit_price) AS total_sales
FROM order_items
WHERE unit_price > 100.00                   -- Row-level: filter individual items before grouping
GROUP BY product_id
HAVING SUM(quantity * unit_price) > 5000.00; -- Group-level: filter product groups after summing
```

#### مثال 1: كتابة تصفية غير تجميعية في الـ HAVING (كارثة أداء)
تخيل لو كتبت الاستعلام كده:
`SELECT product_id, SUM(quantity) FROM order_items GROUP BY product_id HAVING product_status = 'Active';`
مع إن الاستعلام ده ممكن يشتغل في بعض قواعد البيانات، إلا إنه يعتبر جريمة في حق الأداء (Performance). إنت هنا بتجبر الداتابيز تعمل Grouping وتجمع كميات لكل المنتجات النشطة وغير النشطة الأول، وبعدين تعمل فلترة وتستبعد المنتجات غير النشطة بـ `HAVING`. الصح إنك تحط `WHERE product_status = 'Active'` عشان تفلتر المنتجات من البداية وتقلل عدد الصفوف اللي هتعمل لها Grouping وتوفر مجهود السيرفر.

#### مثال 2: استخدام الـ Aggregate functions داخل الـ WHERE
لو حاولت تكتب الاستعلام ده:
`SELECT * FROM employees WHERE salary > AVG(salary);`
الداتابيز هتطلعلك خطأ فوراً لأن الـ `WHERE` مش بتسمح باستخدام الدوال التجميعية زي `AVG` مباشرة جواها. عشان تحسب المتوسط، لازم الداتابيز تجمع كل الموظفين الأول، والـ `WHERE` مش وظيفتها التجميع. الحل هنا هو استخدام استعلام فرعي (Subquery) يحسب المتوسط الأول كقيمة منفردة، وبعدين الـ `WHERE` تقارن بيها:
`WHERE salary > (SELECT AVG(salary) FROM employees);`

### الفايدة الانترفيوية
What is the difference between the WHERE and HAVING clauses in SQL? Can they be used without a GROUP BY?
**الإجابة المثالية:**
الفرق الجوهري هو أن بند `WHERE` يُستخدم لتصفية الصفوف الفردية قبل عملية التجميع (Before Aggregation)، ولا يمكن استخدامه مع الدوال التجميعية (Aggregate Functions). بينما بند `HAVING` يُستخدم لتصفية المجموعات الناتجة بعد عملية التجميع (After Aggregation) ويعمل مباشرة على نتائج الدوال التجميعية مثل `SUM` و `COUNT`.
نعم، يمكن استخدام `WHERE` بدون `GROUP BY` وهو الاستخدام الطبيعي لها لتصفية الصفوف. أما بالنسبة لـ `HAVING` فيمكن استخدامها تقنياً بدون `GROUP BY` في معيار SQL، وفي الحالة دي تعامل الجدول بأكمله كمجموعة واحدة (Single Group)، ولكن الاستخدام الشائع والعملي لها هو أن تأتي مقترنة بـ `GROUP BY` لتصفية المجموعات.

## Q17 — إيه هي الـ DISTINCT؟ وإزاي بتأثر على أداء الاستعلامات الكبيرة؟

### أصل الحكاية
تخيل إنك بتبني محرك البحث في تطبيق توصيل طلبات ومطاعم شهير زي طلبات أو HungerStation. المدير طلب منك تعرض لستة بكل المدن الفريدة (Unique Cities) اللي فيها مطاعم نشطة عشان نعرضها في قائمة اختيار المدينة للمستخدم.
بما إن عندنا مثلاً 500,000 مطعم في الداتابيز، لو استعلمنا عن عمود المدينة من جدول المطاعم مباشرة، هيطلع لنا اسم مدينة "القاهرة" متكرر 100,000 مرة، و"الإسكندرية" 50,000 مرة وهكذا.
عشان نحل ده بنستخدم أمر `DISTINCT` اللي بيقوم بتصفية المتكرر وعرض كل مدينة مرة واحدة بس:
`SELECT DISTINCT city FROM restaurants WHERE status = 'Active';`

لكن كمهندس برمجيات، لازم تسأل نفسك: "إيه اللي بيحصل تحت الغطاء (Under the hood) لما الداتابيز تنفذ `DISTINCT`؟"
قاعدة البيانات عشان تشيل التكرار لازم تعمل واحدة من اتنين:
1. **الفرز (Sorting)**: ترتب كل البيانات اللي راجعة أبجدياً أو رقمياً، وبكده القيم المتشابهة هتيجي ورا بعض فتقدر تحذف المكرر بسهولة.
2. **جدول الهاش المؤقت (Temp Hash Table)**: تبني Hash Table في الذاكرة (RAM) وكل ما تقرأ صف تشوف لو قيمته موجودة في الـ Hash Table ولا لأ. لو مش موجودة تضيفها وتطلّعها في الناتج، ولو موجودة تهملها.

في الجداول الكبيرة جداً اللي فيها ملايين الصفوف، لو العمود اللي بتعمل عليه `DISTINCT` مش مفهرس (Not Indexed)، العملية دي هتكون بطيئة جداً ومستهلكة للـ CPU والـ RAM، وممكن تجبر الداتابيز تكتب ملفات مؤقتة على الهارد ديسك (Disk Sorting) لو الذاكرة مش مكفية، وده بيوقع أداء السيرفر تماماً.

```sql
-- Using DISTINCT to fetch unique cities with active restaurants
SELECT DISTINCT city 
FROM restaurants 
WHERE status = 'Active';
```

#### مثال 1: بديل الـ DISTINCT باستخدام الـ GROUP BY
في كواليس محركات قواعد البيانات (Database Optimizers)، تشغيل الاستعلام بـ `DISTINCT` زي:
`SELECT DISTINCT city FROM restaurants;`
بيتم تحويله داخلياً لنفس خطة تنفيذ الاستعلام باستخدام `GROUP BY`:
`SELECT city FROM restaurants GROUP BY city;`
الاثنين ليهم نفس الأداء ونفس استهلاك الموارد بالظبط. لو مش محتاج تحسب Aggregates، يفضل تستخدم `DISTINCT` لأنها أوضح في القراءة للمطورين اللي بيقروا الكود وراك.

#### مثال 2: خطأ استخدام DISTINCT كمسكن للألم في الـ Joins
ساعات المطورين بيقعوا في مشكلة إنهم يعملوا `JOIN` بين جدولين (مثلاً المستخدمين والطلبات) وبسبب شرط ربط خاطئ تظهر الداتا مكررة في الناتج. كحل سريع وسهل، المطور يروح كاتب `DISTINCT` في أول الاستعلام عشان يمسح التكرار. ده حل كارثي وقت الـ Scale! لأن الداتابيز هتضطر تعمل Join وتطلع ملايين الصفوف المكررة الأول، وبعدين تستهلك موارد السيرفر كله في ترتيبهم وحذف المكرر. الحل الصح هو تصحيح علاقة الـ Join أو استخدام `EXISTS` لمنع حدوث التكرار من الأساس.

### الفايدة الانترفيوية
What is the purpose of SELECT DISTINCT, and what are the performance implications when executing it on non-indexed columns in large tables?
**الإجابة المثالية:**
تُستخدم `DISTINCT` لإزالة السجلات المكررة من ناتج الاستعلام وإرجاع القيم الفريدة فقط. لتحقيق ذلك، يقوم محرك قاعدة البيانات بعملية فرز للبيانات (Sorting) أو بناء جدول هاش مؤقت (Temporary Hash Table) في الذاكرة. إذا تم تشغيل `DISTINCT` على أعمدة غير مفهرسة (Non-indexed) في جداول ضخمة، فإن ذلك يتسبب في بطء شديد واستهلاك كبير للمعالج والذاكرة، وقد يضطر المحرك للكتابة على القرص الصلب (Disk Spilling) لفرز البيانات. لتفادي ده، لازم نتأكد من وجود فهرس (Index) على الأعمدة المستخدمة، مما يسمح للمحرك بعمل Index Scan وجلب القيم الفريدة مباشرة دون الحاجة لفرز البيانات يدوياً.

## Q18 — إيه هي الـ Aggregate Functions (COUNT, SUM, AVG, MIN, MAX)؟ وإزاي بتتعامل مع الـ NULL؟

### أصل الحكاية
تخيل إنك المهندس المسؤول عن نظام المدفوعات والتحويلات المالية لتطبيق دمج بنكي زي Instapay أو فوري. المدير المالي طلب منك تقرير يومي سريع فيه:
- إجمالي عدد المعاملات اللي تمت النهارده.
- إجمالي المبالغ اللي اتحولت في السيستم.
- متوسط قيمة المعاملة الواحدة.
- أصغر معاملة وأكبر معاملة تمت النهارده.

عشان تعمل ده، مش هتقرأ المعاملات وتجمعها في السيرفر عندك؛ إنت بتخلي الـ Database تعمل ده بكفاءة عالية جداً على مستوى الـ Storage باستخدام **الدوال التجميعية (Aggregate Functions)**:
- `COUNT()`: لعد الصفوف.
- `SUM()`: لجمع القيم الرقمية.
- `AVG()`: لحساب المتوسط الحسابي.
- `MIN()` & `MAX()`: لجلب أصغر وأكبر قيمة.

لكن هنا بيظهر التحدي الحقيقي اللي بيقع فيه مهندسين كتير: **إزاي الدوال دي بتتعامل مع القيم الفارغة `NULL`؟**
القاعدة الذهبية في قواعد البيانات العلائقية هي: **جميع الدوال التجميعية (باستثناء `COUNT(*)`) بتتجاهل القيم الفارغة `NULL` تماماً في حساباتها**.
لو عندك جدول فيه 5 صفوف لعمود العمولات `commission_fee` وقيمها كالتالي:
`[10, 20, NULL, 30, NULL]`
- لو شغلت `COUNT(commission_fee)`، الناتج هيكون **3** وليس 5.
- لو شغلت `SUM(commission_fee)`، الناتج هيكون `10 + 20 + 30 = 60`.
- لو شغلت `AVG(commission_fee)`، الكارثة هنا إن الناتج هيكون `60 / 3 = 20`! الداتابيز جمعت القيم وقسمتها على عدد الصفوف غير الفارغة (3)، وأهملت الصفين الـ NULL تماماً من القسمة. لو البزنس بيعتبر الـ NULL ده معناه عمولة صفر وعايز تحسب المتوسط الحقيقي لكل المعاملات الخمسة، الحسبة دي هتكون غلط تماماً وهتخسر البنك فلوس في التقارير.

```sql
-- Demostrating how Aggregate Functions handle NULLs
SELECT 
    COUNT(*) AS total_rows,                         -- Counts all 5 rows (includes NULLs)
    COUNT(commission_fee) AS non_null_count,        -- Counts only 3 rows (ignores NULLs)
    SUM(commission_fee) AS total_commission,        -- Sums non-NULL values (= 60.00)
    AVG(commission_fee) AS raw_avg_commission,      -- Calculates 60 / 3 = 20.00 (ignores NULLs)
    AVG(COALESCE(commission_fee, 0)) AS real_avg    -- Replaces NULL with 0, calculates 60 / 5 = 12.00
FROM transactions;
```

#### مثال 1: حساب متوسط التقييمات في تطبيق مطاعم
لو بتبني تطبيق زي طلبات، وعندك جدول للتقييمات `reviews` فيه عمود `rating` بيقبل قيم من 1 لـ 5، وبيقبل `NULL` لو المستخدم كتب تعليق نصي بس وساب النجوم فاضية. لو حسبت المتوسط بـ `AVG(rating)`، الداتابيز هتتجاهل الـ NULLs وتقسم المجموع على عدد الناس اللي سابت نجوم فعلياً، وده صح ومطلوب. لكن لو كنت بتتعامل مع نسبة خصم وتعتبر الـ NULL يعني الخصم 0%، لازم تستخدم `COALESCE(discount, 0)` عشان تدخل الأصفار في حساب المتوسط الحسابي للخصومات.

#### مثال 2: الفرق الجوهري بين COUNT(*) و COUNT(column_name) وقت الـ Scale
في الجداول المليونية، تشغيل `SELECT COUNT(*) FROM orders;` بيكون سريع جداً ومحسن داخلياً بواسطة الـ Database Optimizer؛ لأنه مش بيبص على محتوى الأعمدة، هو مجرد بيعد الصفوف بأسرع طريقة (ساعات بيقرأ الفهرس الأصغر حجماً مباشرة). لكن لو كتبت `SELECT COUNT(coupon_code) FROM orders;`، الداتابيز مجبرة تفحص قيمة عمود الـ `coupon_code` في كل صف من الملايين صفوف عشان تتأكد إنها مش `NULL` قبل ما تعدها، وده بيعمل بطء واستهلاك موارد أكبر بكتير على السيرفر.

### الفايدة الانترفيوية
How do SQL aggregate functions handle NULL values, and what is the difference between COUNT(*) and COUNT(column_name)?
**الإجابة المثالية:**
جميع الدوال التجميعية (مثل `SUM`, `AVG`, `MIN`, `MAX`) وكذلك `COUNT(column)` تتجاهل القيم الفارغة `NULL` تماماً أثناء الحساب. فمثلاً، عند حساب `AVG(column)`، يتم تقسيم المجموع على عدد الصفوف اللي مش بتحتوي على قيم فارغة فقط.
أما الفرق بين `COUNT(*)` و `COUNT(column)`:
- `COUNT(*)` تقوم بعدّ كافة الصفوف في الجدول بغض النظر عن محتواها (حتى لو كانت الصفوف بالكامل تحتوي على قيم `NULL` أو مكررة)، وتكون محسنة جداً في الأداء لأن المحرك لا يحتاج لفحص قيم الأعمدة.
- `COUNT(column)` تقوم بعدّ الصفوف اللي بتحتوي على قيم غير فارغة (Not NULL) فقط في العمود المحدد ده، وده بيجبر المحرك على فحص قيمة العمود صفاً بصف.

## Q19 — إيه هي الـ GROUP BY؟ وإزاي بتشكل مجموعات البيانات مع الـ Aggregates؟

### أصل الحكاية
تخيل إنك شغال في سيستم إداري لشركة Uber. نائب الرئيس طلب منك تقرير يوضح "عدد الرحلات الكلي وإجمالي الدخل اللي حققناه في كل مدينة على حدة".
لو بصيت لجدول الرحلات `trips` هتلاقيه جدول ضخم فيه ملايين الصفوف وكل صف يمثل رحلة معينة. إحنا هنا مش عايزين نعرض الرحلات دي كلها؛ إحنا عايزين نجمع الرحلات دي في Buckets (مجموعات) بناءً على عمود المدينة `city_id` ونطلع صف ملخص واحد لكل مدينة.
دي وظيفة الـ `GROUP BY` الأساسية. لما الداتابيز بتشوف `GROUP BY city_id` بتعمل الآتي:
1. تقسم الجدول لمجموعات فرعية مؤقتة في الذاكرة بناءً على القيم الفريدة في عمود الـ `city_id` (مجموعة للقاهرة، مجموعة للرياض، مجموعة لدبي).
2. تطبق الدوال التجميعية (Aggregates) المطلوبة في الـ `SELECT` على كل مجموعة بشكل مستقل (تعد الرحلات في مجموعة القاهرة بـ `COUNT` وتجمع أسعارها بـ `SUM`).
3. تخرج صف واحد نهائي لكل مجموعة يمثل الملخص.

لكن تشغيل `GROUP BY` بيجي مع قاعدة ذهبية صارمة جداً ومصدر خطأ شهير لمعظم المطورين: **أي عمود تضعه في بند الـ `SELECT` ولا يقع تحت تأثير دالة تجميعية (Aggregate Function) لازم تحطه في بند الـ `GROUP BY`**.
ليه؟ لأنك لو كتبت `SELECT city_id, status, COUNT(trip_id)` وعملت `GROUP BY city_id` فقط. الداتابيز هتقولك: "أنا القاهرة عندي فيها 10,000 رحلة، وحالتهم مختلفة (Completed, Cancelled)، إنت طالب مني أعرض صف واحد بس للقاهرة وجنبه العدد الكلي، أعرض أنهي حالة فيهم في عمود الـ `status`؟". ده منطقياً مستحيل، وعشان كده الداتابيز هترفض تشغيل الاستعلام.

```sql
-- Grouping trips by city to get aggregated statistics
SELECT 
    city_id, 
    COUNT(trip_id) AS total_trips,
    SUM(fare) AS total_revenue
FROM trips
GROUP BY city_id;
```

#### مثال 1: التجميع على مستويات متعددة (Multi-column Grouping)
تقدر تجمع البيانات بأكتر من مستوى. لو عايزين نعرف أداء الكباتن في كل فئة سيارات في كل مدينة، بنكتب:
`GROUP BY city_id, car_tier`
هنا الداتابيز هتعمل مجموعات فرعية أدق: (القاهرة - VIP)، و(القاهرة - Economy)، و(الرياض - VIP)، وتطبع صف ملخص لكل توليفة فريدة من العمودين معاً.

#### مثال 2: خطأ تشغيل ONLY_FULL_GROUP_BY في MySQL
في النسخ القديمة من MySQL، لو كتبت استعلام بيخالف القاعدة الذهبية (أعمدة في الـ SELECT مش في الـ GROUP BY)، كانت الداتابيز بتعديه عادي وتطبع قيمة عشوائية من الصفوف المجمعة في العمود ده! وده كان بيسبب مشاكل منطقية صعبة التتبع. في النسخ الحديثة، تم تفعيل وضع `ONLY_FULL_GROUP_BY` افتراضياً، وبقت الداتابيز بتطلع Error واضح وصريح يرفض الاستعلام لمنع البيانات الخاطئة.

### الفايدة الانترفيوية
What is the logical rule of selecting columns when using a GROUP BY clause in SQL?
**الإجابة المثالية:**
عند استخدام بند `GROUP BY` لتجميع البيانات، فإن القاعدة الأساسية هي أن أي عمود يتم إدراجه في بند الـ `SELECT` ولا يتم تطبيقه داخل دالة تجميعية (Aggregate Function) مثل `SUM` أو `COUNT` أو `AVG`، لازم تحطه بالكامل في بند الـ `GROUP BY`. لو ما حصلش ده، سيرفض محرك قاعدة البيانات الاستعلام ويطلق خطأ مثل `Expression not in GROUP BY key`؛ لأن المحرك لن يستطيع تحديد قيمة فردية واحدة لعرضها من بين قيم الصفوف المتعددة المجمعة داخل المجموعة الواحدة.

## Q20 — إزاي بتفرز وتحدد ناتج الاستعلام بـ ORDER BY و LIMIT / OFFSET؟ وإزاي بتأثر على الـ Pagination؟

### أصل الحكاية
تخيل إنك بتبني صفحة عرض المنتجات (Product Catalog) في تطبيق تجارة إلكترونية كبير. لما المستخدم يدخل، بيشوف المنتجات مترتبة من الأرخص للأغلى (Sort by Price)، والصفحة بتعرض 10 منتجات بس في المرة الواحدة. ولما يضغط على "الصفحة التالية"، السيستم بيعرض الـ 10 منتجات اللي بعدهم.
عملياً، إحنا بنعمل ده في الـ Database باستخدام تلاتة أوامر أساسية:
- `ORDER BY price ASC`: لترتيب المنتجات تصاعدياً حسب السعر.
- `LIMIT 10`: لتحديد عدد الصفوف المسترجعة بـ 10 صفوف فقط.
- `OFFSET 10`: لتخطي (Skip) أول 10 صفوف وجلب الـ 10 اللي بعدهم (أوردرات الصفحة الثانية).

دي الطريقة الكلاسيكية وبنسميها **Offset-based Pagination**.
ولكن كمهندس برمجيات محترف شغال على نظام ضخم (Scale)، لازم تعرف إن الطريقة دي فيها **عيب أداء مدمر** عند المستويات العالية.
لو مستخدم راح لصفحة رقم 10,000 في السيستم، الأبليكيشن هيبعت أمر:
`LIMIT 10 OFFSET 100000;`
تحت الغطاء، قاعدة البيانات عشان تتخطى 100,000 صف وتجيب الـ 10 اللي بعدهم، هي مجبرة تقرأ وتفرز الـ 100,010 صف بالكامل من الهارد ديسك وتحملهم في الذاكرة، وبعدين ترمي أول 100,000 صف في الزبالة وتديك الـ 10 صفوف الآخرين!
ده معناه إن كل ما المستخدم يتعمق في الصفحات، كل ما الاستعلام هيكون أبطأ بكتير ويستهلك موارد السيرفر بالكامل. ده بنسميه **Offset Pagination Bottleneck**.

الحل الاحترافي للمشكلة دي هو الانتقال لـ **Cursor-based Pagination** (أو Keyset Pagination). هنا مش بنستخدم `OFFSET` خالص. إحنا بنخزن معرف (ID) آخر منتج ظهر للمستخدم في الصفحة السابقة (الـ Cursor)، والاستعلام الجديد بيطلب البيانات اللي بعد المعرف ده مباشرة بـ `WHERE id > last_seen_id LIMIT 10` وبكده الداتابيز بتقفز مباشرة للمكان المطلوب باستخدام الفهرس (Index Scan) بدون ما تقرأ صف واحد زيادة من الصفوف السابقة.

```sql
-- 1. Offset-based Pagination (Slow at scale)
-- Skips the first 100,000 rows and takes 10. The DB must read 100,010 rows first.
SELECT product_id, title, price 
FROM products 
ORDER BY price ASC, product_id ASC 
LIMIT 10 OFFSET 100000;

-- 2. Cursor-based Pagination (Fast at scale, constant time O(1))
-- DB jumps directly to the target record using the Index on (price, product_id).
-- Assuming last seen price was 150.00 and last seen product_id was 8502.
SELECT product_id, title, price 
FROM products 
WHERE (price > 150.00) OR (price = 150.00 AND product_id > 8502)
ORDER BY price ASC, product_id ASC 
LIMIT 10;
```

#### مثال 1: الفرز العشوائي (Filesort) الكارثي
لو كتبت استعلام لترتيب الطلبات حسب تاريخ الإنشاء: `ORDER BY created_at DESC LIMIT 10` وعمود التاريخ `created_at` مش عليه فهرس (Index). الداتابيز عشان تجيب أحدث 10 طلبات من وسط 10 مليون صف، هتضطر تسحب الـ 10 مليون صف وتعمل لهم فرز وترتيب في ملفات مؤقتة على القرص (Filesort)، وده هيخلي الاستعلام ياخد ثواني طويلة. لو ضفت Index على `created_at`، الداتابيز هتقرأ أول 10 سجلات من الفهرس مباشرة وتخلص الاستعلام في 1 مللي ثانية.

#### مثال 2: متى يكون الـ Offset pagination مقبولاً؟
الـ Offset pagination مقبول جداً في لوحات التحكم الإدارية (Admin Dashboards) واللي بتكون جداول البيانات صغيرة الحجم (بضعة آلاف من الصفوف)، وحيث يحتاج المدير للتنقل لصفحة معينة مباشرة بالرقم (زي القفز لصفحة 7 مثلاً). لكن في تطبيقات التصفح اللانهائي (Infinite Scroll) زي فيسبوك وتويتر وتيك توك، الـ Cursor Pagination هو الخيار الوحيد الممكن لضمان سرعة التصفح ومنع تكرار البوستات لو اتضافت بوستات جديدة في أعلى الـ Feed أثناء التصفح.

### الفايدة الانترفيوية
Why does performance degrade with high OFFSET values in SQL pagination, and what is the alternative?
**الإجابة المثالية:**
يتدهور الأداء بشكل كبير عند استخدام قيم `OFFSET` عالية لأن محرك قاعدة البيانات يضطر لقراءة وفحص وتخطي جميع الصفوف السابقة للـ Offset (مثلاً لو الـ Offset 100,000، سيقوم بقراءة 100,000 صف وترميزها في الذاكرة ثم التخلص منها ليأخذ الـ 10 صفوف المطلوبة فقط). البديل الاحترافي هو **Cursor-based Pagination** (أو Keyset Pagination)، واللي نتخلص من الـ `OFFSET` تماماً ونقوم بفلترة البيانات باستخدام شرط `WHERE` بناءً على قيمة آخر سجل تم عرضه (مثل `WHERE id > last_seen_id`) مع وجود فهرس، مما يسمح للمحرك بالقفز مباشرة إلى السجل المطلوب دون تحميل أي بيانات سابقة.

## Q21 — إزاي بنستخدم الـ LIKE والـ Wildcards للبحث النصي؟ وإيه تأثيرها المدمر على الـ Index؟

### أصل الحكاية
تخيل إنك بتبني ميزة البحث عن الرسائل في تطبيق محادثات ضخم زي Telegram أو WhatsApp. المستخدم بيكتب كلمة في شريط البحث، والسيستم بيحتاج يجيب كل الرسائل اللي بتحتوي على الكلمة دي.
الطريقة التقليدية في SQL هي استخدام عامل `LIKE` مع الرموز التعبيرية (Wildcards):
- `%`: بتمثل أي عدد من الحروف (بما فيها الصفر).
- `_`: بتمثل حرف واحد بالظبط.

عند كتابة استعلامات البحث، بيظهر فرق جوهري ومدمر في أداء قواعد البيانات بناءً على مكان الـ Wildcard:
1. **البحث بالبداية (Left-anchored search / Prefix)**: زي `LIKE 'urgent%'`. هنا إنت بتبحث عن الرسائل اللي بتبدأ بكلمة "urgent". الاستعلام ده **سريع وبيستخدم الفهرس (Index)** بكفاءة؛ لأن الداتابيز بتقدر تروح للفهرس (B-Tree Index) وتدور على الحروف الأولى زي ما بتدور في القاموس، وتعمل (Index Range Scan) مباشرة.
2. **البحث بالنهاية أو الاحتواء (Substring search)**: زي `LIKE '%urgent'` أو `LIKE '%urgent%'`. هنا إنت بتدور على كلمة في أي مكان في النص. الاستعلام ده **مدمر للأداء ولا يمكنه استخدام الفهرس**؛ لأن الحروف الأولى مجهولة للداتابيز، وبالتالي الفهرس المرتب أبجدياً أصبح بلا قيمة. المحرك بيضطر يعمل مسح كامل للجدول (Full Table Scan) ويقرأ رسالة رسالة من الهارد ديسك ويفحص النص جواها، وده بيبطئ السيستم تماماً عند الـ Scale.

```sql
-- 1. Prefix Search (Fast, uses B-Tree Index Range Scan)
SELECT * FROM messages 
WHERE text LIKE 'urgent%';

-- 2. Substring Search (Slow, forces Full Table Scan, destroys performance)
SELECT * FROM messages 
WHERE text LIKE '%urgent%';
```

#### مثال 1: البحث عن كود الخصم (Coupon Codes)
لو عندك جدول كوبونات مبيعات والعملاء بيبحثوا بالكوبون. لو كتبت `WHERE code LIKE 'SUMMER%'` وكان فيه Index على عمود `code`، الاستعلام هيتنفذ في لمح البصر. لكن لو بتبحث عن الكوبونات اللي بتنتهي برقم مع معين فكتبت `LIKE '%20'`، الداتابيز هتعمل Full Table Scan.

#### مثال 2: الانتقال للـ Full-Text Search عند الـ Scale
لو السيستم بتاعك كبر وبقى عندك ملايين المستخدمين والرسائل، والبحث بـ `LIKE '%word%'` بقا بيوقع السيرفر. الحل الاحترافي مش الـ SQL التقليدي. قواعد البيانات الحديثة بتوفر نوع فهرس خاص اسمه **Full-Text Index** بيقوم بتقطيع النصوص لكلمات وبناء فهرس مقلوب (Inverted Index) بيربط كل كلمة بالصف اللي ظهرت فيه. أو بنلجأ لربط قاعدة البيانات بمحرك بحث خارجي متخصص زي Elasticsearch أو Algolia لتنفيذ عمليات البحث النصي المعقدة بلمح البصر وبدون تحميل على قاعدة البيانات الرئيسية.

### الفايدة الانترفيوية
Under what conditions can a SQL LIKE query utilize a B-Tree index, and how do you handle substring search at scale?
**الإجابة المثالية:**
يمكن لاستعلام `LIKE` استخدام الفهرس التقليدي (B-Tree Index) فقط إذا كان محدد البداية (Left-anchored) ولا يبدأ بعلامة النسبة المئوية، مثل `LIKE 'prefix%'`؛ لأن المحرك يستطيع مقارنة الحروف الأولى والتنقل داخل الفهرس للوصول للنطاق المطلوب (Index Range Scan). أما إذا بدأ الاستعلام بعلامة نسبة مئوية مثل `LIKE '%substring%'`، فإن الفهرس يصبح غير مفيد لأن البداية غير معروفة، مما يجبر المحرك على عمل مسح كامل للجدول (Full Table Scan). للتعامل مع النوع ده من البحث عند الـ Scale، نعتمد على الفهارس النصية الكاملة (Full-Text Search Indexes) أو محركات بحث متخصصة مثل Elasticsearch تعتمد على الـ Inverted Index.

## Q22 — إزاي بنتعامل مع القيم الفارغة (NULL) في SQL؟ وليه المقارنة بـ `= NULL` دايمًا غلط؟

### أصل الحكاية
تخيل إنك شغال في لوحة تحكم شؤون الموظفين (HR Portal) لشركة كبيرة. الجدول `employees` فيه عمود اسمه `manager_id` بيخزن المعرف بتاع مدير كل موظف. بالنسبة للمدير التنفيذي للشركة (CEO)، هو مش بيبلغ حد، فعمود الـ `manager_id` بتاعه قيمته فارغة `NULL`.
المدير طلب منك تجيب لستة بكل الموظفين اللي ملهمش مديرين في الشركة (عشان يراجع هيكل الإدارة).
أول حاجة ممكن تخطر على بالك هي كتابة الاستعلام ده:
`SELECT * FROM employees WHERE manager_id = NULL;`
لكن الصدمة هنا إن الاستعلام ده **مش هيرجع أي صفوف نهائياً!** حتى لو الـ CEO والمديرين الكبار كلهم في الجدول وقيمهم `NULL`.
ليه الكلام ده بيحصل؟

في قواعد البيانات العلائقية، القيمة `NULL` ليست قيمة عادية (مثل الرقم 0 أو النص الفارغ `''`)؛ هي تعبر عن **غياب القيمة أو قيمة مجهولة (Unknown/Missing Value)**.
ولغة SQL بتتعامل مع منطق رياضي اسمه **المنطق ثلاثي القيم (Three-Valued Logic - 3VL)**. المنطق ده فيه تلات نتايج لأي عملية مقارنة:
1. صواب (True)
2. خطأ (False)
3. مجهول (Unknown)

بناءً على المنطق ده، لو سألت الداتابيز: "هل القيمة المجهولة (NULL) بتساوي 5؟" الإجابة هتكون مجهول (Unknown).
ولو سألتها: "هل القيمة المجهولة (NULL) لا تساوي 5؟" الإجابة برضه مجهول (Unknown).
وحتى لو سألتها: "هل القيمة المجهولة بتساوي قيمة مجهولة تانية؟" (يعني `NULL = NULL`)، الإجابة برضه هتكون **Unknown**! لأننا منعرفش القيمة المجهولة الأولى إيه والتانية إيه عشان نحكم بالتساوي.
وبما إن شرط الـ `WHERE` مش بيعدي غير الصفوف اللي نتيجة شرطها صواب (True) فقط، فجميع عمليات المقارنة مع `NULL` باستخدام المعاملات العادية (`=`, `<>`, `>`, `<`) بتفشل وبترجع صفر صفوف.
الحل الصح والوحيد للمقارنة مع NULL هو استخدام المعاملات الخاصة `IS NULL` و `IS NOT NULL`.

```sql
-- WRONG: This will always return 0 rows
SELECT * FROM employees 
WHERE manager_id = NULL;

-- CORRECT: This is how we query for NULLs
SELECT * FROM employees 
WHERE manager_id IS NULL;

-- Using COALESCE to handle NULL fallbacks in reports
SELECT 
    emp_name, 
    COALESCE(manager_id, 0) AS manager_id_cleansed -- Returns 0 if manager_id is NULL
FROM employees;
```

#### مثال 1: الوقوع في فخ النفي مع الـ NULLs
تخيل لو بتكتب استعلام يجيب كل الموظفين اللي مديرهم مش أحمد (أحمد الـ ID بتاعه 5):
`SELECT * FROM employees WHERE manager_id <> 5;`
الاستعلام ده هيتجاهل تماماً الـ CEO اللي الـ `manager_id` بتاعه `NULL`. ليه؟ لأن المقارنة `NULL <> 5` نتيجتها "Unknown" فبالتالي الصف مش هيظهر. عشان تجيب الـ CEO معاهم في النتيجة، لازم تكتب الشرط بشكل صريح:
`WHERE manager_id <> 5 OR manager_id IS NULL;`

#### مثال 2: استخدام دالة COALESCE للتنظيف والتقارير
لما بنعرض تقارير مالية أو فواتير للمستخدمين، مش لطيف يظهر كلمة `NULL` في الواجهة (UI). بنستخدم دالة `COALESCE(val1, val2, ...)` ودي دالة بتاخد مجموعة قيم وترجع أول قيمة مش `NULL` تقابلها.
مثلاً لو بنعرض الخصم على الفاتورة:
`COALESCE(discount, 0)` ➔ لو الخصم موجود هيعرضه، لو `NULL` هيعرض صفر.
لو بنعرض اسم العميل وممكن يكون مش مسجل اسم أول، فبندور على الموبايل:
`COALESCE(first_name, nickname, 'Dear Customer')` ➔ هيدور بالترتيب ويعرض المتاح.

### الفايدة الانترفيوية
Why does standard equality (=) fail when comparing with NULL in SQL, and how does Three-Valued Logic work?
**الإجابة المثالية:**
تفشل المقارنة المساواة العادية مع `NULL` في SQL لأن `NULL` لا تعبر عن قيمة محددة وإنما تعبر عن غياب القيمة أو حالة مجهولة (Unknown/Absence of Value). تعتمد لغة SQL على المنطق ثلاثي القيم (Three-Valued Logic) والذي يضيف حالة "Unknown" بجانب "True" و "False". نتيجة أي عملية مقارنة مباشرة مع `NULL` (حتى مقارنة `NULL = NULL`) تكون دائماً "Unknown". وبما أن بند الـ `WHERE` لا يسمح بمرور السجلات إلا إذا كانت نتيجة تقييم الشرط هي "True" حصراً، المقارنات دي بتفشل دائماً ويرجع الاستعلام صفراً من السجلات. للتحقق من القيم الفارغة بشكل صحيح، لازم تستخدم المعاملين المخصصين `IS NULL` أو `IS NOT NULL`.

## Topic 3: Joins (الروابط في قواعد البيانات)

### Q23 — الـ JOIN وأصل الحكاية: إيه هو وليه بنحتاجه؟
#### أصل الحكاية
لما بنصمم قاعدة البيانات، بنطبق قواعد الـ Normalization علشان نمنع تكرار البيانات ونحافظ على تكاملها. فـ بنفصل البيانات لعدة جداول؛ مثلاً، بيانات العملاء في جدول `customers` والأوردرات في جدول `orders`.
لكن المشكلة بتظهر لما نحتاج نعرض تقرير كامل فيه بيانات العميل مع الأوردر بتاعه في نفس الصفحة. لو مفيش Join، هنضطر نعمل استعلام لجدول الأوردرات، وبعدين نلف في حلقة تكرارية (Loop) في الباك-إند علشان نبعت استعلام تاني لكل عميل يجيب بياناته! ده طبعاً كارثة أداء معروفة باسم (N+1 query problem).
هنا بييجي دور الـ JOIN. ده معامل منطقي في الـ SQL بيخلي الداتابيز تربط الصفوف من جدولين أو أكتر بناءً على علاقات منطقية (زي الـ Foreign Key والـ Primary Key). الربط ده بيحصل على سيرفر قاعدة البيانات في خطوة واحدة، وبيرجع لنا نتيجة واحدة مدمجة بدل ما نهلك الشبكة والسيرفر باستعلامات رايحة جاية.

```sql
-- Retrieve orders along with customer names to avoid N+1 query problem
SELECT 
    o.order_id,
    o.order_date,
    o.total_amount,
    c.customer_name,
    c.email
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id;
```

#### مثال 1: الوقوع في فخ الـ N+1 Queries
في تطبيق تجارة إلكترونية، لو بنعرض صفحة تفاصيل الأوردر للعميل. من غير Join، الباك-إند هيبعت استعلام يجيب الأوردر: `SELECT * FROM orders WHERE id = 123`
بعد كدة هيلاقي `customer_id` قيمته `456` فـ يبعت استعلام تاني: `SELECT * FROM customers WHERE id = 456`.
الـ Join بيخلينا نجيب كل ده بضربة واحدة للسيرفر، فـ نقلل الـ latency وتكاليف الـ I/O.

#### مثال 2: تقارير المبيعات الضخمة
تخيل لو بنعمل تقرير مبيعات سنوي فيه 10,000 أوردر. لو عملنا استعلام للـ 10,000 أوردر، ولفينا عليهم في كود التطبيق نجيب العميل لكل أوردر، هنبعت 10,001 استعلام للداتابيز! ده هيوقع السيرفر فوراً. باستخدام الـ JOIN، السيرفر بيعمل عملية الربط دي داخلياً وبيرجع الـ 10,000 صف في استعلام واحد بس وسريع جداً.

### الفايدة الانترفيوية
What is SQL JOIN and what major performance issue does it prevent?
**الإجابة النموذجية:**
الـ JOIN هو آلية في لغة SQL لربط السجلات من جدولين أو أكثر بناءً على حقل مشترك (غالباً علاقة PK-FK). الفائدة الأساسية منه هي منع مشكلة الأداء الشهيرة (N+1 Query Problem)، واللي بتحصل لما يجيب الكود سجلات من جدول معين، ثم يلف عليها في حلقة تكرارية ويبعت استعلام منفصل لقاعدة البيانات لكل سجل علشان يجيب بياناته المرتبطة من جدول تاني. الـ JOIN بيحل المشكلة دي عن طريق دمج البيانات وعمل الربط على مستوى محرك قاعدة البيانات نفسه في استعلام واحد، فـ يوفر استهلاك الشبكة ووقت المعالجة.

### Q24 — الـ INNER JOIN والـ OUTER JOINs (LEFT, RIGHT, FULL) من تحت الغطا
#### أصل الحكاية
الـ JOIN مش نوع واحد، هو كذا نوع وكل نوع بيحدد إزاي بنتعامل مع الصفوف اللي ملهاش مقابل في الجدول التاني.
1. **INNER JOIN**: ده النوع الافتراضي. بيرجع الصفوف اللي ليها مقابل في الجدولين بس. يعني لو فيه أوردر ملوش عميل (أو عميل ملوش أوردرات)، مش هيظهروا في النتيجة.
2. **LEFT (OUTER) JOIN**: بيرجع كل الصفوف من الجدول الشمال (اللي اتكتب الأول بعد `FROM`)، والصفوف المتطابقة من الجدول اليمين. لو فيه صف في الشمال ملوش مقابل في اليمين، الأعمدة بتاعة الجدول اليمين بتنزل بـ `NULL`.
3. **RIGHT (OUTER) JOIN**: عكس الـ LEFT تماماً. بيرجع كل الصفوف من الجدول اليمين (اللي بعد كلمة `JOIN`)، والصفوف المتطابقة من الشمال. لو مفيش مقابل، أعمدة الشمال بتنزل بـ `NULL`. (غالباً مش بنستخدمه لأننا بنقدر نرتب الجداول ونستخدم LEFT علطول علشان الكود يكون أسهل في القراية).
4. **FULL (OUTER) JOIN**: بيلم كله. بيرجع الصفوف المتطابقة، والصفوف اللي ملهاش مقابل في الشمال، والصفوف اللي ملهاش مقابل في اليمين. أي حتة ناقصة بتنزل بـ `NULL`.

تحت الغطا، قاعدة البيانات بتحدد الجداول وتستخدم خوارزميات ربط (زي الـ Hash Match أو Nested Loops) لفلترة الصفوف بناءً على نوع الـ Join. في الـ Inner Join، الفلترة بتكون صارمة ومفيش أي قيم مجهولة بتظهر في الأعمدة المشتركة. أما في الـ Outer Joins، السيرفر بيحتفظ بالصفوف غير المتطابقة وبيحط مكان القيم الغايبة `NULL`.

```sql
-- 1. INNER JOIN: Only customers who placed orders
SELECT c.customer_name, o.order_id
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id;

-- 2. LEFT JOIN: All customers, even if they have 0 orders
SELECT c.customer_name, o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

-- 3. FULL JOIN: All customers and all orders, matched where possible
SELECT c.customer_name, o.order_id
FROM customers c
FULL OUTER JOIN orders o ON c.customer_id = o.customer_id;
```

#### مثال 1: إيجاد الحسابات غير النشطة
في لوحة تحكم تطبيق لوجستيات، لو عايزين نعرف مين العملاء اللي سجلوا في الموقع لكن لسه معملوش ولا أوردر علشان نبعت لهم إيميل ترويجي. هنا بنستخدم `LEFT JOIN` وبنفلتر بالصفوف اللي فيها الأوردر بـ `NULL`:
```sql
SELECT c.customer_name, c.email
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;
```
لو استخدمنا `INNER JOIN` هنا، النتيجة هتكون فاضية تماماً والعملاء دول مش هيظهروا.

#### مثال 2: تقارير المنتجات والمبيعات
في نظام إدارة مستودعات (WMS)، لو بنربط جدول المنتجات `products` بجدول المبيعات `sales`. لو فيه منتج جديد اتضاف ومتباعش منه ولا قطعة، وعملنا `INNER JOIN` علشان نحسب إجمالي المبيعات، المنتج ده هيختفي تماماً من التقرير كأنه مش موجود. الصح نستخدم `LEFT JOIN` علشان يظهر في التقرير وقيمة مبيعاته تظهر صفر (باستخدام `COALESCE`).

### الفايدة الانترفيوية
What is the difference between INNER JOIN, LEFT JOIN, and FULL JOIN? Provide a business scenario for LEFT JOIN.
**الإجابة النموذجية:**
الـ `INNER JOIN` بيرجع السجلات المشتركة والموجودة في الجدولين معاً فقط. الـ `LEFT JOIN` بيرجع كل السجلات من الجدول الأيسر، بالإضافة للسجلات المطابقة من الجدول الأيمن، وفي حال عدم وجود مطابقة، تظهر أعمدة الجدول الأيمن بقيمة `NULL`. أما الـ `FULL JOIN` فبيرجع كل السجلات من الجدولين سواء كانت متطابقة أو لا، ويعوض النقص بـ `NULL`.
سيناريو عملي للـ `LEFT JOIN`: لما نحب نطلع قائمة بكل المستخدمين وعدد المنشورات اللي كتبوها، حتى لو فيه مستخدمين مفرطين في الكسل وكتبوا صفر منشورات. لو استخدمنا `INNER JOIN` المستخدمين دول هيتحذفوا من القائمة، لكن باستخدام الـ `LEFT JOIN` هيخليهم يظهروا وجنبهم القيمة صفر.

### Q25 — الـ CROSS JOIN (Cartesian Product): إمتى بنحتاجه وإمتى بيكون كارثة؟
#### أصل الحكاية
الـ `CROSS JOIN` بيقوم بعملية الضرب الديكارتي (Cartesian Product) بين جدولين. يعني إيه؟ يعني بياخد كل صف من الجدول الأول ويربطه مع كل الصفوف في الجدول الثاني. لو الجدول الأول فيه 10 صفوف والجدول الثاني فيه 10 صفوف، النتيجة هتكون 100 صف (10 * 10).
المميز في الـ `CROSS JOIN` إنه مش بيحتاج شرط ربط `ON`؛ هو بيربط عشوائي وبشكل أعمى كل الصفوف ببعضها.

المشكلة الكبيرة إن الـ Cross Join ممكن يحصل بالخطأ في الكود لو نسيت تكتب شرط الـ `ON` في الـ Join العادي (في الصيغ القديمة من الـ SQL زي الربط في الـ `WHERE`). ده ممكن يولد ملايين الصفوف في ثواني، ويهلك رامات السيرفر ويهنج التطبيق.
لكن ده مش معناه إنه بلا فائدة؛ هو مفيد جداً لما تحب تولد كل التباديل والتوافيق الممكنة بين مجموعتين من البيانات.

```sql
-- Generating all possible product variants (Colors x Sizes)
SELECT 
    p.product_name,
    c.color_name,
    s.size_name
FROM products p
CROSS JOIN colors c
CROSS JOIN sizes s;
```

#### مثال 1: توليد تشكيلة المنتجات في E-commerce
تخيل لو بتصمم متجر ملابس وعايز تولد كل البدائل (SKUs) المتاحة لتيشرت معين. تيشرت متوفر بـ 3 ألوان (أحمر، أزرق، أخضر) و 4 مقاسات (S, M, L, XL). باستخدام الـ `CROSS JOIN` بين جدول الألوان وجدول المقاسات للمنتج ده، تقدر ولد الـ 12 تشكيلة المتاحة في خطوة واحدة وبمنتهى السهولة لحفظهم في قاعدة البيانات.

#### مثال 2: الكارثة وانهيار السيرفر
تخيل لو بتكتب استعلام لربط جدول الموظفين (1,000 موظف) بجدول الحركات المالية (1,000,000 حركة). لو كتبت:
`SELECT * FROM employees, financial_transactions;`
أو نسيت شرط الـ `ON` في الـ `JOIN`:
قاعدة البيانات هتعمل `CROSS JOIN` وهتنتج **مليار صف** (1,000 * 1,000,000). الاستعلام ده هيحجز رامات السيرفر بالكامل وممكن يسبب انهيار قاعدة البيانات (Out of Memory) ويوقف الخدمة عن المستخدمين.

### الفايدة الانترفيوية
What is a CROSS JOIN, how does it differ from other joins, and what is its performance risk?
**الإجابة النموذجية:**
الـ `CROSS JOIN` هو عملية ضرب ديكارتي ينتج عنها ربط كل صف من الجدول الأول بكل صف من الجدول الثاني بدون شروط ربط (`ON`). الفرق بينه وبين باقي الأنواع هو عدم حاجته لشرط ربط. خطورته على الأداء تكمن في الزيادة الأسيّة لحجم النتيجة؛ فلو اتطبق بالخطأ على جداول كبيرة الحجم (مثلاً جدول فيه 10,000 صف وجدول فيه 100,000 صف)، هينتج مليار سجل، وده هيهلك موارد السيرفر (الذاكرة والمعالج) وممكن يسبب انهيار النظام بالكامل.

### Q26 — الـ NATURAL JOIN: وليه بنعتبره "جريمة" في الكود البرودكشن?
#### أصل الحكاية
الـ `NATURAL JOIN` هو نوع من الـ Inner Join لكنه بيشتغل بشكل "ذكي" وتلقائي. بدل ما تكتب شرط الربط `ON table1.column = table2.column` بإيدك، الـ `NATURAL JOIN` بيبص على الجدولين ويدور على الأعمدة اللي ليها نفس الاسم ونفس نوع البيانات في الجدولين، ويربط بناءً عليها لوحده.
للوهلة الأولى، ده يبدو ساحر وموفر في كتابة الكود. لكن في عالم البرودكشن، الـ `NATURAL JOIN` بيعتبر قنبلة موقوتة وجريمة في حق صيانة الكود (Maintainability).
ليه؟ لأن كودك بقا بيعتمد على فرضية مستترة وثابتة لأسماء الأعمدة. لو حد بعد سنة عدل في أسماء الأعمدة أو ضاف عمود جديد بالصدفة له نفس الاسم في الجدولين، شرط الربط هيتغير تلقائياً وبشكل صامت تماماً، والنتيجة هتكون استعلامات بتجيب بيانات غلط أو فاضية من غير ما يظهر أي خطأ برمجى واضح!

```sql
-- DANGEROUS: Implictly joins on ANY columns sharing the same name (e.g. 'id' or 'created_at')
SELECT * 
FROM orders
NATURAL JOIN customers;

-- SAFE & EXPLICIT: Always define your join conditions explicitly
SELECT *
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id;
```

#### مثال 1: الخطر الصامت وتغيير أسماء الأعمدة
تخيل لو عندك جدولين `orders` و `customers`. الاتنين فيهم عمود اسمه `customer_id`. لما تعمل `NATURAL JOIN` هيربط عليهم تمام.
بعد فترة، المطورين قرروا يضيفوا عمود لتسجيل تاريخ الإنشاء في الجدولين وسموه `created_at` في `orders` و `created_at` في `customers`.
الآن، الـ `NATURAL JOIN` هيحاول يربط تلقائياً بالعمودين: `customer_id` **و** `created_at`.
بما إن تاريخ إنشاء حساب العميل يختلف عن تاريخ عمل الأوردر، الاستعلام مش هيرجع أي صفوف! فجأة السيستم هيظهر صفر أوردرات بدون أي Error في اللوجز.

#### مثال 2: مشكلة عمود الـ id الشهير
لو الجداول بتاعتك بتتبع أسلوب تسمية المعرف الفريد باسم `id` في كل الجداول (يعني معرف العميل اسمه `id` في جدول `customers` ومعرف الأوردر اسمه `id` في جدول `orders`).
لو عملت `NATURAL JOIN` بينهم، السيرفر هيربطهم بناءً على عمود الـ `id`! ده معناه إنه هيربط العميل اللي الـ `id` بتاعه 5 بالأوردر اللي الـ `id` بتاعه 5، ودي علاقة ملهاش أي معنى منطقي وتؤدي لخلط بيانات الكستمرز بالأوردرات بشكل عشوائي.

### الفايدة الانترفيوية
What is a NATURAL JOIN and why is it generally avoided in production databases?
**الإجابة النموذجية:**
الـ `NATURAL JOIN` هو نوع من الـ JOIN يقوم بربط الجداول تلقائياً بناءً على الأعمدة اللي بتحمل نفس الاسم ونفس نوع البيانات في كلا الجدولين دون كتابة شرط ربط صريح.
يُتجنب تماماً في بيئات العمل الحقيقية (Production) للأسباب التالية:
1. **الخطورة عند تعديل الهيكل (Schema changes)**: لو اتضاف عمود جديد لأحد الجداول يحمل بالصدفة نفس اسم عمود في الجدول الآخر (مثل `created_at` أو `status`)، هيقوم الاستعلام بتعديل شرط الربط تلقائياً ليشمل العمود الجديد، مما يفسد نتائج الاستعلام بشكل صامت.
2. **الغموض وصعوبة القراءة (Implicit behavior)**: الكود لا يكون واضحاً للقارئ لمعرفة على أي أعمدة حصل الربط، مما يجعل صيانة الكود وتصحيح الأخطاء (Debugging) أمراً غاية في الصعوبة.


### Q27 — الـ EQUI JOIN والـ NON-EQUI JOIN: الربط بشروط غير التساوي
#### أصل الحكاية
في 99% من الحالات، بنربط الجداول ببعضها باستخدام معامل التساوي (`=`)؛ يعني هاتلي الأوردر لما الـ `customer_id` فيه بيساوي الـ `id` في جدول العملاء. النوع ده اسمه **EQUI JOIN** (ربط التساوي).
لكن الـ SQL مرن جداً وبيسمح لنا نربط الجداول باستخدام أي معامل مقارنة تاني (زي `>`, `<`, `>=`, `<=`, `!=`, `BETWEEN`). ده اسمه **NON-EQUI JOIN** (ربط غير التساوي).
إمتى بنحتاجه؟ لما نكون مش بندور على تطابق تام، بل بندور على وقوع قيمة في مدى معين (Range)، أو بنربط بناءً على شروط زمنية أو فئات سعرية.

```sql
-- NON-EQUI JOIN: Matching orders to their appropriate shipping discount tier based on order total
SELECT 
    o.order_id,
    o.total_amount,
    d.tier_name,
    d.discount_percentage
FROM orders o
JOIN discount_tiers d 
    ON o.total_amount BETWEEN d.min_amount AND d.max_amount;
```

#### مثال 1: تحديد مستويات الخصم (Discount Tiers)
تخيل لو عندنا جدول للأوردرات `orders` وجدول لمستويات الخصم `discount_tiers` فيه:
- Tier A: من 0 لـ 100 دولار (خصم 0%)
- Tier B: من 101 لـ 500 دولار (خصم 5%)
- Tier C: من 501 لـ 1000 دولار (خصم 10%)
الجدولين دول مفيش بينهم Foreign Key مباشر! علشان نربطهم ونجيب الخصم المناسب لكل أوردر، بنستخدم `NON-EQUI JOIN` بشرط إن الـ `total_amount` بتاع الأوردر يكون `BETWEEN` الحد الأدنى والحد الأقصى في جدول الخصومات.

#### مثال 2: مقارنة الأسعار التاريخية (Historical Price Audit)
في نظام تجارة إلكترونية، لو عايزين نتأكد إن سعر المنتج وقت شراء الأوردر هو نفسه السعر اللي كان ساري في جدول الأسعار التاريخية `price_history`.
جدول الأسعار التاريخية فيه `product_id` وتاريخ بداية السعر `start_date` وتاريخ نهايته `end_date`.
بنربطهم كدة:
```sql
SELECT o.order_id, o.product_id, o.purchase_price, h.price AS history_price
FROM order_items o
JOIN price_history h 
    ON o.product_id = h.product_id 
   AND o.purchase_date >= h.start_date 
   AND o.purchase_date <= h.end_date;
```
ده ربط غير متساوي باستخدام التواريخ وبيساعدنا نعمل تدقيق مالي للأسعار.

### الفايدة الانترفيوية
What is the difference between an EQUI-JOIN and a NON-EQUI JOIN? Provide a real-world use case for the latter.
**الإجابة النموذجية:**
الـ `EQUI-JOIN` هو الربط اللي بيعتمد على معامل التساوي (`=`) لمطابقة القيم بين الجداول (مثل الربط بين المفتاح الأساسي والأجنبي). أما الـ `NON-EQUI JOIN` فهو الربط اللي بيستخدم معاملات مقارنة تانية غير التساوي (مثل `>`, `<`, `BETWEEN`, `!=`).
حالة استخدام عملية: ربط جدول المعاملات المالية بجدول الفئات الضريبية أو مستويات الخصم، بحيث يقع مبلغ المعاملة بين الحد الأدنى والأقصى للفئة الضريبية دون وجود مفتاح ربط مباشر متساوي بين الجدولين.

### Q28 — الـ SELF JOIN: لما الجدول يربط مع نفسه
#### أصل الحكاية
في بعض الأحيان، الجدول بيحتاج يربط مع نفسه! ده بيحصل لما نكون بنخزن بيانات ليها طبيعة هرمية (Hierarchical Data) في نفس الجدول.
أشهر مثال هو هيكل الموظفين والمديرين: المدير هو في النهاية موظف وله سجل في نفس جدول الموظفين `employees`. فـ بنخزن لكل موظف الـ `manager_id` بتاعه، والـ `manager_id` ده بيشير لـ `employee_id` تاني في نفس الجدول!
الـ `SELF JOIN` مش جملة جديدة في الـ SQL؛ هو مجرد `INNER JOIN` أو `LEFT JOIN` للجدول مع نفسه، بس بنستخدم أسماء مستعارة (Aliases) مختلفة للجدول علشان الداتابيز متتلخبطش وتعرف نفرق بين النسخة الأولى والنسخة الثانية.

```sql
-- Retrieve employees along with their managers' names using a Self Join
SELECT 
    e.employee_name AS Employee,
    m.employee_name AS Manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.employee_id;
```

#### مثال 1: شجرة التصنيفات (Category Tree)
في متجر إلكتروني، لو عندنا نظام تصنيفات هرمي (مثل: أجهزة إلكترونية ➔ موبايلات ➔ موبايلات ذكية).
كل التصنيفات دي في جدول واحد اسمه `categories` وفيه عمود اسمه `parent_category_id`.
علشان نعرض كل تصنيف وجنبه اسم التصنيف الأب بتاعه، بنعمل `SELF JOIN`:
```sql
SELECT 
    sub.category_name AS SubCategory,
    parent.category_name AS ParentCategory
FROM categories sub
LEFT JOIN categories parent ON sub.parent_category_id = parent.category_id;
```

#### مثال 2: نظام الإحالات (Referral System)
في تطبيق توصيل أو تجارة إلكترونية، لو بنسجل العميل ومين العميل التاني اللي عمله دعوة (Referral).
جدول المستخدمين `users` فيه عمود `referred_by_user_id` اللي بيشير لـ `user_id` في نفس الجدول.
لو عايزين نطلع تقرير بكل مستخدم ومين اللي دعاه للموقع، بنعمل `SELF JOIN`. لو العميل مسجل لوحده من غير دعوة، بيظهر الخانة التانية بـ `NULL` (علشان كدة بنستخدم `LEFT JOIN` مش `INNER JOIN` علشان العملاء دول ميختفوش من التقرير).

### الفايدة الانترفيوية
What is a SELF JOIN, and how do you implement it in SQL? Give a database design example.
**الإجابة النموذجية:**
الـ `SELF JOIN` هو عملية ربط الجدول بنفسه. ده بيحصل عن طريق استدعاء الجدول مرتين في نفس الاستعلام مع إعطاء اسم مستعار (Alias) مختلف لكل نسخة (مثل `e` للموظف و `m` للمدير)، وتحديد شرط الربط بين أعمدة النسختين.
مثال تصميمي: جدول الموظفين واللي يحتوي كل صف على معرف الموظف `employee_id` ومعرف مديره المباشر `manager_id` واللي بيمثل مفتاحاً أجنبياً (FK) بيشير إلى نفس الجدول.

### Q29 — خوارزميات الـ JOIN تحت الغطا: Nested Loop vs Hash Join vs Merge Sort Join
#### أصل الحكاية
قاعدة البيانات مش بتعمل الـ Join بالسحر؛ هي بتستخدم خوارزميات محددة بناءً على حجم البيانات وجودة الفهارس (Indexes). الـ Query Optimizer هو المسؤول عن اختيار الخوارزمية الأنسب.
الخوارزميات الأساسية هي:
1. **Nested Loop Join**:
   - **فكرته**: بياخد كل صف من الجدول الأول (Outer Table)، ويلف على الجدول الثاني صف صف (Inner Table) يدور على التطابق. زي الـ Nested For Loops في البرمجة.
   - **إمتى بيستخدم**: لما يكون جدول منهم صغير جداً، والجدول التاني عليه Index على عمود الربط.
   - **السرعة**: سريع جداً لو الجدول الصغير فيه صفوف قليلة والتاني متفهرس، لكنه بطيء جداً (كارثة $O(N 	imes M)$) لو الجداول كبيرة ومفيش فهارس.

2. **Hash Join**:
   - **فكرته**: بيقرأ الجدول الأصغر ويبني جدول هاش (Hash Table) في الرامات بناءً على مفتاح الربط. بعد كدة يقرأ الجدول التاني (Probe Input) ويمشي على صفوفه صف صف، ويبص في الـ Hash Table فوراً ($O(1)$) يشوف فيه تطابق ولا لأ.
   - **إمتى بيستخدم**: لما الجداول تكون ضخمة ومفيش فهارس جاهزة على أعمدة الربط.
   - **السرعة**: بيحتاج رامات كبيرة لبناء الـ Hash Table، لكنه سريع جداً للمعالجة الضخمة للبيانات غير المفهرسة.

3. **Merge Sort Join**:
   - **فكرته**: بيرتب الجدولين بناءً على مفتاح الربط الأول، وبعد كدة يمشي عليهم مع بعض في نفس الوقت بمؤشرين (Two-pointer approach) يطابق الصفوف المرتبة.
   - **إمتى بيستخدم**: لما الجداول تكون كبيرة والبيانات بالفعل مرتبة (أو متفهرسة بفهرس مرتب زي الـ Clustered Index) على حقل الربط.
   - **السرعة**: سريع جداً ومستقر، ومش بيستهلك رامات ضخمة زي الـ Hash Join لأن ترتيب البيانات متخزن جاهز في الفهرس.

```sql
-- Query Optimizer determines which algorithm to use under the hood.
-- We can view the execution plan to see the selected join algorithm:
-- EXPLAIN SELECT * FROM orders o JOIN customers c ON o.customer_id = c.customer_id;
```

#### مثال 1: الـ Hash Join المنقذ في الـ Data Warehousing
تخيل لو بنعمل استعلام بيحلل ملايين الحركات المالية لربطها بجدول الفروع. الجداول ملهاش فهارس مشتركة لأن الاستعلام بيحصل في بيئة تحليلية (OLAP). الـ Optimizer هنا هيختار الـ Hash Join فوراً؛ هيبني Hash Table للفروع في الرامات، ويمشي على ملايين الحركات يطابقها بسرعة رهيبة.

#### مثال 2: الـ Nested Loop في الـ OLTP السريع
في تطبيق الموبايل للبنك، العميل بيفتح تطبيق كارت الائتمان علشان يشوف أحدث 10 معاملات له. الاستعلام بيربط جدول المعاملات بجدول تفاصيل الكارت.
بما إن الكارت له سجل واحد بس (Outer table) والمعاملات مفهرسة بـ `card_id` (Inner table)، الـ Optimizer هيستخدم `Nested Loop`. هيمسك الكارت، وبسرعة الـ Index هيجيب الـ 10 معاملات في أجزاء من الملي ثانية.

### الفايدة الانترفيوية
Explain the three main join algorithms used by DB engine (Nested Loop, Hash Join, Merge Join) and when each is preferred.
**الإجابة النموذجية:**
1. **Nested Loop**: يمر على صفوف الجدول الأول صفاً صفاً ويبحث عن المطابقة في الجدول الثاني. يفضل استخدامه عندما يكون أحد الجدولين صغيراً جداً والآخر يحتوي على فهرس (Index) على عمود الربط.
2. **Hash Join**: يقوم ببناء جدول هاش (Hash Table) في الذاكرة للجدول الأصغر، ثم يمر على الجدول الثاني للمطابقة. يفضل استخدامه مع الجداول الكبيرة جداً اللي معندهاش فهارس على حقل الربط.
3. **Merge Sort Join**: يقوم بترتيب الجدولين بناءً على حقل الربط أولاً ثم يطابقهما معاً بمؤشرين. يفضل استخدامه عندما تكون البيانات مرتبة مسبقاً بفعل وجود فهارس مرتبة (مثل B-Tree Clustered Index).

### Q30 — الـ Multi-table JOINs: إزاي الـ Query Optimizer بيرتب الحفلة دي؟
#### أصل الحكاية
لما بنكتب استعلام فيه ربط بين 4 أو 5 جداول، محرك قاعدة البيانات مش بيربطهم كلهم مرة واحدة في الهوا. الـ SQL لغة تصريحية (Declarative)؛ إحنا بنقولها "عايزين إيه" وهي بتحدد "إزاي يتعمل".
الـ Query Optimizer بياخد الاستعلام ويبدأ يحلل الطرق الممكنة لربط الجداول دي. بيحدد الترتيب الأفضل لعملية الربط (Join Order) ونوع الخوارزمية لكل ربط.
مثلاً، لو بنربط `A` و `B` و `C`. ممكن الـ Optimizer يقرر يربط `A` مع `B` الأول، والناتج يربطه مع `C`. أو يربط `B` مع `C` الأول، والناتج يربطه مع `A`.
الهدف دايماً هو **تقليل حجم البيانات الوسيطة (Intermediate Result Set)** بأسرع شكل ممكن. فـ لو جدول `B` فيه فلتر قوي هيطير 90% من الصفوف، الـ Optimizer هيبدأ بيه علشان يصغر الداتا اللي هتتربط بعد كدة.

```sql
-- Joining 4 tables: Orders, Customers, OrderItems, Products
SELECT 
    o.order_id,
    c.customer_name,
    p.product_name,
    oi.quantity
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id;
```

#### مثال 1: فلترة البيانات مبكراً (Early Filtering)
لو بنعمل استعلام نجيب أوردرات اليوم للعملاء من القاهرة للمنتجات الرياضية:
- الـ Optimizer مش هيروح يربط كل الأوردرات بكل المنتجات الرياضية الأول.
- هيبص يلاقي فلتر التواريخ على الأوردرات (أوردرات اليوم فقط) بيصغر حجم جدول الأوردرات من مليون صف لـ 100 صف بس.
- فـ يبدأ بالـ 100 صف دول، ويربطهم بالعملاء والمنتجات. كدة وفر ملايين العمليات الحسابية غير الضرورية.

#### مثال 2: شجرة الربط (Join Trees) وصلاحيات الذاكرة
في الاستعلامات الكبيرة (أكتر من 10 جداول)، عدد الاحتمالات لترتيب الربط بيكون فلكي ($N!$). الـ Optimizer مش هيقدر يجربهم كلهم لأن وقت حساب الاحتمالات هيكون أطول من وقت تشغيل الاستعلام نفسه!
هنا بيستخدم خوارزميات تقريبية (Heuristics) أو الـ Genetic Algorithms لتحديد ترتيب ممتاز وسريع (حتى لو مش الأفضل بنسبة 100%) لمنع استهلاك وقت السيرفر في التخطيط.

### الفايدة الانترفيوية
How does the SQL Query Optimizer handle multi-table joins, and what is "Join Order"?
**الإجابة النموذجية:**
بيحول الـ Query Optimizer استعلام الجداول المتعددة إلى سلسلة من عمليات الربط الثنائية (Binary Joins) على شكل شجرة ربط (Join Tree). بيحدد الـ Optimizer ترتيب الجداول في الربط (Join Order) بناءً على تكلفة الإدخال والإخراج وحجم البيانات المتوقع، وبيدور دايماً على البدء بالجداول اللي فيها شروط تصفية (Filters) قوية لتقليص حجم البيانات الوسيطة في أسرع وقت. مع الجداول الكتيرة جداً، بيستخدم خوارزميات ذكية لتحديد ترتيب شبه مثالي بسرعة لتجنب استهلاك الوقت في تقييم كل الاحتمالات الممكنة ($N!$).

### Q31 — تأثير الفهارس (Indexes) على سرعة الـ JOIN
#### أصل الحكاية
لو بتعمل Join بين جدولين كبار ومفيش فهارس (Indexes) على مفاتيح الربط، السيرفر هيضطر يعمل Full Table Scan للجدولين، أو يضطر يبني Hash Table في الرامات ويدهور الأداء.
الفهارس هي الصديق الصدوق للـ Join. لما بنحط Index على الـ Foreign Key في الجدول التابع، قاعدة البيانات بتقدر تطابق الصفوف بسرعة البرق.
بدل ما تلف على الجدول صف صف يدوي، بتستخدم الفهرس وتعمل بحث لوغاريتمي (Index Seek) وتجيب الصف المطابق علطول.
القاعدة الذهبية للـ Joins: **أي عمود بتستخدمه في شرط الربط (بعد كلمة `ON`)، لازم يكون متفهرس (Indexed) في الجدولين.**

```sql
-- Creating indexes on Foreign Keys to dramatically speed up JOINs
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_order_items_order_id ON order_items(order_id);
```

#### مثال 1: التحول من الـ Hash Join للـ Nested Loop Seek
تخيل جدولين `customers` (10,000 صف) و `orders` (1,000,000 صف).
من غير فهرس على `orders.customer_id`:
الـ Optimizer هيضطر يعمل `Hash Join` أو Full Table Scan لجدول الأوردرات بالكامل. الاستعلام هياخد 3 ثواني.
لما بنضيف فهرس على `orders.customer_id`:
الـ Optimizer هيستخدم `Nested Loop` مع `Index Seek`. هيمسك كل عميل، ويروح للفهرس يجيب أوردراته في أقل من 1 ملّي ثانية. الاستعلام كله هيخلص في 10 ملّي ثانية!

#### مثال 2: تحديث فهارس المفاتيح الأجنبية
في بعض قواعد البيانات (زي PostgreSQL أو MySQL)، لما بتنشئ Foreign Key، مش دايماً بيتفهرس تلقائياً (بعكس الـ Primary Key اللي بياخد Clustered Index تلقائي).
المطورين المحترفين دايماً بيكتبوا سكريبتات للتأكد من إن كل FK في قاعدة البيانات متغطي بفهرس مخصص له، لأن غياب الفهرس ده بيخلي عمليات الـ DELETE والـ UPDATE على الجدول الأساسي بطيئة جداً لأن الداتابيز بتضطر تعمل سكان كامل للجدول التابع للتأكد من عدم كسر التكامل المرجعي (Referential Integrity).

### الفايدة الانترفيوية
Why is it critical to index Foreign Keys used in JOIN conditions, and what is the impact on DELETE/UPDATE operations?
**الإجابة النموذجية:**
وجود فهارس (Indexes) على حقول المفاتيح الأجنبية (FKs) المستخدمة في شروط الـ JOIN هو أمر بالغ الأهمية لأنه يسمح لمحرك قاعدة البيانات باستبدال عمليات البحث الكاملة (Full Table Scans) المكلفة بعمليات بحث سريعة في الفهرس (Index Seeks)، مما يحسن سرعة الربط بآلاف المرات.
بالإضافة إلى كدة، غياب الفهرس عن المفتاح الأجنبي بيتسبب في بطء شديد لعمليات الـ `DELETE` والـ `UPDATE` على الجدول الرئيسي؛ لأن محرك الداتابيز بيضطر يعمل مسح كامل للجدول التابع للتحقق من عدم وجود سجلات مرتبطة تمنع الحذف أو التعديل للحفاظ على التكامل المرجعي.

## Topic 4: Normalization & DB Design (تطبيع وتصميم قواعد البيانات)

### Q32 — إيه هي عملية الـ Normalization (التطبيع)؟ وإيه هي المشاكل (Anomalies) اللي بنحاول نحلها؟
#### أصل الحكاية
لما بنيجي نصمم قاعدة بيانات من الصفر، لو قررنا نحط كل البيانات في جدول واحد كبير وعريض، زي إننا نعمل جدول واحد للمبيعات فيه اسم العميل، وعنوانه، وتفاصيل المنتج، وسعره، وتاريخ الشراء، واسم الكاشير. دي طريقة سهلة وسريعة في القراءة في البداية لأننا مش محتاجين نعمل JOINs، بس الكارثة الحقيقية بتظهر لما نحاول نعدل أو نضيف أو نمسح بيانات.
المشاكل دي بنسميها الـ Anomalies (عيوب التصميم):
1. **Insert Anomaly (مشكلة الإدخال)**: لو عندنا عميل جديد لسة ما اشتراش أي حاجة، مش هنقدر نسجل بياناته في قاعدة البيانات! لأن الصف في الجدول العريض ده بيشترط وجود عملية شراء ورقم أوردر. لو سبنا حقول الأوردر فاضية (NULL)، فـ ده تصميم سيئ وبيعمل فوضى في الداتا.
2. **Update Anomaly (مشكلة التعديل)**: لو عميل غير عنوان سكنه، وهو عنده 50 أوردر مسجلين في الجدول، هنضطر نعدل العنوان في الـ 50 صف دول صف صف. لو نسينا صف واحد أو حصل عطل أثناء التحديث، العنوان هيبقى مختلف بين السجلات، والداتا هتبقى غير متسقة (Inconsistent).
3. **Delete Anomaly (مشكلة الحذف)**: لو عندنا عميل اشترى منتج وحيد، وقررنا نمسح الأوردر ده علشان اتلغى، بمسح الأوردر ده هنمسح معاه بيانات العميل نفسه من السيستم بشكل نهائي! لأن بيانات العميل متخزنة جوة صف الأوردر.

عملية الـ Normalization هي علم تقسيم الجداول دي لجداول أصغر ومترابطة بمفاتيح خارجية (Foreign Keys) عشان نمنع التكرار ونقضي على الـ Anomalies دي تماماً.

```sql
-- Bad design: Everything in one single table (Unnormalized)
CREATE TABLE bad_orders (
    order_id INT,
    customer_id INT,
    customer_name VARCHAR(100),
    customer_email VARCHAR(100),
    product_id INT,
    product_name VARCHAR(100),
    price DECIMAL(10,2),
    order_date DATE
);

-- Good design: Normalized tables
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    customer_name VARCHAR(100),
    customer_email VARCHAR(100) UNIQUE
);

CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name VARCHAR(100),
    price DECIMAL(10,2)
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,
    product_id INT,
    order_date DATE,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);
```

#### مثال 1: تعديل سعر منتج شهير
تخيل لو عندنا منتج بنبيعه كتير، وسعره اتغير. في الجدول المشترك غير المنظم (bad_orders)، هنضطر نلف على كل الأوردرات القديمة ونعدل سعر المنتج فيها، وده غلط لأن الأوردرات القديمة لازم تحتفظ بسعر الشراء وقتها. ولو غيرنا السعر في جدول المنتجات المنفصل (products)، التعديل هيحصل في مكان واحد بس وهيسمع للمبيعات الجديدة علطول، والقديمة بتتحفظ بسعر الشراء الفعلي.

#### مثال 2: حذف أوردر عميل جديد
لو عميل عمل أوردر وحيد واتلغى، في التصميم النظيف، لما نمسح الصف من جدول `orders` بيانات العميل هتفضل محفوظة وموجودة في جدول `customers` عادي جداً ومستحيل تتمسح، وبالتالي نقدر نبعت له عروض تسويقية بعد كدة.

### الفايدة الانترفيوية
What is database Normalization, and what are the three main types of database anomalies?
**الإجابة النموذجية:**
الـ Normalization هي عملية تنظيم وتصميم جداول قاعدة البيانات العلاقاتية لتقليل تكرار البيانات (Redundancy) ومنع حدوث مشاكل تعديل وحذف وإدخال البيانات (Anomalies). المشاكل الثلاثة الرئيسية هي:
1. **Insert Anomaly**: عدم القدرة على إضافة بيانات لكيان معين إلا لو ارتبطت بكيان آخر (مثل إضافة عميل جديد بدون أن يشتري).
2. **Update Anomaly**: الاضطرار لتحديث نفس المعلومة في صفوف متعددة لو تكررت، مما يعرض البيانات لخطر عدم الاتساق (Inconsistency) لو سقطت صفوف من التعديل.
3. **Delete Anomaly**: فقدان بيانات كيان بشكل غير مقصود عند حذف سجل مرتبط بكيان آخر (مثل مسح بيانات العميل بالكامل بمجرد حذف الأوردر اليتيم بتاعه).

### Q33 — الشروط التفصيلية للمستوى الأول (1NF - First Normal Form) مع مثال حقيقي لفك الجداول المكلكعة
#### أصل الحكاية
علشان نقول إن الجدول بتاعنا وصل للمستوى الأول من التطبيع (1NF)، لازم نطبق قاعدة أساسية: **كل خلية في الجدول لازم تحتوي على قيمة واحدة بس غير قابلة للتجزئة (Atomic Value)، وممنوع وجود مجموعات متكررة (Repeating Groups) أو مصفوفات داخل الخلية.**
تخيل إنك بتصمم جدول للمستخدمين في نظام تجارة إلكترونية، والمستخدم عنده أكتر من رقم تليفون. لو عملت حقل اسمه `phone_numbers` وحطيت فيه الأرقام مفصولة بفاصلة (زي: "010000000, 012000000")، الجدول ده كدة كسر شرط الـ 1NF.
المشكلة هنا إن لو حبيت تبحث عن رقم تليفون معين، الداتابيز مش هتعرف تستخدم الفهرس (Index) وهتضطر تعمل Full Table Scan مع عمليات معالجة نصوص معقدة وبطيئة جداً. وكمان إضافة رقم جديد أو تعديل رقم هيبقى كابوس.
الشروط الرسمية للـ 1NF:
1. القيم في كل عمود لازم تكون ذرية (Atomic).
2. البيانات في كل عمود لازم تكون من نفس النوع (Domain).
3. كل صف لازم يكون فريد (وجود مفتاح أساسي Primary Key).
4. ترتيب الصفوف أو الأعمدة مش بيأثر على معنى البيانات.

```sql
-- Bad design: Non-1NF table (Repeating groups inside one field)
CREATE TABLE users_bad_1nf (
    user_id INT PRIMARY KEY,
    username VARCHAR(100),
    phones VARCHAR(255) -- "010111,012222,015555" (Violates 1NF)
);

-- Good design: 1NF compliant table
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    username VARCHAR(100)
);

CREATE TABLE user_phones (
    phone_id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT,
    phone_number VARCHAR(20) UNIQUE,
    FOREIGN KEY (user_id) REFERENCES users(user_id)
);
```

#### مثال 1: البحث عن عميل برقم تليفونه
لو عميل اتصل بالدعم الفني ورقم تليفونه متخزن في سلسلة نصية طويلة (phones):
- السيستم هيضطر يلف على كل العملاء ويعمل استعلام زي `LIKE '%010111%'` وده استعلام مدمر للأداء ومستحيل يستفيد من أي Index.
- في التصميم المنظم (1NF)، البحث هيبقى مباشر بـ `SELECT user_id FROM user_phones WHERE phone_number = '010111'` والاستعلام ده هيخلص في جزء من الملي ثانية لأن عمود رقم التليفون متفهرس.

#### مثال 2: تحديث أو حذف رقم تليفون معين
لو يوزر حب يمسح رقم تليفون قديم من حساب فيه 3 أرقام، في التصميم السيئ السيرفر هيضطر يقرأ النص بالكامل، ويعمل عمليات قص ولصق للنص في الكود، ويرجع يحفظه. في التصميم الصح، بنعمل `DELETE` للصف الخاص بالرقم ده من جدول الهواتف بطلب مباشر وبسيط.

### الفايدة الانترفيوية
What is the First Normal Form (1NF), and what is an "Atomic Value"?
**الإجابة النموذجية:**
المستوى الأول من التطبيع (1NF) يشترط أن تكون كل القيم المخزنة في خلايا الجدول قيمًا ذرية (Atomic Values)، أي غير قابلة للتقسيم أو التجزئة، ويمنع تماماً تخزين قوائم أو مصفوفات أو مجموعات متكررة في خلية واحدة. كذلك، يتطلب تحديد مفتاح أساسي (Primary Key) لتمييز كل صف بشكل فريد. عدم تطبيق 1NF يؤدي إلى صعوبة البحث والتصفية، ويمنع محرك قاعدة البيانات من استخدام الفهارس (Indexes) بكفاءة لتسريع الاستعلامات.

### Q34 — المستوى الثاني (2NF - Second Normal Form): إزاي بنتخلص من الـ Partial Dependency؟
#### أصل الحكاية
علشان الجدول يتأهل للمستوى الثاني (2NF)، لازم يحقق شرطين:
1. يكون بالفعل محقق شروط المستوى الأول (1NF).
2. **عدم وجود أي اعتماد جزئي (No Partial Dependency)**. ده معناه إن كل الأعمدة اللي مش جزء من المفتاح الأساسي (Non-key attributes) لازم تعتمد على المفتاح الأساسي بالكامل، مش على جزء منه بس.
المشكلة دي بتظهر تحديداً لما يكون عندنا مفتاح أساسي مركب (Composite Primary Key) بيتكون من أكتر من عمود.
تخيل نظام لتسجيل الطلاب في الكورسات. عملنا جدول فيه المفتاح الأساسي هو (`student_id` و `course_id`) مع بعض.
وحطينا في نفس الجدول الأعمدة دي: `grade` (الدرجة)، و `course_name` (اسم الكورس).
هنا الـ `grade` بتعتمد على الطالب والكورس مع بعض (اعتماد كلي)، فـ ده تمام.
لكن `course_name` بيعتمد على `course_id` بس! ملوش أي علاقة بالـ `student_id`. ده اسمه **Partial Dependency (اعتماد جزئي)**.
لو كورس ملوش طلبة مسجلين فيه، مش هنقدر نسجل اسم الكورس في السيستم! ولو غيرنا اسم الكورس، هنضطر نعدل الاسم في كل صفوف الطلبة اللي مسجلين فيه.

الحل هنا إننا نفصل البيانات دي لجدولين: جدول للكورسات وجدول لربط الطلاب بالكورسات وتسجيل الدرجات.

```sql
-- Bad design: Violates 2NF (Partial dependency on course_id)
CREATE TABLE student_courses_bad (
    student_id INT,
    course_id INT,
    course_name VARCHAR(100), -- Depends ONLY on course_id, not student_id
    grade VARCHAR(2),
    PRIMARY KEY (student_id, course_id)
);

-- Good design: 2NF compliant
CREATE TABLE courses (
    course_id INT PRIMARY KEY,
    course_name VARCHAR(100)
);

CREATE TABLE student_courses (
    student_id INT,
    course_id INT,
    grade VARCHAR(2),
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (course_id) REFERENCES courses(course_id)
);
```

#### مثال 1: تعديل اسم كورس في الجامعة
لو الجامعة قررت تغير اسم كورس "مبادئ البرمجة" لـ "البرمجة للمبتدئين":
- في التصميم السيئ، لو فيه 5000 طالب مسجلين الكورس، هنعدل 5000 صف.
- في التصميم الـ 2NF، هنعدل صف واحد بس في جدول `courses` والتعديل هيسمع تلقائياً لكل الطلبة بدون أي تكرار أو خطر لعدم الاتساق.

#### مثال 2: طرح كورس جديد في السيستم
لو حابين نطرح كورس جديد لسة مفيش أي طالب سجل فيه:
- في التصميم القديم، مستحيل نسجله لأن الـ `student_id` جزء من المفتاح الأساسي ومينفعش يكون NULL.
- في التصميم الجديد، هنسجل الكورس بكل سهولة في جدول `courses` وننتظر لحد ما الطلبة تبدأ تسجل فيه براحتها.

### الفايدة الانترفيوية
What is Second Normal Form (2NF), and what is "Partial Dependency"?
**الإجابة النموذجية:**
المستوى الثاني من التطبيع (2NF) يشترط أولاً أن يكون الجدول في المستوى الأول (1NF)، وثانياً أن يقضي تماماً على الاعتماد الجزئي (Partial Dependency). الاعتماد الجزئي يعني وجود عمود غير مفتاحي يعتمد على جزء فقط من المفتاح الأساسي المركب (Composite Primary Key) وليس على المفتاح بالكامل. لحل المشكلة دي، بنفصل الأعمدة ذات الاعتماد الجزئي في جدول مستقل يكون الجزء المعتمد عليه هو المفتاح الأساسي له.

### Q35 — المستوى الثالث (3NF - Third Normal Form): التخلص من الـ Transitive Dependency بالبلدي وبالمثال
#### أصل الحكاية
علشان الجدول يوصل للمستوى الثالث (3NF)، لازم يحقق شرطين:
1. يكون بالفعل محقق شروط المستوى الثاني (2NF).
2. **عدم وجود أي اعتماد انتقالي (No Transitive Dependency)**. بالبلدي كدة: الأعمدة اللي مش مفتاح أساسي لازم تعتمد على المفتاح الأساسي بس، ومينفعش عمود يعتمد على عمود تاني والعمود التاني ده هو اللي بيعتمد على المفتاح الأساسي.
فيه مقولة مشهورة بتلخص ده: "البيانات لازم تعتمد على المفتاح الأساسي، المفتاح الأساسي بالكامل، ولا شيء غير المفتاح الأساسي" (The key, the whole key, and nothing but the key).
تخيل نظام لإدارة الموظفين في شركة. عملنا جدول للموظفين فيه الأعمدة دي: `emp_id` (مفتاح أساسي)، `emp_name` (اسم الموظف)، `dept_id` (معرف القسم)، و `dept_name` (اسم القسم).
هنا:
- `emp_name` بيعتمد مباشرة على الـ `emp_id` (صح).
- `dept_id` بيعتمد مباشرة على الـ `emp_id` (صح).
- `dept_name` بيعتمد على `dept_id`! وبما إن `dept_id` بيعتمد على `emp_id` فـ كدة الـ `dept_name` بيعتمد بشكل انتقالي على الـ `emp_id`.
ده اسمه **Transitive Dependency (اعتماد انتقالي)**.
لو مسحنا الموظف الوحيد اللي شغال في قسم "التسويق"، بيانات قسم "التسويق" واسمه هيتمسحوا تماماً من السيستم! ولو حبينا نعدل اسم القسم، هنضطر نعدله في كل صفوف الموظفين اللي شغالين فيه.

الحل هنا إننا نفصل بيانات الأقسام في جدول مستقل ونربطهم بـ `dept_id`.

```sql
-- Bad design: Violates 3NF (Transitive dependency on dept_id)
CREATE TABLE employees_bad (
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(100),
    dept_id INT,
    dept_name VARCHAR(100) -- Depends on dept_id, which depends on emp_id
);

-- Good design: 3NF compliant
CREATE TABLE departments (
    dept_id INT PRIMARY KEY,
    dept_name VARCHAR(100)
);

CREATE TABLE employees (
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(100),
    dept_id INT,
    FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
);
```

#### مثال 1: نقل موظف لقسم جديد
لو موظف اتنقل من قسم "الحسابات" لقسم "الموارد البشرية":
- في التصميم السيئ، لو غيرنا الـ `dept_id` ونسينا نغير الـ `dept_name` الموظف هيبقى عنده بيانات متضاربة (مثلاً المعرف 2 بس الاسم الحسابات).
- في التصميم الـ 3NF، بنغير الـ `dept_id` بس للموظف، والاسم بيتقرأ تلقائياً من جدول الأقسام، وبكدة منعنا أي تضارب.

#### مثال 2: الاحتفاظ بأقسام خالية من الموظفين
لو أنشأنا قسم جديد اسمه "البحث والتطوير" ولسة ما عيناش فيه حد:
- في التصميم القديم، مستحيل نسجل القسم ده لأن مفيش موظف يتربط بيه.
- في التصميم الجديد، بنضيف القسم في جدول `departments` ويفضل موجود ومحفوظ حتى لو ملوش أي سجلات مرتبطة في جدول الموظفين.

### الفايدة الانترفيوية
What is Third Normal Form (3NF), and what is "Transitive Dependency"?
**الإجابة النموذجية:**
المستوى الثالث من التطبيع (3NF) يتطلب أن يكون الجدول في المستوى الثاني (2NF)، وألا يحتوي على أي اعتماد انتقالي (Transitive Dependency). الاعتماد الانتقالي يحدث عندما يعتمد عمود غير مفتاحي على عمود غير مفتاحي آخر، والذي بدوره يعتمد على المفتاح الأساسي (إذا كان A -> B و B -> C، فإن A -> C هو اعتماد انتقالي). للتخلص منه، نقوم بفصل العمود المعتمد والمعتمد عليه في جدول مستقل لمنع تكرار البيانات وحمايتها من التضارب والتلف عند الحذف.

### Q36 — الـ BCNF (Boyce-Codd Normal Form): إيه الفرق بينه وبين 3NF وإيه الحالات النادرة اللي بنحتاجه فيها؟
#### أصل الحكاية
الـ BCNF هو نسخة أقوى وأكتر صرامة من الـ 3NF، وبيتسمى ساعات "المستوى 3.5".
القاعدة الذهبية للـ BCNF بتقول: **لكل اعتماد وظيفي غير تافه (Non-trivial Functional Dependency) في الجدول على شكل X -> Y، لازم الـ X يكون مفتاح مرشح (Candidate Key / Super Key).**
يعني ببساطة: أي حقل بيحدد قيمة حقل تاني، لازم يكون مفتاح أساسي أو جزء من مفتاح أساسي مرشح لتمييز الصف.
في الـ 3NF، كان مسموح لعمود يكون معتمد على حقل مش مفتاح أساسي، بشرط إن العمود المعتمد ده يكون جزء من مفتاح مرشح (Prime Attribute). الـ BCNF قفل الباب ده تماماً ومنع الاستثناء ده.
المشكلة دي نادرة الحدوث وبتحصل بس لما يكون عندنا:
1. الجدول له مفاتيح مرشحة متعددة ومتداخلة (Composite Candidate Keys).
2. المفاتيح دي بتشترك في أعمدة مع بعض.

تخيل تطبيق لتنظيم الدروس الخصوصية في مدرسة. عندنا الجدول فيه:
- `student_id` (معرف الطالب).
- `subject` (المادة).
- `teacher` (المدرس).
وعندنا القواعد دي:
- كل طالب بياخد مادة معينة مع مدرس واحد بس للمادة دي. فـ المفتاح الأساسي المركب هيبقى (`student_id`, `subject`).
- كل مدرس بيدرس مادة واحدة بس (يعني `teacher` بيحدد الـ `subject`).
هنا فيه اعتماد وظيفي: `teacher` -> `subject`.
لكن الـ `teacher` مش مفتاح أساسي ولا مفتاح مرشح! هو مجرد عمود عادي.
الجدول ده في الـ 3NF لأن الـ `subject` جزء من المفتاح الأساسي المركب (Prime Attribute).
لكنه كاسر لشرط الـ BCNF لأن الـ `teacher` (الطرف الأيسر من الاعتماد) مش Candidate Key.
ده بيعمل مشاكل: لو مدرس اتعين جديد وبيدرس مادة معينة، مش هنقدر نسجله في الداتابيز إلا لو ربطناه بطالب سجل عنده!

الحل هو تفكيك الجدول لجدولين: جدول يربط المدرس بالمادة، وجدول يربط الطالب بالمدرس.

```sql
-- Bad design: Violates BCNF (teacher -> subject, but teacher is not a candidate key)
CREATE TABLE tutoring_bad (
    student_id INT,
    subject VARCHAR(100),
    teacher VARCHAR(100),
    PRIMARY KEY (student_id, subject)
);

-- Good design: BCNF compliant
CREATE TABLE teacher_subjects (
    teacher VARCHAR(100) PRIMARY KEY,
    subject VARCHAR(100) NOT NULL
);

CREATE TABLE student_teachers (
    student_id INT,
    teacher VARCHAR(100),
    PRIMARY KEY (student_id, teacher),
    FOREIGN KEY (teacher) REFERENCES teacher_subjects(teacher)
);
```

#### مثال 1: إضافة مدرس جديد للمدرسة
لو وظفنا مدرس جديد اسمه "مستر أحمد" لمادة "الرياضيات":
- في التصميم السيئ، لو مفيش طالب حجز معاه، مش هنعرف نخزن في السيستم إن مستر أحمد بيدرس رياضيات.
- في التصميم الجديد، هنضيف السجل ببساطة في جدول `teacher_subjects` ويبقى جاهز للحجز.

#### مثال 2: استقالة مدرس
لو المدرس الوحيد لمادة الفلسفة استقال ومسحناه:
- في التصميم القديم، لو مسحنا صف الطالب والمدرس، مادة الفلسفة نفسها هتتمسح من قائمة المواد المتاحة.
- في التصميم الجديد، المادة بتفضل محفوظة ومسجلة في جدول المواد والمدرسين المنفصل.

### الفايدة الانترفيوية
What is Boyce-Codd Normal Form (BCNF), and how does it differ from 3NF?
**الإجابة النموذجية:**
الـ BCNF هو مستوى متقدم من التطبيع وهو حالة خاصة وأكثر صرامة من الـ 3NF. الشرط الأساسي للـ BCNF هو أنه لكل اعتماد وظيفي $X 
ightarrow Y$، لازم الطرف الأيسر $X$ مفتاحاً مرشحاً (Candidate Key). الفرق بينهما هو أن الـ 3NF يسمح بالاعتماد إذا كان الطرف الأيمن $Y$ جزءاً من مفتاح مرشح (Prime Attribute)، بينما الـ BCNF يلغي الاستثناء ده تماماً. نلجأ للـ BCNF لحل حالات التكرار الناتجة عن تداخل المفاتيح المركبة المرشحة في الجدول.

### Q37 — الـ Denormalization (إلغاء التطبيع): إمتى بيكون شر لابد منه لتحسين الأداء؟ وإيه المقابل (Trade-offs)؟
#### أصل الحكاية
بعد ما بنعمل Normalization ونوصل للجداول المثالية الخالية من أي تكرار، بنكتشف ساعات في التطبيقات الضخمة (على مستوى ملايين العمليات) إن الأداء بدأ يتدهور جداً في عمليات القراءة (SELECT).
السبب هو إن عشان نعرض صفحة واحدة للمستخدم (زي صفحة تفاصيل الطلب مع بيانات الشحن واسم العميل وتفاصيل المنتجات وعروض الخصم)، السيرفر بيضطر يعمل 7 أو 8 JOINs بين جداول مختلفة. الـ JOINs الكتيرة بتستهلك معالجة الـ CPU والـ Disk IO وبتخلي الاستعلامات بطيئة.
هنا بيجي دور **الـ Denormalization (إلغاء التطبيع)**. وهي خطوة متعمدة بنرجع فيها خطوة لورا، وبنضيف بعض التكرار المحسوب للبيانات أو بنجمع بيانات في صف واحد لتقليل عمليات الـ JOINs وتسريع القراءة.
أمثلة شهيرة للـ Denormalization:
1. **أعمدة التجميع (Aggregation Columns)**: زي تخزين `total_amount` في جدول الأوردر، أو `followers_count` في جدول المستخدمين، بدل ما نعمل `COUNT` أو `SUM` في كل مرة اليوزر بيفتح صفحته.
2. **تكرار حقول للقراءة فقط (Read-Only Fields Cache)**: زي تخزين اسم المنتج وصورته مباشرة داخل جدول تفاصيل الطلب (Order Items)، عشان مش كل ما نعرض الفاتورة نروح نربط بجدول المنتجات، خصوصاً إن المنتجات القديمة ممكن تتمسح أو صورتها تتغير والعميل محتاج يشوف شكل المنتج وقت ما اشتراه.

المقابل (Trade-offs):
- **سرعة القراءة (Read Performance)** بتبقى رهيبة وسريعة جداً.
- **صعوبة الكتابة وتحديث البيانات (Write Complexity)** بتزيد، لأن لو غيرنا قيمة، لازم نحدثها في كذا مكان في نفس الوقت علشان نمنع التضارب، وده بيحتاج نعمل Transactions معقدة أو نستخدم Triggers.
- **مساحة تخزين أكبر** بسبب تكرار الداتا.

```sql
-- Normalized design:
-- Total amount must be calculated on-the-fly: SELECT SUM(price * quantity) ...
-- Denormalized design:
CREATE TABLE orders_denormalized (
    order_id INT PRIMARY KEY,
    customer_id INT,
    total_amount DECIMAL(10,2), -- Denormalized column to store pre-calculated sum
    customer_name_cached VARCHAR(100) -- Cached to display in order list without JOIN
);
```

#### مثال 1: صفحة الـ News Feed في السوشيال ميديا
في تطبيقات زي فيسبوك، لو السيستم بيحسب الـ likes والـ comments لكل بوست بـ `COUNT` حية من جداول التفاعل كل ما يوزر يمرر الشاشة، السيرفرات هتقع فوراً.
السيستم بيخزن رقم مسبق الحساب `likes_count` و `comments_count` في صف البوست نفسه، وبيزوده بـ +1 مع كل تفاعل جديد. دي عملية كتابة أغلى سنة، بس بتوفر ملايين العمليات الحسابية في الثانية للقراءة.

#### مثال 2: الفواتير التاريخية وتغير الأسعار
لو عميل اشترى تيشرت بـ 100 جنيه، وبعد شهر سعر التيشرت في المحل بقى 150 جنيه.
في التصميم المطبع بالكامل، لو الفاتورة بتربط بجدول المنتجات عشان تجيب السعر والصورة الحالية، الفاتورة القديمة هتظهر للعميل بـ 150 جنيه وده خطأ مالي فادح. تكرار السعر والصورة داخل صف الفاتورة (Denormalization) هنا مش بس بيحسن الأداء، ده ضرورة عمل لتوثيق الحالة التاريخية للمعاملة المالية.

### الفايدة الانترفيوية
What is database Denormalization, and when is it acceptable to use it?
**الإجابة النموذجية:**
الـ Denormalization هي عملية إدخال تكرار للبيانات بشكل متعمد ومدروس في قاعدة البيانات بعد عملية التطبيع، بهدف تسريع استعلامات القراءة (Read Queries) وتقليل عمليات الـ JOINs وحسابات التجميع (Aggregations) المكلفة على السيرفر.
يتم قبول استخدامها في الأنظمة اللي تكون فيها نسبة القراءة أعلى بكثير من الكتابة (Read-Heavy Systems) مثل لوحات التحكم (Dashboards) وصفحات التواصل الاجتماعي.
المقايضة الرئيسية (Trade-off) هي الحصول على سرعة قراءة فائقة مقابل زيادة تعقيد عمليات الكتابة (Write Complexity) والحاجة لإدارة مزامنة البيانات المتكررة لمنع التضارب، بالإضافة لاستهلاك مساحة تخزين أكبر.

### Q38 — علاقات الجداول الثلاثة (1:1، 1:N، N:M): إزاي بنصممها صح في الـ Schema وبنمنع الغلطات الشائعة؟
#### أصل الحكاية
في تصميم الـ Schema، العلاقات بين الكيانات بتنقسم لتلات أنواع رئيسية. تصميم العلاقة دي غلط بيوقع أداء السيستم وبيقسم الداتا بطرق غريبة.
1. **علاقة واحد لواحد (1:1 - One to One)**:
   - **المفهوم**: كل صف في الجدول `A` يرتبط بصف واحد بس في الجدول `B` والعكس.
   - **التصميم الصح**: بنحط الـ Primary Key بتاع الجدول `A` كـ Foreign Key في الجدول `B` مع وضع شرط الفرادة عليه (`UNIQUE`).
   - **مثال**: جدول المستخدمين `users` وجدول تفاصيل الحساب السري والمستندات `user_profiles`. بنفصلهم للحفاظ على أمان البيانات وسرعة قراءة الجدول الأساسي.
2. **علاقة واحد لمتعدد (1:N - One to Many)**:
   - **المفهوم**: الصف الواحد في الجدول `A` يرتبط بأكثر من صف في الجدول `B`، بس الصف في `B` يرتبط بصف واحد بس في `A`.
   - **التصميم الصح**: بنحط المفتاح الأساسي للجدول `A` (الواحد) كمفتاح خارجي (Foreign Key) في الجدول `B` (المتعدد).
   - **مثال**: العميل والأوردرات. العميل الواحد له أوردرات كتير، بس الأوردر ملوش غير عميل واحد صاحب الطلب.
3. **علاقة متعدد لمتعدد (N:M - Many to Many)**:
   - **المفهوم**: الصف الواحد في `A` يرتبط بأكثر من صف في `B`، والصف الواحد في `B` يرتبط بأكثر من صف في `A`.
   - **التصميم الصح**: مستحيل نمثلها بجدولين بس مباشرة. لازم نعمل جدول وسيط (Junction / Bridge / Association Table) يحتوي على المفاتيح الأساسية للجدولين كـ Foreign Keys مع بعض، والاتنين سوا بيعملوا المفتاح الأساسي المركب للجدول الوسيط.
   - **مثال**: الطلاب والمواد الدراسية، أو المنتجات والأوردرات (المنتج يظهر في كذا أوردر، والأوردر يحتوي على كذا منتج).

الغلطات الشائعة:
- محاولة تصميم علاقة N:M بوضع قائمة معرفات مفصولة بفاصلة في جدول واحد (كسر الـ 1NF).
- نسيان وضع الـ `UNIQUE` constraint في علاقة الـ 1:1، مما يحولها لعلاقة 1:N بدون قصد.
- نسيان تحديد الـ Cascade policies (ماذا يحدث للبيانات التابعة عند حذف السجل الرئيسي: هل يتم الحذف تلقائياً `ON DELETE CASCADE` أم نمنع الحذف `ON DELETE RESTRICT` أم نضع قيم فارغة `ON DELETE SET NULL`؟).

```sql
-- 1. One-to-One (1:1)
CREATE TABLE user_profiles (
    profile_id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT UNIQUE, -- UNIQUE constraint makes it 1:1
    bio TEXT,
    FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE
);

-- 2. One-to-Many (1:N)
CREATE TABLE orders (
    order_id INT PRIMARY KEY AUTO_INCREMENT,
    customer_id INT, -- Foreign key here allows multiple orders for one customer
    order_date DATE,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id) ON DELETE RESTRICT
);

-- 3. Many-to-Many (N:M) using a Junction Table
CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT,
    PRIMARY KEY (order_id, product_id), -- Composite PK
    FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE CASCADE,
    FOREIGN KEY (product_id) REFERENCES products(product_id) ON DELETE RESTRICT
);
```

#### مثال 1: الـ Junction Table في الـ E-commerce
لو بنصمم سلة المشتريات لمتجر، ما ينفعش نحط المنتجات جوة جدول الأوردر مباشرة كعمود نصي لأن ده هيمنعنا من حساب إجمالي الأرباح لكل منتج أو عمل جرد للمخزن.
الجدول الوسيط `order_items` هو اللي بيسمح لنا نربط أي منتج بأي أوردر ونخزن معاه معلومات خاصة بالعملية دي بالذات زي الكمية وسعر البيع وقتها.

#### مثال 2: خطورة الحذف التلقائي (Cascading Delete) في الأنظمة المالية
في نظام المدفوعات، لو مسحنا حساب عميل:
- لو ضبطنا العلاقة `ON DELETE CASCADE` بين العملاء والفواتير، السيستم هيمسح كل فواتير العميل وتاريخه المالي تلقائياً! وده كارثة محاسبية وجريمة قانونية للشركات.
- التصميم الصح في الحالات دي هو استخدام `ON DELETE RESTRICT` لمنع حذف العميل لو له أي سجل مالي، أو تعديل حالة الحساب لـ "غير نشط" بدل مسحه تماماً.

### الفايدة الانترفيوية
Explain the three types of database relationships and how they are physically implemented in SQL schemas.
**الإجابة النموذجية:**
العلاقات الثلاثة هي:
1. **One-to-One (1:1)**: يتم ربط الجدولين عن طريق وضع المفتاح الأساسي للجدول الأول كمفتاح خارجي (Foreign Key) في الجدول الثاني مع إضافة قيد الفرادة (`UNIQUE`) عليه لمنع ارتباط السجل بأكثر من سجل آخر.
2. **One-to-Many (1:N)**: يتم تمثيلها بوضع المفتاح الأساسي لجدول الطرف "الواحد" كمفتاح خارجي في جدول الطرف "المتعدد".
3. **Many-to-Many (N:M)**: لا يمكن تمثيلها مباشرة بين جدولين، ويتم حلها بإنشاء جدول وسيط (Junction Table) يحتوي على مفتاحين خارجيين يشيران للجدولين الرئيسيين، ويشكلان معاً المفتاح الأساسي المركب للجدول الوسيط.

### Q39 — الـ Constraints (القيود) في تصميم الجداول (CHECK, UNIQUE, NOT NULL): تأثيرها على جودة البيانات وعلى سرعة الكتابة
#### أصل الحكاية
المطورين المبتدئين دايماً بيقولوا: "أنا هعمل كل عمليات التحقق من البيانات (Validation) في كود الباك إند (Node.js/Python)، ومش محتاج أحط قيود (Constraints) في قاعدة البيانات علشان ما تضايقنيش وأنا بكتب داتا".
دي وجهة نظر خطيرة جداً. كود التطبيق ممكن يحتوي على ثغرات، أو يحصل فيه أخطاء برمجية (Bugs) تسجل داتا بايظة. كمان، قاعدة البيانات ممكن يتكتب فيها من مصادر تانية زي لوحات التحكم (Admin Panels) أو أدوات الهجرة (Migration Scripts)، ومن غير قيود داخلية، الداتا هتبوظ بسرعة.
الـ Constraints هي خط الدفاع الأخير والأقوى لسلامة البيانات (Data Integrity):
1. **NOT NULL**: بيجبر السيستم إن الحقل لازم يحتوي على قيمة، ومستحيل يكون فارغ (NULL). زي البريد الإلكتروني للعميل.
2. **UNIQUE**: بيضمن إن القيمة مش هتتكرر في الجدول كله، ومحرك الداتابيز بيعمل فهرس فريد (Unique Index) تحت الـ hood لتسريع التحقق.
3. **CHECK Constraint**: بيسمح لنا نحدد شرط منطقي لازم القيمة تحققه عشان تتخزن. زي: `CHECK (age >= 18)` أو `CHECK (price > 0)`.

التأثير على الأداء:
- **عمليات القراءة (Read Performance)**: بتتحسن! الـ Optimizer يقدر يستخدم الـ Constraints دي لبناء خطة استعلام ذكية (مثلاً لو كتبت استعلام يدور على سعر أقل من صفر، الـ Optimizer هيرد فوراً بصفر صفوف بدون ما يقرأ من الديسك أصلاً لأنه عارف إن فيه قيد بيمنع ده).
- **عمليات الكتابة (Write Performance)**: بتقل بنسبة بسيطة جداً، لأن السيرفر بيضطر يعمل عملية تحقق إضافية مع كل عملية `INSERT` أو `UPDATE` للتأكد من عدم كسر القيود. لكن التكلفة دي لا تذكر مقارنة بالأمان وجودة البيانات اللي بنحصل عليها.

```sql
-- Creating a table with strong constraints
CREATE TABLE bank_accounts (
    account_id INT PRIMARY KEY AUTO_INCREMENT,
    account_holder VARCHAR(100) NOT NULL, -- Cannot be empty
    email VARCHAR(100) UNIQUE NOT NULL,    -- Cannot be duplicated, builds Unique Index
    balance DECIMAL(15,2) DEFAULT 0.00,
    status VARCHAR(20) DEFAULT 'active',
    -- CHECK constraints block invalid data at the engine level
    CONSTRAINT chk_balance CHECK (balance >= 0.00),
    CONSTRAINT chk_status CHECK (status IN ('active', 'suspended', 'closed'))
);
```

#### مثال 1: منع الرصيد السالب في البنوك
لو بنعمل عملية سحب فلوس، وحصل خطأ برمجي (Race Condition) سمح بسحب مبلغ أكبر من المتاح.
لو عندنا `CHECK (balance >= 0.00)`، قاعدة البيانات هترفض العملية فوراً وتعمل Rollback للحركة المالية تلقائياً وتطلع خطأ للمستخدم، وبكدة حمت البنك من خسارة مالية حقيقية.

#### مثال 2: البريد الإلكتروني المتكرر
لو يوزر حاول يعمل حسابين بنفس الإيميل في نفس اللحظة بالتوازي. لو التحقق في الباك إند بس، الاستعلامين ممكن يعدوا مع بعض ويسجلوا الإيميل مرتين.
وجود الـ `UNIQUE` constraint هيخلي الداتابيز تمنع العملية التانية فوراً لأن الـ Unique Index بيعمل قفل يمنع التكرار اللحظي.

### الفايدة الانترفيوية
Why should you enforce constraints (like CHECK, UNIQUE, NOT NULL) at the database level instead of relying solely on application-level validation?
**الإجابة النموذجية:**
فرض القيود (Constraints) على مستوى قاعدة البيانات أمر جوهري لأنه يضمن سلامة البيانات واتساقها (Data Integrity) كخط دفاع أخير ضد الأخطاء البرمجية (Bugs) في كود التطبيق، ويحمي البيانات عند تعديلها من مصادر متعددة خارج التطبيق الرئيسي (مثل لوحات التحكم أو أدوات التحليل).
علاوة على ذلك، القيود تساعد الـ Query Optimizer في استبعاد العمليات المستحيلة مبكراً وتحسين خطط الاستعلام. بينما تكلفتها على أداء الكتابة ضئيلة وتتمثل في وقت التحقق الإضافي، إلا أنها توفر حماية كاملة للبيانات تمنع حدوث مشاكل مالية أو تقنية معقدة لاحقاً.

### Q40 — إيه هي الـ Transaction وإيه الفرق بين Commit وRollback؟
#### أصل الحكاية
لما بنعمل تحويل بنكي من حساب لحساب تاني، السيستم لازم ينفذ خطوتين في نفس الوقت: يخصم من الحساب الأول، ويضيف للحساب التاني. لو الخطوة الأولى نجحت والسيرفر وقع قبل الخطوة التانية، الفلوس راحت من الحساب ومجاتش للحساب التاني!

الـ **Transaction** هي مجموعة من عمليات قاعدة البيانات بتتعامل كوحدة واحدة لا تتجزأ. إما كلها بتنجح (**Commit**) وإما كلها بتتراجع (**Rollback**) كأنها ما حصلتش.

```sql
-- Banking transfer example
START TRANSACTION;

UPDATE accounts SET balance = balance - 500 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 500 WHERE account_id = 2;

-- If everything is OK:
COMMIT;

-- If any error happened:
-- ROLLBACK;
```

#### مثال: طلب شراء في E-commerce
لما مستخدم بيكمل عملية الشراء، السيستم لازم ينفذ 3 عمليات مع بعض:
1. يخصم الكمية من المخزون.
2. يسجل الأوردر الجديد.
3. يسجل عملية الدفع.

لو أي واحدة فيهم فشلت، الـ Rollback بيرجع كل حاجة لحالتها الأصلية ومفيش حاجة اتأثرت.

### الفايدة الانترفيوية
What is a database transaction, and what is the difference between COMMIT and ROLLBACK?
**الإجابة النموذجية:**
الـ Transaction هي وحدة عمل منطقية تجمع أكثر من عملية على قاعدة البيانات تُنفَّذ كوحدة واحدة لا تتجزأ. الـ `COMMIT` يحفظ كل التغييرات بشكل دائم، والـ `ROLLBACK` يتراجع عن كل التغييرات كأنها لم تحدث، لضمان اتساق البيانات في حالات الأخطاء.

### Q41 — خصائص الـ ACID: شرح كل خاصية بمثال واقعي من الأنظمة الحقيقية
#### أصل الحكاية
الـ ACID هي الضمان الأساسي لأي قاعدة بيانات علاقاتية جادة. كل حرف فيها بيمثل خاصية:

**A — Atomicity (الذرية)**
الـ Transaction كلها تنجح أو كلها تفشل. مفيش نص نجاح.
- **المثال**: لو السيستم وقع بعد خصم الفلوس من حسابك ومقدرش يضيفها للحساب التاني، الـ Rollback التلقائي بيرجع الفلوس لحسابك فوراً.

**C — Consistency (الاتساق)**
قاعدة البيانات لازم تبدأ من حالة صحيحة وتنهي في حالة صحيحة. الـ Constraints والـ Rules مش بتتكسر أبداً.
- **المثال**: لو عندك `CHECK (balance >= 0)`، الـ Transaction اللي بتحاول تخلي الرصيد سالب هتتعمل Rollback تلقائياً حتى لو الكود نسي يتحقق.

**I — Isolation (العزل)**
كل Transaction شايفاها العالم وحدها. التغييرات اللي بتعملها مش بيشوفها حد تاني لحد ما تعمل Commit.
- **المثال**: لو اتنين مستخدمين بيشتروا آخر قطعة في المخزون في نفس الوقت، الـ Isolation بيضمن إن واحد بس هيتمكن من الإكمال.

**D — Durability (الديمومة)**
بعد الـ Commit، البيانات بتتحفظ بشكل دائم حتى لو السيرفر وقع في اللحظة دي.
- **المثال**: بنك بيعمل Commit لتحويل مالي، السيرفر وقع بعدها بثانية. لما السيرفر بيرجع، التحويل بيلاقيه محفوظ لأن الداتابيز بتكتب في الـ Write-Ahead Log (WAL) قبل ما تأكد الـ Commit.

```sql
-- Demonstrating ACID in a banking transaction
START TRANSACTION;

-- A: Both operations succeed or both fail (Atomicity)
UPDATE accounts SET balance = balance - 1000 WHERE id = 1 AND balance >= 1000;
-- Check if the row was actually updated (Consistency check)
-- Application code checks affected rows count here

UPDATE accounts SET balance = balance + 1000 WHERE id = 2;

COMMIT;
-- D: After COMMIT, data survives server crashes (Durability via WAL)
```

### الفايدة الانترفيوية
Explain the four ACID properties with a real-world example for each.
**الإجابة النموذجية:**
الـ ACID هي 4 خصائص بتضمن موثوقية الـ Transactions:
- **Atomicity**: كل عمليات الـ Transaction تنجح أو تفشل كوحدة واحدة — إما كلها أو لا شيء.
- **Consistency**: البيانات تبدأ وتنتهي في حالة صحيحة تحترم كل القيود المعرَّفة.
- **Isolation**: الـ Transactions المتزامنة معزولة عن بعض، ومش بتشوف التغييرات الوسيطة لبعضها.
- **Durability**: بعد الـ Commit، البيانات محفوظة للأبد حتى في حالة انهيار السيرفر، عن طريق الـ Write-Ahead Log.

### Q42 — مشاكل التزامن (Concurrency Problems): الـ Dirty Read، Phantom Read، وNon-Repeatable Read
#### أصل الحكاية
لما عندنا ملايين المستخدمين بيعملوا عمليات على قاعدة البيانات في نفس الوقت، بتظهر 3 مشاكل كلاسيكية:

**1. Dirty Read (القراءة القذرة)**
Transaction بتقرأ بيانات عدّلتها Transaction تانية لسه ما عملتش Commit. لو التانية عملت Rollback، الأولى قرأت بيانات خاطئة.
- **مثال**: كاشير بيشوف رصيد حساب = 5000 جنيه. في نفس اللحظة، Transaction تانية خصمت 4000 جنيه ولسه ما عملتش Commit. الكاشير سمح بعملية بـ 3000 جنيه اعتماداً على الـ 5000 القديمة. بعدين التانية عملت Rollback والرصيد رجع 5000. النتيجة: العميل اشترى بـ 3000 من رصيد 5000 ما اتخصمتش منه فعلاً.

**2. Non-Repeatable Read (القراءة غير المتكررة)**
Transaction بتقرأ نفس الصف مرتين وبتلاقي الداتا اتغيرت بين القراءتين لأن Transaction تانية عملت Commit في النص.
- **مثال**: تقرير مالي بيجمع بيانات على مرحلتين. في المرحلة الأولى قرأ سعر منتج = 100. Transaction تانية غيرت السعر لـ 120 وعملت Commit. في المرحلة التانية التقرير قرأ 120. التقرير خرج غير متسق.

**3. Phantom Read (القراءة الوهمية)**
Transaction بتنفذ استعلام مرتين وبتلاقي عدد الصفوف اتغير في المرة التانية لأن Transaction تانية أضافت أو مسحت صفوف في النص.
- **مثال**: Transaction بتعد عدد المستخدمين المشتركين في خطة مميزة. مرة أولى لقيت 99. Transaction تانية أضافت مستخدم جديد وعملت Commit. مرة تانية لقيت 100. الـ Transaction الأولى شافت صف جديد (Phantom) ما كانش موجود أول مرة.

### الفايدة الانترفيوية
What are the three main concurrency anomalies: Dirty Read, Non-Repeatable Read, and Phantom Read?
**الإجابة النموذجية:**
- **Dirty Read**: قراءة بيانات غير مؤكدة (Uncommitted) من Transaction لسه شغالة.
- **Non-Repeatable Read**: قراءة نفس الصف مرتين والحصول على نتائج مختلفة بسبب Commit لـ Transaction تانية في المنتصف.
- **Phantom Read**: تنفيذ نفس الاستعلام مرتين والحصول على عدد صفوف مختلف بسبب إضافة أو حذف صفوف من Transaction تانية.

### Q43 — مستويات العزل (Isolation Levels): الـ Trade-offs بين الأمان والأداء
#### أصل الحكاية
قواعد البيانات بتقدم 4 مستويات للعزل بين الـ Transactions المتزامنة. كل مستوى بيتحكم في أي من المشاكل الثلاثة السابقة بيحميك منها، وبتزيد فيه الحماية بتقل فيه السرعة:

| مستوى العزل | Dirty Read | Non-Repeatable Read | Phantom Read | الأداء |
|---|---|---|---|---|
| **READ UNCOMMITTED** | ❌ ممكن | ❌ ممكن | ❌ ممكن | 🚀 أسرع |
| **READ COMMITTED** | ✅ محمي | ❌ ممكن | ❌ ممكن | سريع |
| **REPEATABLE READ** | ✅ محمي | ✅ محمي | ❌ ممكن | متوسط |
| **SERIALIZABLE** | ✅ محمي | ✅ محمي | ✅ محمي | 🐢 أبطأ |

**كيف تختار المستوى المناسب؟**
- **READ UNCOMMITTED**: نادراً ما يُستخدم. مناسب لتقارير إحصائية تقريبية والدقة المطلقة مش مطلوبة وسرعة القراءة أهم.
- **READ COMMITTED**: الإعداد الافتراضي في PostgreSQL وأغلب الأنظمة. مناسب لأغلب تطبيقات الويب العادية.
- **REPEATABLE READ**: الإعداد الافتراضي في MySQL/InnoDB. مناسب للتقارير المالية اللي لازم تكون متسقة طول فترة التنفيذ.
- **SERIALIZABLE**: للعمليات الحساسة جداً زي إتمام صفقات بورصة أو حجز تذاكر طيران وأي phantom يسبب كارثة.

```sql
-- Setting isolation level in PostgreSQL
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
-- Your queries here
COMMIT;

-- Setting in MySQL
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

### الفايدة الانترفيوية
What are the four SQL transaction isolation levels, and what concurrency problems does each prevent?
**الإجابة النموذجية:**
الـ 4 مستويات بالترتيب من الأقل للأكثر عزلاً: READ UNCOMMITTED (لا حماية)، READ COMMITTED (يمنع Dirty Read فقط)، REPEATABLE READ (يمنع Dirty و Non-Repeatable Read)، SERIALIZABLE (يمنع الثلاث مشاكل تماماً). الاختيار بيكون Trade-off بين الحماية من مشاكل التزامن وبين الأداء والـ Throughput.

### Q44 — الـ Deadlock: إيه هو وإزاي الداتابيز بتكتشفه وبتتعامل معاه؟
#### أصل الحكاية
الـ **Deadlock** بيحصل لما Transaction A بتستنى Transaction B تحرر Lock على Resource معين، وفي نفس الوقت Transaction B بتستنى Transaction A تحرر Lock على Resource تاني. الاتنين واقفين يستنوا بعض ومش هيتحركوا أبداً.

**مثال من نظام Banking:**
- Transaction A: خصمت من حساب 1 (Locked حساب 1)، وعايزة تضيف لحساب 2 (اللي Transaction B حاطة Lock عليه).
- Transaction B: خصمت من حساب 2 (Locked حساب 2)، وعايزة تضيف لحساب 1 (اللي Transaction A حاطة Lock عليه).
النتيجة: Deadlock!

**إزاي الداتابيز بتتعامل معاه؟**
محرك الداتابيز (InnoDB في MySQL أو PostgreSQL) عنده خوارزمية بتشتغل في الخلفية لاكتشاف الـ Deadlock عن طريق رسم مخطط Wait-For Graph. لما بيشوف دورة (Cycle) في المخطط، بيختار الـ Transaction الأصغر تكلفة ويعمل لها Rollback تلقائياً، والتانية بتكمل شغلها.

**إزاي تقلل الـ Deadlocks في الكود؟**
1. **ترتيب ثابت للـ Resources**: دايماً Lock الـ resources بنفس الترتيب في كل الـ Transactions (مثلاً دايماً اقفل الحساب الأصغر رقماً أولاً).
2. **Transactions قصيرة**: كلما كانت الـ Transaction بتخلص بسرعة، قل وقت الـ Lock وقلت فرصة الـ Deadlock.
3. **Retry Logic**: لما التطبيق يتلقى خطأ Deadlock، يحاول تاني أوتوماتيكياً.

```sql
-- Preventing deadlock: Always lock in consistent order
-- Transaction A and B both lock account with smaller ID first:
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE; -- Lock lower ID first
SELECT * FROM accounts WHERE id = 2 FOR UPDATE; -- Then higher ID
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;
```

### الفايدة الانترفيوية
What is a database deadlock, how does the database engine detect it, and how can you prevent it?
**الإجابة النموذجية:**
الـ Deadlock حالة يحصل فيها انتظار دائري بين Transactions — كل واحدة بتستنى الأخرى تحرر Lock. محرك الداتابيز بيكتشفه عبر Wait-For Graph، ولما يلاقي دورة (Cycle) بيختار Transaction ويعمل لها Rollback تلقائياً. للوقاية: دايماً اقفل الـ Resources بترتيب ثابت ومتسق، خلي الـ Transactions قصيرة قدر الإمكان، وأضف Retry Logic في كود التطبيق.

### Q45 — الـ Optimistic vs Pessimistic Locking: إمتى تستخدم أي منهم؟
#### أصل الحكاية
في الأنظمة المتزامنة، فيه استراتيجيتين للتعامل مع تعارض عمليات الكتابة:

**Pessimistic Locking (القفل المتشائم)**
بتفترض إن التعارض هيحصل غالباً، فبتقفل الـ Resource من أول ما تبدأ تقرأه حتى ما تخلصش من الكتابة.
- الأداة: `SELECT ... FOR UPDATE` في SQL.
- متى تستخدمه؟ في الأنظمة اللي فيها كتابة كتيرة على نفس الـ Rows (زي حجوزات الفنادق، تذاكر الحفلات، مخزون محدود جداً).
- العيب: بطيء لأن الـ Rows المقفولة بتبلوك الـ Transactions التانية.

**Optimistic Locking (القفل المتفائل)**
بتفترض إن التعارض نادر، فمش بتقفل أي حاجة. بدل كدة، بتضيف عمود `version` أو `updated_at` للـ Row. لما بتحاول تكتب، بتتحقق إن الـ version لسه نفسه اللي قرأته. لو اتغير معناها حد تاني سبقك، وبترجع للتطبيق يعالج الموقف.
- متى تستخدمه؟ في الأنظمة اللي فيها قراءة كتيرة وكتابة قليلة وتعارض نادر (زي تعديل بروفايل مستخدم، تعديل مقال في CMS).

```sql
-- Pessimistic Locking: Lock the row immediately on read
START TRANSACTION;
SELECT stock FROM products WHERE id = 42 FOR UPDATE; -- Row is locked now
-- Nobody else can modify this row until we COMMIT
UPDATE products SET stock = stock - 1 WHERE id = 42;
COMMIT;

-- Optimistic Locking: Use a version column
-- Read phase (no lock):
SELECT stock, version FROM products WHERE id = 42;
-- Returns: stock=5, version=7

-- Write phase (check version before update):
UPDATE products 
SET stock = 4, version = 8 
WHERE id = 42 AND version = 7; -- Only updates if nobody changed it
-- If 0 rows affected: conflict! Someone else updated it first. Retry.
```

### الفايدة الانترفيوية
What is the difference between Optimistic and Pessimistic Locking, and when do you use each?
**الإجابة النموذجية:**
الـ **Pessimistic Locking** بتقفل الـ Resource فور القراءة (`SELECT FOR UPDATE`) وبتمنع أي تعديل من طرف تاني لحد الـ Commit. مناسب لأنظمة الكتابة المكثفة على نفس البيانات. الـ **Optimistic Locking** مش بتقفل أي حاجة، بس بتستخدم عمود `version` للتحقق عند الكتابة إن البيانات لم تتغير. مناسب لأنظمة القراءة المكثفة واللي فيها التعارض نادر الحدوث.

### Q46 — الـ Savepoints: إزاي بنعمل Rollback جزئي للـ Transaction؟
#### أصل الحكاية
في العمليات الطويلة والمعقدة، ساعات بنحتاج نرجع خطوة أو اتنين لورا بدل ما نعمل Rollback كامل لكل الـ Transaction من أولها.
الـ **Savepoint** هو علامة بنحطها في نص الـ Transaction. لو حصل خطأ بعدها، بنقدر نعمل `ROLLBACK TO SAVEPOINT` ونرجع للعلامة دي بس، والعمليات اللي قبلها بتفضل محفوظة.

**مثال: نظام E-commerce لمعالجة أوردر**
```sql
START TRANSACTION;

-- Step 1: Record the order
INSERT INTO orders (customer_id, total) VALUES (101, 250.00);
SAVEPOINT order_created; -- Checkpoint 1

-- Step 2: Deduct stock for each item
UPDATE products SET stock = stock - 2 WHERE id = 5;
SAVEPOINT stock_updated; -- Checkpoint 2

-- Step 3: Try to apply discount coupon
UPDATE coupons SET used = TRUE WHERE code = 'SAVE20' AND used = FALSE;
-- If 0 rows affected, coupon is invalid or already used:
-- ROLLBACK TO SAVEPOINT stock_updated; -- Undo only the coupon step, keep the rest
-- (continue without discount)

-- Step 4: Record payment
INSERT INTO payments (order_id, amount) VALUES (LAST_INSERT_ID(), 250.00);

COMMIT; -- Save everything permanently
```

### الفايدة الانترفيوية
What are Savepoints in SQL transactions, and when would you use them?
**الإجابة النموذجية:**
الـ Savepoints هي نقاط تفتيش (Checkpoints) داخل الـ Transaction تسمح بعمل Rollback جزئي للعمليات اللي تمت بعد نقطة معينة دون التأثير على العمليات قبلها. بتُستخدم في العمليات المعقدة متعددة الخطوات واللي فيها فشل خطوة واحدة لا يستوجب إلغاء كل العمل السابق.

### Q47 — الـ Two-Phase Commit (2PC): كيف بنضمن الـ ACID في الأنظمة الموزعة؟
#### أصل الحكاية
في الأنظمة الموزعة (Distributed Systems) زي الـ Microservices، بتكون الداتا موزعة على قواعد بيانات مختلفة على سيرفرات مختلفة. التحدي هو إزاي بنضمن إن Transaction بتشمل قواعد بيانات متعددة تنجح كلها أو تفشل كلها؟

**الـ Two-Phase Commit (بروتوكول التأكيد الثنائي)**
فيه طرف وسيط بنسميه **Coordinator** وأطراف بنسميها **Participants**.

**المرحلة الأولى — Prepare Phase:**
الـ Coordinator بيبعث رسالة "استعد للـ Commit" لكل Participant. كل Participant بيكتب العمليات في الـ WAL بتاعه، ويرد بـ "Ready" أو "Abort" لو فيه مشكلة.

**المرحلة التانية — Commit Phase:**
لو كل الـ Participants ردوا بـ "Ready"، الـ Coordinator بيبعث "Commit" للكل وكلهم بيطبقوا التغييرات. لو أي واحد رد بـ "Abort"، الـ Coordinator بيبعث "Rollback" للكل.

**عيوب الـ 2PC:**
- بطيء: بيحتاج رحلتين كاملتين على الشبكة.
- لو الـ Coordinator نفسه وقع في المرحلة التانية، الـ Participants بيبقوا متعلقين (Blocking Protocol).

**البديل الحديث:** كتير من الـ Microservices بتتجنب الـ 2PC وبتستخدم بدلاً منه نمط الـ **Saga** (سلسلة من Transactions المحلية مع Compensating Transactions للتراجع) لأنه أسرع وأكثر مرونة.

### الفايدة الانترفيوية
What is the Two-Phase Commit protocol, and what are its limitations in distributed systems?
**الإجابة النموذجية:**
الـ 2PC بروتوكول يضمن Atomicity عبر أنظمة موزعة متعددة. في المرحلة الأولى (Prepare) كل المشاركين بيؤكدون استعدادهم للـ Commit، وفي المرحلة التانية (Commit) الـ Coordinator بيأمر بالتطبيق النهائي. عيوبه: الأداء منخفض بسبب رحلتين على الشبكة، وهو Blocking Protocol، يعني لو الـ Coordinator وقع، الـ Participants بيفضلوا متعلقين. البديل الأحدث هو نمط الـ Saga.

## Topic 6: Indexing & Query Optimization (الفهارس وتحسين الاستعلامات)

### Q48 — إيه هو الـ Index وإزاي بيشتغل في الداخل؟ (B-Tree vs Hash Index)
#### أصل الحكاية
لما بتعمل استعلام زي `SELECT * FROM users WHERE email = 'ahmed@mail.com'` من غير Index، الداتابيز بتعمل **Full Table Scan**: بتقرأ كل صف في الجدول صف صف لحد ما تلاقي الـ email المطلوب. في جدول فيه 10 مليون مستخدم، ده كارثي.

الـ **Index** هو هيكل بيانات منفصل عن الجدول الأصلي، بيتبنى على عمود معين، وبيخلي الداتابيز تقدر تلاقي البيانات بسرعة شديدة بدل ما تلف على كل الجدول.

**النوع الأكثر شيوعاً: B-Tree Index**
البنية اللي بيستخدمها MySQL وPostgreSQL افتراضياً. المعلومات بتتخزن في شجرة متوازنة (Balanced Tree) وكل نود بيحتوي على مفاتيح مرتبة وبيشير لـ nodes أصغر وأكبر. الوصول لأي قيمة بياخد `O(log n)` بدل `O(n)`.
- ✅ مثالي لـ: استعلامات المساواة (`=`)، النطاقات (`BETWEEN`, `>`, `<`)، والترتيب (`ORDER BY`).

**Hash Index**
بيحسب Hash للقيمة ويستخدمها للوصول المباشر للـ bucket المناسب. الوصول `O(1)` في الحالات المثالية.
- ✅ مثالي لـ: استعلامات المساواة البحتة (`=`) فقط.
- ❌ مش بيشتغل مع النطاقات (`>`, `<`, `BETWEEN`) أو الترتيب.

```sql
-- Creating a standard B-Tree index (default)
CREATE INDEX idx_users_email ON users(email);

-- Creating a Hash index (PostgreSQL syntax)
CREATE INDEX idx_sessions_token ON sessions USING HASH (token);

-- Checking if a query uses the index
EXPLAIN SELECT * FROM users WHERE email = 'ahmed@mail.com';
-- Look for "Index Scan" or "Index Seek" in the output
-- If you see "Seq Scan" or "Full Table Scan", the index is NOT being used
```

#### مثال 1: قاعدة بيانات LinkedIn مع 900 مليون يوزر
البحث عن يوزر بالاسم أو الإيميل من غير Index معناه قراءة 900 مليون صف في كل بحث. مستحيل. الـ B-Tree Index على عمود `email` خلّى البحث ياخد microseconds بدل دقائق.

#### مثال 2: جدول المعاملات البنكية (Transactions)
في بنك بيسجل مليار معاملة في السنة، لما العميل يطلب كشف حساب شهر معين، الاستعلام بيحتاج فلترة بالتاريخ. الـ B-Tree Index على عمود `transaction_date` بيخلي الداتابيز تنتقل مباشرة لصفحات الشهر المطلوب بدل ما تقرأ المليار صف.

### الفايدة الانترفيوية
What is a database index, and what is the difference between a B-Tree index and a Hash index?
**الإجابة النموذجية:**
الـ Index هيكل بيانات منفصل (غالباً B-Tree) يُبنى على عمود معين ويسمح بالوصول للبيانات في `O(log n)` بدلاً من `O(n)` في Full Table Scan. الـ B-Tree Index مثالي للاستعلامات على النطاقات والمساواة والترتيب. الـ Hash Index أسرع للمساواة البحتة `O(1)` لكنه لا يدعم النطاقات أو الترتيب.

### Q49 — الـ Composite Index: متى يكون أقوى من عدة Indexes منفردة؟ وما هي قاعدة الـ Leftmost Prefix؟
#### أصل الحكاية
الـ **Composite Index** هو Index مبني على أكثر من عمود مع بعض. قوته الحقيقية بتظهر لما بتبحث بأكثر من شرط في نفس الوقت، لأنه أسرع بكتير من استخدام الداتابيز لـ Index منفرد لكل عمود وبعدين تعمل Merge.

**قاعدة الـ Leftmost Prefix (المفتاح: الترتيب مهم جداً!)**
الـ Composite Index بيشتغل فعّال فقط لو الاستعلام بيستخدم الأعمدة بالترتيب من الشمال لليمين. يعني لو عملت `INDEX (last_name, first_name, city)`:
- ✅ استعلام بـ `last_name` بس = يستخدم الـ Index.
- ✅ استعلام بـ `last_name` و`first_name` = يستخدم الـ Index.
- ✅ استعلام بـ `last_name` و`first_name` و`city` = يستخدم الـ Index بالكامل.
- ❌ استعلام بـ `first_name` بس (بدون `last_name`) = لا يستخدم الـ Index!
- ❌ استعلام بـ `city` بس = لا يستخدم الـ Index!

```sql
-- Creating a composite index for e-commerce order search
CREATE INDEX idx_orders_composite ON orders(customer_id, status, order_date);

-- Uses the index fully (leftmost prefix respected):
SELECT * FROM orders 
WHERE customer_id = 101 AND status = 'shipped' AND order_date > '2024-01-01';

-- Uses the index partially (only customer_id):
SELECT * FROM orders WHERE customer_id = 101;

-- Does NOT use this composite index (skips customer_id):
SELECT * FROM orders WHERE status = 'shipped';
-- You'd need a separate index on status for this query
```

#### مثال من E-commerce: صفحة "طلباتي"
لما يوزر بيفتح صفحة طلباته، الاستعلام بيفلتر بالـ `customer_id` وبيرتب بالـ `order_date`. الـ Composite Index على `(customer_id, order_date)` بيخلي العملية دي فائقة السرعة لأن كل بيانات العميل متجمعة ومرتبة في نفس الـ Index.

### الفايدة الانترفيوية
What is a Composite Index, and what is the Leftmost Prefix Rule?
**الإجابة النموذجية:**
الـ Composite Index هو فهرس يُبنى على أكثر من عمود بترتيب معين. قاعدة الـ Leftmost Prefix تقول إن الاستعلام لا يستفيد من الـ Composite Index إلا إذا استخدم الأعمدة بدءاً من العمود الأول (أقصى اليسار) بالترتيب. تخطي العمود الأول أو استخدام عمود أوسط دون ما قبله يجعل الـ Index غير فعّال أو غير مستخدم كلياً.

### Q50 — الـ EXPLAIN / EXPLAIN ANALYZE: كيف تقرأ خطة تنفيذ الاستعلام وتكتشف المشاكل؟
#### أصل الحكاية
لما يكون عندك استعلام بطيء وما عارفش ليه، `EXPLAIN` هي أول أداة بتفتحها. بتقولك بالضبط إزاي محرك الداتابيز قرر ينفذ الاستعلام بتاعك.

**المصطلحات المهمة في الـ Output:**

| المصطلح | المعنى |
|---|---|
| **Seq Scan** | Full Table Scan — كارثة في الجداول الكبيرة |
| **Index Scan** | استخدم Index ثم قرأ الصف الأصلي |
| **Index Only Scan** | استخدم Index فقط بدون قراءة الجدول (أسرع) |
| **Nested Loop** | Join ببطء O(n*m) |
| **Hash Join** | Join أسرع باستخدام Hash Table |
| **rows** | عدد الصفوف المتوقع معالجتها (تقدير) |
| **cost** | تكلفة نسبية (مش بالثواني) |
| **actual time** | الوقت الفعلي (في EXPLAIN ANALYZE فقط) |

```sql
-- Basic EXPLAIN (shows the plan without executing)
EXPLAIN SELECT * FROM orders 
WHERE customer_id = 101 AND status = 'pending';

-- EXPLAIN ANALYZE (executes the query and shows actual timings)
EXPLAIN ANALYZE SELECT * FROM orders 
WHERE customer_id = 101 AND status = 'pending';

-- Sample output to understand:
-- Seq Scan on orders (cost=0.00..45000.00 rows=5 width=120)
--   Filter: ((customer_id = 101) AND (status = 'pending'))
-- Buffers: shared hit=42000  <-- Reading 42000 pages! BAD!
-- Planning Time: 0.5 ms
-- Execution Time: 3200.0 ms  <-- 3.2 seconds. PROBLEM!

-- After adding index:
-- Index Scan using idx_orders_composite on orders (cost=0.43..8.50 rows=5)
-- Planning Time: 0.3 ms
-- Execution Time: 0.8 ms  <-- 0.8ms. PERFECT!
```

### الفايدة الانترفيوية
How do you use EXPLAIN/EXPLAIN ANALYZE to diagnose slow queries?
**الإجابة النموذجية:**
الـ `EXPLAIN` بيعرض خطة تنفيذ الاستعلام بدون تنفيذه فعلياً، و`EXPLAIN ANALYZE` بينفذه ويعرض الأوقات الحقيقية. بنبحث عن: Seq Scan في جداول كبيرة (مؤشر على Index مفقود)، وارتفاع قيمة `rows` (معالجة صفوف زيادة عن اللازم)، وارتفاع `actual time`. الهدف دايماً نشوف Index Scan أو Index Only Scan بدل Seq Scan.

### Q51 — الـ Covering Index: إزاي يلغي الحاجة للرجوع للجدول الأصلي خالص؟
#### أصل الحكاية
حتى بعد استخدام الـ Index، الداتابيز بتعمل خطوة تانية اسمها **Table Lookup** أو **Heap Fetch**: بتاخد الـ Row Pointer من الـ Index وبتروح الجدول الأصلي تجيب باقي بيانات الصف. لو الجدول كبير ومتفرق على الـ Disk، الخطوة دي ممكن تكون بطيئة.

الـ **Covering Index** بيحل المشكلة دي: هو Index بيحتوي على كل الأعمدة اللي بيحتاجها الاستعلام، فالداتابيز بتقدر تجيب كل البيانات من الـ Index نفسه من غير ما ترجع للجدول خالص. وده اللي بيسميه PostgreSQL **Index Only Scan**.

```sql
-- Query that frequently runs: Show order list for a customer
SELECT order_id, order_date, status, total_amount
FROM orders
WHERE customer_id = 101
ORDER BY order_date DESC;

-- Normal index on customer_id alone:
-- Uses Index to find rows, then fetches each row from the table (Table Lookup)

-- Covering Index: includes all columns needed by the query
CREATE INDEX idx_orders_covering 
ON orders(customer_id, order_date DESC)
INCLUDE (order_id, status, total_amount); -- PostgreSQL syntax

-- Now the DB can answer the entire query from the index alone (Index Only Scan)
-- Zero table lookups = maximum speed!
```

#### مثال: صفحة الأوردرات في Shopify
في Shopify، كل تاجر بيفتح صفحة "الطلبات" مئات المرات في اليوم. الاستعلام دايماً بيجيب نفس الأعمدة (id, date, status, total) لنفس المتجر. Covering Index على الأعمدة دي خلّى الصفحة تفتح في أجزاء من الملي ثانية لمليارات الاستعلامات في الشهر.

### الفايدة الانترفيوية
What is a Covering Index, and how does it enable "Index Only Scan"?
**الإجابة النموذجية:**
الـ Covering Index هو Index يحتوي على جميع الأعمدة اللي بيحتاجها الاستعلام (سواء في الـ WHERE أو الـ SELECT أو الـ ORDER BY). عندها تستطيع قاعدة البيانات الإجابة على الاستعلام كلياً من الـ Index دون الحاجة لقراءة الجدول الأصلي (Index Only Scan)، وهو أسرع من Index Scan العادي.

### Q52 — متى لا تنفع الـ Indexes؟ وما هي حالات الـ Index Invalidation؟
#### أصل الحكاية
الـ Indexes مش حل سحري لكل مشكلة أداء. فيه حالات كتيرة الـ Index بيكون موجود بس الداتابيز بتتجاهله وتعمل Full Table Scan عوضاً عنه.

**الحالات اللي الـ Index ما بيشتغلش فيها:**

1. **استخدام Function على العمود المفهرس:**
```sql
-- BAD: Function on indexed column kills the index!
SELECT * FROM users WHERE UPPER(email) = 'AHMED@MAIL.COM';
-- GOOD: Store data consistently and query directly
SELECT * FROM users WHERE email = 'ahmed@mail.com';
```

2. **استخدام LIKE مع Wildcard في البداية:**
```sql
-- BAD: Leading wildcard prevents index usage
SELECT * FROM products WHERE name LIKE '%phone%';
-- GOOD: Trailing wildcard can use the index
SELECT * FROM products WHERE name LIKE 'iphone%';
-- For full-text search, use Full-Text Index or Elasticsearch
```

3. **مقارنة من نوعين مختلفين (Implicit Type Casting):**
```sql
-- BAD: phone column is VARCHAR but we compare with integer
SELECT * FROM users WHERE phone_number = 01012345678;
-- GOOD: Match the data type
SELECT * FROM users WHERE phone_number = '01012345678';
```

4. **الجدول صغير جداً:** لو الجدول عنده 500 صف، محرك الداتابيز ممكن يقرر إن Full Table Scan أسرع من الذهاب للـ Index أولاً.

5. **الـ Index على عمود بـ Low Cardinality:** لو عمود الـ `gender` فيه قيمتين بس (M أو F)، Index عليه ممكن ميفيدش لأن كل قيمة بترجع 50% من الجدول.

### الفايدة الانترفيوية
When does a database ignore an index even if it exists?
**الإجابة النموذجية:**
الداتابيز بتتجاهل الـ Index في عدة حالات: استخدام دوال على العمود المفهرس (مثل `UPPER()` أو `YEAR()`)، استخدام `LIKE` مع Wildcard في البداية، مقارنة من نوعين مختلفين، وجود صفوف قليلة في الجدول (Full Scan أسرع)، أو عمود ذو Cardinality منخفضة جداً. الحل دايماً هو `EXPLAIN` للتحقق من استخدام الـ Index فعلياً.

### Q53 — الـ Query Optimization: خطوات تحسين استعلام بطيء بشكل منهجي
#### أصل الحكاية
لما يجيلك استعلام بطيء في الـ Production، فيه منهج منظم للتعامل معاه:

**الخطوة 1: اعرف الاستعلامات الأبطأ**
```sql
-- MySQL: Enable and check slow query log
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1; -- Log queries taking > 1 second

-- PostgreSQL: Find top 10 slowest queries
SELECT query, mean_exec_time, calls
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;
```

**الخطوة 2: حلل خطة التنفيذ**
```sql
EXPLAIN ANALYZE <your slow query>;
-- Look for: Seq Scan on large tables, high rows estimate, high actual time
```

**الخطوة 3: أضف الـ Index المناسب**
```sql
-- Add index based on WHERE and ORDER BY columns
CREATE INDEX CONCURRENTLY idx_new ON table(col1, col2);
-- CONCURRENTLY: builds index without locking the table (PostgreSQL)
```

**الخطوة 4: أعد كتابة الاستعلام لو لزم**
```sql
-- BAD: Correlated subquery (runs once per row)
SELECT * FROM orders o
WHERE total > (SELECT AVG(total) FROM orders WHERE customer_id = o.customer_id);

-- GOOD: Use a JOIN with a derived table (runs once total)
SELECT o.*
FROM orders o
JOIN (
    SELECT customer_id, AVG(total) AS avg_total
    FROM orders GROUP BY customer_id
) avg_orders ON o.customer_id = avg_orders.customer_id
WHERE o.total > avg_orders.avg_total;
```

**الخطوة 5: راقب بعد التغيير**
- قارن الـ Execution Time قبل وبعد.
- راقب الـ CPU والـ Disk IO على السيرفر.

### الفايدة الانترفيوية
Walk me through your systematic approach to diagnosing and fixing a slow SQL query.
**الإجابة النموذجية:**
المنهج: أولاً تحديد الاستعلامات البطيئة عبر Slow Query Log أو `pg_stat_statements`، ثانياً تحليل خطة التنفيذ بـ `EXPLAIN ANALYZE` والبحث عن Seq Scan وارتفاع الـ rows، ثالثاً إضافة Index مناسب `CONCURRENTLY` لتجنب قفل الجدول في Production، رابعاً إعادة كتابة الاستعلام لتجنب الـ Correlated Subqueries ومشاكل الـ N+1، وأخيراً قياس الأداء بعد التغيير للتحقق من التحسن.

## Topic 7: NoSQL & Scaling (قواعد البيانات غير العلاقاتية والتوسع)

### Q54 — إيه هي قواعد بيانات الـ NoSQL وإيه الفرق الجوهري بينها وبين الـ SQL؟
#### أصل الحكاية
قواعد بيانات الـ SQL (العلاقاتية) ظلت ملكة السوق لعشرات السنين. بس مع التطور الهائل للإنترنت في العشرينيات، بقى فيه أنواع جديدة من البيانات والمتطلبات:
- بيانات ضخمة جداً (Big Data) بتتضاعف بسرعة مجنونة.
- بيانات مش بيانات متنظمة (Unstructured) زي البوستات والتعليقات وبيانات الـ IoT.
- الحاجة للتوسع الأفقي (Horizontal Scaling) على مئات من السيرفرات بدل سيرفر واحد قوي.
- متطلبات قراءة/كتابة بلايين العمليات في الثانية.

هنا ظهرت قواعد بيانات الـ **NoSQL (Not Only SQL)** وهي مش بديلة للـ SQL بس لازم تفهم الفرق:

| المعيار | SQL (Relational) | NoSQL |
|---|---|---|
| **الهيكل** | Schema ثابت ومحدد مسبقاً | Schema مرن أو معدوم |
| **العلاقات** | Joins معقدة بين الجداول | لا Joins — بيانات مدمجة في وثيقة واحدة |
| **التوسع** | Vertical (سيرفر أقوى) | Horizontal (سيرفرات أكتر) |
| **الـ ACID** | ضمان كامل | مش دايماً (BASE model غالباً) |
| **الاستخدام المثالي** | بيانات منظمة وعلاقات معقدة | بيانات غير منظمة وحجم ضخم |

### الفايدة الانترفيوية
What is NoSQL, and what are the main differences between SQL and NoSQL databases?
**الإجابة النموذجية:**
الـ NoSQL هي قواعد بيانات غير علاقاتية ظهرت لمواجهة تحديات البيانات الضخمة والتوسع الأفقي. الفروق الجوهرية: SQL بتعتمد على Schema ثابت وJoins وتضمن ACID كاملاً، مناسبة للبيانات المنظمة والعلاقات المعقدة. NoSQL بتوفر Schema مرن وتوسع أفقي وأداء قراءة/كتابة مرتفع، لكن غالباً بتتنازل عن بعض ضمانات الـ ACID مقابل السرعة والمرونة.

### Q55 — أنواع الـ NoSQL الأربعة: Document، Key-Value، Column-Family، Graph
#### أصل الحكاية
مش كل الـ NoSQL زي بعض. فيه 4 أنواع رئيسية، كل نوع مصمم لحل مشكلة مختلفة:

**1. Document Databases (قواعد الوثائق)**
بتخزن البيانات في وثائق JSON/BSON. كل وثيقة (Document) مكتفية بنفسها ومش محتاجة تعمل Join مع وثيقة تانية.
- **أمثلة**: MongoDB, Firebase Firestore, CouchDB
- **متى تستخدمها؟** Catalogs (كتالوجات المنتجات)، بروفايلات المستخدمين، المحتوى المتغير الـ Schema.
- **مثال من الواقع**: في نظام مثل Airbnb، كل شقة ليها خصائص مختلفة (شقة عندها pool، أخرى عندها parking). في SQL لازم تعمل عشرات الأعمدة الفارغة. في MongoDB كل شقة Document منفصلة بخصائصها الفريدة.

**2. Key-Value Databases (قواعد المفتاح-القيمة)**
القاموس الضخم في قاعدة البيانات. بتحط قيمة أي نوع بمفتاح فريد.
- **أمثلة**: Redis, DynamoDB, Memcached
- **متى تستخدمها؟** Caching، Sessions، Leaderboards، Rate Limiting.
- **مثال من الواقع**: Twitter بيخزن الـ Timeline بتاع كل يوزر كـ Key-Value في Redis. المفتاح هو user_id والقيمة هي قائمة بـ tweet IDs. الجلب فوري.

**3. Column-Family Databases (قواعد عائلة الأعمدة)**
بتخزن البيانات بشكل أعمدة بدل صفوف، وكل صف ممكن يكون له أعمدة مختلفة.
- **أمثلة**: Apache Cassandra, Google Bigtable, Apache HBase
- **متى تستخدمها؟** Time-Series Data، IoT Data، Analytics.
- **مثال من الواقع**: Netflix بيستخدم Cassandra لتخزين مشاهدات المستخدمين (من شاف إيه وإمتى). الكتابة سريعة جداً لأن Cassandra optimized للـ Append-Only writes.

**4. Graph Databases (قواعد الرسوم البيانية)**
بتخزن البيانات كـ Nodes وEdges (علاقات). مثالية لأي حاجة علاقاتها معقدة ومترابطة.
- **أمثلة**: Neo4j, Amazon Neptune
- **متى تستخدمها؟** شبكات التواصل الاجتماعي، توصيات المنتجات، كشف الاحتيال.
- **مثال من الواقع**: LinkedIn بيستخدم Graph DB لخاصية "الناس اللي ممكن تعرفهم". في SQL استعلام "أصدقاء أصدقاء أصدقائي" ده هيعمل JOINs مدمرة. في Graph DB ده مجرد traversal على الـ edges.

### الفايدة الانترفيوية
Name and explain the four main types of NoSQL databases with a real-world use case for each.
**الإجابة النموذجية:**
1. **Document**: MongoDB — لبيانات JSON مرنة زي كتالوجات المنتجات في Airbnb.
2. **Key-Value**: Redis — لـ Caching والـ Sessions زي Timelines في Twitter.
3. **Column-Family**: Cassandra — لـ Time-Series وIoT Data زي مشاهدات Netflix.
4. **Graph**: Neo4j — للعلاقات المعقدة زي توصيات LinkedIn.

### Q56 — نظرية الـ CAP: ليه مستحيل تحقق الثلاثة مع بعض؟ وإزاي بتختار؟
#### أصل الحكاية
نظرية الـ CAP (تُعرف كذلك بنظرية Brewer) بتقول إن أي نظام قاعدة بيانات موزع مستحيل يحقق الخصائص الثلاثة دي في نفس الوقت:

- **C — Consistency (الاتساق)**: كل القراءات لازم ترجع أحدث قيمة مكتوبة. كل السيرفرات شايفة نفس البيانات في نفس اللحظة.
- **A — Availability (التوفر)**: كل طلب لازم ياخد رد (حتى لو مش أحدث داتا). السيستم مش بيقول "مش متاح دلوقتي".
- **P — Partition Tolerance (تحمل التقسيم)**: السيستم بيفضل شغال حتى لو انقطع التواصل بين أجزاء منه (Network Partition).

**ليه مستحيل الثلاثة مع بعض؟**
لو حصل Network Partition (جزء من السيستم مش قادر يتواصل مع الجزء التاني)، هتضطر تختار:
- **CP (Consistency + Partition Tolerance)**: توقف الـ Writes وابدأ ترفض الطلبات لحد ما الشبكة ترجع وتتزامن البيانات (تضحي بالـ Availability). → مثال: HBase, MongoDB, Redis Cluster.
- **AP (Availability + Partition Tolerance)**: فضّل ترد على الطلبات حتى لو البيانات القديمة شوية (تضحي بالـ Consistency). → مثال: CouchDB, DynamoDB, Cassandra.

**في الواقع:** الـ P (Partition Tolerance) مش اختياري في الأنظمة الموزعة — الشبكات بتنقطع والأنظمة بتوقع. عشان كدة الاختيار الحقيقي بيكون بين **CP** و**AP** فقط.

### الفايدة الانترفيوية
Explain the CAP theorem. Why can't a distributed database achieve all three properties simultaneously?
**الإجابة النموذجية:**
نظرية CAP بتقول إن أي نظام موزع يستطيع ضمان اثنتين فقط من ثلاث خصائص: Consistency (كل السيرفرات ترى نفس البيانات)، Availability (كل طلب يحصل على رد)، وPartition Tolerance (النظام يعمل رغم انقطاع الشبكة). لأن الـ Partition Tolerance ضرورة في الأنظمة الموزعة، فالاختيار الفعلي يكون بين CP (تضحي بالتوفر لصالح الاتساق) أو AP (تضحي بالاتساق الفوري لصالح التوفر المستمر).

### Q57 — الـ Sharding (التجزئة الأفقية): إزاي بنوزع البيانات على سيرفرات متعددة؟
#### أصل الحكاية
لما جدول الأوردرات في e-commerce يوصل لـ 10 مليار صف، السيرفر الواحد مش قادر يتعامل معاه حتى لو كان فيه كل الـ RAM والـ SSD في الدنيا. هنا بيجي دور الـ **Sharding**.

الـ **Sharding** هو توزيع البيانات على أكثر من سيرفر (أو مجموعة سيرفرات) وكل سيرفر بيخزن جزء (Shard) من البيانات الكلية.

**استراتيجيات الـ Sharding:**

**1. Range-Based Sharding:**
تقسيم البيانات بناءً على نطاق قيمة معينة.
- Shard 1: user_id من 1 لـ 1,000,000
- Shard 2: user_id من 1,000,001 لـ 2,000,000
- العيب: لو معظم المستخدمين الجدد بتتجمع في نفس الـ Shard (Hot Spot).

**2. Hash-Based Sharding:**
يحسب `hash(user_id) % عدد_السيرفرات` لتحديد الـ Shard.
- توزيع أكثر عدلاً وتجنب الـ Hot Spots.
- العيب: لما بتضيف سيرفر جديد، لازم تعيد توزيع (Rebalance) جزء كبير من البيانات.

**3. Directory-Based Sharding:**
جدول منفصل (Lookup Table) بيقول "user_id X موجود في Shard رقم Y".
- مرونة عالية لكن الـ Lookup Table نفسه ممكن يبقى Single Point of Failure.

```
User Request --> Shard Router
                    |
          [Hash(user_id) % 4]
          /        |               Shard 0  Shard 1  Shard 2  Shard 3
```

**تحديات الـ Sharding:**
- الـ Cross-Shard Joins صعبة ومكلفة.
- الـ Transactions الموزعة معقدة (محتاجة 2PC أو Saga).
- إعادة التوزيع (Resharding) عملية معقدة وصعبة.

### الفايدة الانترفيوية
What is database sharding, and what are the main sharding strategies?
**الإجابة النموذجية:**
الـ Sharding هو توزيع بيانات قاعدة البيانات أفقياً على أكثر من سيرفر (كل جزء يُسمى Shard) لتجاوز حدود السيرفر الواحد. الاستراتيجيات الرئيسية: Range-Based (تقسيم بالنطاق، سهل لكن يعاني من Hot Spots)، Hash-Based (توزيع متساوٍ باستخدام hash function، أكثر عدلاً)، وDirectory-Based (جدول مرجعي، مرن لكن يضيف Single Point of Failure). التحديات الرئيسية: Cross-Shard Queries، وصعوبة Resharding عند التوسع.

### Q58 — الـ Replication: Master-Slave vs Master-Master، ومتى تستخدم كل نوع؟
#### أصل الحكاية
الـ **Replication** هي نسخ بيانات قاعدة البيانات من سيرفر لسيرفر آخر (أو أكتر) في الوقت الفعلي أو شبه الفعلي. بتحقق هدفين: **High Availability** (لو سيرفر وقع، في سيرفر تاني جاهز) و**Read Scalability** (نوزع عمليات القراءة على أكثر من سيرفر).

**1. Master-Slave Replication (Primary-Replica)**
- سيرفر Master (Primary) واحد بيستقبل كل عمليات الـ Write.
- سيرفر أو أكتر Slave (Replica) بيستقبلوا نسخ البيانات من الـ Master ويردوا على عمليات الـ Read فقط.
- **الاستخدام**: تطبيقات Read-Heavy (القراءة أكتر من الكتابة) زي منصات الأخبار أو البحث.
- **العيب**: لو الـ Master وقع، السيستم مش هيقدر يكتب لحد ما نرفع Slave ليبقى Master جديد (Failover Process).

**2. Master-Master Replication (Multi-Primary)**
- أكتر من سيرفر بيقدر يستقبل Writes في نفس الوقت.
- كل Master بيبعت تغييراته للـ Masters التانية.
- **الاستخدام**: تطبيقات في أكثر من منطقة جغرافية (Multi-Region) وتحتاج Write availability في كل منطقة.
- **العيب**: الـ Write Conflicts (تعارض الكتابة). لو نفس الصف اتعدّل على Master A وMaster B في نفس اللحظة، السيستم لازم يحل التعارض ده بطريقة ما (Last Write Wins أو Custom Conflict Resolution).

```
Master-Slave:
Client Write --> [Master] --> Replicates to --> [Slave 1] [Slave 2]
Client Read  -->                                [Slave 1] or [Slave 2]

Master-Master:
Client (Region A) Write --> [Master A] <--> [Master B] <-- Client (Region B) Write
(Conflict Resolution needed if same row updated simultaneously)
```

### الفايدة الانترفيوية
What is database replication, and what is the difference between Master-Slave and Master-Master replication?
**الإجابة النموذجية:**
الـ Replication نسخ البيانات من قاعدة بيانات لأخرى لتحقيق High Availability وتوزيع أحمال القراءة. Master-Slave: سيرفر واحد يستقبل الكتابة والباقي للقراءة فقط — بسيط لكن الـ Failover يدوي. Master-Master: أكثر من سيرفر يقبل الكتابة — متاح للكتابة من أي مكان لكن يحتاج آلية لحل Write Conflicts.

### Q59 — متى تستخدم Redis؟ وإيه الفرق بين In-Memory Database والـ Cache؟
#### أصل الحكاية
**Redis (Remote Dictionary Server)** هو قاعدة بيانات In-Memory بتخزن البيانات في الـ RAM بدل الـ Disk، وده بيخليه أسرع بـ 100x من قواعد البيانات العادية.

**الـ Cache vs. In-Memory Database**
- **Cache (زي Memcached)**: مخصص لتخزين نسخ مؤقتة من بيانات موجودة في مكان تاني (الـ Primary DB). البيانات بتتمسح لو الذاكرة امتلأت (Eviction). هدفه تسريع القراءة فقط.
- **In-Memory Database (زي Redis)**: قاعدة بيانات كاملة بتخزن البيانات في الـ RAM، وممكن تعمل Persistence على الـ Disk (RDB snapshots أو AOF logs). بيدعم هياكل بيانات متقدمة (Lists, Sets, Sorted Sets, Hashes) وبيستخدم للـ Caching والكثير أكتر.

**أشهر استخدامات Redis في الأنظمة الحقيقية:**

1. **Caching**: تخزين نتائج Queries غالية أو HTML Pages مُجهّزة. `GET cache:product:42` بيرجع في < 1ms بدل استعلام DB يأخد 200ms.

2. **Session Management**: تخزين Session بيانات المستخدمين المسجلين. كل الـ Web Servers بيشوفوا نفس الـ Session (Stateless architecture).

3. **Rate Limiting**: منع المستخدم من إرسال أكتر من 100 طلب في الدقيقة.
```python
# Rate Limiting with Redis
pipe = redis.pipeline()
pipe.incr(f"rate:{user_id}")
pipe.expire(f"rate:{user_id}", 60)  # Reset every 60 seconds
count, _ = pipe.execute()
if count > 100:
    raise TooManyRequestsError()
```

4. **Pub/Sub Messaging**: إرسال رسائل بين Services في الـ Microservices.

5. **Sorted Sets للـ Leaderboards**: تخزين ترتيب اللاعبين في لعبة أونلاين.
```python
# Add/Update player score
redis.zadd("game:leaderboard", {"player_ahmed": 15000})
# Get top 10 players instantly
top_10 = redis.zrevrange("game:leaderboard", 0, 9, withscores=True)
```

### الفايدة الانترفيوية
What is Redis, what is the difference between a Cache and an In-Memory Database, and what are the common use cases for Redis?
**الإجابة النموذجية:**
Redis قاعدة بيانات In-Memory تخزن البيانات في الـ RAM مع إمكانية Persistence. الفرق عن الـ Cache البسيط (مثل Memcached): Redis يدعم هياكل بيانات متنوعة (Lists, Sets, Sorted Sets)، والـ Persistence، والـ Pub/Sub، وScript execution. أشهر استخداماته: Caching لنتائج الاستعلامات الثقيلة، Session Storage، Rate Limiting، Leaderboards بـ Sorted Sets، وMessage Queuing بـ Pub/Sub.

### Q60 — الـ Window Functions: ROW_NUMBER، RANK، DENSE_RANK، وLAG/LEAD
#### أصل الحكاية
الـ **Window Functions** هي من أقوى خصائص SQL الحديثة وسؤال ثابت في كل إنترفيو. الفرق الجوهري بينها وبين `GROUP BY`:
- `GROUP BY` بيجمع الصفوف ويخرج صف واحد لكل مجموعة (تفقد تفاصيل الصفوف الأصلية).
- الـ Window Functions بتحسب على مجموعة من الصفوف (Window/Partition) لكن بتحتفظ بكل الصفوف الأصلية.

```sql
-- Sample table: sales per employee per month
CREATE TABLE employee_sales (
    emp_id INT,
    emp_name VARCHAR(50),
    dept VARCHAR(30),
    month DATE,
    sales_amount DECIMAL(10,2)
);
```

**ROW_NUMBER()** — رقم تسلسلي فريد داخل الـ Partition:
```sql
-- Rank employees by sales within each department (no ties)
SELECT emp_name, dept, sales_amount,
    ROW_NUMBER() OVER (PARTITION BY dept ORDER BY sales_amount DESC) AS row_num
FROM employee_sales WHERE month = '2024-01-01';
-- Even if two employees have equal sales, they get different row numbers (1, 2)
```

**RANK()** — ترتيب مع فجوات عند التعادل:
```sql
SELECT emp_name, dept, sales_amount,
    RANK() OVER (PARTITION BY dept ORDER BY sales_amount DESC) AS rank
FROM employee_sales;
-- If two employees tie for 1st place: both get rank 1, next gets rank 3 (gap!)
```

**DENSE_RANK()** — ترتيب بدون فجوات:
```sql
SELECT emp_name, dept, sales_amount,
    DENSE_RANK() OVER (PARTITION BY dept ORDER BY sales_amount DESC) AS dense_rank
FROM employee_sales;
-- If two employees tie for 1st place: both get 1, next gets 2 (no gap)
```

**LAG() و LEAD()** — الوصول لقيمة صف سابق أو لاحق:
```sql
-- Calculate month-over-month sales growth
SELECT emp_name, month, sales_amount,
    LAG(sales_amount, 1) OVER (PARTITION BY emp_id ORDER BY month) AS prev_month_sales,
    sales_amount - LAG(sales_amount, 1) OVER (PARTITION BY emp_id ORDER BY month) AS growth
FROM employee_sales;
-- This is impossible to do cleanly without Window Functions!
```

#### مثال من E-commerce: أعلى 3 منتجات مبيعاً في كل فئة
```sql
SELECT * FROM (
    SELECT
        product_name,
        category,
        total_sold,
        RANK() OVER (PARTITION BY category ORDER BY total_sold DESC) AS rank_in_category
    FROM products
) ranked
WHERE rank_in_category <= 3;
-- Get top 3 products PER CATEGORY in one elegant query!
```

### الفايدة الانترفيوية
What are Window Functions in SQL? Explain the difference between ROW_NUMBER, RANK, and DENSE_RANK.
**الإجابة النموذجية:**
الـ Window Functions بتحسب على مجموعة صفوف (Partition) مع الاحتفاظ بالصفوف الأصلية، عكس GROUP BY اللي بتدمجها. الفرق بين الثلاثة: ROW_NUMBER() بيعطي رقم تسلسلي فريد حتى مع التعادل. RANK() بيعطي نفس الرتبة عند التعادل لكن بيترك فجوة في الترقيم. DENSE_RANK() زي RANK لكن بدون فجوات.

### Q61 — الـ CTEs وRecursive CTEs: إزاي بنعمل استعلامات هرمية؟
#### أصل الحكاية
الـ **CTE (Common Table Expression)** هي طريقة لتعريف جدول مؤقت باستخدام `WITH` في بداية الاستعلام. بتخلي الاستعلامات المعقدة أسهل في القراءة والصيانة.

```sql
-- Without CTE: Ugly nested subquery
SELECT emp_name FROM (
    SELECT emp_name, AVG(sales_amount) as avg_sales FROM employee_sales GROUP BY emp_name
) avg_table WHERE avg_sales > 10000;

-- With CTE: Much cleaner and readable
WITH avg_sales_per_emp AS (
    SELECT emp_name, AVG(sales_amount) AS avg_sales
    FROM employee_sales
    GROUP BY emp_name
)
SELECT emp_name FROM avg_sales_per_emp WHERE avg_sales > 10000;
```

**Recursive CTEs — الاستعلامات الهرمية (مثال المنظمة)**
الاستعلام التراكمي بيسمح بعمل استعلام على هياكل شجرية زي: المنظمة الهرمية (موظف → مديره المباشر → مديره → المدير التنفيذي)، أو تصنيفات المنتجات المتداخلة.

```sql
-- Employee hierarchy table: each employee has a manager
CREATE TABLE employees (
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(100),
    manager_id INT  -- NULL for the CEO
);

-- Recursive CTE: Get all employees under a specific manager (all levels)
WITH RECURSIVE org_chart AS (
    -- Base case: start with the top manager
    SELECT emp_id, emp_name, manager_id, 0 AS level
    FROM employees WHERE emp_id = 1  -- CEO (id=1, manager_id=NULL)

    UNION ALL

    -- Recursive case: find all direct reports
    SELECT e.emp_id, e.emp_name, e.manager_id, oc.level + 1
    FROM employees e
    INNER JOIN org_chart oc ON e.manager_id = oc.emp_id
)
SELECT emp_id, emp_name, level FROM org_chart ORDER BY level, emp_id;
-- Returns the entire org tree: CEO (level 0) -> VPs (level 1) -> Managers (level 2) -> ...
```

### الفايدة الانترفيوية
What are CTEs, and how do Recursive CTEs work for hierarchical data?
**الإجابة النموذجية:**
الـ CTE (Common Table Expression) تُعرَّف بـ `WITH` وبتنشئ جدول مؤقت مقروء ومرتب بديلاً عن الـ Subqueries المتداخلة. الـ Recursive CTE بيضيف `UNION ALL` مع مرجع للـ CTE نفسها، وبيشتغل في مرحلتين: Base Case (نقطة البداية) وRecursive Case (يضيف مستوى جديد في كل دورة). يُستخدم لاستعلام البيانات الهرمية زي المنظمات والتصنيفات المتداخلة.

### Q62 — الـ Stored Procedures vs Functions vs Triggers: الفروق والاستخدامات
#### أصل الحكاية
فيه 3 طرق لتنفيذ منطق برمجي داخل قاعدة البيانات:

**Stored Procedure (الإجراء المخزن)**
مجموعة SQL statements بتتنفذ كوحدة واحدة. ممكن تقبل Input Parameters وتعمل Transactions وترجع نتائج.
```sql
-- Stored Procedure: Transfer money between accounts
DELIMITER $$
CREATE PROCEDURE transfer_funds(
    IN sender_id INT,
    IN receiver_id INT,
    IN amount DECIMAL(10,2)
)
BEGIN
    START TRANSACTION;
    UPDATE accounts SET balance = balance - amount WHERE id = sender_id AND balance >= amount;
    IF ROW_COUNT() = 0 THEN
        ROLLBACK;
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Insufficient funds';
    END IF;
    UPDATE accounts SET balance = balance + amount WHERE id = receiver_id;
    COMMIT;
END $$

-- Call it from application:
CALL transfer_funds(1, 2, 500.00);
```

**Function (الدالة)**
زي الـ Stored Procedure لكن لازم ترجع قيمة واحدة بس، ومش ممكن تعمل Transaction Control (COMMIT/ROLLBACK). ممكن تستخدمها في SELECT statements.
```sql
CREATE FUNCTION calculate_age(birth_date DATE) RETURNS INT
DETERMINISTIC
RETURN TIMESTAMPDIFF(YEAR, birth_date, CURDATE());

-- Use in SELECT:
SELECT customer_name, calculate_age(birth_date) AS age FROM customers;
```

**Trigger (المشغّل)**
كود بيتنفذ تلقائياً لما يحصل Event معين (INSERT, UPDATE, DELETE) على جدول معين.
```sql
-- Trigger: Log every price change in products table
CREATE TRIGGER log_price_change
AFTER UPDATE ON products
FOR EACH ROW
BEGIN
    IF OLD.price != NEW.price THEN
        INSERT INTO price_audit_log (product_id, old_price, new_price, changed_at)
        VALUES (OLD.product_id, OLD.price, NEW.price, NOW());
    END IF;
END;
```

**متى تستخدم إيه؟**
- **Stored Procedure**: عمليات معقدة محتاجة Transaction control (تحويل بنكي، معالجة أوردر).
- **Function**: حسابات محتاجة تتضمن في SELECT (حساب السن، تنسيق البيانات).
- **Trigger**: Audit Logging، ضمان سلامة البيانات تلقائياً، تحديث بيانات محسوبة.

### الفايدة الانترفيوية
What is the difference between a Stored Procedure, a Function, and a Trigger in SQL?
**الإجابة النموذجية:**
الـ Stored Procedure: مجموعة SQL statements بتتنفذ كوحدة، تدعم Transaction Control، ولا يلزمها إرجاع قيمة. الـ Function: تُرجع قيمة واحدة وممكن تستخدم في SELECT، لكن لا تدعم COMMIT/ROLLBACK. الـ Trigger: بيتنفذ تلقائياً عند أحداث INSERT/UPDATE/DELETE، مش بيتنفذ يدوياً. الاستخدام الأمثل: Procedures للعمليات المعقدة، Functions للحسابات في الاستعلامات، Triggers للـ Audit Logging والتحديثات التلقائية.

### Q63 — الـ Views والـ Materialized Views: الفروق والاستخدامات في الأنظمة الضخمة
#### أصل الحكاية
**View (المنظور)**
استعلام SQL محفوظ بالاسم في قاعدة البيانات. لما بتعمل `SELECT` منه، الداتابيز بتنفذ الاستعلام الأصلي في اللحظة دي. البيانات مش متخزنة، بس الاستعلام هو اللي متخزن.

```sql
-- Create a view: Customer order summary
CREATE VIEW customer_order_summary AS
SELECT
    c.customer_id,
    c.name,
    COUNT(o.order_id) AS total_orders,
    SUM(o.total_amount) AS lifetime_value
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name;

-- Use it like a table:
SELECT * FROM customer_order_summary WHERE lifetime_value > 5000;
-- Internally executes the full JOIN + GROUP BY every time!
```

**Materialized View (المنظور المادي)**
زي الـ View بس البيانات **محسوبة ومخزنة على الديسك** مسبقاً. القراءة فورية لأن الداتا جاهزة. بس لازم تعمل Refresh لتحديثها.

```sql
-- PostgreSQL: Create a materialized view
CREATE MATERIALIZED VIEW monthly_sales_report AS
SELECT
    DATE_TRUNC('month', order_date) AS month,
    product_category,
    SUM(total_amount) AS monthly_revenue
FROM orders
JOIN order_items USING (order_id)
JOIN products USING (product_id)
GROUP BY 1, 2;

-- Refresh when data changes (can be scheduled):
REFRESH MATERIALIZED VIEW monthly_sales_report;
-- OR refresh without locking reads:
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales_report;
```

**متى تستخدم إيه؟**
- **View**: لتبسيط Queries المعقدة ولتطبيق Row-Level Security (كل يوزر يشوف بيانته بس).
- **Materialized View**: للـ Reports الثقيلة اللي بتتحسب على ملايين الصفوف وبتتحدث بشكل دوري (مثل تقرير المبيعات اليومي أو لوحات التحليل).

### الفايدة الانترفيوية
What is the difference between a View and a Materialized View? When would you use each?
**الإجابة النموذجية:**
الـ View استعلام محفوظ بالاسم بيُنفَّذ في كل مرة يُستعلَم عنها — لا يخزن بيانات. الـ Materialized View بيخزن نتيجة الاستعلام فعلياً على الديسك، فالقراءة فورية لكن البيانات قد تكون غير محدثة لحين الـ Refresh. يُستخدم View لتبسيط Queries وإخفاء التعقيد، بينما Materialized View للتقارير الثقيلة اللي بيتم حسابها على ملايين الصفوف واللي قراءتها متكررة ومكلفة.

### Q64 — الـ Partitioning: كيف تقسم جدول ضخم داخل نفس السيرفر لتحسين الأداء؟
#### أصل الحكاية
الـ **Partitioning** مختلف عن الـ Sharding: في الـ Partitioning بيانات الجدول الواحد بتتقسم على أجزاء فيزيائية متعددة (Partitions) على نفس السيرفر، بدل ما تنتقل لسيرفرات مختلفة.

**النوع الأكثر شيوعاً: Range Partitioning**
```sql
-- PostgreSQL: Partition orders table by year
CREATE TABLE orders (
    order_id BIGINT,
    customer_id INT,
    order_date DATE,
    total_amount DECIMAL(10,2)
) PARTITION BY RANGE (EXTRACT(YEAR FROM order_date));

-- Create individual partitions
CREATE TABLE orders_2022 PARTITION OF orders
    FOR VALUES FROM (2022) TO (2023);
CREATE TABLE orders_2023 PARTITION OF orders
    FOR VALUES FROM (2023) TO (2024);
CREATE TABLE orders_2024 PARTITION OF orders
    FOR VALUES FROM (2024) TO (2025);

-- Query transparently uses partition pruning:
SELECT * FROM orders WHERE order_date BETWEEN '2023-01-01' AND '2023-12-31';
-- Only scans orders_2023 partition, ignores 2022 and 2024!
```

**فوائد الـ Partitioning:**
- **Partition Pruning**: الداتابيز بتتخطى الـ Partitions اللي مش علاقتها بالاستعلام (أسرع بكتير).
- **Data Archiving**: تقدر تمسح بيانات قديمة بسرعة عن طريق `DROP PARTITION` بدل `DELETE` صف صف.
- **Parallel Queries**: ممكن تشغل الاستعلام على الـ Partitions بالتوازي.

### الفايدة الانترفيوية
What is table partitioning, and how does it differ from sharding?
**الإجابة النموذجية:**
الـ Partitioning تقسيم جدول كبير لأجزاء فيزيائية متعددة (Partitions) على نفس السيرفر بناءً على قيمة عمود معين (مثل السنة أو المنطقة). عكس الـ Sharding اللي بيوزع البيانات على سيرفرات مختلفة. الفائدة الرئيسية هي Partition Pruning اللي بيخلي الاستعلام يمسح Partition واحد بدل الجدول كله، وكذلك سهولة حذف البيانات القديمة بـ DROP PARTITION بدل DELETE البطيء.
