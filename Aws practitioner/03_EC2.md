## 🧠 EC2 — العقل الأساسي في الـ AWS Cloud

الـ **EC2 (Elastic Compute Cloud)** هو الخدمة اللي بتديك القدرة إنك **تأجر** Computing Power من AWS بدل ما تشتريها. هو الـ **IaaS — Infrastructure as a Service** الرئيسي في AWS.

لما بتقول EC2، بتتكلم عن أربع قدرات أساسية مجمعين مع بعض:
- **Renting Virtual Machines (EC2 Instances)** — الـ Servers نفسها
- **Storing Data on Virtual Drives (EBS)** — الـ Hard Disks الافتراضية
- **Distributing Load Across Machines (ELB)** — موزّع الحِمل
- **Scaling the Services (ASG)** — التكبير والتصغير التلقائي

الـ Exam بيقول إن "Knowing EC2 is fundamental to understand how the Cloud works" — وده مش كلام فاضي. كل الـ Services التانية في AWS إما بتشتغل فوق EC2 أو بتتفاعل معاه.

### EC2 — Overview & Core Concepts

#### 1. The Naive Approach (The Problem):

قبل AWS، لو عندك شركة Startup وعايز تطلع Product — كنت محتاج تشتري Server فيزيائي بـ $5,000-$20,000 مقدماً. الـ Lead Time (الوقت من الطلب للتشغيل) كان 2-8 أسابيع. والـ Capacity Planning كان بيتعمل عشان تتحمّل الـ Peak Load — يعني الـ Server بيشتغل بـ 10% من طاقته معظم الوقت ويتعب في الـ Peak فقط. ده كان معناه رأس مال ميت وتكاليف تشغيل ثابتة حتى لو مفيش حد بيستخدم الـ Application.

#### 2. The Deep Dive:

> [!DEEP-DIVE] Technical Mechanics — What is EC2 Really?
>
> الـ EC2 Instance هو **Virtual Machine (VM)** بيشتغل على Physical Server فيزيائي جوه Data Center بتاع AWS. التقنية اللي بتشغّله اسمها **Hypervisor** — وده برنامج بيقسم الـ Physical Server لـ VMs متعددة، وكل VM بتشتغل عندها كأنها Server مستقل من غير ما تحس بالـ VMs التانية اللي على نفس الـ Physical Host.
>
> **مكونات الـ EC2 Instance:**
> - **AMI (Amazon Machine Image):** الـ Operating System Template. زي صورة جاهزة فيها الـ OS مع الـ Configurations الأساسية. ممكن تستخدم Amazon Linux 2، Ubuntu، Windows، macOS، أو تعمل Custom AMI بنفسك.
> - **Instance Type:** بيحدد حجم الـ CPU وكمية الـ RAM والـ Network Speed. زي `t2.micro` أو `m5.2xlarge`.
> - **Storage:** إما EBS (Network-Attached Virtual Disk) أو EC2 Instance Store (Physical SSD على نفس الـ Host).
> - **Security Group:** الـ Virtual Firewall اللي بيتحكم في الـ Traffic.
> - **Key Pair:** مفتاح التشفير اللي بتستخدمه للـ SSH Access.
> - **User Data Script:** Script بيتشغّل **مرة واحدة بس** عند الـ First Launch لأتمتة الـ Setup.
> - **Network Settings:** الـ VPC والـ Subnet اللي الـ Instance هيقعد فيهم، والـ Public IP.
>
> **الـ EC2 Instance Lifecycle:**
> - **Pending** → AWS بتجهز الـ Instance
> - **Running** → بيشتغل وبتدفع عليه
> - **Stopped** → متوقف، مش بتدفع على الـ Compute، بس بتدفع على الـ EBS Storage
> - **Terminated** → اتحذف نهائياً، مش ممكن يرجع
>
> **Elasticity — ليه اسمه "Elastic"؟**
> الاسم جاي من قدرتك إنك تزود وتنقص الـ Resources حسب الحاجة — زي الـ Elastic اللي بتمدّه وبيرجع. تقدر تبدأ بـ 1 Instance وتوصل لـ Thousands في دقائق، وترجع لـ 1 لما الـ Load ينزل.

#### 3. The Mentor's Story (The "Ashta" Analogy):

تخيل إنك عايز تفتح مطعم. الطريقة القديمة إنك تشتري مبنى كامل بمليون جنيه، تجيب مطبخ، تفرش، تعمل كل حاجة — حتى لو مش بتبيع غير Koshary يوم الجمعة. ده زي إنك تشتري Physical Server.

الـ EC2 زي إنك بتحجز في **Cloud Kitchen** — مطبخ مشترك تدفع فيه بالساعة اللي بتشتغل فيها بس. عايز تطبخ يوم الجمعة بس؟ بتدفع ساعات يوم الجمعة بس. جالك Order كبير؟ بتحجز كمان مطبخ تاني على طول. اتخطأت وطلبت حجم كبير أوي؟ بتلغي من غير خسارة.

الـ `t2.micro` زي إنك استأجرت مطبخ صغير بموقد واحد — كافي لـ Startup صغيرة أو Testing. الـ `r5.16xlarge` زي إنك استأجرت مطبخ Hyatt — 64 موقد وأدوات احترافية للـ Production Database الكبيرة.

#### 4. The Exam Hacker:

> [!WARNING] Exam Traps — EC2 Overview
>
> - **EC2 = IaaS.** لما الـ Exam يسألك "which service model does EC2 belong to?" الإجابة دايماً **Infrastructure as a Service**. مش PaaS ومش SaaS.
> - **EC2 مش Global.** الـ Instances بيتعملوا في **Region محدد** وجوه **Availability Zone محدد**. لو اتسألت "is EC2 a global service?" الإجابة **No** — بخلاف IAM اللي Global.
> - **الـ Stopped Instance بتدفع على الـ EBS** حتى لو الـ Compute وقف. الـ EBS Storage موجود وبياخد مساحة حتى لو الـ Instance Stop.
> - **الـ Terminated Instance مش ممكن يرجع** — terminated يعني حُذف نهائياً.
> - **الـ User Data Script بيشتغل مرة واحدة بس** — عند أول Start. مش بيتشغّل عند كل Restart.
> - **الـ User Data Script بيشتغل بـ root user** — يعني له صلاحيات كاملة على الـ Instance.

#### 5. The "Zatouna" Table:

| Concept | الحقيقة التقنية |
|---|---|
| **Full Name** | Elastic Compute Cloud |
| **Service Model** | IaaS — Infrastructure as a Service |
| **Scope** | Regional (مش Global) |
| **Main Components** | AMI + Instance Type + Storage + SG + Key Pair + User Data |
| **Billing when Stopped** | بتدفع على EBS فقط، مش على Compute |
| **Billing when Running (Linux)** | Per Second (بعد أول دقيقة) |
| **Billing when Running (Windows)** | Per Hour |
| **User Data** | يشتغل مرة واحدة بس عند First Launch، بـ root permissions |

#### 6. The Checkpoint:

> [!question]- 🧪 Test Your Knowledge — Q1
> **A developer launches an EC2 instance running Linux, then stops it for the weekend, then starts it again Monday morning. Which statement is CORRECT regarding billing?**
>
> - A. The developer is billed for Compute only during the time the instance is in "Running" state
> - B. The developer is billed for both Compute and EBS Storage during the weekend stop
> - C. The developer is not billed for anything while the instance is Stopped
> - D. The developer is billed for a full hour even if the instance ran for only 30 seconds

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: A — with an important caveat.**
>
> When an EC2 instance is Stopped, you are **NOT** billed for compute (CPU/RAM). However, you **ARE** billed for any EBS volumes attached to the instance — because the EBS volume still exists and occupies storage capacity. So the full statement is: no compute billing when stopped, but EBS storage billing continues.
>
> **Why B is wrong:** It says "both Compute and EBS" — the Compute billing stops, only EBS continues.
> **Why C is wrong:** EBS storage is still billed even when stopped.
> **Why D is wrong:** Linux instances are billed per-second (after the first minute), not per-hour. Windows is per-hour.

### EC2 Sizing & Configuration Options

#### 1. The Naive Approach (The Problem):

لما كنت بتشتري Physical Server، كنت بتحدد المواصفات مرة واحدة وبتفضل معاها للأبد. لو اتحسبت غلط وجبت Server بـ 4 CPU وطلعت محتاج 32 — مش في إيدك حاجة تعملها غير تشتري Server جديد. الـ EC2 بيديك مرونة تختار كل مكوّن على حدة وتغيره وقت ما تشاء.

#### 2. The Deep Dive:

> [!DEEP-DIVE] Technical Mechanics — Configuration Dimensions
>
> الـ EC2 Instance بيتحدد من خلال 7 أبعاد أساسية:
>
> **1. Operating System (OS):**
> تختار بين Linux (الأرخص والأكثر شيوعاً في Production)، Windows، أو macOS. كل OS ليه تأثير على الـ Billing — Linux بيتحاسب per-second، Windows per-hour.
>
> **2. CPU (Compute Power & Cores):**
> الـ vCPU — Virtual CPU. مش Physical Core كامل بالضرورة — ممكن يكون Thread على Physical Core. الـ `t2.micro` عنده 1 vCPU، الـ `c5.18xlarge` عنده 72 vCPU.
>
> **3. RAM (Random-Access Memory):**
> من 0.5 GiB (الـ `t2.nano`) لحد 24,576 GiB = 24 TB (الـ `u-24tb1.metal`). الـ Memory-Intensive workloads زي الـ In-Memory Databases محتاجة Instance Types بـ RAM عالي.
>
> **4. Storage:**
> - **EBS (Elastic Block Store):** Network-Attached Virtual Hard Disk. بيفضل موجود حتى لو الـ Instance Stop أو Terminate (لو اتعمل Detach). بيتحاسب بشكل منفصل.
> - **EFS (Elastic File System):** Shared File System بين Instances متعددة.
> - **EC2 Instance Store:** Physical SSD على نفس الـ Physical Host اللي الـ Instance شغّال عليه. أسرع بكتير من EBS، لكن **Ephemeral (مؤقت)** — بيتمسح لو الـ Instance Stop أو Terminate.
>
> **5. Network Card:**
> بتحدد سرعة الشبكة (بالـ Gbps) وإذا كان في Public IP. الـ `t2.micro` عنده "Low to Moderate" Network Performance. الـ `c5n.18xlarge` عنده 100 Gbps.
>
> **6. Security Group:**
> الـ Virtual Stateful Firewall المرتبط بالـ Instance. بيتحكم في الـ Inbound وOutbound Traffic. مش جزء من الـ Instance نفسه — بيقعد "outside" عليه.
>
> **7. EC2 User Data:**
> Bootstrap Script — Script بيتشغّل **مرة واحدة** عند أول Launch بـ Root Privileges. بتستخدمه لتثبيت الـ Packages، تحميل الـ Code، إعداد الـ Configurations. لو مش شغّال الـ Instance من جديد، الـ Script مش هيتشغّل تاني.

#### 3. The Mentor's Story (The "Ashta" Analogy):

تخيل إنك بتطلب عربية من **معرض**. أي عربية عندها مواصفات: حجم المحرك (CPU)، حجم الصالون (RAM)، حجم الشنطة (Storage)، سرعة القصوى (Network). الـ EC2 Configuration زي Order Form العربية — بتختار كل بند على حدة.

الـ User Data زي إنك قلت للموزع: "يا عم، أنا عايز العربية تيجي وفيها مفيش بنزين، ودي الـ Script اللي تعمله أول ما توصل البيت: روح المحطة، امل بنزين، اشتري زيت، جيب مناديل." الـ Script بيتنفّذ **أول مرة بس**. بعد كده العربية جاهزة ومش بيتعاد الـ Setup تاني.

#### 4. The Exam Hacker:

> [!WARNING] Exam Traps — Configuration Options
>
> - **EC2 Instance Store = Ephemeral = Data Loss on Stop/Terminate.** لو الـ Exam ذكر "high performance local storage" و"data must persist" — **مش EC2 Instance Store**، المفروض تختار EBS.
> - **User Data runs with root user** — مش بـ Limited User. ده معناه إن كل الـ Commands جوه الـ User Data بيتنفذوا بكامل الصلاحيات.
> - **User Data runs ONLY on first boot** — مش على كل Restart. لو عايزه يشتغل على كل Start، محتاج Configuration تانية خارج نطاق الـ Exam.
> - **الـ Public IP بيتغير** لما الـ Instance بتعمله Stop/Start — لو عايز IP ثابت محتاج **Elastic IP** (هيجي في موضوع منفصل).

#### 5. The "Zatouna" Table:

| Configuration Dimension | Options | ملاحظة مهمة |
|---|---|---|
| **OS** | Linux / Windows / macOS | Linux = per second billing |
| **CPU** | 1 → 192 vCPU | حسب Instance Type |
| **RAM** | 0.5 GiB → 24 TB | حسب Instance Type |
| **Network Storage** | EBS أو EFS | يفضل بعد Stop/Terminate |
| **Local Storage** | EC2 Instance Store | Ephemeral — بيتمسح! |
| **Network** | Low → 100 Gbps | حسب Instance Type |
| **Security Group** | Stateful Firewall | Outside الـ Instance |
| **User Data** | Bootstrap Script | مرة واحدة، root user |

#### 6. The Checkpoint:

> [!question]- 🧪 Test Your Knowledge — Q2
> **A company needs an EC2 instance where data written to local storage must be accessible even after the instance is stopped and restarted. Which storage type should be used?**
>
> - A. EC2 Instance Store because it offers the highest I/O performance
> - B. EBS (Elastic Block Store) because it persists independently of the instance lifecycle
> - C. S3 because it is highly durable object storage
> - D. EFS because it supports multiple concurrent connections

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: B**
>
> EBS volumes are **network-attached** and exist independently of the EC2 instance lifecycle. When you stop and start an instance, the EBS volume remains intact with all its data. The root EBS volume is re-attached when the instance restarts.
>
> **Why A is wrong:** EC2 Instance Store IS the highest I/O performer, but it is **ephemeral** — all data is lost on Stop, Terminate, or hardware failure. The question explicitly requires data to persist after stop/restart.
> **Why C is wrong:** S3 is object storage, not a block device you can attach to an EC2 instance as a local disk. You'd need to use the S3 API explicitly.
> **Why D is wrong:** EFS is valid for persistence, but it's a shared file system designed for multiple instances accessing the same data concurrently — it's not the primary answer for single-instance block storage persistence.

### EC2 Instance Types — Overview & Naming Convention

#### 1. The Naive Approach (The Problem):

لما كنت بتشتري Physical Server، كنت عندك خيارات محدودة جداً من Vendors زي Dell وHP وLenovo. الـ Configurations كانت مقيّدة بما هو متاح في الـ Catalog. الـ AWS بيديك أكتر من **750 Instance Type** مختلفة — كل واحد متخصص في نوع معين من الـ Workloads.

#### 2. The Deep Dive:

> [!DEEP-DIVE] Technical Mechanics — Naming Convention & Families
>
> **نظام التسمية:**
> كل Instance Type بيتسمى على نظام `[Family][Generation].[Size]`. مثال: **`m5.2xlarge`**
> - **`m`** = Instance Family/Class (General Purpose)
> - **`5`** = Generation (الجيل الخامس — AWS بتحسّن كل جيل)
> - **`2xlarge`** = Size جوه الـ Family
>
> **The 4 Main Families:**
>
> **① General Purpose (T, M, A families):**
> بتوفر Balance متوازن بين Compute وMemory وNetworking. مناسبة لـ Web Servers، Code Repositories، والـ Environments اللي الـ Load مش متنبأ بيه.
> - `t2.micro` (1 vCPU / 1 GiB RAM) — Free Tier، مناسبة للـ Testing
> - `t3.medium` (2 vCPU / 4 GiB RAM) — Burstable Performance
> - `m5.xlarge` (4 vCPU / 16 GiB RAM) — Balanced Production Workloads
>
> **② Compute Optimized (C family):**
> High Ratio of CPU-to-Memory. للـ Workloads اللي محتاجة Processing Power عالي من غير Huge RAM.
> Use Cases: Batch Processing، Media Transcoding، High Performance Web Servers، HPC (High-Performance Computing)، Scientific Modeling، Machine Learning Inference، Dedicated Gaming Servers.
> - `c5.xlarge` (4 vCPU / 8 GiB RAM)
> - `c6g.16xlarge` (64 vCPU / 128 GiB RAM)
>
> **③ Memory Optimized (R, X, z families):**
> High Ratio of Memory-to-CPU. للـ Workloads اللي بتعالج Large Data Sets في الـ RAM.
> Use Cases: High Performance Relational/Non-Relational Databases، Distributed Web Scale Cache Stores (Redis, Memcached)، In-Memory Databases للـ Business Intelligence، Real-Time Processing of Big Unstructured Data.
> - `r5.xlarge` (4 vCPU / 32 GiB RAM)
> - `r5.16xlarge` (64 vCPU / 512 GiB RAM)
> - `x1e.32xlarge` (128 vCPU / 3,904 GiB RAM)
>
> **④ Storage Optimized (I, D, H families):**
> High Sequential Read/Write Access إلى Large Data Sets على الـ Local Storage. بتوفر عشرات الآلاف من الـ Low-Latency IOPS.
> Use Cases: High-Frequency OLTP Systems، Relational & NoSQL Databases، Cache للـ In-Memory Databases (Redis)، Data Warehousing، Distributed File Systems.
> - `i3.large` (2 vCPU / 15.25 GiB RAM / NVMe SSD)
> - `d2.8xlarge` (36 vCPU / 244 GiB RAM / HDD Storage)
>
> **Instance Size Scale (داخل نفس الـ Family):**
> `nano` → `micro` → `small` → `medium` → `large` → `xlarge` → `2xlarge` → `4xlarge` → `8xlarge` → `16xlarge` → `32xlarge`
> كل مرة بتزود الـ Size، بتضاعف الـ CPU والـ RAM تقريباً.

#### 3. The Mentor's Story (The "Ashta" Analogy):

تخيل إنك بتشتري **عامل للمصنع**. في أنواع متخصصين:

**General Purpose (M, T)** = عامل **Multi-Tasker** — بيعرف يشتغل في أي قسم، وكويس في كل حاجة من غير ما يكون أحسن حاجة في حاجة معينة. مناسب لـ 70% من الـ Jobs.

**Compute Optimized (C)** = **محاسب Turbo** — دماغه سريعة جداً، بس مش لازم تديه مكتب كبير (RAM). تديه ورق كتير يحسبه (Batch Jobs) وينهيه بسرعة. عنده موهبة في الحسابات المعقدة.

**Memory Optimized (R)** = **محقق بيحتفظ بكل التفاصيل في دماغه** — عنده RAM خيالية. بيشيل جميع بيانات الـ Database في دماغه وبيرد على أي سؤال على طول من غير ما يرجع للـ Disk.

**Storage Optimized (I, D)** = **موظف أرشيف** — متخصص في الكتابة والقراءة من الـ Storage بسرعة مجنونة. مش بيهمه الـ CPU أو الـ RAM بقدر ما بيهمه إنه يوصل للـ File اللي محتاجه في Milliseconds.

#### 4. The Exam Hacker:

> [!WARNING] Exam Traps — Instance Types
>
> - **C = Compute Optimized** (مش "Cloud" ومش "Cache"). لما السؤال يقول "batch processing" أو "media transcoding" أو "gaming servers" → الإجابة Instance Family بتبدأ بـ **C**.
> - **R = Memory Optimized** (فكّر في "RAM"). لما السؤال يقول "in-memory database" أو "real-time big data processing" → Instance Family بتبدأ بـ **R**.
> - **I, D = Storage Optimized**. لما السؤال يقول "OLTP" أو "high IOPS" أو "NoSQL databases" → I أو D families.
> - **T2/T3 = Burstable** — الـ T instances عندها CPU Credit System. بتجمع Credits لما الـ CPU Low وبتستخدمها لما محتاج Burst. مناسبة للـ Workloads اللي Variable وغير Regular.
> - **الـ Free Tier = t2.micro** (أو t3.micro في بعض الـ Regions). الـ Exam بيسأل عنه كـ Free Tier eligible instance.
> - **Generation رقم عالي = أفضل وأرخص عادةً.** الجيل الخامس (m5) أفضل وغالباً أرخص من الرابع (m4).

#### 5. The "Zatouna" Table:

| Instance Family | الكود | الـ Use Case الأساسي | الـ Keyword في الـ Exam |
|---|---|---|---|
| **General Purpose** | T, M, A | Web Servers, Repos, Mixed | "balanced", "diverse workloads" |
| **Compute Optimized** | C | Batch Jobs, Gaming, HPC, ML | "compute-intensive", "high CPU" |
| **Memory Optimized** | R, X, z | In-Memory DB, Big Data RT | "in-memory", "large dataset in RAM" |
| **Storage Optimized** | I, D, H | OLTP, NoSQL, Data Warehouse | "high IOPS", "sequential read/write" |
| **Free Tier** | t2.micro | Testing, Learning | 1 vCPU / 1 GiB / EBS-Only |

#### 6. The Checkpoint:

> [!question]- 🧪 Test Your Knowledge — Q3
> **A company runs a Redis in-memory caching layer that holds the entire working dataset in RAM to serve sub-millisecond query responses. Which EC2 instance family is MOST appropriate?**
>
> - A. C5 — Compute Optimized
> - B. I3 — Storage Optimized
> - C. R5 — Memory Optimized
> - D. T3 — General Purpose Burstable

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: C — R5 (Memory Optimized)**
>
> Redis is an in-memory data structure store. The defining characteristic of this workload is that the **entire dataset must reside in RAM** for sub-millisecond access. Memory Optimized instances (R family) provide the highest RAM-to-vCPU ratio in EC2, making them the correct choice for any workload that says "in-memory", "cache", or "large dataset in RAM".
>
> **Why A is wrong:** C5 prioritizes CPU. Redis doesn't need extreme CPU — it needs RAM. A compute-optimized instance would waste money by having lots of CPU with comparatively little RAM.
> **Why B is wrong:** I3 is optimized for high IOPS on local NVMe storage — Redis keeps everything in memory, not on disk (by design). Storage Optimized is the wrong dimension entirely.
> **Why D is wrong:** T3 is burstable General Purpose — suitable for variable workloads, but not designed for memory-intensive workloads holding large datasets. It would run out of RAM quickly for a serious Redis cache layer.

### Security Groups — الـ Firewall الافتراضي لـ EC2

#### 1. The Naive Approach (The Problem):

في الـ On-Premise world، لو عندك Server وعايز تحميه من الـ Internet — كنت بتشتري Hardware Firewall فيزيائي (Cisco، Palo Alto، Checkpoint)، بتحطه قبل الـ Server، وبتبرمج فيه الـ Rules. ده كان غالي، معقد، ومحتاج Network Engineer متخصص. والـ Rules كانت بتترتبط بالـ IP Addresses الفيزيائية المثبتة. الـ EC2 بيجي مع Virtual Firewall مدمج اسمه **Security Group** — مجاني، لحظي، وبيتبع الـ Instance مش الـ IP.

#### 2. The Deep Dive:

> [!DEEP-DIVE] Technical Mechanics — How Security Groups Work
>
> الـ **Security Group** هو **Virtual Stateful Firewall** بيتعلق بالـ EC2 Instance (أو أي AWS Resource تاني). اللفظ "Stateful" ده مهم جداً — معناه إنه بيتذكر الـ Connection State.
>
> **الـ Stateful طبيعته:**
> لو سمحت بـ Inbound Traffic على Port 80 من IP معين، الـ Security Group بيسمح تلقائياً بالـ Outbound Traffic اللي هو Response لنفس الـ Connection — من غير ما تعمل Outbound Rule صريحة. ده عكس الـ Network ACLs (Stateless) اللي محتاج تعمل Rules في الاتجاهين.
>
> **بنية الـ Security Group Rule:**
> كل Rule بتتكوّن من:
> - **Type:** نوع الـ Protocol (SSH, HTTP, HTTPS, Custom TCP, etc.)
> - **Protocol:** TCP, UDP, ICMP
> - **Port Range:** Port محدد أو Range (e.g., 8080-8090)
> - **Source (Inbound) / Destination (Outbound):** يمكن أن يكون:
>   - IP Address بصيغة CIDR: `122.149.196.85/32` (IP واحد بالظبط) أو `0.0.0.0/0` (كل الـ Internet)
>   - Security Group ID: تسمح بـ Traffic من أي Instance عليه Security Group معين
>
> **الـ Default Behavior:**
> - **All Inbound Traffic: BLOCKED by default** — مش هيدخل أي حاجة لحد ما تضيف Allow Rule
> - **All Outbound Traffic: ALLOWED by default** — الـ Instance يقدر يكلّم أي IP على أي Port من غير Rules
>
> **Security Group Live "OUTSIDE" the EC2 Instance:**
> ده Concept مهم جداً. الـ Security Group مش برنامج شغّال جوه الـ OS — هو Firewall بيقعد على الـ AWS Network Layer قبل ما الـ Traffic يوصل للـ Instance نفسه. لو حد بعت Packet وإتبلوك من الـ Security Group، الـ EC2 مش حتى بتشوف الـ Packet ده.
>
> **Referencing Security Groups (Advanced Feature):**
> بدل ما تحدد IP Addresses، تقدر تحدد **Security Group كـ Source**. الـ Rule بتقول: "اسمح بـ Traffic على Port 123 من أي Instance عليه Security Group رقم sg-xxxx." ده نظام قوي جداً في الـ Microservices — بدل ما تحفظ الـ IPs اللي بتتغير، بتثق في أي Instance عليه نفس الـ Security Group.
>
> **Security Group — Many-to-Many Relationship:**
> - Security Group واحد ممكن يتحط على **Instances متعددة** (مش مرتبط بـ Instance واحد)
> - Instance واحد ممكن يكون عليه **Security Groups متعددة** (بياخد Union من كل الـ Allow Rules)
>
> **Locked to Region/VPC Combination:**
> الـ Security Group مش Global ومش Regional بالكامل — هو مرتبط بـ **VPC** معين في **Region** معين. لو عندك VPCs متعددة، Security Group من VPC A مش ممكن يُستخدم على Instance في VPC B.

#### 3. The Mentor's Story (The "Ashta" Analogy):

تخيل إن الـ EC2 Instance ده شقة في عمارة. الـ Security Group ده **الباب الأوتوماتيكي** قبل المدخل الرئيسي — مش الباب الشقة نفسها.

الـ Inbound Rules زي قائمة الـ VIP اللي عند الـ Bawwab: "الدكتور X على Port 22 (SSH) من IP معين — اعمل له Salute وخليه يدخل. كل تاني على Port 22 — مش مسموح." لو التاجر جاي بـ Delivery (HTTP على Port 80) من أي IP في الـ Internet — مسموح. لو حد جه بدون Rule — الباب مقفول تلقائياً.

الـ Outbound Rules: الشقة تقدر تطلع وتشتري من أي محل بدون قيد — طالما هي اللي بادية بالطلب. لو الـ Delivery جه من الخارج أول، لازم يكون في Inbound Rule. لو هي طلبت Delivery، الـ Response يعدي من غير Outbound Rule لأن الـ Security Group بيتذكر إن هي هي اللي طلبت (Stateful).

#### 4. The Exam Hacker:

> [!WARNING] Exam Traps — Security Groups
>
> - **Timeout error = Security Group issue.** لو الـ Application مش Accessible وبتاخد Timeout (الـ Request بيقعد يستنى وبعدين يفشل) — ده بيعني إن الـ Traffic اتبلوك قبل ما يوصل للـ Instance. السبب الأول دايماً: Security Group Rule ناقصة. **مش Application Error.**
> - **Connection Refused error = Application issue.** لو وصل الـ Traffic للـ Instance وجاتلك "Connection Refused" — معناه الـ Traffic وصل للـ Instance (الـ SG سمح)، لكن الـ Application نفسه مش شغّال أو مش بيسمع على الـ Port ده.
> - **Security Groups contain ALLOW rules ONLY** — مفيش Deny Rules في الـ Security Groups. لو عايز Deny، محتاج **Network ACL** اللي هو أداة تانية على مستوى الـ Subnet.
> - **Security Group is STATEFUL** — الـ Network ACL هو الـ Stateless. الفرق ده بييجي في الـ Exam كتير.
> - **All Inbound = Blocked by default. All Outbound = Allowed by default.** ده من أكتر الـ Facts اللي بتيجي في الـ Exam.
> - **Security Group مرتبط بـ Region/VPC** — مش بـ Region لوحدها. مهم لما بتتكلم عن Multi-VPC Architectures.
> - **نصيحة Stephane:** ابقى دايماً عندك Security Group منفصل للـ SSH Access — مش تحطه في نفس SG الـ Application. عشان تقدر تـ Revoke الـ SSH Access بسهولة من غير ما تأثر على الـ Application Traffic.

#### 5. The "Zatouna" Table:

| Characteristic | القيمة |
|---|---|
| **Type** | Stateful Virtual Firewall |
| **Location** | Outside the EC2 Instance (على الـ Network Layer) |
| **Default Inbound** | Block ALL |
| **Default Outbound** | Allow ALL |
| **Rule Type** | Allow ONLY (No Deny rules) |
| **Scope** | Region + VPC Combination |
| **Timeout Error** | Security Group Issue |
| **Connection Refused Error** | Application Issue |
| **One SG to many Instances** | ✅ ممكن |
| **One Instance with many SGs** | ✅ ممكن |
| **Reference another SG** | ✅ ممكن (بدل IP) |

#### 6. The Checkpoint:

> [!question]- 🧪 Test Your Knowledge — Q4
> **A developer cannot connect to their EC2 Linux instance on port 22. The connection attempt hangs until it times out. What is the MOST likely cause?**
>
> - A. The SSH daemon (sshd) is not running on the EC2 instance
> - B. The Security Group attached to the instance does not have an inbound rule allowing port 22 from the developer's IP
> - C. The EC2 instance's operating system firewall (iptables) is blocking the connection
> - D. The instance's EBS volume is full, preventing new SSH sessions

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: B**
>
> A **timeout** (the connection hangs and eventually fails) is the diagnostic signature of a Security Group blocking the traffic. The packet never reaches the instance — it is dropped at the AWS network layer by the Security Group. This is different from "Connection Refused," which would mean the packet reached the instance but the application (sshd) rejected it.
>
> **Why A is wrong:** If sshd were not running, the connection would immediately return "Connection Refused" — not a timeout. A "Connection Refused" means the traffic reached the instance but nothing was listening.
> **Why C is wrong:** If iptables were blocking it, the behavior would still depend on how iptables is configured — but the primary Security Group question is the first thing to check, and it lives outside the instance. The exam almost always expects Security Group as the answer for timeout issues.
> **Why D is wrong:** A full EBS volume affects write operations but does not cause SSH connection timeouts at the network level.

### Classic Ports to Know

#### 1. The Naive Approach (The Problem):

الـ Network Ports زي أرقام الشقق في عمارة. لما الـ IP Address يديك عنوان العمارة، الـ Port بيحدد أنهي شقة (أنهي Service) هتكلمها. بدون معرفة الـ Ports الأساسية، مش هتعرف تعمل Security Group Rules صح ومش هتعرف تفسر الـ Network Troubleshooting.

#### 2. The Deep Dive:

> [!DEEP-DIVE] Technical Mechanics — Critical Ports
>
> الـ TCP/IP Protocol بيستخدم Port Numbers من 0 لحد 65535 عشان يميّز بين الـ Services المختلفة على نفس الـ IP Address. الـ Well-Known Ports بيتراوحوا من 0 لـ 1023 وبيكونوا standardized.
>
> **الـ Ports المهمة للـ Exam:**
>
> | Port | Protocol | الاستخدام |
> |---|---|---|
> | **22** | SSH (Secure Shell) | Remote terminal access لـ Linux Instances |
> | **21** | FTP (File Transfer Protocol) | Upload files (مش مشفّر — قديم) |
> | **22** | SFTP (Secure FTP) | Upload files بشكل مشفّر عبر SSH |
> | **80** | HTTP | Web Traffic غير مشفّر |
> | **443** | HTTPS | Web Traffic مشفّر (TLS/SSL) |
> | **3389** | RDP (Remote Desktop Protocol) | Remote Desktop لـ Windows Instances |
>
> **ملاحظة Trap مهمة:** Port 22 بيستخدمه كل من SSH وSFTP. ده لأن SFTP هو FTP Protocol شغّال فوق SSH tunnel.
>
> **RDP vs SSH:**
> - Linux Instances → SSH (Port 22)
> - Windows Instances → RDP (Port 3389)
> ده Rule ثابت. مش ممكن تعمل RDP لـ Linux ولا SSH لـ Windows بنفس الطريقة.

#### 3. The Mentor's Story (The "Ashta" Analogy):

تخيل إن الـ Server ده عمارة فيها شقق بأرقام. الـ IP Address هو عنوان العمارة. الـ Port هو رقم الشقة.

الـ Bawwab (Security Group) بيقف على باب العمارة ومش بيخلي حد يدخل غير اللي عنده Appointment. "عايز تتكلم مع صاحب الـ Port 80؟ — التاجر اللي بيبيع Web Pages. عايز Port 22؟ — الـ IT Manager اللي بيدي Access للـ Server."

بدون Security Group Rule صح على الـ Port الصح، حتى لو الشخص الصح جاي للعنوان الصح — الـ Bawwab هيرفضه تلقائياً.

#### 4. The Exam Hacker:

> [!WARNING] Exam Traps — Classic Ports
>
> - **Port 22 = SSH لـ Linux وSFTP.** مش RDP.
> - **Port 3389 = RDP لـ Windows فقط.** لما الـ Exam يقول "connect to Windows EC2 instance" → 3389.
> - **Port 80 = HTTP (غير مشفّر). Port 443 = HTTPS (مشفّر).** الفرق مهم في سياق الـ Security.
> - **SFTP بيشتغل على Port 22** — مش Port 21. كتير ناس بيتوهوا هنا.
> - **لو بتعمل Web Server على EC2:** لازم تفتح Port 80 و/أو 443 في الـ Inbound Rules على الـ Security Group من Source `0.0.0.0/0` (كل الـ Internet).

#### 5. The "Zatouna" Table:

| Port | Protocol | OS/Use | تذكيرة |
|---|---|---|---|
| **22** | SSH | Linux — Remote Terminal | "Secure Shell" |
| **22** | SFTP | Any — Secure File Transfer | فوق SSH |
| **21** | FTP | Any — File Transfer | غير مشفّر (قديم) |
| **80** | HTTP | Web (Unencrypted) | — |
| **443** | HTTPS | Web (Encrypted) | — |
| **3389** | RDP | Windows — Remote Desktop | "Remote Desktop" |

### SSH & EC2 Instance Connect

#### 1. The Naive Approach (The Problem):

عندك EC2 Instance شغّال — كيف توصله؟ الـ Server مش عنده شاشة ومش عنده keyboard فيزيائي. محتاج طريقة للـ Remote Access — إنك تفتح Terminal من كمبيوترك وتشتغل على الـ Instance وكأنه قدامك.

#### 2. The Deep Dive:

> [!DEEP-DIVE] Technical Mechanics — SSH and EC2 Instance Connect
>
> **SSH (Secure Shell):**
> الـ SSH Protocol بيستخدم **Public/Private Key Pair Cryptography** للـ Authentication بدل الـ Username/Password التقليدي. لما بتعمل EC2 Instance، بتحدد أو بتعمل **Key Pair** (`.pem` file). الـ Public Key بيتحط على الـ Instance تلقائياً. الـ Private Key (الـ `.pem` file) عندك إنت بس.
>
> لما بتعمل SSH:
> 1. الـ Client بتاعك بيبعت طلب اتصال
> 2. الـ Server بيبعتلك Challenge مشفّر بالـ Public Key
> 3. الـ Client بيحل الـ Challenge باستخدام الـ Private Key
> 4. لو الحل صح — Connected
>
> **Access Methods per OS:**
> - **Mac/Linux:** استخدم الـ `ssh` command المدمجة `ssh -i key.pem ec2-user@PUBLIC_IP`
> - **Windows < 10:** استخدم **PuTTY** (برنامج مجاني بيحوّل الـ `.pem` لـ `.ppk`)
> - **Windows >= 10:** تقدر تستخدم `ssh` command مباشرة زي Mac/Linux، أو PuTTY
>
> **EC2 Instance Connect:**
> طريقة أحدث وأسهل — بتستخدمها من **AWS Console في المتصفح مباشرة** من غير ما تحتاج Key Pair محلي أو Terminal. الـ "Magic" اللي بيحصل وراء الكواليس: AWS بتعمل **Temporary Key Pair** تلقائياً، بترفعه على الـ Instance لثواني، بتعمل الـ Connection، وبتمسحه — كل ده في الخلفية من غير ما تحس.
>
> **قيود EC2 Instance Connect:**
> - بيشتغل out-of-the-box على **Amazon Linux 2** (وبعض الـ Ubuntu versions)
> - لازم الـ **Port 22 يكون مفتوح** في الـ Security Group حتى لو بتستخدم Instance Connect
> - محتاج الـ EC2 Instance Connect IAM Permissions
>
> **المقارنة:**
>
> | Method | OS | Key Needed | How |
> |---|---|---|---|
> | SSH | Mac/Linux | `.pem` file | Command Line |
> | PuTTY | Windows < 10 | `.ppk` file | GUI Tool |
> | SSH Native | Windows >= 10 | `.pem` file | Command Line |
> | EC2 Instance Connect | All | AWS Console | Browser |

#### 3. The Mentor's Story (The "Ashta" Analogy):

الـ SSH زي مفتاح الشقة الرئيسي — إنت اللي بتحتفظ بيه، ومفيش نسخة تانية. لو ضيّعته، تعبان.

الـ EC2 Instance Connect زي إن **الشركة المالكة للعمارة (AWS) عندها Master Key الطوارئ**. بتطلب منها دخول مؤقت، بتفتحلك الباب بمفتاحها الخاص، وبعد ما خرجت بتغير الـ Lock تاني. طريقة الطوارئ دي أسهل لكن محتاجة إنت تكون Authorized من AWS Console.

#### 4. The Exam Hacker:

> [!WARNING] Exam Traps — SSH & EC2 Instance Connect
>
> - **EC2 Instance Connect لازم Port 22 مفتوح** حتى لو بتتصل من المتصفح. الناس بتفتكر إنه Bypass للـ Security Group — لا. الـ Traffic لسه بيمشي على Port 22.
> - **EC2 Instance Connect = Temporary Keys** — AWS بترفع Temp Key على الـ Instance لثواني ثم بتمسحه. مش بتستخدم الـ Key Pair الأصلي.
> - **لـ Linux: SSH (Port 22). لـ Windows: RDP (Port 3389).** EC2 Instance Connect كمان لـ Linux بس out-of-the-box.
> - **`.pem` file لـ Mac/Linux. `.ppk` file لـ Windows/PuTTY.** الـ PuTTYgen بيحوّل بين الاتنين.

### IAM Roles for EC2 Instances

#### 1. The Naive Approach (The Problem):

تخيل إن الـ EC2 Instance بتاعك محتاج يكلّم خدمات AWS تانية — زي إنه يقرأ من S3 Bucket، أو يكتب في DynamoDB، أو يبعت Logs لـ CloudWatch. الطريقة الساذجة هي إنك تعمل IAM User وتحط الـ Access Key وSecret Key جوه الـ Instance في ملف Config أو Environment Variable. المشكلة؟ الـ Access Keys دي **Long-Term Credentials** — لو حد وصل للـ Instance، أو لو غلطة بسيطة كشفت الـ Credentials، المهاجم عنده مفاتح دائمة لحساب AWS بتاعك. AWS نفسها بتقول صراحة: "Never store access keys on EC2 instances."

#### 2. The Deep Dive:

> [!DEEP-DIVE] Technical Mechanics — IAM Roles for EC2
>
> الـ **IAM Role** هو Identity مؤقت بتديه لـ AWS Service (مش لـ Human User). لما بتـ Attach IAM Role على EC2 Instance، الـ Instance بيقدر يتصرف بصلاحيات الـ Role ده بشكل آمن تلقائياً.
>
> **كيف بيشتغل تقنياً:**
> الـ EC2 Instance بيكون عنده متاح Internal Metadata Service على الـ IP المخصص: `169.254.169.254`. الـ AWS SDKs وCLI بيعرفوا تلقائياً إنهم يروحوا لعنوان الـ Metadata ده ويطلبوا **Temporary Credentials** (Access Key + Secret Key + Session Token) اللي بيتجددوا تلقائياً كل ساعة. الـ Credentials دي Short-Term ومرتبطة بالـ Role المحددة.
>
> **الـ Flow:**
> 1. بتعمل IAM Role وبتحط عليه الـ Policies اللي تحتاجها (e.g., S3 ReadOnly)
> 2. بتـ Attach الـ Role على الـ EC2 Instance
> 3. الـ Instance بيطلب Temp Credentials من الـ Metadata Service
> 4. الـ App أو الـ AWS CLI على الـ Instance بيستخدم الـ Temp Credentials تلقائياً
> 5. الـ Credentials بتتجدد تلقائياً قبل انتهائها
>
> **Common EC2 Roles:**
> - **EC2 Instance Roles** — للـ EC2 Instances تعمل API calls على AWS Services
> - **Lambda Execution Roles** — للـ Lambda Functions
> - **Roles for CloudFormation** — للـ CloudFormation Stacks
>
> **ليه Roles أحسن من Access Keys على الـ Instance:**
> - Temporary Credentials (بتنتهي تلقائياً)
> - Automatic Rotation (مش محتاج تجدد يدوي)
> - No Secrets stored on disk (مش في ملف أو Code)
> - Auditable (كل Call بيتسجّل في CloudTrail بـ Role Identity)

#### 3. The Mentor's Story (The "Ashta" Analogy):

تخيل إنك عندك **عامل توصيل (EC2)** محتاج يدخل المخزن (S3) ويجيب بضاعة. الطريقة الغلطة إنك تدي العامل **نسخة من مفتاح المخزن الدائم** — لو العامل اتسرق أو فصل من الشغل ونسيت تاخد منه المفتاح، المخزن مكشوف.

الطريقة الصح (IAM Role) إنك تدي العامل **Badge يومي** — كل يوم الصبح بياخد Badge جديد من مكتب الأمن بيسمحله يدخل المخزن بس. البادج بينتهي في آخر اليوم تلقائياً. لو العامل اتسرق أو فُصل — البادج بتاعه انتهى، ومفيش مفتاح دائم في إيده.

#### 4. The Exam Hacker:

> [!WARNING] Exam Traps — IAM Roles for EC2
>
> - **Never use Access Keys on EC2 Instances.** لو الـ Exam سألك كيف تدي EC2 Instance Permissions للـ AWS Services — الإجابة دايماً **IAM Role**. مش Access Key محفوظ في الـ Instance.
> - **EC2 Instance Groups في IAM مش ممكن.** الـ IAM Groups بتحتوي على Users فقط، مش Services. لو السؤال قال "add EC2 to IAM Group" — غلط تقنياً.
> - **الـ Role بيُحدَث بدون Restart.** لو غيّرت الـ Role Permissions، الـ Instance بياخد الـ Permissions الجديدة على الـ Next Credential Refresh (كل ساعة تقريباً) من غير ما تعيد تشغيله.
> - **Least Privilege ينطبق على الـ Roles كمان.** الـ Role المفروض بيكون عنده أقل Permissions بالضبط اللي الـ Instance محتاجه.

#### 5. The "Zatouna" Table:

| Concept | التفاصيل |
|---|---|
| **الـ Method الصح** | Attach IAM Role على الـ Instance |
| **الـ Method الغلط** | حفظ Access Keys على الـ Instance |
| **نوع الـ Credentials** | Temporary (Short-Term) |
| **مكان الـ Credentials** | Instance Metadata Service: `169.254.169.254` |
| **التجديد** | تلقائي كل ~1 ساعة |
| **Common Use Case** | EC2 يقرأ S3، يكتب DynamoDB، يبعت CloudWatch Logs |

### EC2 Purchasing Options — دليل الشراء الكامل

#### 1. The Naive Approach (The Problem):

في الـ Traditional Data Center، كنت بتشتري Server وخلاص — سعر واحد، ملكية دائمة، مش في خيارات. الـ AWS بيديك 7 طرق مختلفة لـ"شراء" (الإيجار في الحقيقة) الـ Compute Resources، وكل طريقة مناسبة لـ Scenario معين. معرفة الفرق بينهم ده من أكتر الموضوعات اللي بتيجي في الـ Exam.

#### 2. The Deep Dive:

> [!DEEP-DIVE] Technical Mechanics — All 7 Purchasing Options
>
> **① On-Demand Instances — ادفع على اللي بتستخدمه:**
> الـ Default Option. بتـ Launch الـ Instance، بيشتغل، بتدفع. بتـ Terminate الـ Instance، بيوقف الفاتورة.
> - Linux/Windows: بـ Second (بعد أول دقيقة)
> - Other OSes: بـ Hour
> - أعلى سعر بين الكل
> - مفيش Upfront Payment ومفيش Commitment
> - **متى تستخدمه:** Short-Term workloads، Testing، Development، حاجة مش قادر تتنبأ بمدتها أو حجمها.
>
> **② Reserved Instances (1 or 3 Years) — حجز مسبق بخصم كبير:**
> بتلتزم بـ Instance Type + Region + Tenancy + OS لمدة 1 أو 3 سنين.
> - Discount: حتى **72%** مقارنة بـ On-Demand
> - Scope: **Regional** (خصم على أي AZ في الـ Region) أو **Zonal** (حجز Capacity في AZ محدد)
> - Payment: No Upfront (+discount)، Partial Upfront (++ discount)، All Upfront (+++ discount) — كلما دفعت أكتر مقدماً، كلما الخصم أعلى
> - تقدر تشتري وتبيع في الـ **Reserved Instance Marketplace** لو مش محتاجها قبل انتهائها
> - **Convertible Reserved Instance:** بيسمحلك تغيّر الـ Instance Type وFamily والـ OS والـ Scope أثناء المدة، لكن الخصم أقل (حتى 66% بس).
> - **متى تستخدمه:** Steady-state applications زي Databases، Production Servers ثابتة.
>
> **③ EC2 Savings Plans (1 or 3 Years) — التزام بمبلغ مش بـ Instance:**
> بدل ما تلتزم بـ Instance Type بالظبط، بتلتزم بـ **مبلغ بالساعة** (e.g., $10/hr لمدة سنة). أي استخدام جوه الـ Commitment بياخد خصم. ما يزيد عن الـ Commitment بيتحاسب بـ On-Demand Price.
> - نفس الـ Discount الـ Reserved Instances (حتى 72%)
> - أكثر **مرونة** — تقدر تغيّر Instance Size وOS وTenancy جوه نفس الـ Instance Family والـ Region
> - **متى تستخدمه:** لو عارف إن عندك Baseline Usage ثابت لكن مش عارف بالظبط أنهي Instance Types هتحتاجها.
>
> **④ Spot Instances — المزاد الذكي (أرخص وأكتر مخاطرة):**
> AWS عندها Physical Servers فيها Spare Capacity (طاقة زيادة مش اتأجرت). بتبيعها بالمزاد. إنت بتحدد **Max Price** اللي مستعد تدفعه. لو الـ Spot Price الحالي > الـ Max Price بتاعك — الـ Instance **بيتحذف تلقائياً مع إشعار 2 دقيقة بس**.
> - Discount: حتى **90%** مقارنة بـ On-Demand
> - الأرخص على الإطلاق في AWS
> - **لا تستخدمها في:** Databases، Critical Applications، حاجة مش تقدر تتحمل Interruption
> - **تستخدمها في:** Batch Jobs، Data Analysis، Image Processing، أي Distributed Workload فيه Fault Tolerance
>
> **⑤ Dedicated Hosts — استئجار الـ Physical Server كله:**
> بتستأجر **Physical Server كامل** مخصص ليك لوحدك. إنت بتتحكم في Placement الـ Instances على الـ Server ده.
> - الأغلى خيار في AWS
> - Purchasing: On-Demand (بالثانية) أو Reserved (1-3 سنين)
> - **لماذا تستخدمه؟**
>   - **BYOL (Bring Your Own License):** Software Licenses قديمة مرتبطة بعدد الـ Physical Sockets أو Cores (Oracle، SQL Server، etc.)
>   - **Regulatory Compliance:** بعض الـ Regulations بتشترط الـ Physical Isolation
>
> **⑥ Dedicated Instances — Isolation بدون تحكم كامل:**
> الـ Instances بتشتغل على Hardware مخصص ليك — مش في Hardware مشترك مع Customers تانيين. لكن **بتتفرق عن Dedicated Hosts** في:
> - **مش بتتحكم** في الـ Instance Placement على الـ Physical Host
> - **ممكن تشارك الـ Hardware** مع Instances تانية من **نفس Account بتاعتك**
> - بيتحاسب بـ Per-Instance billing + $2/region fee
> - أرخص من Dedicated Hosts لكن أغلى من On-Demand
>
> **⑦ Capacity Reservations — ضمان الـ Capacity بدون Discount:**
> بتحجز **On-Demand Capacity** في **AZ محددة** لأي مدة. مش محتاج Commitment (تقدر تحجز وتلغي وقتما شئت). لكن:
> - **مفيش Discount** — بتدفع On-Demand Price حتى لو الـ Instance مش شغّال
> - **بتدفع حتى لو ما Launched إنستانس** — بس بتضمن إن الـ Capacity موجودة لما تحتاجها
> - ممكن تعملها مع Reserved Instances أو Savings Plans عشان تاخد Discount
> - **متى تستخدمها:** Disaster Recovery، أحداث مؤقتة محتاج فيها Capacity مضمونة (زي Black Friday Events)

#### 3. The Mentor's Story (The "Ashta" Analogy — The Hotel):

Stephane نفسه استخدم أنالوجي الـ **Hotel**:

**On-Demand:** زي إنك تيجي الـ Hotel وتقول "عايز أوضة" — بتدفع Full Price، بتنام، وبتفضل يوم وأنت مسافر تلاقي الأوضة فاضية من تاني. مفيش Commitment ومفيش Discount.

**Reserved:** زي إنك حجزت الأوضة من 6 شهور قبل الرحلة — اتقالك "فيه خصم 72% لو حجزت سنة كاملة." الأوضة لك حتى لو ما جيتش، لكن إنت بتوفر فلوس كتيرة على المدى الطويل.

**Savings Plans:** زي إنك قلت للـ Hotel "أنا هدفع $10 الليلة كل يوم لسنة كاملة" — يدوك خصم، وتقدر تنام في أي نوع أوضة (Standard, Suite, Sea View) طالما الـ Spend مش زايد عن $10. لو طلبت أوضة بـ $15 — الـ $5 الزيادة بـ Full Price.

**Spot Instances:** زي إن الـ Hotel بيعلن: "عندنا أوض فاضية — اللي بيـ Bid التمن الأعلى ياخدها." إنت بتقول "مستعد أدفع $3." لو ما فيش حد بيدفع أكتر من $3، الأوضة ليك. لو جه حد بيدفع $4 — الـ Hotel بياخدك وبيديها هو.

**Dedicated Hosts:** زي إنك **استأجرت دور كامل في الـ Hotel** — مش أوضة، دور كامل. إنت بتتحكم في كل حاجة. الأغلى بكتير لكن ضروري لو عندك Corporate Policy أو License Agreement.

**Capacity Reservations:** زي إنك حجزت الأوضة بـ Full Price — حتى لو ما جيتيش، بتدفع. مجرد ضمان إن الأوضة موجودة ليك وقتما تحتاجها.

> - **"Cheapest long-term commitment" = Reserved Instances or Savings Plans.**
> - **"Cannot be interrupted" + "Cheapest long-term" = Reserved Instances.** مش Spot لأن Spot قابل للـ Interruption.

>   - السؤال عن "BYOL (Bring Your Own License)" → Dedicated **HOST** دايماً
> - **Capacity Reservations = No Discount.** الناس بتخلط بينها وبين Reserved Instances. الـ Capacity Reservation مجرد ضمان الـ Capacity — مفيش خصم في نفسها.
> - **Convertible Reserved = أقل Discount (66% مش 72%).** مقابل المرونة في تغيير الـ Instance Type.
> - **Reserved Instance Marketplace:** تقدر تبيع الـ Reserved Instances اللي مش محتاجها قبل انتهائها.

#### 6. The Checkpoint:

> [!question]- 🧪 Test Your Knowledge — Q5
> **A startup is running a batch image-processing job every night. The job takes 4 hours, can be restarted from a checkpoint if interrupted, and the company wants to minimize cost above all else. Which purchasing option is MOST appropriate?**
>
> - A. On-Demand Instances — to ensure the job always completes without interruption
> - B. Reserved Instances (1 Year) — for the consistent nightly usage pattern
> - C. Spot Instances — for maximum cost savings on a fault-tolerant workload
> - D. Dedicated Hosts — for guaranteed capacity every night

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: C — Spot Instances**
>
> Three key signals in the question point directly to Spot Instances: (1) **"minimize cost above all else"** — Spot gives up to 90% discount; (2) **"can be restarted from a checkpoint if interrupted"** — this explicitly says the workload is fault-tolerant and can handle Spot interruptions; (3) **"batch job"** — batch processing is the textbook Spot use case.
>
> **Why A is wrong:** On-Demand is more expensive and there's no requirement that the job MUST complete without interruption. The question says it can checkpoint and restart.
> **Why B is wrong:** Reserved Instances give good discounts for steady-state usage, but they require 1-3 year commitment. This is a nightly batch job — the instance isn't running 24/7. You'd be paying for idle capacity most of the day. Also, Reserved doesn't fit as well as Spot when the primary requirement is minimum cost AND fault tolerance exists.
> **Why D is wrong:** Dedicated Hosts are the most expensive option. They're for BYOL licensing and strict compliance requirements — completely unnecessary for a batch processing job.

> [!question]- 🧪 Test Your Knowledge — Q6
> **A company needs to run a mission-critical Oracle Database 24/7 with existing per-socket Oracle licenses. The compliance team requires physical server isolation. The database must NOT be interrupted under any circumstances. Which purchasing option is MOST appropriate?**
>
> - A. Reserved Instances (3 Years, All Upfront) for maximum discount
> - B. Spot Instances for maximum cost savings
> - C. Dedicated Hosts with Reserved pricing
> - D. Dedicated Instances with On-Demand pricing

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: C — Dedicated Hosts with Reserved pricing**
>
> Three signals here: (1) **"existing per-socket Oracle licenses" (BYOL)** — Oracle licenses are per physical socket/core. Only Dedicated Hosts give you visibility into the physical socket and core count, enabling BYOL. (2) **"physical server isolation" compliance requirement** — Dedicated Hosts give you a physical server 100% to yourself. (3) **"24/7, never interrupted"** — Reserved pricing on Dedicated Hosts gives the best long-term cost for persistent workloads.
>
> **Why A is wrong:** Standard Reserved Instances don't give you physical isolation, and they don't support BYOL per-socket licensing. The physical host is still shared with other AWS customers.
> **Why B is wrong:** Spot Instances can be interrupted at any time — catastrophic for a mission-critical database.
> **Why D is wrong:** Dedicated Instances DO give physical isolation (different physical hardware than other customers), but they do NOT provide visibility into socket/core count. You cannot use per-socket BYOL licenses with Dedicated Instances — only with Dedicated Hosts. Also, On-Demand pricing on Dedicated Instances would be more expensive than Reserved Dedicated Host for a 24/7 workload.

### Shared Responsibility Model for EC2

#### 1. The Naive Approach (The Problem):

لما كنت بتشغّل Data Center On-Premise، إنت مسؤول عن كل حاجة — من الكهربا والتبريد لحد الـ OS Updates والـ Application Security. الـ Cloud بيغيّر المعادلة دي — AWS بتاخد جزء من المسؤولية وإنت بتفضل مسؤول عن الجزء التاني.

#### 2. The Deep Dive:

> [!DEEP-DIVE] Technical Mechanics — Shared Responsibility for EC2
>
> الـ Shared Responsibility Model بيتقسم بوضوح:
>
> **AWS مسؤولة عن (Security OF the Cloud):**
> - **Infrastructure:** Global Network Security، Physical Data Center Security
> - **Isolation:** Physical isolation بين الـ EC2 Instances على نفس الـ Physical Host (الـ Hypervisor Isolation)
> - **Hardware:** استبدال الـ Faulty Hardware تلقائياً
> - **Compliance Validation:** الـ Certifications اللي AWS بتحافظ عليها (ISO، SOC، PCI-DSS) على مستوى الـ Infrastructure
>
> **الـ Customer مسؤول عن (Security IN the Cloud):**
> - **Security Groups Rules:** إنت بتقرر مين يتصل بالـ Instance ومن أين وعلى أنهي Port
> - **OS Patches and Updates:** الـ Guest OS جوه الـ EC2 Instance مسؤوليتك. AWS مش بتعمل `yum update` على Instance بتاعك. لو ظهر Vulnerability في الـ Linux Kernel، إنت اللي لازم تـ Patch.
> - **Software and Utilities Installed on the Instance:** كل برنامج بتحطه على الـ Instance — أمانه ومدى توافقه مسؤوليتك
> - **IAM Roles Assigned to EC2 & IAM User Access Management:** إنت بتقرر أنهي Permissions تدي الـ Instance وأنهي Users يوصلوه
> - **Data Security on the Instance:** تشفير الـ Data على الـ EBS، حماية الـ Sensitive Data

#### 3. The Mentor's Story (The "Ashta" Analogy):

الـ Shared Responsibility زي **شقة إيجار**. صاحب العمارة (AWS) مسؤول عن: الأساسات، الحيطان، الكهربا الرئيسية، الأمن في المدخل، وصيانة الـ Infrastructure. إنت (الـ Customer) مسؤول عن: مفاتيح الشقة (Security Groups)، تنظيف الشقة (OS Patches)، التأكد من إن الأجهزة اللي جبتها مأمونة (Installed Software)، ومين عنده key للشقة (IAM Roles).

لو سرقة حصلت بسبب مفتاح نسيته في الباب — مسؤوليتك إنت. لو حصل زلزال خرّب العمارة — مسؤولية صاحب العمارة.

#### 4. The Exam Hacker:

> [!WARNING] Exam Traps — Shared Responsibility EC2
>
> - **OS Patching = CUSTOMER Responsibility على EC2.** ده بيختلف عن الـ Managed Services زي RDS اللي AWS بتعمل فيها الـ OS Patching.
> - **Physical Host Security = AWS Responsibility.** إنت مش مسؤول عن الـ Hypervisor أو الـ Physical Server.
> - **Security Groups Configuration = Customer Responsibility.** AWS بتوفر الـ Tool، إنت بتستخدمه صح أو غلط.
> - **IAM Roles for EC2 = Customer Responsibility.** إنت اللي بتقرر أنهي Permissions تدي الـ Instance.

| المسؤولية | AWS | Customer |
|---|---|---|
| Physical Security | ✅ | ❌ |
