## 🚪 الحكاية بتبدأ بسؤال بسيط — مين يقدر يدخل؟

تخيل إنك بنيت شركة ناجحة على AWS. عندك Servers شغالة، Databases مليانة بيانات، Storage فيه ملفات حساسة. الشركة بدأت تكبر وبدأت تشغّل موظفين — Developers وOps Engineers وAccountants وData Analysts. السؤال اللي بيطرح نفسه فوراً: **هل كل الموظفين دول المفروض يوصلوا لكل حاجة؟**

الـ Developer مش محتاج يشوف فواتير الـ Billing. الـ Accountant مش محتاج يحذف Servers. الـ Junior Developer مش المفروض يمسح الـ Production Database. لو الكل عنده صلاحية كل حاجة — يوم واحد غلطة بسيطة أو اختراق صغير ممكن يمسح كل حاجة بنيتها.

ده بالظبط المشكلة اللي **IAM** جاي يحلها.

---

## 🧠 IAM — الحارس الرسمي لـ AWS Account بتاعتك

الـ **IAM (Identity and Access Management)** هو الخدمة اللي بتتحكم في **مين** يقدر يدخل على الـ AWS Account بتاعتك، و**إيه** اللي مسموحله يعمله بالظبط. مش بس "يدخل أو ما يدخلش" — ده تحكم دقيق جداً على مستوى كل Action على كل Resource.

أهم حاجة تعرفها عن IAM قبل أي حاجة تانية: هو **Global Service** — يعني مش مرتبط بـ Region معين. لما بتعمل IAM User في `us-east-1`، نفس الـ User موجود في `ap-southeast-1` وفي `me-south-1` وفي كل الـ Regions تلقائياً من غير ما تعمل حاجة إضافية. ده بيختلف عن خدمات زي EC2 اللي بتعملها في Region محدد وبتفضل فيه بس.

## 👑 الـ Root Account — اللي المفروض متلمهوش خالص

لما بتفتح AWS Account جديدة لأول مرة، بيتعمل تلقائياً حاجة اسمها **Root Account**. ده الأكونت الإله — ليه صلاحية على **كل حاجة** في الـ AWS Account بدون استثناء ومن غير أي قيد. يقدر يعمل Billing Changes، يحذف كل الـ Resources، يغير إعدادات الأمان الأساسية، يغلق الـ Account كلها، ويعمل حاجات مستحيلة على أي User تاني حتى لو Admin.

المشكلة مش في وجوده — المشكلة في استخدامه بشكل يومي. لو حد اتهكت الـ Root credentials بأي طريقة — هجوم Phishing، باسورد ضعيف، أي حاجة — ده معناه إن المهاجم عنده كنترول كامل ومطلق على كل حاجة في الـ Account. مش بس يسرق بيانات — يقدر يشغّل Servers بالآلاف ويفضل يدفع إنت، أو يحذف كل حاجة بنيتها.

عشان كده القاعدة الذهبية اللي بتيجي في الـ Exam دايماً:

> **الـ Root Account بتستخدمها مرة واحدة بس — عند الـ Setup الأولي. بعدها بتعمل IAM Admin User وبتشتغل منه. ومش بتشاركها مع حد أبداً.**

## 👥 Users وGroups — هيكل المؤسسة

بعد ما عملت الـ Root Account وأمّنتها، جه وقت تنظيم الناس اللي هيشتغلوا على الـ Account.

الـ **IAM Users** هم الأشخاص الحقيقيين في مؤسستك — كل واحد بياخد User خاص بيه بـ Username وPassword. كل User بيمثل شخص واحد بعينه ومسؤوليته مش تتشارك مع حد. لو اتشارك User — مش هتعرف مين عمل إيه لما تيجي تراجع الـ Logs.

الـ **IAM Groups** هي طريقة تنظيم الـ Users في مجموعات منطقية بتعكس هيكل الشركة. بدل ما تدي كل Developer صلاحياته منفردة — بتعمل Group اسمها "Developers" وبتحط فيها كل الـ Developers، وبتدي الـ Group الصلاحيات — وكل User جوه الـ Group بياخدها تلقائياً. لما Developer جديد بييجي — بتضيفه للـ Group وخلاص. لما Developer بيمشي — بتشيله من الـ Group وكل صلاحياته بتتشال تلقائياً.

**قواعد مهمة لازم تحفظها:**
- الـ Groups بتحتوي على **Users فقط** — مش ممكن تحط Group جوه Group أبداً.
- الـ User **مش مجبور** يكون في Group — ممكن يكون User بدون Group.
- الـ User ممكن يكون في **أكتر من Group** في نفس الوقت وبياخد صلاحيات الكل.

## 📋 الـ Policies — قانون الصلاحيات المكتوب

الصلاحيات في AWS مش كلام — هي **JSON Documents** رسمية اسمها **Policies**. كل Policy بتقول بالظبط: "مسموح أو ممنوع — تعمل الـ Action ده — على الـ Resource ده."

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ec2:Describe*",
      "Resource": "*"
    }
  ]
}
```

الـ Policy دي بتقول: "مسموحلك تشوف (Describe) كل الـ EC2 Resources." بس بتشوف — مش تحذف أو تعدّل أو تشغّل.

**تشريح كل عنصر في الـ Policy:**

- **Version** — دايماً `"2012-10-17"` بدون نقاش. ده مش تاريخ اليوم ومش تاريخ إنشاء الـ Policy — ده اسم الـ Policy Language Version اللي AWS بتستخدمه.
- **Statement** — الجزء الأساسي الإلزامي. بيحتوي على قاعدة واحدة أو أكتر.
- **Effect** — إما `"Allow"` أو `"Deny"` بس. لو في تعارض بين الاتنين — الـ **Deny بيكسب دايماً بدون استثناء.**
- **Action** — الفعل المحدد اللي بتتكلم عنه. `"s3:GetObject"` يعني قراءة ملف من S3. `"*"` يعني كل الـ Actions.
- **Resource** — على إيه بتطبق القاعدة. `"*"` يعني كل الـ Resources.
- **Principal** — مين اللي الـ Policy دي بتأثر عليه. بيتستخدم في Resource-Based Policies.
- **Condition** — شروط إضافية اختيارية. مثلاً "بس لو الـ Request جاي من IP معين."
- **Sid** — Statement Identifier اختياري. اسم وصفي للـ Statement للتوثيق.

## 🔗 الـ Inheritance — الصلاحيات بتتوارث

لما بتدي Group صلاحية، كل User جوه الـ Group بيورّثها تلقائياً. Alice في الـ Developers Group اللي عندها صلاحيات EC2 وS3؟ Alice تلقائياً عندها نفس الصلاحيات. Alice كمان في الـ Audit Team Group اللي عندها صلاحيات CloudTrail؟ Alice بتاخد صلاحيات الاتنين مجمعين.

ومش لازم تكون في Group — ممكن تدي User صلاحية مباشرة اسمها **Inline Policy**. بس ده مش الـ Best Practice — لأنه بيخلي الإدارة صعبة. لو عندك 50 Developer وكل واحد عنده Inline Policy — لازم تعدّل الـ 50 Policy واحدة واحدة. لو استخدمت Group — بتعدّل Policy واحدة وبتأثر على الـ 50 في نفس الوقت.

**القاعدة الأهم: الـ Deny بيكسب الـ Allow دايماً.** لو User في مجموعتين — إحداهما بتسمح بـ S3 والتانية بتمنع S3 — النتيجة النهائية: ممنوع. الـ Explicit Deny بيـ Override أي Allow.

## ⚖️ مبدأ الـ Least Privilege — أقل صلاحيات ممكنة

ده المبدأ الأساسي في كل الـ IAM والأمان بشكل عام. المعنى بسيط: **تدي الـ User بس اللي يحتاجه بالظبط — لا أكتر ولا أقل.**

كل صلاحية زيادة هي خطر زيادة. لو حساب موظف اتـ Compromise — يعني حد سرق الباسورد بتاعه — الـ Damage بيكون محدود بصلاحياته هو بس. الشركات الكبيرة اللي اتهكت تاريخياً — السبب الأول في الاختراقات دي كان دايماً Overpermissioned Users أو Roles عندها صلاحيات أكتر من اللازم.

## 🔒 تأمين الـ Account — طبقتان لا غنى عنهما

**الطبقة الأولى — Password Policy:**
بتحدد قواعد إلزامية لكلمات المرور على كل الـ IAM Users. تقدر تشترط: طول أدنى، Uppercase وLowercase وNumbers وSpecial Characters، تغيير الباسورد كل فترة (Expiration)، ومنع إعادة استخدام باسورد قديم (Reuse Prevention).

**الطبقة التانية — MFA (Multi-Factor Authentication):**

> **MFA = شيء بتعرفه (الباسورد) + شيء بتمتلكه (Device أو App)**

حتى لو المهاجم عنده الباسورد — مش هيقدر يدخل بدون الـ Physical Device. الكود بيتغير كل 30 ثانية. الـ Root Account وكل الـ Admin Users **لازم** يبقى عليهم MFA — مش اختياري.

**أنواع الـ MFA Devices على AWS:**
- **Virtual MFA** — Apps زي Google Authenticator أو Authy على الموبايل. بتولّد OTP بيتغير كل 30 ثانية. بتدعم أكتر من Account على نفس الـ App.
- **U2F Security Key** — جهاز فيزيائي زي **YubiKey من Yubico**. بتوصله في USB. مقاوم لهجمات الـ Phishing. بيدعم أكتر من User على نفس الـ Key.
- **Hardware Key Fob** — جهاز فيزيائي من **Gemalto** بيولّد كود. للـ Standard AWS Accounts.
- **Hardware Key Fob لـ GovCloud** — من **SurePassID**، مخصص لـ **AWS GovCloud** للحكومة الأمريكية.

## 🖥️ إزاي بتدخل على AWS — ثلاث طرق بس

**الأولى — AWS Management Console:**
الموقع الرسمي. بتدخل بـ Account ID + Username + Password + MFA. للاستخدام اليدوي البشري.

**التانية — AWS CLI (Command Line Interface):**
Tool بتشتغل من Terminal. بتكتب Commands مباشرة زي `aws s3 ls`. محمية بـ **Access Keys**. مفيدة للـ Automation والـ Scripts. مبنية على الـ AWS SDK for Python من تحت.

**التالتة — AWS SDK:**
مكتبات برمجية جوه الـ Application Code. بتدعم JavaScript، Python، Java، .NET، Go وغيرهم. كمان محمية بـ **Access Keys**.

**الـ Access Keys:**
- **Access Key ID** ≈ Username — مش سري.
- **Secret Access Key** ≈ Password — **سري جداً، مش بتشاركه أبداً.**

لو Access Key اتسرق — بتعمله Deactivate فوراً وبتعمل واحد جديد.

## 🤖 IAM Roles — لما السيرفر نفسه محتاج صلاحية

الـ Services في AWS أحياناً محتاجة تعمل Actions على Services تانية. مثال: EC2 Instance عايز يقرأ من S3. السيرفر مش إنسان — مش عنده Username وPassword.

الحل الغلط: تحط Access Keys جوه الكود. لو حد وصل للكود أو لقى الـ Keys في GitHub — عنده Access Keys حقيقية.

الحل الصح: **IAM Role** — مجموعة صلاحيات بتلصقها على الـ Service مباشرة. AWS بتدير الـ Temporary Credentials داخلياً وبتجددها تلقائياً. مش محتاج تحط أي Keys في أي مكان.

**أشهر الـ Roles:** EC2 Instance Roles — Lambda Function Roles — Roles for CloudFormation.

## 🔍 IAM Security Tools — تدقيق وتحقق

**IAM Credentials Report (Account-Level):**
Report على مستوى الـ Account كلها. بتشوف فيها كل الـ Users وحالة كل Credential — الباسورد متغير إمتى، الـ MFA مفعّل ولا لأ، الـ Access Keys اتُستخدمت إمتى. للـ Security Audit الشامل.

**IAM Access Advisor (User-Level):**
بتبصها على **User بعينه**. بتشوف إيه الـ Services اللي مسموحله يوصلها، وإمتى آخر مرة وصل لكل Service فعلاً. لو User معاه صلاحية S3 بس ما استخدمهاش من 6 شهور — ممكن تشيلها. ده بيساعدك تطبق الـ Least Privilege بشكل عملي.

> **الفرق في جملة:** Credentials Report = Account كلها + حالة الـ Credentials. Access Advisor = User معين + إمتى استخدم الـ Services.

## 🤝 الـ Shared Responsibility في IAM

**AWS مسؤولة عن:** الـ Infrastructure الخاصة بـ IAM — الـ Physical Security، الـ Global Availability، الـ Compliance Validation.

**إنت مسؤول عن:** إنشاء الـ Users والـ Groups والـ Roles والـ Policies صح — تفعيل MFA — تدوير الـ Access Keys — مراجعة الصلاحيات بانتظام — عدم مشاركة أي Credentials.

| ❌ لا تعمل | ✅ اعمل |
|---|---|
| تستخدم Root Account يومياً | اعمل IAM Admin User فوراً |
| تشارك IAM Users | شخص واحد = User واحد |
| تدي صلاحيات زيادة | Least Privilege دايماً |

**Q1. A company has just created a new AWS account. Which account should be used for day-to-day administrative tasks?**

- A. The Root account, as it has full permissions
- B. An IAM user with administrative permissions
- C. An IAM user with read-only permissions
- D. A shared IAM user for the entire team

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: B**
>
> The Root account should **never** be used for daily tasks. This is one of AWS's most fundamental security rules. Immediately after account creation, create an IAM Admin User and work exclusively from it. The Root account should be locked away with MFA and only touched for a very small set of tasks that explicitly require Root (like changing the AWS Support plan or closing the account entirely).
>
> **Why the others fail:**
> - **A** — Using Root daily means one compromised password = full account takeover. No IAM policy can restrict the Root account.
> - **C** — Read-only cannot perform administrative tasks by definition.
> - **D** — Sharing IAM users destroys the audit trail. You can never trace which person performed which action in CloudTrail logs.

**Q2. Which of the following statements about IAM Groups is CORRECT?**

- A. A group can contain other groups
- B. Every IAM user must belong to at least one group
- C. A user can belong to multiple groups simultaneously
- D. Groups can be assigned MFA devices

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: C**
>
> A single IAM user can be a member of multiple groups at the same time and inherits the **combined** permissions from all groups. For example, Alice can be in both "Developers" and "Audit Team" groups simultaneously, getting permissions from both.
>
> **Why the others fail:**
> - **A** — This is the #1 IAM trap. Groups can ONLY contain users — **never other groups**. Nested groups do not exist in IAM.
> - **B** — Users don't have to belong to any group. A user can exist with no group membership (though this is not best practice for permission management).
> - **D** — MFA devices are attached to individual IAM **users**, not groups.

---

**Q3. What is the primary purpose of the Least Privilege Principle in IAM?**

- A. Grant users only the permissions they need to perform their job
- B. Give all users the same level of access to ensure fairness
- C. Restrict the Root account from accessing billing information
- D. Ensure all users have MFA enabled before accessing AWS

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: A**
>
> Least Privilege = minimum permissions necessary, nothing more. If a developer only needs to read from S3, they get S3 read-only — not S3 write, not EC2, not RDS. This limits the **blast radius** of any compromised account. Major cloud breaches (Capital One 2019, Uber 2022) traced back to overpermissioned roles and users.
>
> **Why the others fail:**
> - **B** — Equal access for everyone is the **opposite** of Least Privilege. Different roles require different permissions.
> - **C** — Restricting Root from Billing is about account security, not Least Privilege.
> - **D** — MFA is authentication hardening, unrelated to permission scoping.

**Q4. A developer needs to interact with AWS services programmatically from their local machine using scripts. What is the correct authentication method?**

- A. Username and password via the AWS Management Console
- B. The Root account credentials
- C. An IAM Group configured for programmatic access
- D. AWS CLI configured with an Access Key ID and Secret Access Key

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: D**
>
> Programmatic access (CLI and SDK) is authenticated using **Access Keys** — an Access Key ID (public, like a username) and a Secret Access Key (private, like a password). These are configured locally using `aws configure` and used to sign API requests.
>
> **Why the others fail:**
> - **A** — The Management Console uses username/password + MFA. It's browser-based and cannot be used for scripting or automation.
> - **B** — Never use Root credentials for programmatic access. This is a critical security violation with no justification.
> - **C** — Groups are for organizing users and attaching policies. You cannot authenticate as a Group — Groups have no credentials.

---

**Q5. Which element in an IAM Policy document is ALWAYS required?**

- A. Id
- B. Statement
- C. Sid
- D. Condition

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: B**
>
> The `Statement` element is the core of any IAM policy — it contains the actual permission rules (Effect, Action, Resource). Without it, the policy has no rules and does nothing useful.
>
> **Why the others fail:**
> - **A** — `Id` is an **optional** identifier for the whole policy document.
> - **C** — `Sid` (Statement ID) is an **optional** label for individual statements, used for documentation purposes.
> - **D** — `Condition` is **optional** and used for advanced logic like IP restrictions or requiring MFA to be active.

**Q6. An EC2 instance needs to upload files to an S3 bucket automatically. What is the MOST secure and recommended approach?**

- A. Store Access Keys as environment variables inside the EC2 instance
- B. Hardcode the Access Keys directly in the application source code
- C. Attach an IAM Role with the necessary S3 permissions to the EC2 instance
- D. Create a shared IAM user and distribute its credentials to all EC2 instances

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: C**
>
> IAM Roles are the purpose-built solution for granting AWS services permission to act on your behalf. When you attach a Role to an EC2 instance, AWS automatically provides **temporary, rotating credentials** to the instance through the instance metadata service. No hardcoded keys, no manual rotation, no risk of accidental exposure.
>
> **Why the others fail:**
> - **A** — Environment variables on EC2 can be exposed through application vulnerabilities or the instance metadata API endpoint.
> - **B** — Hardcoding credentials in source code is one of the most common causes of AWS account breaches. Code gets committed to GitHub, and automated scanners (like TruffleHog) find the keys within minutes.
> - **D** — Sharing credentials across multiple instances breaks the audit trail, violates Least Privilege, and means one compromised instance = all instances affected.

**Q7. What is the KEY difference between the IAM Credentials Report and IAM Access Advisor?**

- A. Credentials Report is for users; Access Advisor is for groups
- B. Credentials Report shows account-wide credential status; Access Advisor shows per-user service access history
- C. Credentials Report is real-time; Access Advisor has a 24-hour delay
- D. Credentials Report requires Admin access; Access Advisor is available to all users

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: B**
>
> These two tools serve different purposes at different scopes:
> - **Credentials Report** = Account-level. Shows ALL users and ALL their credential statuses (password age, MFA enabled, access key last rotated). Used for compliance audits across the whole account.
> - **Access Advisor** = User-level. Shows which services a **specific user** has permissions for AND when they last actually used each service. Used to identify and safely remove unused permissions to enforce Least Privilege.
>
> **Why the others fail:**
> - **A** — Both tools relate to users. Access Advisor is per-user analysis, not per-group.
> - **C and D** — These distinctions are fabricated and not how these tools actually work.

**Q8. Which of the following is a valid MFA device option in AWS IAM? (Select TWO)**

- A. Google Authenticator app on a smartphone
- B. Biometric fingerprint recognition
- C. YubiKey hardware security key
- D. SMS one-time password sent to a phone number
- E. Email verification code

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answers: A and C**
>
> - **A (Google Authenticator)** — This is a Virtual MFA device. It generates time-based one-time passwords (TOTP) and is officially supported by AWS IAM.
> - **C (YubiKey)** — This is a U2F (Universal 2nd Factor) Security Key — a physical USB device officially supported by AWS as an MFA option. It's also phishing-resistant.
>
> **Why the others fail:**
> - **B** — AWS IAM does **not** support biometric authentication as an MFA factor.
> - **D** — **This is the biggest trap here.** AWS IAM does **NOT** support SMS-based MFA. Many people assume it does because SMS OTP is common elsewhere. It is not a supported IAM MFA method.
> - **E** — Email OTP is not a supported MFA type in AWS IAM.

**Q9. A user belongs to two IAM Groups. Group A has an Allow policy for S3. Group B has an explicit Deny policy for S3. What happens when the user tries to access S3?**

- A. Allow wins because the user has a positive permission from Group A
- B. Deny wins — the user cannot access S3 at all
- C. AWS asks the user which policy should apply at login
- D. The most recently attached policy takes effect

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: B**
>
> This is one of the most fundamental IAM rules: **an explicit Deny ALWAYS overrides any Allow.** No exceptions. The IAM policy evaluation logic works like this: first check for explicit Deny → if found, access **denied immediately**. Then check for explicit Allow → if found, access allowed. If neither exists, **implicit deny** (default is always deny).
>
> One explicit Deny anywhere in the chain is enough to block access completely, regardless of how many Allow policies exist.
>
> **Why the others fail:**
> - **A** — Allow never wins against an explicit Deny. There are zero exceptions to this rule in AWS IAM.
> - **C** — AWS never prompts users to choose between policies. Evaluation is automatic and deterministic.
> - **D** — Policy evaluation has nothing to do with attachment order or recency.

**Q10. According to the IAM Shared Responsibility Model, which task is the CUSTOMER'S responsibility?**

- A. Maintaining the physical security of the data centers that run the IAM service
- B. Ensuring the IAM service itself remains globally available
- C. Patching the underlying servers and infrastructure that power IAM
- D. Rotating IAM user access keys regularly and enabling MFA on all users

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: D**
>
> Under the Shared Responsibility Model: AWS manages the **infrastructure** that runs IAM (physical security, availability, patching of the service itself). The **customer** is responsible for HOW they configure and use IAM — enabling MFA, rotating access keys, setting password policies, reviewing permissions, and following security best practices.
>
> Simple rule: **AWS runs IAM. You configure IAM.**
>
> **Why the others fail:**
> - **A, B, C** — All of these are AWS's responsibility. The customer never has access to or responsibility for the physical infrastructure running IAM.

**Q11. A solutions architect needs to allow an AWS Lambda function to write logs to CloudWatch. What should be created?**

- A. An IAM User with CloudWatch write permissions and its Access Keys in Lambda's environment variables
- B. An IAM Role with CloudWatch write permissions, attached to the Lambda function
- C. An IAM Group for Lambda functions with CloudWatch permissions
- D. A shared Access Key configured across all Lambda functions in the account

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: B**
>
> When an AWS **service** (Lambda) needs to interact with another AWS **service** (CloudWatch), the correct and only recommended approach is an **IAM Role**. You create a Role with the necessary permissions, attach it to Lambda, and Lambda automatically assumes the role when executing. AWS handles temporary credential rotation internally — no hardcoded keys anywhere.
>
> **Why the others fail:**
> - **A** — Storing Access Keys in Lambda environment variables is an anti-pattern and a security risk. Roles exist precisely to eliminate this pattern.
> - **C** — IAM Groups are for **human users only**. You cannot add an AWS service like Lambda to a Group.
> - **D** — Sharing a single Access Key across all Lambda functions violates Least Privilege and creates a single point of credential compromise.

**Q12. What is the correct value for the Version field in an IAM Policy document?**

- A. The current year (e.g., "2026")
- B. The date the policy was created (e.g., "2026-03-16")
- C. "2012-10-17"
- D. "1.0" or "2.0" depending on the policy type

> [!success]- ✅ Reveal Answer & Explanation
> **Correct Answer: C**
>
> The `Version` field in IAM Policy documents is **always** `"2012-10-17"` — this is the version identifier of the **IAM Policy Language itself**, not a date you choose or update. It never changes regardless of when you create the policy or what year it is. Using an older value like `"2008-10-17"` limits you to older policy features; using anything else will cause an error.
>
> **Why the others fail:**
> - **A and B** — The Version field has absolutely nothing to do with today's date or the policy creation date. This is the #1 exam trap on this specific topic — many candidates instinctively think it should be today's date.
> - **D** — There is no "1.0" or "2.0" versioning system in IAM policies.
